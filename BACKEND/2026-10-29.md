# PART 1. APIRouter와 미들웨어
### | 왜 라우트를 파일로 분리해야 하나 |

- `main.py` 하나에 할 일(Task) 관련 엔드포인트와 회원(User) 관련 엔드포인트를 전부 몰아넣으면, 기능이 늘어날수록 파일 하나가 수백 줄로 비대해지고 서로 다른 담당 영역의 코드가 뒤섞여 어디를 고쳐야 할지 찾기 어려워진다. `APIRouter`는 "할 일 담당 라우터", "회원 담당 라우터"처럼 도메인별로 엔드포인트 묶음을 별도 파일로 쪼갠 뒤, `main.py`에서는 그것들을 조립만 하도록 만들어준다.

```python
# src/routers/tasks.py
import logging
from fastapi import APIRouter, Depends

logger = logging.getLogger("kanban.tasks")
router = APIRouter(prefix="/tasks", tags=["Tasks"])

def get_db_session():
    print("데이터베이스 임시 세션이 활성화되었습니다")
    try:
        yield "fake-session"
    finally:
        print("데이터베이스 세션을 종료합니다")

@router.get("")
def read_tasks(db=Depends(get_db_session)):
    logger.info("할 일 목록을 조회합니다.")
    return list(task_db.values())
```

```python
# src/routers/users.py
import logging
from fastapi import APIRouter, HTTPException, Header, Depends

logger = logging.getLogger("kanban.users")

def verify_kanban_token(x_kanban_token: str = Header(default=None)):
    if x_kanban_token != "study-hard":
        raise HTTPException(status_code=403, detail="칸반 보드 회원 관리 영역 접근 권한이 부족합니다.")

router = APIRouter(prefix="/users", tags=["Users"], dependencies=[Depends(verify_kanban_token)])
user_database: list = []

@router.post("")
def register_user(username: str, email: str):
    logger.info("회원 가입 요청: %s", username)
    user_database.append({"username": username, "email": email})
    return {"username": username, "email": email}
```

```python
# src/main.py
from fastapi import FastAPI
from routers import tasks, users

app = FastAPI()
app.include_router(tasks.router)
app.include_router(users.router)
```

- `prefix="/tasks"`를 라우터에 걸어두면 그 라우터 안의 모든 경로 앞에 자동으로 `/tasks`가 붙으므로, 각 함수마다 `/tasks/...`를 반복해서 쓸 필요가 없다. `tags=["Tasks"]`는 Swagger 자동 문서(`/docs`)에서 같은 도메인끼리 그룹으로 묶어 보여주는 역할이다.

### | 라우터 분리가 없다면 |

- 모든 엔드포인트가 `main.py`에 한 줄로 늘어서 있으면, "회원가입 로직만 수정하고 싶은데 파일을 열면 할 일 관련 코드 수백 줄을 거쳐야 원하는 함수를 찾을 수 있다. 팀 작업이라면 여러 사람이 같은 파일을 동시에 수정하면서 git 충돌이 잦아지고, 테스트할 때도 "할 일 기능만" 따로 떼어 실행하기 어렵다.

### | 미들웨어란 무엇이고 왜 필요한가 |

- 미들웨어는 공항 보안 검색대와 같다. 승객(요청) 한 명 한 명이 각자 다른 게이트(엔드포인트)로 가지만, 보안 검색만큼은 모든 승객이 예외 없이 공통으로 거쳐야 한다. `@app.middleware("http")`로 등록한 함수는 모든 요청이 실제 라우트 함수에 도달하기 전/후를 가로채서, 로깅이나 처리 시간 측정 같은 공통 작업을 엔드포인트 함수마다 중복해서 쓰지 않고 한 곳에서 처리하게 해준다.

```python
# src/main.py
import time
import logging

logging.basicConfig(level=logging.INFO)

@app.middleware("http")
async def log_and_time_requests(request, call_next):
    logging.info(f"{request.method} {request.url.path}")
    start_time = time.time()
    response = await call_next(request)
    process_time = time.time() - start_time
    response.headers["X-Process-Time"] = f"{process_time:.6f}"
    return response
```

**실행 결과**
```
$ curl -i -X GET "http://127.0.0.1:8000/tasks"
HTTP/1.1 200 OK
content-type: application/json
x-process-time: 0.000842

[{"id":1,"title":"FastAPI 공부하기","status":"TODO"}, ...]
```
서버 터미널:
```
INFO:root:GET /tasks
데이터베이스 임시 세션이 활성화되었습니다
INFO:kanban.tasks:할 일 목록을 조회합니다.
데이터베이스 세션을 종료합니다
```

### | 미들웨어가 없다면 |

- 요청마다 걸린 시간을 재고 싶다면, `read_tasks`, `register_user` 등 모든 엔드포인트 함수 안에 `start = time.time()` ~ `print(시간차)` 코드를 일일이 복사해 붙여야 한다. 새 엔드포인트를 추가할 때마다 이 코드를 또 빠뜨리지 않고 넣어야 하는 부담이 생기고, 나중에 "시간 측정 방식을 바꾸자"고 하면 모든 함수를 찾아다니며 고쳐야 한다. 미들웨어는 "모든 요청에 공통으로 적용할 로직"을 한 군데에 선언해 일관성을 보장하는 장치다.

### | 미들웨어 등록 순서와 TrustedHostMiddleware |

- Starlette(FastAPI의 기반 프레임워크)는 미들웨어를 **등록된 순서의 역순**으로 감싼다. 즉 나중에 등록한 미들웨어일수록 더 바깥쪽 껍질을 차지해서, 요청이 들어올 때 가장 먼저 그 미들웨어를 통과한다.

```python
from fastapi.middleware.trustedhost import TrustedHostMiddleware

# log_and_time_requests가 먼저 등록되어 있으므로(위 코드), 아래 TrustedHostMiddleware는
# 나중에 등록되어 더 바깥쪽(= 요청을 가장 먼저 받는 자리)에 위치하게 된다.
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["127.0.0.1", "localhost"])
```

| 등록 순서 | 요청 처리 순서(바깥→안쪽) | 역할 |
| --- | --- | --- |
| ① `log_and_time_requests` (먼저 등록) | 2번째로 통과 | 안쪽에 위치, 허용된 호스트의 요청만 로깅/시간측정 |
| ② `TrustedHostMiddleware` (나중 등록) | 1번째로 통과 | 가장 바깥쪽, 허용되지 않은 호스트를 가장 먼저 차단 |

**실행 결과**
```
$ curl -i -X GET "http://127.0.0.1:8000/tasks" -H "Host: evil.com"
HTTP/1.1 400 Bad Request
content-type: text/plain; charset=utf-8

Invalid host header
```
(서버 터미널에는 `GET /tasks` 로그가 전혀 찍히지 않는다 — TrustedHostMiddleware가 더 바깥쪽에서 허용되지 않은 호스트를 먼저 차단했기 때문에, 안쪽의 로깅 미들웨어까지 요청이 도달하지 못한 것이다.)

- 등록 순서를 반대로 했다면(TrustedHostMiddleware를 먼저 등록) 어떻게 될까. 그 경우 TrustedHostMiddleware가 더 안쪽에 위치하게 되어, 허용되지 않은 호스트의 요청이라도 일단 로깅 미들웨어를 통과하며 로그와 시간 측정이 먼저 수행된 뒤에야 차단된다. 악성 요청을 걸러내는 보안 검문을 가능한 한 가장 바깥에 둬야, 불필요한 처리 비용을 아끼고 공격 흔적도 더 깔끔하게 구분할 수 있다.

### | 라우터 전용 Depends로 접근 제어 가드 걸기 |

- `get_db_session`처럼 `Depends()`는 함수 하나하나에 주입할 수도 있지만, `APIRouter(dependencies=[Depends(verify_kanban_token)])`로 라우터 생성 시점에 걸어두면 그 라우터에 속한 **모든** 엔드포인트가 자동으로 권한 검증을 거치게 된다. 위 `users.py` 코드가 이 방식이다.

**실행 결과**
```
$ curl -i -X GET "http://127.0.0.1:8000/users"
HTTP/1.1 403 Forbidden
content-type: application/json

{"detail":"칸반 보드 회원 관리 영역 접근 권한이 부족합니다."}

$ curl -i -X POST "http://127.0.0.1:8000/users" \
  -H "X-Kanban-Token: study-hard" \
  -H "Content-Type: application/json" \
  -d '{"username":"minji","email":"minji@example.com"}'
HTTP/1.1 200 OK
content-type: application/json

{"username":"minji","email":"minji@example.com"}
```

### | 라우터 전역 의존성이 없다면 |

- `dependencies=[Depends(verify_kanban_token)]`를 라우터에 걸지 않고, 각 엔드포인트 함수 매개변수마다 `dep=Depends(verify_kanban_token)`를 일일이 추가하는 방식이었다면, 나중에 `users.py`에 새 엔드포인트(예: 회원 탈퇴 API)를 추가할 때 이 의존성 추가를 깜빡 빠뜨리기 쉽다. 그러면 그 엔드포인트만 토큰 검증 없이 외부에 뚫려 있는 보안 구멍이 생긴다. 라우터 단위로 걸어두면 "이 라우터 아래 생기는 모든 경로는 예외 없이 이 검증을 통과해야 한다"는 규칙이 구조적으로 강제된다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 라우터 | APIRouter | 엔드포인트들을 도메인별로 묶어 별도 파일로 분리할 수 있게 해주는 FastAPI 객체 |
| 미들웨어 | Middleware | 모든 요청/응답에 공통으로 끼어들어 로깅·보안 등을 처리하는 함수 |
| 의존성 주입 | Dependency Injection | `Depends()`로 함수 실행 전 필요한 자원이나 검증 로직을 자동으로 주입하는 방식 |
| 신뢰 호스트 미들웨어 | TrustedHostMiddleware | `Host` 헤더가 허용 목록에 없는 요청을 먼저 차단하는 내장 보안 미들웨어 |

# PART 2. 백그라운드 태스크 및 스트리밍 파일 처리
### | 백그라운드 태스크가 왜 필요한가 |

- 할 일을 새로 등록할 때마다 슬랙/이메일로 알림을 보내야 한다고 하자. 알림 전송에 3초가 걸린다면, 엔드포인트 안에서 그 전송이 끝나기를 `await`로 기다린 뒤 응답을 돌려주는 방식은 클라이언트가 실제로는 즉시 끝난 "할 일 등록" 작업 결과를 받기 위해 불필요하게 3초를 더 기다리게 만든다. `BackgroundTasks`는 "응답은 먼저 보내고, 알림 전송은 응답을 보낸 뒤에 따로 처리해줘"라고 위임하는 방식이다 — 택배로 치면 포장(핵심 작업)만 먼저 끝내서 고객에게 송장 번호(응답)를 바로 보여주고, 실제 배송(알림 전송)은 그 뒤에 진행하는 것과 같다.

```python
import asyncio

async def dispatch_kanban_event_notification_task(task_id: int, action_name: str):
    print(f"[백그라운드 통보 시작] task_id={task_id}, action={action_name}")
    await asyncio.sleep(3)  # 슬랙/이메일 전송을 흉내 낸 지연
    print(f"[백그라운드 통보 완료] task_id={task_id}")

from fastapi import BackgroundTasks

@router.post("", status_code=201)
def create_task(payload: dict, background_tasks: BackgroundTasks):
    new_id = max(task_db.keys(), default=0) + 1
    task_db[new_id] = {"id": new_id, "title": payload["title"], "status": "TODO", "attachments": []}
    background_tasks.add_task(dispatch_kanban_event_notification_task, new_id, "CREATE")
    return task_db[new_id]
```

**실행 결과**
```

HTTP/1.1 201 Created
content-type: application/json

{"id":4,"title":"회의록 정리","status":"TODO","attachments":[]}
```
서버 터미널 (클라이언트가 201 응답을 받은 "이후"에 찍힌다):
```

[백그라운드 통보 시작] task_id=4, action=CREATE
[백그라운드 통보 완료] task_id=4
```
- 클라이언트는 201 응답을 즉시 받고, 그로부터 3초 뒤에야 서버 콘솔에 완료 로그가 찍힌다. 이 3초 동안 클라이언트는 전혀 대기하지 않는다. `BackgroundTasks` 없이 `await dispatch_kanban_event_notification_task(...)`를 엔드포인트 안에서 직접 호출했다면, 클라이언트는 201 응답을 받기까지 정확히 3초 이상 블로킹되어 기다려야 한다 — "할 일 등록"이라는 빠른 작업이 "알림 전송"이라는 느린 작업에 발목 잡히는 셈이다.

### | 다중 파일 업로드와 정적 파일 매핑 |

```python
# src/domain/task.py
class Task:
    def __init__(self, id: int, title: str):
        self.id = id
        self.title = title
        self.attachments: list[str] = []

    def add_attachment_path(self, virtual_url_path: str) -> None:
        if not virtual_url_path.startswith("/static/attachments/"):
            raise ValueError("잘못된 첨부파일 경로입니다.")
        self.attachments.append(virtual_url_path)

    def to_dict(self) -> dict:
        return {"id": self.id, "title": self.title, "attachments": self.attachments}
```

```python
# src/main.py
import os
from fastapi.staticfiles import StaticFiles

STORAGE_DIR = "storage"
os.makedirs(STORAGE_DIR, exist_ok=True)
app.mount("/static/attachments", StaticFiles(directory=STORAGE_DIR), name="attachments")
```

### | 업로드 파일 보안 검증 — 없으면 어떤 일이 벌어지는가 |

- 아무 검증 없이 클라이언트가 보낸 파일을 그대로 디스크에 저장해버리면, 누군가 500MB짜리 영상 파일이나 `.exe` 실행 파일을 계속 업로드해서 서버 디스크를 가득 채우는 공격(DoS)이 가능해진다. 게다가 업로드된 파일이 `/static/attachments` 경로로 그대로 노출되므로, 악성 실행 파일을 다른 사용자가 내려받게 될 위험도 생긴다. 그래서 디스크에 쓰기 전에 확장자와 용량을 먼저 검사하는 관문을 둔다.

```python
import os
from fastapi import UploadFile, File, HTTPException

MAX_FILE_SIZE_LIMIT = 5 * 1024 * 1024  # 5MB
SECURE_ALLOWED_EXTENSIONS = {".txt", ".pdf", ".png", ".jpg", ".jpeg"}
CHUNK_SIZE = 1024 * 1024  # 1MB

@router.post("/{task_id}/upload-attachments", status_code=201)
async def upload_attachments(task_id: int, files: list[UploadFile] = File(...)):
    saved_paths = []
    for file in files:
        ext = os.path.splitext(file.filename)[1].lower()
        if ext not in SECURE_ALLOWED_EXTENSIONS:
            raise HTTPException(status_code=415, detail=f"허용되지 않은 확장자입니다: {ext}")

        await file.seek(0, os.SEEK_END)
        file_size = await file.tell()
        await file.seek(0)  # 디스크에 쓰기 전, 읽기 위치를 반드시 처음으로 되돌려야 한다

        if file_size > MAX_FILE_SIZE_LIMIT:
            raise HTTPException(status_code=413, detail="파일 크기가 5MB를 초과했습니다.")

        save_path = os.path.join(STORAGE_DIR, file.filename)
        with open(save_path, "wb") as f:
            while chunk := await file.read(CHUNK_SIZE):
                f.write(chunk)

        saved_paths.append(f"/static/attachments/{file.filename}")

    return {"task_id": task_id, "attachments": saved_paths}
```

**실행 결과**
```
$ curl -i -X POST "http://127.0.0.1:8000/tasks/4/upload-attachments" -F "files=@malware.exe"
HTTP/1.1 415 Unsupported Media Type
content-type: application/json

{"detail":"허용되지 않은 확장자입니다: .exe"}

$ curl -i -X POST "http://127.0.0.1:8000/tasks/4/upload-attachments" -F "files=@big_file.pdf"
HTTP/1.1 413 Request Entity Too Large
content-type: application/json

{"detail":"파일 크기가 5MB를 초과했습니다."}
```

- `await file.read()`처럼 크기를 지정하지 않고 파일 전체를 한 번에 읽으면, 동시에 여러 사용자가 5MB에 가까운 파일을 업로드할 때 서버 메모리 사용량이 동시 요청 수만큼 배로 뛸 수 있다. 1MB씩 끊어 읽고 바로 써서 버퍼를 비우는 청크(chunk) 방식은 파일 크기와 무관하게 한 요청당 메모리 사용량을 1MB 수준으로 묶어둔다.

### | StreamingResponse가 왜 필요한가 — 없으면 요청이 어떻게 블로킹되는가 |

- 칸반 보드 전체 데이터를 CSV로 내보낼 때, 모든 행을 문자열로 다 이어 붙인 뒤 한 번에 `Response`로 반환하는 방식을 생각해보자. 데이터가 수만 건이라면 서버가 그 전체 문자열을 메모리에 다 만들 때까지 클라이언트는 첫 바이트조차 받지 못하고 계속 대기(블로킹)해야 한다. 서버 메모리 사용량도 전체 행 수에 비례해 계속 커진다. `StreamingResponse`는 한 줄(row)이 만들어지는 즉시 클라이언트에게 흘려보내는 컨베이어 벨트 같은 방식이라, 첫 바이트를 받기까지 걸리는 시간이 데이터 양과 무관하게 거의 일정하고, 서버 메모리도 한 줄 분량만 유지하면 된다.

```python
import csv
import io
from fastapi.responses import StreamingResponse

async def async_kanban_task_csv_row_generator():
    buffer = io.StringIO()
    writer = csv.writer(buffer)

    writer.writerow(["id", "title", "status"])
    yield buffer.getvalue()
    buffer.seek(0)
    buffer.truncate(0)

    for task in task_db.values():
        writer.writerow([task["id"], task["title"], task["status"]])
        yield buffer.getvalue()
        buffer.seek(0)
        buffer.truncate(0)

@router.get("/export/csv")
async def export_tasks_csv():
    return StreamingResponse(
        async_kanban_task_csv_row_generator(),
        media_type="text/csv",
        headers={"Content-Disposition": 'attachment; filename="kanban_tasks_report.csv"'},
    )
```

- `buffer.seek(0)` 후 `buffer.truncate(0)`를 매번 호출하는 이유: `io.StringIO`는 한 번 쓴 내용이 계속 누적되는 가상 버퍼다. 비우지 않고 계속 `writer.writerow(...)`만 반복하면 `yield`로 내보내는 값에 이전 행들까지 중복으로 계속 쌓여 전송된다. 매 행마다 버퍼 포인터를 처음으로 되돌리고(`seek(0)`) 내용을 지워야(`truncate(0)`) "이번 행 하나만" 깨끗하게 내보낼 수 있다.

**실행 결과**
```
$ curl -i "http://127.0.0.1:8000/tasks/export/csv" -o kanban_tasks_report.csv
HTTP/1.1 200 OK
content-type: text/csv; charset=utf-8
content-disposition: attachment; filename="kanban_tasks_report.csv"

$ cat kanban_tasks_report.csv

2,장고 비교 정리,IN_PROGRESS
3,TIL 작성,DONE
4,회의록 정리,TODO
```

### | 일반 Response vs StreamingResponse |

| 구분 | 일반 Response | StreamingResponse |
| --- | --- | --- |
| 데이터 준비 | 전체 내용을 메모리에 다 만든 뒤 한 번에 반환 | 생성되는 즉시 조금씩(chunk) 반환 |
| 메모리 사용량 | 전체 데이터 크기에 비례해 증가 | 한 조각 분량으로 일정하게 유지 |
| 첫 바이트까지 걸리는 시간 | 전체 처리가 끝나야 전송 시작 | 첫 조각이 만들어지는 즉시 전송 시작 |
| 적합한 상황 | 작은 JSON 응답 등 | 대용량 파일, CSV/로그 다운로드 등 |

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 백그라운드 태스크 | Background Task | 응답을 먼저 반환한 뒤 서버가 이어서 처리하는 후속 작업 |
| 스트리밍 응답 | Streaming Response | 데이터를 한 번에 모으지 않고 생성되는 대로 흘려보내는 응답 방식 |
| 비동기 제너레이터 | Async Generator | `async def` 안에서 `yield`로 값을 하나씩 내보내는 비동기 함수 |
| 업로드 파일 | UploadFile | 요청으로 전송된 파일을 스트림 형태로 다루는 FastAPI 전용 타입 |
| 청크 | Chunk | 큰 데이터를 메모리 절약을 위해 일정 크기로 잘라 처리하는 단위 |
