# PART 1. FastAPI 개요 및 환경 설정
### | FastAPI는 왜 나왔나 — WSGI와 ASGI |

- 전통적인 파이썬 웹 프레임워크(Flask, Django)는 **WSGI(Web Server Gateway Interface)** 규격을 따른다. WSGI는 클라이언트 요청 하나에 OS 스레드 하나를 1:1로 붙여서 처리하는 직렬 구조다. 문제는 실제 서비스에서 느려지는 구간 대부분이 계산(CPU)이 아니라 DB 쿼리 응답, 외부 API 호출처럼 **기다리는 시간(I/O bound)** 이라는 점이다. WSGI 방식에서는 요청을 처리하는 스레드가 DB 응답을 기다리는 동안 그냥 멈춰 있는다(blocking I/O). 동시 접속을 늘리려면 스레드·프로세스를 더 띄우는 수밖에 없는데, 이건 메모리 비용이 크다.
- FastAPI는 **ASGI(Asynchronous Server Gateway Interface)** 위에서 동작한다. ASGI는 WSGI의 비동기 버전 규격으로, `async def`로 선언한 핸들러는 이벤트 루프 하나가 여러 요청을 번갈아 처리한다. `await`로 I/O를 기다리는 지점에서 제어권을 다른 요청에 넘기고, 응답이 오면 다시 돌아온다. 스레드 수를 늘리지 않고도 동시 접속을 많이 처리할 수 있는 이유다.
- 주의할 점: 이건 **동시성(concurrency)** 이지 **병렬성(parallelism)** 이 아니다. CPU를 많이 쓰는 연산(이미지 처리, 복잡한 계산)은 이벤트 루프를 막아버려서 오히려 손해가 될 수 있다. 비동기는 "기다리는 일(I/O-bound)"에 유리하지, "계산하는 일(CPU-bound)"에는 유리하지 않다.
- ASGI가 없었다면 어떻게 될까. 동시 접속자가 늘어날 때마다 서버 프로세스·스레드를 계속 추가해야 하고, 그 비용(메모리·컨텍스트 스위칭)이 그대로 서버 자원을 갉아먹는다. FastAPI/Starlette는 이 구조적 병목을 "스레드를 더 쓰지 않고 I/O 대기 중에 다른 요청을 처리"하는 방식으로 우회한다.

| 구분 | WSGI (Flask, Django) | ASGI (FastAPI, Starlette) |
| --- | --- | --- |
| 요청 처리 단위 | 요청 1개 = 스레드 1개 | 요청 여러 개 = 이벤트 루프 1개 |
| I/O 대기 중 동작 | 스레드가 멈춰 있음(blocking) | 제어권을 다른 요청에 넘김(non-blocking) |
| 동시 접속 확장 방법 | 스레드/프로세스 증설 | 이벤트 루프가 여러 요청을 번갈아 처리 |
| 유리한 작업 | — | I/O-bound(DB, 외부 API 호출) |

### | 타입 힌트 하나로 검증과 문서화까지 |

- FastAPI의 핵심 차별점은 함수 인자에 붙이는 **타입 힌트**다. 예를 들어 `async def create_item(item: Item)`처럼 Pydantic 모델을 매개변수 타입으로 선언하면, 이 한 줄이 동시에 세 가지 일을 한다.
  1. **런타임 검증**: 요청 바디가 선언한 스키마와 맞는지 자동으로 체크하고, 안 맞으면 422 에러를 알아서 반환한다.
  2. **파싱/역직렬화**: JSON → Python 객체 변환을 자동으로 처리한다.
  3. **OpenAPI 스키마 생성**: 이 타입 정보를 읽어서 `/docs`(Swagger UI), `/redoc` 문서를 자동 생성한다.
- Flask였다면 이 세 가지를 각각 수동으로 짜야 한다 — 요청 바디를 직접 파싱하고, 필드마다 `if` 문으로 검증하고, API 문서는 별도 문서 파일이나 주석으로 관리해야 한다. 코드와 문서가 분리되어 있으면 코드는 바뀌는데 문서는 안 바뀌는 "문서 노후화" 문제가 거의 필연적으로 생긴다.
- 타입 힌트 기반 자동 검증이 없다면 어떤 버그가 생기나: `title`이 문자열이어야 하는데 숫자가 들어오거나, 필수 필드가 통째로 빠진 요청이 그대로 비즈니스 로직까지 흘러 들어간다. 함수 내부 깊숙한 곳에서 `AttributeError`나 `TypeError`가 터지거나, 최악의 경우 에러 없이 잘못된 값이 DB에 저장되어버린다. FastAPI는 이 검증을 요청이 핸들러 함수에 도달하기 **전** 단계에서 강제로 막는다.

```python
import logging

from fastapi import FastAPI

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
)
logger = logging.getLogger("fastapi-practice")

app = FastAPI()


@app.get("/")
async def root():
    # 호출될 때마다 서버 콘솔에 방문 기록을 남긴다
    logger.info("방문 기록: GET / 호출됨")
    return {"message": "Hello, FastAPI!"}


@app.get("/status")
async def status():
    return {"status": "sandbox_running", "worker_thread": 1}
```

### | 자동 문서화 — Swagger UI와 ReDoc |

- FastAPI 앱을 띄우기만 하면 문서 화면 두 개와 스펙 파일 하나가 자동으로 생긴다.

| 경로 | 이름 | 특징 |
| --- | --- | --- |
| `/docs` | Swagger UI | API 목록을 보고 "Try it out"으로 바로 요청을 보내볼 수 있다. 실습 때 가장 많이 쓰는 방법 |
| `/redoc` | ReDoc | 같은 스펙을 읽기 좋은 문서 형태로 보여준다. 테스트 기능은 없음 |
| `/openapi.json` | OpenAPI 3.1.0 스펙 | 위 두 화면의 원본 데이터. 타입 힌트와 Pydantic 모델에서 자동 생성됨 |

**실행 결과**
```
$ curl http://127.0.0.1:8000/openapi.json
{"openapi":"3.1.0","info":{"title":"FastAPI","version":"0.1.0"},
"paths":{"/":{"get":{"summary":"Root","operationId":"root__get",
"responses":{"200":{"description":"Successful Response"}}}},
"/status":{"get":{"summary":"Status","operationId":"status_status_get",
"responses":{"200":{"description":"Successful Response"}}}}}}
```

- 자동 문서화가 없었다면 어떻게 될까. API 엔드포인트가 늘어날 때마다 사람이 직접 문서(노션, 위키, README 등)를 손으로 업데이트해야 한다. 코드를 고쳤는데 문서를 깜빡하면, 프론트엔드 개발자는 실제로는 사라진 필드를 여전히 있다고 믿고 요청을 보내게 된다. Swagger UI는 코드에 선언한 타입 힌트 자체가 곧 문서이므로, 코드와 문서가 어긋날 수가 없다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| WSGI | Web Server Gateway Interface | 요청 하나에 스레드 하나를 붙여 직렬로 처리하는 전통적인 서버-프레임워크 규격 |

| 이벤트 루프 | Event Loop | I/O 대기 지점에서 제어권을 다른 작업에 넘기며 여러 요청을 번갈아 처리하는 비동기 실행 구조 |
| Uvicorn | - | FastAPI 앱을 구동하는 ASGI 서버 |
| Swagger UI | - | 자동 생성된 API 문서를 보고 직접 요청을 테스트할 수 있는 웹 화면 |
| OpenAPI 스펙 | OpenAPI Specification | 타입 힌트·Pydantic 모델에서 자동 생성되는 API 명세 데이터 |

# PART 2. HTTP 메서드와 기본 라우팅
### | 도메인 모델 스스로 검증하기 (자가 검증) |

- 실습 과제는 칸반 보드의 "할 일(Task)"을 다루는 API를 만드는 것이다. 핵심은 검증 로직을 라우터 함수 안이 아니라 **도메인 모델 클래스 내부**에 둔다는 점이다. 제목(title)이 빈 문자열이거나 공백(`"   "`)으로만 구성되어 들어오면, 생성자 시점에 바로 `ValueError`를 발생시켜 잘못된 데이터가 더 깊은 곳까지 흘러가는 걸 막는다.
- 이런 자가 검증(Self-Validation)이 없다면 어떻게 될까. "제목이 비어있지 않은지" 같은 규칙을 라우터 함수마다, 호출하는 곳마다 매번 중복해서 작성해야 한다. 한 군데라도 그 검사를 깜빡하면 빈 제목을 가진 Task가 그대로 저장소에 쌓인다. 검증 로직을 객체 생성 지점(생성자) 하나로 모아두면, Task 객체가 존재한다는 사실 자체가 "이 객체는 이미 검증을 통과했다"는 보장이 된다.

```python
# src/domain/task.py
from typing import Literal, Optional

TaskStatus = Literal["TODO", "IN_PROGRESS", "DONE"]


class Task:
    def __init__(self, task_id: int, title: str, description: Optional[str] = None):
        if not title or not title.strip():
            raise ValueError("할 일 제목은 공백일 수 없습니다")

        self.id = task_id
        self.title = title
        self.description = description
        self.status: TaskStatus = "TODO"  # 초기 상태는 항상 TODO로 고정

    def to_dict(self) -> dict:
        return {
            "id": self.id,
            "title": self.title,
            "description": self.description,
            "status": self.status,
        }
```

### | POST/GET으로 기본 CRUD 라우트 구현하기 |

- 저장소는 아직 DB 없이 인메모리 딕셔너리(`task_db`)와 증가하는 ID 카운터로 흉내 낸다. 도메인 모델의 `ValueError`를 라우터에서 잡아서 HTTP 400으로 바꿔주는 변환 과정이 필요하다 — 이게 없으면 파이썬 예외가 그대로 서버를 터뜨려서 클라이언트는 500 Internal Server Error만 받게 된다.

```python
# src/main.py
from fastapi import FastAPI, HTTPException

from domain.task import Task

app = FastAPI()

task_db: dict[int, Task] = {}
task_id_counter = 1


@app.post("/tasks")
async def create_task(payload: dict):
    global task_id_counter
    try:
        task = Task(task_id_counter, payload.get("title", ""), payload.get("description"))
    except ValueError as e:
        # 도메인 모델의 ValueError를 HTTP 400으로 변환한다
        raise HTTPException(status_code=400, detail=str(e))

    task_db[task.id] = task
    task_id_counter += 1
    return task.to_dict()


@app.get("/tasks")
async def list_tasks():
    return {tid: t.to_dict() for tid, t in task_db.items()}
```

### | PUT으로 수정하기 + 쿼리 스트링 필터/정렬 |

- `PUT /tasks/{task_id}`는 **경로 매개변수(Path Parameter)** 로 수정 대상 ID를 받는다. 존재하지 않는 ID가 들어오면 404를 반환해야 한다 — 이 체크가 없으면 `task_db[task_id]`에 바로 접근하는 순간 `KeyError`가 터져 500 에러로 이어지거나, 혹은 아예 새 데이터를 조용히 만들어버려 "수정"과 "생성"의 의미가 뒤섞인다.
- `GET /tasks`는 **쿼리 스트링(Query String)** 으로 `status`(상태 필터), `q`(제목 부분 검색), `sort_by_id=desc`(ID 역순 정렬)를 선택적으로 받는다. 쿼리 스트링 필터가 없다면 어떻게 될까. "TODO 상태만 보여주는 API", "제목에 특정 단어가 들어간 것만 보여주는 API"처럼 조합마다 별도 엔드포인트를 만들어야 하거나, 클라이언트가 전체 목록을 다 받아온 뒤 자바스크립트로 걸러내야 한다 — 네트워크 낭비이자 서버 쪽 필터링 로직의 재사용을 포기하는 셈이다.

```python
@app.put("/tasks/{task_id}")
async def update_task(task_id: int, payload: dict):
    if task_id not in task_db:
        raise HTTPException(status_code=404, detail="해당 ID의 할 일을 찾을 수 없습니다")

    task = task_db[task_id]
    task.title = payload.get("title", task.title)
    task.description = payload.get("description", task.description)
    task.status = payload.get("status", task.status)
    return task.to_dict()


@app.get("/tasks")
async def list_tasks(status: str | None = None, q: str | None = None, sort_by_id: str | None = None):
    results = list(task_db.values())

    if status:
        results = [t for t in results if t.status == status]
    if q:
        results = [t for t in results if q in t.title]
    if sort_by_id == "desc":
        results.sort(key=lambda t: t.id, reverse=True)

    return [t.to_dict() for t in results]
```

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 경로 매개변수 | Path Parameter | URL 경로 자체에 포함되어 특정 리소스를 식별하는 값 (예: `/tasks/{task_id}`) |
| 쿼리 스트링 | Query String | URL `?` 뒤에 `key=value` 형태로 붙는 선택적 매개변수 |
| 자가 검증 | Self-Validation | 객체 생성 시점에 도메인 모델 스스로 자신의 데이터 유효성을 검사하는 설계 방식 |
| 인메모리 저장소 | In-Memory Storage | DB 없이 파이썬 변수(딕셔너리 등)에 데이터를 임시로 저장하는 방식 |

Q4. RESTful API 설계에서 HTTP 메서드의 성질에 대한 설명으로 옳지 않은 것은 무엇입니까?

[ 보기 ]

a. GET은 안전성(Safety)을 가지므로 여러 번 호출해도 서버 데이터를 변경하지 않는다

b. PUT은 멱등성(Idempotency)을 가지므로 같은 요청을 여러 번 보내도 최종 상태가 동일하다

c. POST는 호출할 때마다 새로운 리소스를 생성하므로 멱등성을 가진다

d. DELETE는 같은 대상에 반복 요청해도 최종적으로 삭제된 상태가 유지되므로 멱등성을 가진다

내 제출 답안 : b. PUT은 멱등성(Idempotency)을 가지므로 같은 요청을 여러 번 보내도 최종 상태가 동일하다 (오답 ❌)

[ 정답 ] c.

-> 교안의 표에 따르면 POST는 멱등성이 No다. 호출할 때마다 새로운 데이터가 생성되므로 같은 요청을 여러 번 보내면 리소스가 계속 늘어나 최종 상태가 달라진다. GET, PUT, DELETE는 모두 멱등성을 가진다.
