# PART 1. SQLAlchemy 2.0 선언형 모델링과 세션 초기화
### | 왜 인메모리 리스트 대신 진짜 데이터베이스가 필요한가 |

- 지금까지 만든 칸반 보드 백엔드는 서버가 재시작되면 데이터가 전부 사라지는 인메모리(파이썬 리스트) 구조였다. 실제 서비스라면 서버를 껐다 켜도, 여러 사용자가 동시에 접속해도 데이터가 안전하게 유지되어야 한다. 이걸 보장하는 것이 **영속성(Persistence)** 이고, PostgreSQL 같은 데이터베이스와 **SQLAlchemy**(파이썬 ORM)를 연동해서 해결한다.

### | 데이터베이스 연결 설정 — engine과 세션 |

```python
# src/database.py
import os
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

# 환경 변수(DATABASE_URL)가 없으면 로컬 PostgreSQL 기본 주소를 사용한다.
DATABASE_URL = os.getenv(
    "DATABASE_URL",
    "postgresql+psycopg2://postgres:password@localhost:5432/kanban_db"
)

# pool_pre_ping=True — 커넥션 풀에서 꺼낸 연결이 실제로 살아있는지 핑을 날려 미리 확인한다.
engine = create_engine(DATABASE_URL, pool_pre_ping=True)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

# FastAPI 의존성 주입(Depends)에 사용할 세션 제공 함수
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()  # 요청이 끝나면 반드시 세션을 닫아 커넥션을 반납한다.
```

- `pool_pre_ping=True`가 왜 필요한가: 데이터베이스 커넥션 풀에 보관된 연결은 오래 안 쓰이면 방화벽이나 DB 서버 쪽에서 끊어버릴 수 있다. 이 옵션이 없으면, 끊어진 줄도 모르고 그 연결을 재사용하려다가 "연결이 끊어졌다"는 에러가 요청 처리 중간에 갑자기 터진다. `pool_pre_ping`은 연결을 실제로 꺼내 쓰기 직전에 가벼운 핑을 보내 살아있는지 확인하고, 죽어있으면 자동으로 새 연결을 만들어준다.
- `get_db()`에서 `yield`를 쓰는 이유: FastAPI가 요청을 처리하는 동안만 세션을 열어주고, 핸들러 함수가 끝나면(`finally` 블록에서) 자동으로 `db.close()`를 호출하게 만들기 위해서다. 이게 없으면 요청마다 세션이 계속 열린 채로 쌓여서, 커넥션 풀이 금방 바닥나 버린다.

### | Mapped와 mapped_column으로 테이블 설계하기 |

- SQLAlchemy 2.0에서는 `Mapped[타입]`과 `mapped_column()`을 조합해서 테이블의 각 컬럼에 **타입 힌트와 DB 제약조건을 동시에** 선언한다.

```python
# src/models/task.py
from sqlalchemy import String, ForeignKey, TIMESTAMP
from sqlalchemy.orm import Mapped, mapped_column, relationship
from src.database import Base

class Task(Base):
    __tablename__ = "tasks"

    id: Mapped[int] = mapped_column(primary_key=True, index=True)
    # 파이썬 변수명(title)과 실제 DB 컬럼명(task_title)이 다를 때 name으로 매핑한다.
    title: Mapped[str] = mapped_column("task_title", String(100), nullable=False)
    description: Mapped[str | None] = mapped_column(String(500), nullable=True)
    status: Mapped[str] = mapped_column(String(20), nullable=False, default="TODO")
    due_date: Mapped[str | None] = mapped_column(TIMESTAMP, nullable=True)

    # 1:N 관계 — 부모(Task)가 삭제되면 자식(SubTask)도 함께 삭제되도록 cascade 설정
    sub_tasks: Mapped[list["SubTask"]] = relationship(
        back_populates="task",
        cascade="all, delete-orphan"
    )


class SubTask(Base):
    __tablename__ = "sub_tasks"

    id: Mapped[int] = mapped_column(primary_key=True, index=True)
    sub_task_title: Mapped[str] = mapped_column(String(100), nullable=False)
    is_completed: Mapped[bool] = mapped_column(default=False, nullable=False)
    # ondelete="CASCADE" — DB 차원에서도 부모 삭제 시 자식 행을 자동 삭제하도록 외래키에 명시
    task_id: Mapped[int] = mapped_column(
        ForeignKey("tasks.id", ondelete="CASCADE"), nullable=False
    )

    task: Mapped["Task"] = relationship(back_populates="sub_tasks")
```

**실행 결과** — 서버를 띄우고(`uv run uvicorn main:app --app-dir src --reload`) DBeaver 등으로 `kanban_db`에 접속해서 확인하면, `tasks`·`sub_tasks` 두 테이블이 명세된 컬럼·제약조건 그대로 자동 생성되어 있다. `sub_tasks` 테이블의 DDL을 조회하면 `task_id` 외래키에 `ON DELETE CASCADE`가 걸려있는 것도 확인된다.

- **별칭(Alias) 매핑**이 왜 필요한가: 파이썬 코드에서는 `title`이라는 짧고 자연스러운 이름을 쓰고 싶은데, DB 컬럼명은 테이블 전체의 일관성을 위해 `task_title`처럼 지어야 하는 경우가 있다. `mapped_column("task_title", ...)`처럼 첫 인자에 실제 DB 컬럼명을 적어주면, 파이썬에서는 `task.title`로 접근하면서도 DB에는 `task_title` 컬럼으로 저장된다. 이게 없으면 파이썬 변수명과 DB 컬럼명을 억지로 통일해야 해서, 둘 중 하나는 어색한 이름이 되어버린다.
- **CASCADE 삭제**가 없다면 어떻게 될까: `Task`(할 일 카드)를 삭제했는데 그 밑에 달린 `SubTask`(하위 할 일)들이 고아 레코드로 DB에 그대로 남는다. 부모가 없는 자식 데이터가 쌓이면서 DB가 지저분해지고, 나중에 "삭제됐어야 할 하위 할일이 왜 아직도 조회되지?" 같은 버그로 이어진다. `cascade="all, delete-orphan"`(ORM 레벨)과 `ondelete="CASCADE"`(DB 레벨)를 같이 걸어두면, 부모를 지우는 순간 자식도 자동으로 깔끔하게 함께 지워진다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 영속성 | Persistence | 서버 재시작과 무관하게 데이터가 안전하게 보존되는 성질 |
| 선언형 모델링 | Declarative Mapping | 파이썬 클래스로 테이블 구조를 선언하면 ORM이 실제 DDL로 변환해주는 방식 |
| 커넥션 풀 | Connection Pool | 매번 새로 연결하지 않도록 DB 연결을 미리 만들어 재사용하는 저장소 |
| CASCADE 삭제 | Cascade Delete | 부모 레코드가 삭제될 때 연관된 자식 레코드도 함께 삭제되는 정책 |

# PART 2. Pydantic 제네릭 공통 응답과 CRUD 라우터 통합
### | 왜 모든 API 응답을 같은 모양으로 통일해야 하나 |

- 프론트엔드가 API를 호출할 때마다 응답 구조가 제각각이면, 매번 다른 파싱 코드를 짜야 한다. `{ success, data, error }`처럼 공통 틀을 정해두면, 프론트는 항상 같은 방식으로 응답을 처리할 수 있다. 어제(10/27) 배운 `TypeVar`/`Generic`을 여기서 그대로 활용한다.

```python
# src/schemas/task.py
from typing import Generic, TypeVar, Optional
from pydantic import BaseModel, ConfigDict

class SubTaskResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)  # SQLAlchemy 객체를 그대로 읽을 수 있게 함
    id: int
    sub_task_title: str
    is_completed: bool

class TaskResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    title: str
    description: Optional[str]
    status: str
    sub_tasks: list[SubTaskResponse] = []

T = TypeVar("T")

class APIResponse(BaseModel, Generic[T]):
    success: bool
    data: Optional[T] = None
    error: Optional[str] = None
```

- `from_attributes=True`가 왜 필요한가: Pydantic은 기본적으로 딕셔너리(`dict`)나 키워드 인자로 데이터를 받는 걸 전제로 한다. 그런데 SQLAlchemy의 `Task` 객체는 딕셔너리가 아니라 `.title`, `.status`처럼 속성(attribute)으로 접근하는 일반 파이썬 객체다. `from_attributes=True`(과거 `orm_mode`)가 없으면 `TaskResponse(task_db_object)`처럼 DB 객체를 바로 스키마에 넣었을 때 "딕셔너리가 아니다"라는 에러가 난다. 이 옵션이 ORM 객체 ↔ Pydantic 스키마 사이의 다리 역할을 한다.

### | CRUD 라우터에 공통 응답 적용하기 |

```python
# src/main.py (일부)
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
from src.database import get_db
from src.schemas.task import TaskResponse, APIResponse

app = FastAPI()

@app.post("/tasks", response_model=APIResponse[TaskResponse])
def create_task(payload: TaskCreate, db: Session = Depends(get_db)):
    try:
        new_task = Task(title=payload.title, description=payload.description)
        db.add(new_task)
        db.commit()
        db.refresh(new_task)
        return APIResponse(success=True, data=new_task)
    except Exception:
        db.rollback()  # 예외 발생 시 지금까지의 변경사항을 전부 취소
        raise HTTPException(status_code=500, detail="할 일 생성 중 오류가 발생했습니다.")


@app.get("/tasks", response_model=APIResponse[list[TaskResponse]])
def list_tasks(page: int = 1, size: int = 10, db: Session = Depends(get_db)):
    # 대량 데이터를 한꺼번에 내려주지 않도록 페이지 단위로 잘라서 조회한다.
    tasks = db.query(Task).offset((page - 1) * size).limit(size).all()
    return APIResponse(success=True, data=tasks)


@app.put("/tasks/{task_id}", response_model=APIResponse[TaskResponse])
def update_task(task_id: int, payload: TaskUpdate, db: Session = Depends(get_db)):
    task = db.query(Task).filter(Task.id == task_id).first()
    if not task:
        raise HTTPException(status_code=404, detail="해당 할 일을 찾을 수 없습니다.")

    # 비즈니스 규칙: 하위 할일이 전부 완료돼야만 DONE으로 바꿀 수 있다.
    if payload.status == "DONE":
        if any(not sub.is_completed for sub in task.sub_tasks):
            raise HTTPException(
                status_code=400,
                detail="하부 세부 할일들이 모두 완료 상태여야 메인 카드를 DONE 처리할 수 있습니다."
            )

    task.status = payload.status
    db.commit()
    db.refresh(task)
    return APIResponse(success=True, data=task)
```

**실행 결과** — 하위 할일 중 `is_completed: false`인 항목이 남아있는 상태로 `PUT /tasks/1`에 `status: "DONE"`을 보내면:
```
HTTP/1.1 400 Bad Request
{
  "detail": "하부 세부 할일들이 모두 완료 상태여야 메인 카드를 DONE 처리할 수 있습니다."
}
```
정상 케이스(`GET /tasks/1`)는 다음처럼 `data` 필드 안에 실제 데이터가 캡슐화되어 반환된다:
```
{
  "success": true,
  "data": { "id": 1, "title": "SQLAlchemy 학습", "status": "TODO", "sub_tasks": [...] },
  "error": null
}
```

- 이 비즈니스 검증 규칙(`DONE 전환 시 하위 할일 완료 여부 체크`)이 없다면 어떻게 될까. 데이터베이스 제약조건(컬럼 타입, NOT NULL 등)만으로는 "하위 할일이 다 끝나야 부모를 완료 처리할 수 있다" 같은 업무 규칙을 표현할 방법이 없다. 그래서 이런 규칙은 라우터 핸들러 안에서 직접 코드로 검증하고, 위반 시 `HTTPException(400)`으로 명확하게 알려줘야 한다.
- `db.rollback()`이 왜 필요한가: 여러 DB 변경 작업(예: Task 생성 + 로그 기록) 도중 중간에 에러가 나면, 이미 실행된 일부 변경만 어중간하게 저장되는 상황이 생길 수 있다. `rollback()`은 현재 세션에서 아직 커밋되지 않은 모든 변경을 취소해서, "전부 성공하거나 전부 취소되거나" 둘 중 하나만 일어나게 만든다(트랜잭션의 원자성).

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 제네릭 응답 모델 | Generic Response Model | data 필드의 실제 타입을 호출 시점에 유연하게 대입하는 공통 응답 구조 |
| 트랜잭션 롤백 | Transaction Rollback | 커밋 전 변경사항을 전부 취소해 데이터 일관성을 지키는 동작 |
| 페이지네이션 | Pagination | 대량 데이터를 페이지 단위로 잘라서 조회하는 기법 |

# PART 3. 표준 에러 응답 문서화와 N+1 쿼리 최적화
### | Swagger 문서에 에러 응답까지 명세하기 |

- 지금까지는 성공 응답(200)만 Swagger 문서에 자동으로 뜨고, 400·404 같은 에러 응답의 실제 모양은 문서에 나오지 않았다. 프론트엔드 개발자가 "이 API는 실패하면 어떤 형태로 에러가 오나요?"를 매번 직접 물어봐야 하는 상황을 막기 위해, 에러 응답도 명세에 포함시킨다.

```python
# src/schemas/task.py
from datetime import datetime
from pydantic import BaseModel

class CommonErrorResponse(BaseModel):
    error_code: str
    message: str
    timestamp: datetime

# src/main.py
@app.put(
    "/tasks/{task_id}",
    response_model=APIResponse[TaskResponse],
    responses={
        400: {"model": CommonErrorResponse, "description": "비즈니스 규칙 위반"},
        404: {"model": CommonErrorResponse, "description": "데이터가 존재하지 않음"},
    }
)
def update_task(task_id: int, payload: TaskUpdate, db: Session = Depends(get_db)):
    ...
```

**실행 결과** — `/docs`(Swagger UI)에서 `PUT /tasks/{task_id}`를 펼치면, 기존 200 성공 응답 외에 `Responses` 탭에 400·404 항목이 추가로 보이고, 각각 `CommonErrorResponse` 스키마(`error_code`, `message`, `timestamp`) 구조로 명세되어 있는 것이 확인된다.

- `responses` 매개변수가 없다면 어떻게 될까. 코드상으로는 `HTTPException(400, ...)`을 던지고 있지만, 이건 런타임에만 발생하는 동작이라 Swagger 문서(정적 명세)에는 전혀 드러나지 않는다. 프론트엔드 입장에서는 실제로 요청을 날려서 에러를 유발해보기 전까지 에러 응답의 모양을 알 수 없다. `responses`로 미리 선언해두면 문서만 보고도 모든 실패 케이스의 응답 형태를 파악할 수 있다.

### | N+1 문제와 joinedload 최적화 |

- `Task` 목록을 조회하면서 각 Task의 `sub_tasks`에 접근하면, SQLAlchemy는 기본적으로 **Task를 조회하는 쿼리 1번 + 각 Task마다 SubTask를 조회하는 쿼리 N번**, 총 N+1번의 쿼리를 날린다. Task가 100개면 쿼리가 101번 나가는 셈이다 — 이게 **N+1 문제**다.

```python
# 최적화 전 — N+1 문제 발생
tasks = db.query(Task).offset((page - 1) * size).limit(size).all()
# 이후 tasks[i].sub_tasks에 접근할 때마다 그때그때 추가 쿼리가 나간다.

# 최적화 후 — joinedload로 한 번의 LEFT OUTER JOIN으로 해결
from sqlalchemy.orm import joinedload

tasks = (
    db.query(Task)
    .options(joinedload(Task.sub_tasks))
    .offset((page - 1) * size)
    .limit(size)
    .all()
)
```

**실행 결과** — SQLAlchemy의 SQL 에코(`echo=True`)를 켜고 `GET /tasks`를 호출하면, 최적화 전에는 쿼리 로그가 `SELECT * FROM tasks ...` 1번에 이어 `SELECT * FROM sub_tasks WHERE task_id = ?`가 Task 개수만큼 반복해서 찍힌다. `joinedload` 적용 후에는 다음과 같이 **단 1개의 쿼리**만 찍힌다:
```
SELECT tasks.*, sub_tasks.* FROM tasks
LEFT OUTER JOIN sub_tasks ON tasks.id = sub_tasks.task_id
LIMIT 10 OFFSET 0
```

- `joinedload`가 없다면 어떻게 될까. 목록에 Task가 많아질수록 쿼리 횟수가 정비례해서 늘어난다. 각 쿼리는 네트워크 왕복(DB 서버와의 통신)을 수반하므로, Task가 1,000개면 1,001번의 네트워크 왕복이 발생해 API 응답이 급격히 느려진다. `joinedload`로 부모·자식 테이블을 한 번의 JOIN으로 묶어 조회하면, 쿼리 횟수가 데이터 양과 무관하게 항상 1번으로 고정된다.

### | 참고 — 다음 강(5장 2강)으로 이어지는 내용 |

- 지금까지 작성한 `database.py`는 동기(sync) 드라이버인 `psycopg2`를 사용했다. 요청마다 DB 응답을 기다리는 동안 이벤트 루프 전체가 블로킹될 수 있다는 한계가 있는데, 다음 강에서는 `asyncpg` 같은 비동기 드라이버로 전환해서 DB 응답을 기다리는 동안에도 서버가 다른 요청을 계속 처리할 수 있도록 리팩토링한다.
