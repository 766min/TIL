# PART 1. 경로/쿼리 매개변수 및 예외 처리
### | Annotated + Query로 쿼리 매개변수에 제약 걸기 |

- FastAPI는 쿼리 매개변수 자리에 `Annotated[타입, Query(조건...)]` 형태를 써서, "이 매개변수는 어떤 타입이고 어떤 범위만 허용한다"는 규칙을 함수 시그니처 자체에 선언할 수 있다. 검색어(`q`)는 공백 검색을 막기 위해 1~20자로, 목록 개수(`limit`)는 서버 과부하를 막기 위해 1~50개로 제한하는 식이다.

```python
from enum import Enum
from typing import Annotated, Optional
from fastapi import FastAPI, Query, Path, HTTPException

app = FastAPI()

class TaskStatus(str, Enum):
    TODO = "TODO"
    IN_PROGRESS = "IN_PROGRESS"
    DONE = "DONE"

task_db = {
    1: {"id": 1, "title": "FastAPI 공부하기", "status": "TODO"},
    2: {"id": 2, "title": "장고 비교 정리", "status": "IN_PROGRESS"},
    3: {"id": 3, "title": "TIL 작성", "status": "DONE"},
}

@app.get("/tasks")
def read_tasks(
    status_filter: Annotated[Optional[TaskStatus], Query(alias="status")] = None,
    q: Annotated[Optional[str], Query(alias="query", min_length=1, max_length=20)] = None,
    limit: Annotated[int, Query(ge=1, le=50, description="출력할 최대 태스크 개수 제한")] = 10,
    offset: Annotated[int, Query(ge=0, description="건너뛸 데이터 오프셋 지표")] = 0,
):
    results = list(task_db.values())
    if status_filter:
        results = [t for t in results if t["status"] == status_filter]
    if q:
        results = [t for t in results if q in t["title"]]
    return results[offset: offset + limit]
```

### | 쿼리 매개변수 검증이 왜 필요한가 |

- `limit`에 제약이 없었다면 클라이언트가 `limit=999999`를 보냈을 때 서버가 그대로 받아들여 전체 데이터를 다 긁어오려 하고, 데이터가 많아질수록 DB 조회량과 응답 용량이 걷잡을 수 없이 커진다. `le=50` 같은 제약은 "요청 하나가 서버에 줄 수 있는 부담의 상한선"을 함수 시그니처 자체에 못 박아, 검증 로직을 매번 if문으로 짜지 않아도 FastAPI가 알아서 422로 걸러준다.
- `q`에 최소 길이(`min_length=1`)가 없었다면 빈 문자열(`""`)이 "검색어 있음" 취급되어 `if q:` 조건을 그냥 통과해버릴 수 있다(단, 공백 문자열은 파이썬에서 `if q:`가 `True`이므로 실제로는 `min_length=1`이 "완전히 빈 값"만 막아준다는 점에 유의 — 의미 없는 검색 요청을 사전에 줄이는 1차 방어선 역할이다).

### | Path 매개변수 제약과 HTTPException으로 404 응답하기 |

- 경로 변수인 `task_id`에도 `Path(gt=0, le=500000)`로 상식적인 범위를 걸어두고, 그 범위 안이라도 실제 저장소에 없는 ID라면 `HTTPException`을 직접 `raise`해서 404와 커스텀 헤더를 함께 돌려준다.

```python
@app.get("/tasks/{task_id}")
def read_task(task_id: Annotated[int, Path(gt=0, le=500000)]):
    if task_id not in task_db:
        raise HTTPException(
            status_code=404,
            detail="해당 ID의 할 일을 찾을 수 없습니다.",
            headers={"X-Task-Status": "NOT_FOUND", "X-Error-Reason": "INVALID_TASK_ID"},
        )
    return task_db[task_id]
```

### | 전역 예외 처리기로 에러 응답 포맷 통일하기 |

- 비즈니스 검증 로직이 여러 곳에 흩어져 있으면, 함수마다 `try/except`를 반복해서 써야 하고 에러 응답 모양도 제각각이 되기 쉽다. `@app.exception_handler(ValueError)`를 서버 최상단에 한 번만 등록해두면, 어디서 `raise ValueError(...)`가 발생하든 똑같은 JSON 포맷으로 응답을 통일할 수 있다.

```python
from datetime import datetime
from pydantic import BaseModel, field_validator
from fastapi import Request
from fastapi.responses import JSONResponse

class TaskCreateSchema(BaseModel):
    title: str
    description: Optional[str] = None

    @field_validator("title")
    @classmethod
    def title_must_not_be_blank(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("제목은 공백만으로 채울 수 없습니다.")
        return v

@app.exception_handler(ValueError)
def value_error_handler(request: Request, exc: ValueError):
    return JSONResponse(
        status_code=400,
        content={
            "success": False,
            "error_type": "VALUE_ERROR",
            "reason": str(exc),
            "timestamp": datetime.now().isoformat(),
        },
    )

@app.post("/tasks", status_code=201)
def create_task(payload: dict):
    # 요청 바디를 FastAPI 파라미터로 바로 받지 않고, 함수 내부에서 수동으로 스키마를 생성한다.
    # 이렇게 해야 field_validator의 ValueError가 FastAPI의 자동 422 변환을 거치지 않고 그대로 올라온다.
    new_task = TaskCreateSchema(**payload)
    new_id = max(task_db.keys(), default=0) + 1
    task_db[new_id] = {"id": new_id, "title": new_task.title, "status": "TODO"}
    return task_db[new_id]
```

**실행 결과**
```
$ curl -i -X POST "http://127.0.0.1:8000/tasks" -H "Content-Type: application/json" -d '{"title": " "}'
HTTP/1.1 400 Bad Request
content-type: application/json

{"success":false,"error_type":"VALUE_ERROR","reason":"제목은 공백만으로 채울 수 없습니다.","timestamp":"2026-10-28T14:02:11.483215"}
```

### | 전역 예외 처리기가 없다면 |

- 전역 핸들러가 없다면, 제목 공백 검증 외에도 "마감일이 과거일 수 없다", "담당자 이메일 형식이 맞아야 한다" 같은 검증 규칙이 늘어날 때마다 엔드포인트 함수마다 `try/except ValueError`를 똑같이 복사해 붙여야 한다. 실수로 한 곳에서 `try/except`를 빠뜨리면 그 엔드포인트만 500 에러를 뱉는 식으로 일관성이 깨진다. 전역 핸들러는 "ValueError라는 신호가 어디서 올라오든 한곳에서 똑같이 처리한다"는 규칙을 서버 전체에 한 번만 선언하는 방식이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 경로 매개변수 | Path Parameter | URL 경로 자체에 포함되는 값(`/tasks/{task_id}`의 `task_id`) |
| 쿼리 매개변수 | Query Parameter | URL의 `?key=value` 형태로 전달되는 선택적 값 |
| 애너테이션 타입 | Annotated | 타입과 추가 메타데이터(Query, Path 등 검증 규칙)를 함께 묶어 선언하는 문법 |
| HTTP 예외 | HTTPException | 특정 상태 코드와 메시지, 헤더를 가진 에러 응답을 직접 발생시키는 FastAPI 전용 예외 클래스 |
| 전역 예외 처리기 | Exception Handler | 특정 예외 타입이 발생했을 때 서버 전체에서 공통으로 실행될 응답 로직을 등록하는 기능 |

# PART 2. Jinja2 템플릿과 정적 파일
### | 왜 템플릿 엔진이 필요한가 |

- FastAPI 엔드포인트는 기본적으로 JSON을 반환하는 API 서버용 틀이다. 그런데 브라우저로 직접 접속하는 사람에게는 사람이 읽을 HTML 화면을 보여줘야 한다. 이때 파이썬 문자열을 f-string으로 이어 붙여 HTML을 만드는 방법도 있지만, 두 가지 문제가 생긴다. 첫째, 자동 이스케이프가 없어서 할 일 제목에 `<script>`가 섞여 들어오면 그대로 실행되는 XSS 취약점이 생긴다. 둘째, 모든 페이지에 똑같이 들어가는 헤더·푸터를 페이지 수만큼 복사-붙여넣기 해야 한다. Jinja2는 이 두 문제를 각각 자동 이스케이프와 템플릿 상속(`extends`)/포함(`include`)으로 해결해준다.

### | 디렉토리 구조와 정적 파일 마운트 |

```txt
kanban-board/
└── src/
    ├── main.py
    ├── schemas/
    │   └── task.py
    ├── static/
    │   └── css/
    │       └── kanban_style.css
    └── templates/
        ├── kanban_header.html
        ├── kanban_footer.html
        ├── kanban_base.html
        └── kanban_board.html
```

```python
from fastapi import FastAPI, Request, Form
from fastapi.responses import HTMLResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

app = FastAPI()
app.mount("/static", StaticFiles(directory="src/static"), name="static")
templates = Jinja2Templates(directory="src/templates")
```

**실행 결과**
```

src/
 ├─ static/css/kanban_style.css   (정적 파일 — 변경 없이 그대로 전송됨)
 └─ templates/*.html               (요청마다 데이터와 합쳐져 렌더링됨)
```

### | 템플릿 상속(extends)과 포함(include)으로 레이아웃 조립하기 |

- 비유하면, `kanban_base.html`은 "액자의 틀"이고 각 페이지는 그 틀 안에 끼우는 "그림"이다. 헤더·푸터는 모든 액자에 공통으로 붙는 장식이라서 별도 조각 파일로 분리해두고 `{% include %}`로 끼워 넣는다.

```html
<!-- kanban_base.html -->
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <title>칸반 보드</title>
    <link rel="stylesheet" href="{{ url_for('static', path='/css/kanban_style.css') }}">
</head>
<body>
    {% include "kanban_header.html" %}
    {% block content %}{% endblock %}
    {% include "kanban_footer.html" %}
</body>
</html>
```

```html
<!-- kanban_board.html -->
{% extends "kanban_base.html" %}
{% block content %}
<form action="/board" method="post">
    <input type="text" name="title" placeholder="할 일 제목" required>
    <input type="text" name="description" placeholder="설명(선택)">
    <button type="submit">추가</button>
</form>
{% if error_message %}
<p class="error">{{ error_message }}</p>
{% endif %}
<div class="board-grid">
    {% for status in ["TODO", "IN_PROGRESS", "DONE"] %}
    <div class="column">
        <h2>{{ status }}</h2>
        {% for task in tasks if task.status == status %}
        <div class="card {% if task.is_overdue %}overdue-danger{% endif %}">
            {{ task.title }}
            {% if task.is_overdue %}<span class="badge">기한 초과</span>{% endif %}
        </div>
        {% endfor %}
    </div>
    {% endfor %}
</div>
{% endblock %}
```

- `url_for('static', path=...)`를 쓰는 이유: CSS 경로를 `"/static/css/kanban_style.css"`처럼 모든 템플릿에 직접 하드코딩해두면, 나중에 정적 파일 마운트 경로가 바뀌었을 때 템플릿 파일 전부를 찾아다니며 고쳐야 한다. `url_for`는 `app.mount`로 등록된 설정을 기준으로 주소를 자동 생성해주므로, 설정 한 곳만 바꾸면 모든 템플릿에 일괄 반영된다.

### | 레이아웃을 분리하지 않으면 어떻게 되는가 |

- `{% include %}`/`{% extends %}` 없이 모든 페이지에 헤더·푸터 HTML을 직접 복사해 넣었다면, 상호명이나 카피라이트 문구 한 줄만 바뀌어도 페이지 개수만큼 파일을 전부 열어 고쳐야 한다. 한 페이지라도 고치는 걸 빠뜨리면 사이트 내 헤더가 페이지마다 달라지는 비일관성이 생긴다.

### | HTML Form과 Pydantic 검증 연동하기 |

```python
from datetime import date
from typing import Optional

@app.get("/board", response_class=HTMLResponse)
def view_board(request: Request, board: str = "스파르타공부방"):
    today = date.today()
    tasks_with_flag = []
    for t in task_db.values():
        t = dict(t)
        if t.get("due_date") and t["due_date"] < today and t["status"] != "DONE":
            t["is_overdue"] = True
        tasks_with_flag.append(t)
    return templates.TemplateResponse(
        request=request,
        name="kanban_board.html",
        context={"tasks": tasks_with_flag, "board": board},
    )

@app.post("/board", response_class=HTMLResponse)
def create_task_from_form(
    request: Request,
    title: str = Form(...),
    description: Optional[str] = Form(None),
):
    error_message = None
    try:
        new_task = TaskCreateSchema(title=title, description=description)
        new_id = max(task_db.keys(), default=0) + 1
        task_db[new_id] = {"id": new_id, "title": new_task.title, "status": "TODO"}
    except ValueError as exc:
        error_message = str(exc)
    return templates.TemplateResponse(
        request=request,
        name="kanban_board.html",
        context={"tasks": list(task_db.values()), "error_message": error_message},
    )
```

### | Form 제출에 예외 처리가 없다면 |

- `try/except` 없이 `TaskCreateSchema(title=title, ...)`를 바로 호출했다면, 공백 제목 제출 시 `field_validator`가 던지는 `ValueError`가 그대로 위로 올라간다. PART 1에서 등록해둔 전역 `ValueError` 핸들러가 있긴 하지만, 그건 `{"success": false, ...}` 같은 JSON을 반환하는 용도다. 브라우저로 폼을 제출한 사용자에게 날것의 JSON 텍스트가 그대로 보이면 "방금 뭐가 잘못됐는지" 전혀 알 수 없는 사용자 경험이 된다. 그래서 브라우저용 엔드포인트에서는 전역 핸들러에 맡기지 않고 그 자리에서 직접 `try/except`로 잡아, 같은 HTML 페이지에 에러 문구를 끼워 넣어 다시 보여주는 방식을 쓴다.

### | Jinja2 조건문으로 마감 기한 지난 카드 강조하기 |

- `view_board` 함수에서 `due_date`가 오늘보다 과거이고 상태가 `DONE`이 아닌 할 일에는 `is_overdue: True` 플래그를 딕셔너리에 동적으로 추가해 템플릿으로 넘긴다. 템플릿은 그 플래그만 보고 `overdue-danger` 클래스와 "기한 초과" 배지를 조건부로 붙인다.

| 조건 | 결과 |
| --- | --- |
| `due_date < 오늘` 이고 `status != DONE` | 카드 배경이 붉은 톤(`overdue-danger`)으로 바뀌고 "기한 초과" 배지가 붙는다 |
| 그 외 | 기본 스타일 그대로 렌더링된다 |

- Jinja2 조건문이 없었다면, "마감 지난 할 일을 빨갛게 보여준다"는 로직을 파이썬 쪽에서 미리 HTML 클래스 문자열(`"card overdue-danger"` 등)을 통째로 만들어 넘겨야 한다. 화면 디자인이 조금만 바뀌어도 파이썬 코드를 고쳐야 하니, 화면 표현과 데이터 로직이 뒤섞여버린다. 템플릿 쪽에 조건문을 두면 "지금 이 태스크가 기한을 넘겼는가"라는 데이터 판단은 파이썬이 하고, "그걸 어떻게 보여줄지"는 템플릿이 전담하도록 역할이 분리된다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 템플릿 엔진 | Template Engine | 데이터와 HTML 뼈대를 합쳐 최종 화면을 만들어주는 도구 |
| 템플릿 상속 | Template Inheritance | `{% extends %}`로 공통 레이아웃을 자식 템플릿이 물려받는 방식 |
| 템플릿 포함 | Template Include | `{% include %}`로 다른 템플릿 조각을 현재 위치에 끼워 넣는 방식 |
| 정적 파일 마운트 | Static File Mount | CSS/이미지처럼 가공 없이 그대로 전송되는 파일 경로를 서버에 등록하는 것 |
| 폼 데이터 | Form Data | `<form>` 태그로 전송되어 `Form(...)` 매개변수로 받는 요청 데이터 |

Q5. 교안의 목록 조회 API에서 limit 변수에 le=50을 설정한 이유를 한 문장으로 설명하세요.

내 제출 답안 : 미제출 (오답 ❌)

[ 정답 ] 서버에 과도한 데이터 요청이 가지 않도록 한 번에 조회 가능한 최대 개수를 50개로 제한하기 위해서
