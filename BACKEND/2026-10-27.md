# PART 1. 타입 힌트와 Pydantic 모델 검증
### | 수작업 검증의 한계 — 어제(10/26) Task 클래스 돌아보기 |

- 어제는 `Task.__init__` 안에 `if not title.strip(): raise ValueError(...)`를 직접 심어서 제목 공백 여부 하나만 검증했다. 오늘 과제는 이 수작업 검증 자체를 Pydantic에게 위임하는 리팩터링이다.
- 검사해야 할 규칙이 하나(제목 공백 금지)뿐일 때는 `if`문 하나로 충분하다. 하지만 "제목 길이는 2~100자", "상태는 TODO/DOING/DONE 중 하나만", "완료 처리된 할 일인데 하위 작업이 안 끝났으면 거부", "하위 작업까지 포함한 중첩 구조"처럼 규칙이 늘어나면, `__init__` 안에 `if`문이 계속 쌓이고 생성(Create)·수정(Update)·응답(Response)마다 거의 똑같은 검증 코드를 중복해서 짜야 한다. Pydantic은 이 규칙들을 "조건문 나열"이 아니라 **선언적으로(declarative)** 모델 필드에 붙이는 방식으로 바꿔준다.

### | Pydantic 모델로 선언적 검증하기 |

- `BaseModel`을 상속한 클래스는 필드마다 타입과 제약 조건(`Field(min_length=..., max_length=...)`)을 선언하기만 하면, FastAPI가 요청을 받는 시점에 자동으로 검증한다. `Literal["TODO", "DOING", "DONE"]`처럼 리터럴 타입으로 상태값을 제한하면, 오타나 정의되지 않은 문자열은 아예 객체로 만들어지지도 못한다.

```python
from datetime import datetime
from typing import Literal, Optional

from pydantic import BaseModel, Field


class SubTask(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    is_completed: bool = False  # 기본값은 미완료


class TaskCreate(BaseModel):
    title: str = Field(min_length=2, max_length=100)
    description: Optional[str] = None
    status: Literal["TODO", "DOING", "DONE"] = "TODO"
    sub_tasks: list[SubTask] = Field(default_factory=list)  # 중첩 구조
    due_date: Optional[datetime] = None
```

- `Literal`이 없었다면 `status`는 그냥 `str`로 선언되었을 테고, `"WRONG"`, `"done"`, `"Done"`처럼 오타·대소문자가 다른 값도 전부 통과해버린다. 이후 코드에서 `if task.status == "DONE":`이라고 비교하는 조건문은 `"Done"`이 들어온 경우 조용히 `False`로 평가되어버려서, 에러도 없이 그냥 로직이 틀어지는 가장 찾기 어려운 종류의 버그가 생긴다.

### | field_validator로 공백 제거 및 커스텀 규칙 적용하기 |

- `Field(min_length=1)`은 문자열의 "길이"만 본다. `"   "`(공백 3칸)는 길이가 3이라 `min_length=1`을 그냥 통과해버린다. `@field_validator`는 Pydantic이 기본 타입 검사를 마친 뒤 실행할 커스텀 파이썬 함수를 등록하는 데코레이터로, `strip()` 같은 가공 로직과 추가 조건을 끼워 넣을 수 있다.

```python
from pydantic import field_validator


class SubTask(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    is_completed: bool = False

    @field_validator("title")
    @classmethod
    def strip_and_check_title(cls, v: str) -> str:
        v = v.strip()
        if not v:
            raise ValueError("하위 작업 제목은 단순 공백 문자 혹은 무의미한 빈 문자열로만 채워질 수 없습니다")
        return v
```

- `field_validator`가 없다면 "길이 조건은 통과했지만 내용은 사실상 비어있는" 데이터가 그대로 저장된다. `min_length`·`max_length` 같은 선언적 제약은 "글자 수"만 검사할 뿐, "의미 있는 내용인가"까지는 판단하지 못한다 — 이 둘의 역할 차이가 핵심이다.

### | model_validator로 여러 필드를 교차 검증하기 |

- `field_validator`는 필드 하나만 보고 판단한다. 하지만 "상태(status)가 DONE인데 하위 작업(sub_tasks) 중 미완료가 남아있으면 안 된다"는 규칙은 두 개 이상의 필드를 동시에 봐야 성립한다. `@model_validator(mode="after")`는 모든 필드가 각자의 검증을 통과해 객체가 거의 완성된 뒤, 객체 전체(`self`)를 보고 필드 간 관계를 검사한다.

```python
from pydantic import model_validator


class TaskCreate(BaseModel):
    title: str = Field(min_length=2, max_length=100)
    description: Optional[str] = None
    status: Literal["TODO", "DOING", "DONE"] = "TODO"
    sub_tasks: list[SubTask] = Field(default_factory=list)
    due_date: Optional[datetime] = None

    @field_validator("title")
    @classmethod
    def strip_title(cls, v: str) -> str:
        v = v.strip()
        if len(v) < 2:
            raise ValueError("할 일 제목은 공백 제거 후 최소 2자 이상이어야 합니다")
        return v

    @model_validator(mode="after")
    def check_done_requires_all_subtasks_completed(self):
        if self.status == "DONE":
            unfinished = [s for s in self.sub_tasks if not s.is_completed]
            if unfinished:
                raise ValueError("완료되지 않은 하위 작업이 있으면 DONE 상태로 저장할 수 없습니다")
        return self
```

### | 부분 수정과 exclude_unset |

- 수정 API는 클라이언트가 보낸 필드만 바꾸고 싶다. 그래서 `TaskUpdate`는 모든 필드를 `Optional`로 선언한다.

```python
class TaskUpdate(BaseModel):
    title: Optional[str] = None
    description: Optional[str] = None
    status: Optional[Literal["TODO", "DOING", "DONE"]] = None
    sub_tasks: Optional[list[SubTask]] = None
    due_date: Optional[datetime] = None

    @field_validator("title")
    @classmethod
    def strip_title(cls, v):
        if v is None:
            return v
        v = v.strip()
        if len(v) < 2:
            raise ValueError("할 일 제목은 공백 제거 후 최소 2자 이상이어야 합니다")
        return v
```

```python
from pydantic import ValidationError


@app.put("/tasks/{task_id}")
async def update_task(task_id: int, payload: TaskUpdate):
    if task_id not in task_db:
        raise HTTPException(status_code=404, detail="해당 ID의 작업을 찾을 수 없습니다")

    stored = task_db[task_id].model_dump()
    update_data = payload.model_dump(exclude_unset=True)  # 실제로 보낸 필드만 추출
    merged = {**stored, **update_data}

    try:
        validated = TaskCreate(**merged)  # 전체 비즈니스 규칙을 다시 교차 검증
    except ValidationError as e:
        raise HTTPException(status_code=400, detail=str(e))

    task_db[task_id] = validated
    return validated
```

- `exclude_unset=True`가 없다면 어떻게 될까. 클라이언트가 `{"status": "DONE"}`만 보내도, `payload.model_dump()`는 `title`·`description` 같은 나머지 필드까지 전부 Pydantic 기본값인 `None`으로 채워서 반환해버린다. 그 결과를 그대로 기존 데이터에 덮어쓰면, 클라이언트가 건드리지도 않은 필드까지 전부 `None`으로 날아가는 사고가 난다. `exclude_unset`은 "클라이언트가 실제로 전송한 키만" 골라내서, 전송하지 않은 필드는 기존 값을 그대로 보존하게 해준다.
- 여기서 `try/except`가 필요한 이유: `TaskUpdate`는 FastAPI가 요청을 받는 시점에 자동으로 검증하므로 실패하면 FastAPI가 알아서 422를 반환한다. 반면 병합(merge) 이후 `TaskCreate(**merged)`로 다시 검증하는 부분은 라우터 함수 안에서 직접 호출한 코드이기 때문에, Pydantic이 던지는 `ValidationError`를 수동으로 잡아 과제 요구사항대로 400으로 바꿔줘야 한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| Pydantic 모델 | Pydantic Model | 타입과 제약 조건을 필드에 선언적으로 붙여 데이터를 자동 검증·파싱하는 클래스 |
| 필드 검증기 | field_validator | 특정 필드 하나에 대해 커스텀 검증·가공 로직을 등록하는 데코레이터 |
| 모델 검증기 | model_validator(mode="after") | 모든 필드 검증이 끝난 뒤 객체 전체를 보고 필드 간 교차 규칙을 검사하는 데코레이터 |
| 리터럴 타입 | Literal | 특정 값들만 허용하도록 타입 범위를 제한하는 선언 |
| exclude_unset | - | 클라이언트가 실제로 전송한 필드만 추출하는 `model_dump()` 옵션 |
| ValidationError | - | Pydantic 모델 검증 실패 시 발생하는 예외 |

# PART 2. FastAPI 응답 모델 및 자동 문서화
### | response_model로 민감한 필드 차단하기 |

- 지금까지 다룬 `Task`/`TaskCreate`에는 저장을 위해 필요하지만 클라이언트에게 그대로 돌려주면 안 되는 내부 전용 정보(보안 해시 토큰, 관리자 편집 기록 등)가 함께 들어있을 수 있다. `response_model`은 라우터가 반환하는 객체를 "이 스키마로 다시 한 번 걸러서" 응답하게 만드는 출력 전용 필터다. 함수가 실제로 무엇을 반환하든, `response_model`에 선언되지 않은 필드는 응답 JSON에서 통째로 제거된다.
- `response_model`이 없다면 어떻게 될까. 라우터 함수가 반환하는 파이썬 객체(혹은 딕셔너리)가 가진 속성이 그대로, 하나도 거르지 않고 직렬화되어 클라이언트에게 나간다. 내부 로직을 위해 저장해둔 민감한 필드가 실수로 섞여 있다면 그대로 외부에 노출되는 보안 사고로 이어진다.

```python
class SubTaskResponse(BaseModel):
    title: str
    is_completed: bool


class TaskResponse(BaseModel):
    id: int
    title: str
    description: Optional[str] = None
    status: str
    sub_tasks: list[SubTaskResponse]  # 필터링된 하위 작업만 노출
    due_date: Optional[datetime] = None
```

```python
from typing import Generic, TypeVar

T = TypeVar("T")


class APIResponse(BaseModel, Generic[T]):
    success: bool
    data: Optional[T] = None
    error: Optional[str] = None


@app.get("/tasks/{task_id}", response_model=APIResponse[TaskResponse])
async def get_task(task_id: int):
    if task_id not in task_db:
        raise HTTPException(status_code=404, detail="해당 ID의 작업을 찾을 수 없습니다")
    return APIResponse(success=True, data=task_db[task_id])
```

**실행 결과**
```

Content-Type: application/json

{"success":true,
 "data":{"id":1,"title":"API 문서화","description":null,"status":"DONE",

                       {"title":"문서 검증","is_completed":true}],
```

(내부 저장 객체에 `security_hash` 같은 필드가 실제로 섞여 있어도, `TaskResponse`에 선언하지 않았으므로 응답에는 절대 나타나지 않는다.)

### | HTTPException과 responses로 에러까지 문서화하기 |

- `raise HTTPException(status_code=404, ...)`은 실제 동작(런타임)은 맞게 처리하지만, 그것만으로는 Swagger UI 문서에 "이 엔드포인트가 404도 반환할 수 있다"는 사실이 드러나지 않는다. 라우트 데코레이터의 `responses` 파라미터에 상태 코드별 스키마와 설명을 선언해야, 자동 생성 문서에도 이 가능성이 함께 기록된다.

```python
class CommonErrorResponse(BaseModel):
    error_code: str
    message: str
    timestamp: datetime


@app.put(
    "/tasks/{task_id}",
    response_model=APIResponse[TaskResponse],
    responses={
        400: {"model": CommonErrorResponse, "description": "하위 과제 미완료 등 업무 규칙 검증 실패 오류"},
        404: {"model": CommonErrorResponse, "description": "지정한 ID의 작업이 존재하지 않는 경우"},
    },
)
async def update_task(task_id: int, payload: TaskUpdate):
    if task_id not in task_db:
        raise HTTPException(status_code=404, detail="해당 ID의 작업을 찾을 수 없습니다")
    # ... 병합 및 검증 로직
```

**실행 결과** (브라우저로 `/docs` 접속 후 PUT 엔드포인트의 Responses 탭 확인)
```
200  Successful Response       APIResponse_TaskResponse_
400  하위 과제 미완료 등 업무 규칙 검증 실패 오류   CommonErrorResponse
404  지정한 ID의 작업이 존재하지 않는 경우         CommonErrorResponse
```

- `responses`가 없으면 어떻게 될까. 코드는 실제로 404·400을 던질 수 있는데도 자동 생성 문서에는 이 라우트가 마치 200 성공 응답만 돌려주는 것처럼 보인다. API를 사용하는 프론트엔드 개발자나 다른 팀은 "이 엔드포인트가 실패할 수도 있다"는 사실을 문서만으로는 알 방법이 없어, 에러 처리를 빠뜨린 채 연동 코드를 짜게 된다.

### | 왜 FastAPI 표준 예외 처리기를 써야 하나 |

- 과제에는 명시적인 안티패턴 금지 규칙이 있다: 400/404 에러 상황에서 `return APIResponse(success=False, error=...)`처럼 정상 응답을 직접 만들어 반환하는 방식은 금지하고, 반드시 `HTTPException`을 `raise`해야 한다.
- 왜 중요한가. `return`으로 직접 응답 객체를 만들면 HTTP 상태 코드는 항상 200으로 나간다 — 바디(body) 안의 `success: false`를 직접 파싱해야만 실패를 알 수 있는 구조가 되어버린다. 이러면 브라우저 네트워크 로그, 모니터링 툴, 캐싱 레이어처럼 HTTP 상태 코드만 보고 성공/실패를 판단하는 모든 인프라가 무력화된다. `raise HTTPException`을 쓰면 FastAPI의 표준 예외 처리기가 상태 코드 자체를 실패로 설정해 응답하고, 앞서 `responses`에 선언한 문서화와도 일관성 있게 맞물린다.

### | 제네릭 공통 응답 포맷으로 전체 라우터 통일하기 |

```python
@app.get("/tasks", response_model=APIResponse[list[TaskResponse]])
async def list_tasks():
    dataset = list(task_db.values())
    return APIResponse(success=True, data=dataset)
```

**실행 결과**
```
$ curl -i -X GET "http://127.0.0.1:8000/tasks"
HTTP/1.1 200 OK
Content-Type: application/json

{"success":true,
 "data":[{"id":1,"title":"API 문서화","description":null,"status":"DONE",
          "sub_tasks":[{"title":"스키마 설계","is_completed":true},
                        {"title":"문서 검증","is_completed":true}],
          "due_date":null}],
 "error":null}
```

- 제네릭(`Generic[T]`)이 없다면 `TaskListResponse`, `TaskSingleResponse`처럼 `data` 타입만 다르고 나머지(`success`, `error`)는 완전히 똑같은 응답 스키마를 엔드포인트 수만큼 따로 선언해야 한다. `APIResponse[T]` 하나로 모든 엔드포인트의 응답 뼈대(성공 여부·데이터·에러)를 통일하면서, `data` 자리에 들어갈 타입만 `[TaskResponse]`, `[list[TaskResponse]]`처럼 그때그때 바꿔 끼울 수 있다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| response_model | - | 라우터가 반환하는 값을 지정한 스키마로 다시 필터링해 응답하는 FastAPI 옵션 |
| 제네릭 | Generic | 타입을 매개변수로 받아 하나의 모델을 여러 데이터 타입에 재사용하는 기능 |
| responses(파라미터) | - | 라우트 데코레이터에서 상태 코드별 응답 스키마·설명을 문서에 선언하는 옵션 |
| HTTPException | - | 발생 즉시 FastAPI 표준 예외 처리기가 해당 상태 코드로 응답을 종료시키는 예외 클래스 |
| 공통 응답 포맷 | Envelope Pattern | success/data/error처럼 모든 API 응답이 공유하는 일관된 바깥 구조 |

Q1. Pydantic v2에서 `@model_validator(mode="after")`의 작동 특징으로 옳은 것은 무엇입니까?

[ 보기 ]

a. 데이터 타입 변환 이전의 가공되지 않은 JSON 원본 데이터를 처리한다.

b. 모든 필드의 기본 타입 검사와 @field_validator가 끝난 후, 완성된 인스턴스(self)를 대상으로 다중 필드 간 검증을 수행한다.

c. FastAPI 라우터가 가동되기 전 단계에서 작동하여 서버 스레드를 늘려준다.

d. exclude_unset 옵션을 강제로 비활성화시킨다.

내 제출 답안 : b. 모든 필드의 기본 타입 검사와 @field_validator가 끝난 후, 완성된 인스턴스(self)를 대상으로 다중 필드 간 검증을 수행한다. (정답 ✅)

[ 정답 ] b.

-> mode="after"는 개별 필드 검증과 타입 변환이 모두 끝난 뒤, 완성된 임시 인스턴스(self)를 기준으로 여러 필드를 비교하는 복합 검증에 사용된다. 원본 가공 전 데이터를 다루는 것은 mode="before"의 특징이며, 나머지 선지는 교안에 없는 내용이다.

Q3. FastAPI의 쿼리스트링 처리와 관련하여 다음 코드에 대한 설명으로 옳은 것은 무엇입니까?

```python
status_filter: Optional[str] = Query(None, alias="status", description="...")
```

[ 보기 ]

a. 클라이언트는 반드시 status_filter라는 이름으로 쿼리 파라미터를 보내야 한다.

b. alias 옵션 덕분에 클라이언트는 URL에 ?status=AVAILABLE 형태로 값을 보내고, 서버 내부에서는 status_filter 변수명으로 접근한다.

c. Optional이 지정되었으므로 값을 생략하면 서버에서 422 오류가 발생한다.

d. Query 함수는 Body와 달리 description, alias 같은 옵션을 지원하지 않는다.

내 제출 답안 : b. alias 옵션 덕분에 클라이언트는 URL에 ?status=AVAILABLE 형태로 값을 보내고, 서버 내부에서는 status_filter 변수명으로 접근한다. (정답 ✅)

[ 정답 ] b.

-> alias는 외부에 노출되는 쿼리 파라미터 이름과 내부 변수명을 다르게 지정할 수 있게 해준다. Optional과 기본값 None이 지정되어 있으므로 값을 생략해도 오류가 나지 않으며, Query는 Body와 동일하게 description, alias 등의 옵션을 지원한다.

Q5. `class APIResponse(BaseModel, Generic[T]):` 와 같이 다중 상속을 선언했을 때, 두 부모 클래스에 동일한 이름의 기능이 존재한다면 실행 우선순위는 어떻게 결정되는가?

[ 보기 ]

a. 클래스 이름의 알파벳 오름차순으로 결정된다.

b. 괄호 안에 나중에(오른쪽에) 적힌 Generic[T]가 항상 우선권을 가진다.

c. 괄호 안에 먼저(왼쪽에) 적힌 BaseModel이 우선권을 가지며, 이를 '왼쪽 우선 법칙(MRO)'이라 한다.

d. 파이썬 인터프리터가 실행할 때마다 무작위로 선택한다.

내 제출 답안 : c. 괄호 안에 먼저(왼쪽에) 적힌 BaseModel이 우선권을 가지며, 이를 '왼쪽 우선 법칙(MRO)'이라 한다. (정답 ✅)

[ 정답 ] c.
