# PART 1. 매개변수와 반환 타입 명세 (3장 1강)

### | 왜 함수에 타입을 붙여야 하나 |

- 자바스크립트에서는 함수를 호출할 때 필요한 값을 누락하거나 다른 형태의 값을 전달해도 코드가 그대로 실행된다. 문제는 실행 중(런타임)에야 비로소 에러가 터진다는 점이다. 타입스크립트는 함수가 받을 값과 반환할 값의 타입을 미리 지정해서, 코드를 돌리기 전(컴파일 시점)에 이런 실수를 잡아낸다.

| 매개변수 타입 | 반환 타입 |
| --- | --- |
| 함수가 전달받는 변수 이름 뒤에 `: 타입` 형태로 작성 | 매개변수 소괄호 `()`의 바로 우측에 `: 타입` 형태로 작성 |

```typescript
function addPrice(base: number, tax: number): number {
    // base, tax는 둘 다 number로 고정됨 — 문자열이 들어오면 이 자리에서 바로 컴파일 에러
    return base + tax;
}

console.log("합계:", addPrice(10000, 1000));
```

**실행 결과**
```
합계: 11000
```

### | 선택적 매개변수 (Optional Parameter) |

- 상황에 따라 값이 입력되지 않을 수도 있는 자리에는 변수명 뒤에 물음표(`?`)를 붙인다. 값이 전달되지 않으면 내부적으로 `undefined`를 가진다.

```typescript
function processPayment(amount: number, couponCode?: string): void {
    console.log(`결제 요청 금액: ${amount}원`);
    if (couponCode) {
        console.log(`적용된 쿠폰 번호: ${couponCode}`);
    } else {
        console.log("적용된 쿠폰이 없습니다.");
    }
}

processPayment(12000);
processPayment(12000, "WELCOME2026");
```

**실행 결과**
```
결제 요청 금액: 12000원
적용된 쿠폰이 없습니다.
결제 요청 금액: 12000원
적용된 쿠폰 번호: WELCOME2026
```

- `?`가 없다면 어떻게 될까. `couponCode: string`으로 고정해버리면, 쿠폰 없이 `processPayment(12000)`만 호출하는 모든 코드에서 "인자가 부족하다"는 컴파일 에러가 뜬다. 즉 쿠폰이 있을 수도 없을 수도 있는 현실을 반영하려면 `?`가 꼭 필요하다 — 없으면 쿠폰 없는 결제 한 건마다 매번 더미 값(`""` 같은)을 억지로 채워 넣어야 하는 억지 코드가 된다.

### | 선택적 매개변수는 왜 꼭 뒤에만 와야 하나 |

```typescript
// 아래처럼 선택적 매개변수 뒤에 필수 매개변수를 두면 컴파일 에러가 발생한다.
// function invalid(couponCode?: string, amount: number) {}
// Error: A required parameter cannot follow an optional parameter.
```

- 함수를 호출할 때 인자는 **위치(순서)** 로 매칭된다. 만약 선택적 매개변수가 앞에 있고 그 값을 생략한 채 호출하면, 컴파일러 입장에서는 그다음에 적은 값이 생략된 자리를 채우는 것인지 그다음 자리의 값인지 구분할 방법이 없다. 그래서 TypeScript는 아예 "선택적 매개변수 뒤에는 필수 매개변수를 둘 수 없다"는 규칙으로 혼동 자체를 차단한다.

### | 가변 인자 (Rest Parameter) |

- 매개변수 개수가 고정되지 않고 여러 개가 들어올 때 사용하며, 항상 배열 타입(`type[]`)으로 정의한다.

```typescript
function aggregateScores(...scores: number[]): number {
    // 가변 인자 scores는 내부적으로 숫자 배열(number[]) 형태로 처리된다.
    return scores.reduce((total, current) => total + current, 0);
}

const roundOne = aggregateScores(100, 200, 150);
const roundTwo = aggregateScores(80, 95);

console.log(`1라운드 총점: ${roundOne}`);
console.log(`2라운드 총점: ${roundTwo}`);
```

**실행 결과**
```
1라운드 총점: 450
2라운드 총점: 175
```

- 가변 인자가 없다면 어떻게 될까. 인자가 2개일 때, 3개일 때, 5개일 때마다 `aggregateScores2(a, b)`, `aggregateScores3(a, b, c)`처럼 매개변수 개수별로 함수를 따로 만들어야 하거나, 타입을 포기하고 `any[]`로 받아야 한다. 가변 인자는 "개수는 모르지만 전부 number"라는 사실만은 타입으로 보장해주는 절충안이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 매개변수 | Parameter | 함수가 실행될 때 외부로부터 값을 전달받기 위해 정의하는 변수 |
| 선택적 매개변수 | Optional Parameter | 값을 필수로 채우지 않아도 오류가 발생하지 않도록 허용하는 속성 |
| 가변 인자 | Rest Parameter | 정해지지 않은 개수의 인자들을 하나의 배열로 모아서 받아내는 문법 |
| 반환값 | Return Value | 함수가 연산을 마친 후 호출된 곳으로 돌려주는 결과 데이터 |

# PART 2. 함수 표현식과 콜백 타입 정의 (3장 2강)

### | 콜백 함수란 무엇이고 왜 필요한가 |

- **콜백 함수(Callback Function)** 란 특정 조건이나 작업이 완료된 시점에 실행되도록, 다른 함수의 인자(Parameter)로 전달하는 함수다. 자바스크립트에서는 함수도 변수에 담거나 다른 함수에 넘길 수 있는 값(일급 객체)이기 때문에 가능한 문법이다.
- 왜 필요한가: "언제 이 코드를 실행할지"를 호출하는 쪽이 아니라 **받는 쪽(고차 함수)** 이 결정하게 만들고 싶을 때 쓴다. 배열의 `map`을 예로 들면, "배열을 처음부터 끝까지 순회한다"는 로직은 `map` 자신이 이미 갖고 있다. 하지만 "각 요소를 어떻게 바꿀지"는 모른다 — 그 변환 로직만 콜백으로 밖에서 건네받아서, 내부적으로 적절한 시점(각 요소를 순회하는 매 순간)에 실행한다.
- 콜백이 없다면 어떻게 될까: `map`처럼 범용으로 쓰이는 고차 함수를 아예 만들 수 없다. "점수를 5점씩 올리는 함수", "점수를 2배로 만드는 함수"처럼 요구사항이 바뀔 때마다 배열 순회 로직 전체를 포함한 함수를 매번 통째로 새로 작성해야 한다 — 똑같은 반복문 코드가 계속 중복된다.
- 동작 원리 요약: 콜백은 전달되는 시점에는 실행되지 않는다. 함수를 넘겨받은 쪽(고차 함수)이 자신의 로직 안에서 `콜백이름(인자)` 형태로 직접 **호출**하는 순간에야 비로소 실행된다. "지금 당장 해줘"가 아니라 "이 함수를 들고 있다가, 때가 되면 네가 알아서 실행해줘"라는 위임이다.

### | 1.1 인라인 함수 타입 표현식 |

- 변수 선언 자리에 `(매개변수: 타입) => 반환타입`을 직접 작성하는 문법이다. 별도로 타입에 이름을 붙이지 않고, 코드가 쓰이는 바로 그 위치에 함수의 형태를 명시한다.

```typescript
const VIPCalc: (amount: number) => number = (amount) => {
    return amount * 0.1; // 10% 적립
};

const normalCalc: (amount: number) => number = (amount) => {
    return amount * 0.05; // 5% 적립
};

console.log("VIP 고객 적립금:", VIPCalc(30000));
console.log("일반 고객 적립금:", normalCalc(30000));
```

**실행 결과**
```
VIP 고객 적립금: 3000
일반 고객 적립금: 1500
```

### | 1.2 인라인 호출 시그니처 |

- 중괄호(`{}`) 내부에 `(매개변수: 타입): 반환타입;` 형태로 함수의 구조를 정의하는 문법이다. 화살표(`=>`) 대신 콜론(`:`)을 쓰며, 함수의 형태를 객체의 속성처럼 상세히 묘사할 때 활용한다.

```typescript
const calculateTax: { (price: number): number } = (price) => {
    return price * 0.1; // 10% 부가가치세 계산
};

console.log("계산된 세금 금액:", calculateTax(50000));
```

**실행 결과**
```
계산된 세금 금액: 5000
```

- 결과만 보면 1.1과 1.2는 동일하게 동작한다. 차이는 표기 스타일이다 — 호출 시그니처 방식은 뒤에서 배울 인터페이스 안에 함수 속성을 정의할 때 자주 쓰이는 형태라서 미리 익혀두는 것이다.

### | 2.1 배열 map 과정에서의 콜백 타입 지정 |

- 다른 함수를 매개변수로 받아 내부에서 실행하는 함수를 **고차 함수**라고 한다. 고차 함수를 정의할 때 매개변수 자리에 전달될 콜백 함수의 타입을 명확히 지정해야, 컴파일 시점에 "엉뚱한 콜백을 넘기는 실수"를 막을 수 있다.

```typescript
function processScores(scores: number[], transformer: (score: number) => number): number[] {
    const result: number[] = [];

    for (let i = 0; i < scores.length; i = i + 1) {
        // 전달받은 콜백 함수(transformer)를 실행하여 결과를 배열에 추가
        result.push(transformer(scores[i]));
    }

    return result;
}

const currentScores = [80, 75, 95];
const updatedScores = processScores(currentScores, (score) => score + 5);

console.log("최종 변경 점수 배열:", updatedScores);
```

**실행 결과**
```
최종 변경 점수 배열: [ 85, 80, 100 ]
```

- `transformer: (score: number) => number`라고 타입을 박아두지 않았다면 어떻게 될까. `(score) => score.toUpperCase()`처럼 숫자에는 없는 메서드를 쓰는 콜백을 실수로 넘겨도 컴파일 단계에서는 아무 문제 없이 통과해버린다. 그러다 실제로 함수가 실행되는 순간 "`toUpperCase`는 함수가 아닙니다" 같은 런타임 에러가 터지거나, 최악의 경우 에러 없이 `NaN`이 결과 배열에 섞여 들어가 버그의 원인을 찾기 어려워진다.

### | 2.2 클릭 이벤트 시스템과 콜백 흐름 |

```typescript
function simulateClick(onClick: (event: { buttonId: string; time: number }) => void) {
    console.log("이벤트 발생 시뮬레이션 시작");

    // 구조에 맞춰 데이터를 구성한 후 콜백 함수를 실행한다.
    onClick({
        buttonId: "main-save-btn",
        time: Date.now()
    });
}

simulateClick((e) => {
    console.log(`버튼 ID: ${e.buttonId}, 발생 시간: ${e.time}`);
});
```

**실행 결과** (time 값은 실행할 때마다 달라지는 타임스탬프이므로 예시 값)
```
이벤트 발생 시뮬레이션 시작
버튼 ID: main-save-btn, 발생 시간: 1759900000000
```

| 단계 | 실제로 벌어지는 일 |
| --- | --- |
| ① `simulateClick(...)` 호출 | 화살표 함수가 `onClick` 자리에 "실행되지 않은 채" 전달만 됨 |
| ② 함수 내부 진행 | "이벤트 발생 시뮬레이션 시작" 출력 후, 클릭에 해당하는 데이터 객체를 구성 |
| ③ 콜백 실행 시점 | `onClick(event)`로, 전달받아 들고 있던 함수를 데이터와 함께 직접 호출 |
| ④ 결과 | 바깥에서 넘겼던 코드가 이 시점에야 비로소 실행되어 메시지 출력 |

- 이 구조는 [10/1 TIL](../JS/2026-10-01.md)에서 다룬 `addEventListener`의 원리와 완전히 같다. `addEventListener("click", handler)`로 넘긴 `handler` 함수도 그 즉시 실행되는 게 아니라 브라우저에 "등록"만 되고, 실제 클릭이 발생하는 순간 브라우저가 내부에서 호출해준다. 오늘 배운 콜백 함수 타입 정의는, 그 `handler` 자리에 어떤 형태의 함수가 들어와야 하는지를 컴파일 시점에 보장해주는 안전장치인 셈이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 인라인 타입 선언 | Inline Type Declaration | 별칭이나 인터페이스 없이 코드가 작성되는 위치에 직접 데이터 구조를 명시하는 방식 |
| 함수 타입 표현식 | Function Type Expression | 함수의 규격을 화살표 문법으로 표현하는 타입 선언 방식 |
| 호출 시그니처 | Call Signature | 함수의 입력·출력 타입을 중괄호 구조 내에 명시하는 방법 |
| 콜백 함수 | Callback Function | 다른 함수의 매개변수로 전달되어 내부 로직에 의해 실행되는 함수 |
| 고차 함수 | Higher-Order Function | 매개변수로 다른 함수를 입력받거나 함수를 결과로 반환하는 함수 |

# PART 3. 타입 별칭과 인터페이스 및 readonly (4장 1강)

### | 타입 별칭(Type Alias)으로 객체 정의하기 |

- `type` 키워드로 기존 타입에 새 이름을 붙이는 방식이다. 객체뿐 아니라 문자열·숫자·배열 등 모든 타입을 가리킬 수 있다.

```typescript
type UserType = {
    id: number;
    name: string;
    email: string;
};

const studentA: UserType = {
    id: 20261101,
    name: "이영희",
    email: "younghee@univ.ac.kr"
};

console.log(studentA.name);
```

**실행 결과**
```
이영희
```

### | 인터페이스(Interface)로 객체 정의하기 |

- `interface` 키워드는 오직 객체의 구조만 정의하기 위해 만들어진 문법이다. 상속·확장성이 뛰어나 React 등에서 데이터를 주고받을 때 자주 쓰인다.

```typescript
interface ProductInterface {
    code: string;
    price: number;
    brand: string;
}

const monitor: ProductInterface = {
    code: "MON-32",
    price: 350000,
    brand: "테크기어"
};

console.log(monitor.price);
```

**실행 결과**
```
350000
```

### | 타입 별칭 vs 인터페이스 |

| 구분 | 인터페이스(interface) | 타입 별칭(type alias) |
| --- | --- | --- |
| 객체 구조 정의 | ✅ 가능 | ✅ 가능 |
| 구조 확장 | ✅ `extends` | ✅ 인터섹션(`&`) |
| 클래스 구현(`implements`) | ✅ 가능 | ✅ 가능 |
| 선언 병합 | ✅ 가능 | ❌ 불가능 |
| 유니온/인터섹션 복합 타입 | ❌ 불가능 | ✅ `|`, `&` 가능 |
| 함수 타입 정의 | ❌ 불가능 | ✅ 가능 |
| 원시값 등 객체 이외 표현 | ❌ 불가능 | ✅ 가능 |
| typeof로 타입 추출 | ❌ 불가능 | ✅ 가능 |

### | readonly로 데이터 훼손 방지하기 |

- 객체 생성 후 특정 속성 값을 수정하지 못하도록 '읽기 전용'으로 잠그는 키워드다. 계좌번호, 결제 금액, 고유 ID처럼 시스템 내에서 절대 바뀌면 안 되는 데이터를 보호할 때 쓴다.

```typescript
interface Account {
    readonly accountId: string; // 읽기 전용 — 생성 후 변경 불가
    owner: string;
    balance: number;
}

const myAccount: Account = {
    accountId: "110-123-456789",
    owner: "김철수",
    balance: 50000
};

myAccount.balance = 55000; // 일반 속성은 정상 수정 가능

// myAccount.accountId = "220-987-654321";
// [컴파일 에러] Cannot assign to 'accountId' because it is a read-only property.

console.log(myAccount.balance, myAccount.accountId);
```

**실행 결과**
```
55000 110-123-456789
```

- `readonly`가 없었다면 어떻게 될까. `accountId`가 일반 속성이었다면 코드 어딘가에서 실수로 `myAccount.accountId = someVar`처럼 재할당해도 컴파일러가 전혀 막아주지 못한다. 계좌번호나 주문 ID처럼 "한 번 정해지면 절대 바뀌면 안 되는 값"이 조용히 바뀌어버리는 사고가 터지고, 그 원인을 찾기도 매우 어렵다. `readonly`는 "이 속성은 애초에 재할당 대상이 아니다"를 컴파일 시점에 강제하는 안전장치다.

### | 선택적 속성(?)으로 유연한 객체 설계하기 |

```typescript
type Profile = {
    userId: string;
    nickname: string;
    bio?: string; // 선택적 속성 — 값이 없어도 에러가 발생하지 않음
};

const userWithBio: Profile = {
    userId: "user01",
    nickname: "코딩왕",
    bio: "안녕하세요! 프론트엔드 개발자입니다."
};

const userWithoutBio: Profile = {
    userId: "user02",
    nickname: "새내기"
};

console.log(userWithBio.nickname);
console.log(userWithoutBio.nickname);
```

**실행 결과**
```
코딩왕
새내기
```

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 타입 별칭 | Type Alias | `type` 키워드로 복잡한 타입에 이름을 붙이는 방법 |
| 인터페이스 | Interface | `interface` 키워드로 객체의 형태를 정의하는 문법 |
| 선언 병합 | Declaration Merging | 같은 이름의 인터페이스 선언을 하나로 자동 합치는 기능 |
| 읽기 전용 속성 | Readonly Property | `readonly` 키워드로 데이터의 임의 수정을 막는 속성 |

# PART 4. 인덱스 시그니처와 인터페이스 확장 (4장 2강)

### | 동적 속성을 다루는 인덱스 시그니처 |

- 객체에 들어올 속성 이름을 미리 확정할 수 없을 때 `[key: T]: V` 형태로 규격을 지정하는 문법이다. Key 자리에는 `string`, `number`, `symbol`, 그리고 특정 패턴의 문자열인 템플릿 리터럴 타입을 쓸 수 있다. 단, **유니온 타입(`'id' | 'name'`)은 Key 자리에 직접 쓸 수 없다** — 특정 키로만 제한하려면 `Record<K, T>`나 맵드 타입을 써야 한다.

```typescript
interface SubjectScores {
  [subjectName: string]: number; // 속성 이름은 string, 값은 number
}

const studentScores: SubjectScores = {
  korean: 90,
  math: 85
};
studentScores.english = 95; // 동적 속성 추가 가능

type AllowedKeys = "id" | "name";
// interface Invalid { [key: AllowedKeys]: string } // 에러: 유니온 직접 사용 불가
const explicitUser: Record<AllowedKeys, string> = {
  id: "101",
  name: "홍길동"
};

console.log("점수 객체:", studentScores);
console.log("제한된 키 객체:", explicitUser);
```

**실행 결과**
```
점수 객체: { korean: 90, math: 85, english: 95 }
제한된 키 객체: { id: '101', name: '홍길동' }
```

- 인덱스 시그니처가 없다면 어떻게 될까. `korean`, `math`, `english`처럼 과목이 몇 개가 될지 모르는 객체는 `interface SubjectScores { korean: number; math: number; }`처럼 속성을 하나하나 다 미리 적어둬야 한다. 새로운 과목이 생길 때마다 인터페이스 정의 자체를 고쳐야 하니 동적인 데이터를 다루기 불가능하다.

### | extends 키워드를 활용한 인터페이스 상속 |

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
}

interface Electronics extends Product {
  warrantyMonths: number; // 보증 기간(월) 속성 추가
}

const myLaptop: Electronics = {
  id: 101,
  name: "노트북",
  price: 1500000,
  warrantyMonths: 24
};

console.log("전자제품 정보:", myLaptop);
```

**실행 결과**
```
전자제품 정보: { id: 101, name: '노트북', price: 1500000, warrantyMonths: 24 }
```

- `extends`가 없다면 `Electronics` 인터페이스를 만들 때 `Product`에 있던 `id`, `name`, `price`를 전부 다시 베껴 써야 한다. 나중에 `Product`에 속성을 하나 추가하면 그걸 상속받는 모든 인터페이스에 일일이 똑같이 추가해야 하는 중복·누락 위험이 생긴다.

### | 자동 선언 병합 (Declaration Merging) |

```typescript
interface User {
  id: number;
  name: string;
}

// 동일한 이름으로 다시 선언 — 자동으로 하나로 합쳐짐
interface User {
  email: string;
}

const userAccount: User = {
  id: 1,
  name: "김철수",
  email: "chulsoo@example.com"
};

console.log("병합된 사용자 계정:", userAccount);
```

**실행 결과**
```
병합된 사용자 계정: { id: 1, name: '김철수', email: 'chulsoo@example.com' }
```

- 이 기능은 인터페이스만 지원하고 타입 별칭은 지원하지 않는다(PART 3의 비교표 참고). 같은 이름으로 `type User = {...}`를 두 번 선언하면 "중복 선언" 에러가 난다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 인덱스 시그니처 | Index Signature | 속성 이름을 명시하지 않고 키·값의 타입만 지정하는 선언 방식 |
| 템플릿 리터럴 타입 | Template Literal Types | 특정 패턴의 문자열만 키로 허용하는 기능 |
| 인터페이스 확장 | Interface Extension | `extends`로 기존 인터페이스를 상속받아 재사용하는 방식 |
| 선언 병합 | Declaration Merging | 같은 이름의 인터페이스가 하나로 자동 합쳐지는 기능 |

# PART 5. Union, Intersection과 리터럴 타입 (5장 1강)

### | 유니온 타입(Union Type) — 다중 타입 허용하기 |

- 바(`|`) 기호로 기재된 타입 중 하나를 만족하면 허용하는 타입 구조다.

```typescript
let userId: string | number;

userId = "user_1004";
userId = 20260721;

console.log("현재 사용자 ID:", userId);
```

**실행 결과**
```
현재 사용자 ID: 20260721
```

- 서로 다른 객체 타입을 유니온으로 묶으면, 컴파일러는 **모든 타입에 공통으로 존재하는 속성만** 접근을 허용한다.

```typescript
interface CardPayment {
  amount: number;
  cardNumber: string; // CardPayment 전용
}

interface BankTransfer {
  amount: number;
  bankCode: string; // BankTransfer 전용
}

type PaymentMethod = CardPayment | BankTransfer;

function processPayment(payment: PaymentMethod): void {
  console.log("결제 요청 금액:", payment.amount); // 공통 속성이라 접근 가능

  // console.log(payment.cardNumber);
  // 에러: Property 'cardNumber' does not exist on type 'BankTransfer'.
}

const myPayment: CardPayment = {
  amount: 50000,
  cardNumber: "1234-5678-9012-3456"
};

processPayment(myPayment);
```

**실행 결과**
```
결제 요청 금액: 50000
```

- 왜 공통 속성만 허용할까. `payment`가 실제로는 `CardPayment`인지 `BankTransfer`인지 컴파일 시점에는 확정할 수 없다. 만약 `cardNumber` 접근을 허용해버리면, 실제로 `BankTransfer` 객체가 들어왔을 때 `payment.cardNumber`는 `undefined`가 되어 런타임 에러로 이어질 수 있다. 공통 속성만 허용하는 제약이 이런 사고를 사전에 차단한다. (각 타입 고유 속성에 안전하게 접근하려면 PART 6에서 배울 "타입 가드"가 필요하다.)

### | 인터섹션 타입(Intersection Type) — 복합 타입 합성하기 |

- 앰퍼샌드(`&`)로 지정된 **모든** 타입의 속성을 동시에 만족하도록 합성하는 타입이다.

```typescript
type UserProfile = {
  name: string;
  email: string;
};

type UserPermissions = {
  adminLevel: number;
};

type SuperAdmin = UserProfile & UserPermissions;

const adminUser: SuperAdmin = {
  name: "김철수",
  email: "admin@company.com",
  adminLevel: 1
};

console.log("관리자 이름:", adminUser.name);
console.log("관리자 등급:", adminUser.adminLevel);
```

**실행 결과**
```
관리자 이름: 김철수
관리자 등급: 1
```

- 결합되는 속성 중 하나라도 빠뜨리면 컴파일 에러가 난다. 또한 `string & number`처럼 양립할 수 없는 원시 타입끼리 결합하면 어떤 값도 할당할 수 없는 `never` 타입이 되어버린다 — "두 조건을 동시에 만족하는 값은 존재하지 않는다"는 뜻을 타입으로 표현한 것이다.

### | 리터럴 타입(Literal Type) — 특정 값으로 범위 제한하기 |

- `string`이나 `number` 타입의 전체 범위 대신, 지정된 값만 허용하는 타입이다.

```typescript
type Direction = "UP" | "DOWN" | "LEFT" | "RIGHT";

let moveDirection: Direction;
moveDirection = "UP";

// moveDirection = "FORWARD";
// 에러: Type '"FORWARD"'는 'Direction' 타입에 할당할 수 없습니다.

console.log("이동 방향:", moveDirection);
```

**실행 결과**
```
이동 방향: UP
```

- 그냥 `string`으로 선언했다면 어떻게 될까. `"forward"`, `"Up"`, `"업"`처럼 오타나 규칙에 안 맞는 문자열이 들어와도 컴파일러가 전혀 막지 못한다. 리터럴 타입은 "이 변수에 들어올 수 있는 값은 이 네 가지뿐"이라는 업무 규칙 자체를 타입 시스템에 새겨 넣는 방법이다.

### | 리터럴 + 유니온 + 인터섹션 종합 모델링 |

```typescript
type OrderStatus = "PENDING" | "SHIPPED" | "DELIVERED";

interface BaseOrder {
  orderId: string;
  totalAmount: number;
}

type DetailedOrder = BaseOrder & {
  status: OrderStatus;
};

const currentOrder: DetailedOrder = {
  orderId: "ORD-2026-001",
  totalAmount: 35000,
  status: "SHIPPED"
};

console.log(`주문 번호 ${currentOrder.orderId}의 현재 상태: ${currentOrder.status}`);
```

**실행 결과**
```
주문 번호 ORD-2026-001의 현재 상태: SHIPPED
```

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 유니온 타입 | Union Type | `|` 연산자로 여러 타입 중 하나를 허용하는 방식 |
| 인터섹션 타입 | Intersection Type | `&` 연산자로 복수 타입의 속성을 결합하는 방식 |
| 리터럴 타입 | Literal Type | 특정 값 자체를 타입으로 지정해 입력 범위를 제한하는 방식 |
| 타입 합성 | Type Composition | 기존 타입을 결합해 새로운 타입 구조를 정의하는 과정 |

# PART 6. 타입 가드와 서로소 판별 유니온 (5장 2강)

### | 왜 타입 가드가 필요한가 |

- PART 5에서 배운 유니온 타입은 공통 속성만 접근을 허용한다는 제약이 있었다. `CardPayment | BankTransfer`처럼 묶인 객체에서 `cardNumber`처럼 한쪽에만 있는 속성에 안전하게 접근하려면, 지금 이 값이 실제로 둘 중 어떤 타입인지 **조건문으로 먼저 확인**해야 한다. 이 확인 구문을 **타입 가드(Type Guard)** 라고 한다. 타입 가드가 없다면 유니온으로 묶인 값의 전용 속성에는 영원히 접근할 방법이 없다.

### | typeof 연산자로 원시 타입 좁히기 |

- 넓은 범위의 유니온 타입을 조건문 내부에서 더 구체적인 타입으로 제한하는 과정을 **타입 좁히기(Type Narrowing)** 라고 한다. `typeof`는 자바스크립트 런타임에서 피연산자의 원시 타입 정보를 문자열로 반환하는 연산자다.

```typescript
function processInput(value: string | number) {
    if (typeof value === "string") {
        // 이 블록 안에서 value는 string으로 좁혀짐
        console.log(`문자열 길이: ${value.length}`);
    } else {
        // 이 블록 안에서 value는 number로 좁혀짐
        console.log(`10을 더한 값: ${value + 10}`);
    }
}

processInput("TypeScript");
processInput(20);
```

**실행 결과**
```
문자열 길이: 10
10을 더한 값: 30
```

### | in 연산자와 instanceof로 객체 타입 좁히기 |

- `in`은 객체 내부에 특정 속성 이름이 존재하는지 확인하고, `instanceof`는 객체가 특정 클래스의 인스턴스인지 확인한다.

```typescript
type Admin = { name: string; privileges: string[] };
type User = { name: string; startDate: Date };

function printUserInfo(account: Admin | User) {
    console.log(`이름: ${account.name}`);

    if ("privileges" in account) {
        // Admin 타입으로 좁혀짐
        console.log(`권한 목록: ${account.privileges.join(", ")}`);
    }

    if ("startDate" in account) {
        // User 타입으로 좁혀짐
        console.log(`가입일: ${account.startDate.toISOString()}`);
    }
}

class Car {
    drive() {
        console.log("운전을 시작합니다.");
    }
}

class Truck {
    drive() {
        console.log("트럭을 운전합니다.");
    }
    loadCargo(amount: number) {
        console.log(`${amount}kg의 짐을 실었습니다.`);
    }
}

type Vehicle = Car | Truck;

function useVehicle(vehicle: Vehicle) {
    vehicle.drive();

    if (vehicle instanceof Truck) {
        // Truck 타입으로 좁혀져 loadCargo 호출 가능
        vehicle.loadCargo(1000);
    }
}

const myTruck = new Truck();
useVehicle(myTruck);
```

**실행 결과**
```
트럭을 운전합니다.
1000kg의 짐을 실었습니다.
```

- `instanceof` 검사가 없다면 어떻게 될까. `vehicle.loadCargo(1000)`를 조건 없이 그냥 호출하면, `Vehicle` 타입에 `Car`가 들어올 가능성도 있으므로 "`Car` 타입에는 `loadCargo`가 없다"는 컴파일 에러가 발생한다. `instanceof`로 좁혀야만 "지금 이 값은 확실히 `Truck`이다"라는 사실이 컴파일러에게 증명된다.

### | 서로소 판별 유니온(Discriminated Union) |

- 객체 타입마다 공통된 리터럴 태그 속성을 부여해서, 조건문에서 타입을 명확히 구분할 수 있도록 만드는 설계 패턴이다. 이 공통 태그를 **판별자(Discriminant)** 라고 한다.

```typescript
type LoadingState = {
    status: "loading";
};

type SuccessState = {
    status: "success";
    data: string[];
};

type ErrorState = {
    status: "error";
    errorMessage: string;
};

type NetworkState = LoadingState | SuccessState | ErrorState;

function renderNetworkState(state: NetworkState) {
    switch (state.status) {
        case "loading":
            console.log("로딩 중입니다.");
            break;
        case "success":
            // status가 "success"로 확정된 블록이라 data 속성 접근 가능
            console.log(`데이터 로드 완료: ${state.data.length}개`);
            break;
        case "error":
            // status가 "error"로 확정된 블록이라 errorMessage 속성 접근 가능
            console.log(`오류 발생: ${state.errorMessage}`);
            break;
    }
}

const responseSuccess: SuccessState = {
    status: "success",
    data: ["상품 A", "상품 B", "상품 C"]
};

const responseError: ErrorState = {
    status: "error",
    errorMessage: "네트워크 연결 오류"
};

renderNetworkState(responseSuccess);
renderNetworkState(responseError);
```

**실행 결과**
```
데이터 로드 완료: 3개
오류 발생: 네트워크 연결 오류
```

- 판별자(`status`)가 없다면 어떻게 될까. `in` 연산자로 `"data" in state`처럼 속성 존재 여부를 매번 확인해야 하고, 상태가 늘어날수록 조건문이 점점 복잡해진다. 공통 리터럴 태그 하나만 심어두면 `switch`문 하나로 모든 상태를 깔끔하게 분기할 수 있다. API 통신의 로딩/성공/실패 상태 관리에 실무에서 매우 흔하게 쓰이는 패턴이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 타입 좁히기 | Type Narrowing | 넓은 유니온 타입 범위를 조건 검사로 구체적인 타입으로 한정하는 과정 |
| 타입 가드 | Type Guard | `typeof`, `in`, `instanceof` 등으로 런타임 데이터 타입을 확인하는 조건 표현식 |
| 서로소 판별 유니온 | Discriminated Union | 구분용 공통 속성으로 객체 상태를 나눈 유니온 타입 |
| 판별자 | Discriminant | 서로소 판별 유니온에서 각 타입을 구분하는 공통 리터럴 속성 |

# PART 7. 제네릭 함수와 제네릭 인터페이스 (6장 1강)

### | any의 한계와 제네릭이 필요한 이유 |

- `any`를 쓰면 컴파일러의 타입 검사가 완전히 꺼져버려서, 실제로 존재하지 않는 메서드를 호출해도 컴파일 시점에는 아무 경고가 없다가 런타임에서야 에러가 터진다. 그렇다고 타입별로 함수를 전부 따로 만들면(`echoNumber`, `echoString`, ...) 똑같은 로직이 계속 중복된다. **제네릭(Generic)** 은 타입을 미리 고정하지 않고, 함수나 인터페이스를 **호출하는 시점에 타입을 인자처럼 전달받아** 결정하는 방식으로 이 둘을 동시에 해결한다.

```typescript
// any 타입을 사용한 함수 — 타입 안전성 없음
function echoAny(value: any): any {
  return value;
}

const resultAny = echoAny(100);
// console.log(resultAny.toUpperCase());
// 숫자에는 toUpperCase가 없으므로 주석을 해제하면 런타임 에러 발생 — 컴파일 시점엔 안 잡힘

// 제네릭을 사용한 함수 — 타입 안전성 확보
function echoGeneric<T>(value: T): T {
  // <T>는 타입 매개변수 — value의 타입을 T로 지정하고 동일한 T 타입을 반환
  return value;
}

const resultNumber = echoGeneric<number>(100);
const resultString = echoGeneric<string>("Hello TypeScript");

console.log(resultNumber.toFixed(2));
console.log(resultString.toUpperCase());
```

**실행 결과**
```
100.00
HELLO TYPESCRIPT
```

- `echoGeneric<number>(100)`의 반환값은 컴파일러가 정확히 `number`로 인지하기 때문에 `.toFixed(2)`를 바로 안전하게 쓸 수 있다. 반면 `echoAny`의 반환값은 `any`라서, `resultAny.toUpperCase()`처럼 숫자에 없는 메서드를 호출하는 실수를 컴파일러가 전혀 잡아주지 못한다.

### | 타입 매개변수 `<T>`와 타입 추론 |

- 관례적으로 Type의 약자인 `<T>`를 쓰며, 여러 개가 필요하면 `<T, U, V>` 순으로 늘린다. 호출 시 `<number>`처럼 타입을 명시하지 않아도, 전달되는 인자 값을 보고 컴파일러가 자동으로 추론한다.

```typescript
function getFirstElement<T>(arr: T[]): T | undefined {
  if (arr.length === 0) {
    return undefined;
  }
  return arr[0];
}

const numbers = [10, 20, 30];
const firstNumber = getFirstElement(numbers); // T는 number로 자동 추론

const words = ["Apple", "Banana", "Cherry"];
const firstWord = getFirstElement(words); // T는 string으로 자동 추론

if (firstNumber !== undefined) {
  console.log(`첫 번째 숫자: ${firstNumber.toFixed(1)}`);
}

if (firstWord !== undefined) {
  console.log(`첫 번째 단어: ${firstWord.toLowerCase()}`);
}
```

**실행 결과**
```
첫 번째 숫자: 10.0
첫 번째 단어: apple
```

- 반환 타입을 `T | undefined`로 잡아둔 이유: 빈 배열이 들어오면 첫 요소가 없으므로 `undefined`를 반환해야 하는데, 이걸 타입에 반영해두지 않으면 호출하는 쪽에서 `undefined` 가능성을 깜빡하고 `.toFixed()`를 바로 불러서 런타임 에러를 낼 수 있다. 타입에 `| undefined`가 박혀 있으면, 위 코드처럼 `if (firstNumber !== undefined)` 체크를 안 하면 애초에 컴파일이 안 되므로 실수 자체가 원천 차단된다.

### | 제네릭 인터페이스와 응답 데이터 모델링 |

- 서버 응답은 보통 성공 여부(`success`)·메시지(`message`)는 고정 구조이고, 실제 데이터(`data`)만 요청 종류마다 달라진다. `data` 속성의 타입을 제네릭 `<T>`로 잡아두면, 인터페이스 하나로 다양한 API 응답을 전부 표현할 수 있다.

```typescript
interface ApiResponse<T> {
  success: boolean;
  message: string;
  data: T;
}

interface UserProfile {
  id: number;
  name: string;
  email: string;
}

interface ProductItem {
  code: string;
  price: number;
}

const userResponse: ApiResponse<UserProfile> = {
  success: true,
  message: "사용자 정보를 성공적으로 불러왔습니다.",
  data: {
    id: 1,
    name: "김철수",
    email: "chulsoo@example.com"
  }
};

const productResponse: ApiResponse<ProductItem> = {
  success: true,
  message: "상품 정보를 성공적으로 불러왔습니다.",
  data: {
    code: "PROD-001",
    price: 25000
  }
};

console.log(`사용자 이름: ${userResponse.data.name}`);
console.log(`상품 가격: ${productResponse.data.price}원`);
```

**실행 결과**
```
사용자 이름: 김철수
상품 가격: 25000원
```

- 제네릭 인터페이스가 없었다면, `UserApiResponse`, `ProductApiResponse`처럼 `data`만 다르고 나머지는 완전히 동일한 인터페이스를 응답 종류 수만큼 전부 따로 작성해야 한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 제네릭 | Generic | 타입을 매개변수로 받아 다양한 타입에 대한 재사용성을 제공하는 기능 |
| 타입 매개변수 | Type Parameter | 제네릭에서 전달받을 타입을 대신 표현하는 식별자(예: `<T>`) |
| 타입 추론 | Type Inference | 명시적 타입 지정 없이도 전달된 값을 보고 타입을 자동 결정하는 기능 |

# PART 8. 제네릭 제약 조건과 keyof 연산자 (6장 2강)

### | 제네릭 제약 조건(Generic Constraints) |

- 제네릭 `T`에 아무 제한을 두지 않으면 모든 타입이 들어올 수 있어서, 특정 속성(예: `.length`)에 접근하려 할 때 "그 속성이 있을지 없을지 모른다"는 타입 에러가 난다. `<T extends 제한할_타입>` 형태로 선언하면 T가 반드시 그 구조를 만족하도록 강제할 수 있다.

```typescript
interface Lengthwise {
  length: number;
}

function printLength<T extends Lengthwise>(item: T): number {
  // item이 length 속성을 가지고 있음이 보장되므로 안전하게 접근
  console.log(`길이: ${item.length}`);
  return item.length;
}

printLength("안녕하세요"); // 문자열도 length를 가짐
printLength([1, 2, 3, 4]); // 배열도 length를 가짐

// printLength(12345);
// 에러: 숫자는 length 속성이 없으므로 Lengthwise를 만족하지 못함
```

**실행 결과**
```
길이: 5
길이: 4
```

- 제약 조건이 없었다면 `item.length`를 쓰는 순간 "`T` 타입에는 `length`가 없을 수도 있다"는 컴파일 에러가 뜬다. `extends Lengthwise`는 "들어올 수 있는 타입의 범위를 `length`를 가진 것들로만 한정한다"는 약속이라서, 함수 내부에서는 안심하고 `.length`를 쓸 수 있게 된다.

### | keyof 연산자 |

- 객체 타입이 가진 모든 속성 키(Key)의 이름을 문자열 리터럴 유니온 타입으로 추출하는 연산자다.

```typescript
interface UserProfile {
  id: number;
  name: string;
  email: string;
  age: number;
}

// UserKeys는 "id" | "name" | "email" | "age" 유니온 타입이 됨
type UserKeys = keyof UserProfile;

const validKey1: UserKeys = "name";
const validKey2: UserKeys = "email";

console.log(`선택된 키: ${validKey1}, ${validKey2}`);

// const invalidKey: UserKeys = "address";
// 에러: "address"는 UserProfile의 키가 아니므로 할당 불가
```

**실행 결과**
```
선택된 키: name, email
```

- `keyof`가 없었다면 `UserKeys`를 `"id" | "name" | "email" | "age"`처럼 직접 손으로 타이핑해야 한다. 나중에 `UserProfile`에 속성을 추가·삭제하면 `UserKeys`도 매번 손으로 맞춰 고쳐야 하니 둘이 어긋나는 사고가 생기기 쉽다. `keyof`는 인터페이스 자체에서 키 목록을 자동으로 뽑아내므로 항상 최신 상태로 동기화된다.

### | 제네릭 제약 조건과 keyof의 결합 — 안전한 속성 조회 함수 |

```typescript
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  // obj의 key 위치 값을 안전하게 조회하여 반환
  return obj[key];
}

const product = {
  id: 101,
  title: "무선 키보드",
  price: 45000,
  isAvailable: true
};

const title = getProperty(product, "title"); // 반환 타입 string으로 추론
const price = getProperty(product, "price"); // 반환 타입 number로 추론

console.log(`상품명: ${title}`);
console.log(`가격: ${price}원`);

// const discount = getProperty(product, "discount");
// 에러: "discount"는 product 객체의 키가 아니므로 할당 불가
```

**실행 결과**
```
상품명: 무선 키보드
가격: 45000원
```

- `K extends keyof T`가 없다면, `key` 자리에 `string` 타입만 받게 되므로 `getProperty(product, "discount")`처럼 오타나 존재하지 않는 키를 넘겨도 컴파일 시점엔 통과해버린다. 실행 시점에 `obj[key]`가 `undefined`를 반환하면서 그 값을 쓰려는 순간에야 문제가 드러난다. `K extends keyof T`는 "두 번째 인자로 올 수 있는 문자열은 반드시 `T`가 실제로 가진 키뿐"이라는 제약을 걸어 이런 사고를 원천 차단한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 제약 조건 | Constraint | 제네릭 매개변수가 가져야 할 최소한의 조건을 지정하는 규칙 |
| 키 추출 연산자 | keyof Operator | 객체의 속성 이름들을 유니온 문자열 타입으로 모아주는 연산자 |
| 인덱스 접근 타입 | Indexed Access Type | 객체의 특정 키에 대응하는 값의 타입을 조회하는 표현식(`T[K]`) |

# PART 9. 클래스 구조와 접근 제한자 및 상속 (7장 1강)

### | 클래스 필드와 생성자 |

- 클래스(Class)는 객체를 찍어내는 틀이다. TypeScript에서는 클래스 내부 변수(필드)의 타입을 미리 명시해야 한다. 생성자(Constructor)는 객체가 생성될 때 가장 먼저 실행되어 필드 값을 초기화한다.

```typescript
class BankAccount {
  owner: string;
  balance: number;

  constructor(owner: string, balance: number) {
    this.owner = owner;
    this.balance = balance;
  }

  getSummary(): string {
    return `${this.owner}님의 현재 잔액은 ${this.balance}원입니다.`;
  }
}

const myAccount = new BankAccount("김철수", 10000);
console.log(myAccount.getSummary());
```

**실행 결과**
```
김철수님의 현재 잔액은 10000원입니다.
```

### | 접근 제한자로 데이터 보호하기 — public, protected, private |

| 제한자 | 접근 가능 범위 |
| --- | --- |
| `public` (기본값) | 클래스 내부, 자식 클래스, 외부 어디서든 접근 가능 |
| `protected` | 클래스 내부와 상속받은 자식 클래스에서만 접근 가능, 외부 불가 |
| `private` | 해당 클래스 내부에서만 접근 가능, 자식 클래스·외부 모두 차단 |

```typescript
class SecureAccount {
  public owner: string;
  protected accountType: string;
  private balance: number;

  constructor(owner: string, accountType: string, balance: number) {
    this.owner = owner;
    this.accountType = accountType;
    this.balance = balance;
  }

  public deposit(amount: number): void {
    if (amount > 0) {
      this.balance += amount;
      console.log(`${amount}원이 입금되었습니다. 현재 잔액: ${this.balance}원`);
    }
  }

  public getBalance(): number {
    return this.balance;
  }
}

const secureAcc = new SecureAccount("이영희", "보통예금", 50000);

console.log(secureAcc.owner); // public — 외부 접근 가능

// console.log(secureAcc.balance);
// 에러: 'balance' is private and only accessible within class 'SecureAccount'.

secureAcc.deposit(20000);
console.log(`조회된 잔액: ${secureAcc.getBalance()}원`);
```

**실행 결과**
```
이영희
20000원이 입금되었습니다. 현재 잔액: 70000원
조회된 잔액: 70000원
```

- 접근 제한자가 없다면(전부 `public`이라면) 어떻게 될까. 외부 코드 어디서든 `secureAcc.balance = -999999`처럼 계좌 잔액을 검증 없이 직접 조작할 수 있게 된다. `private`로 막아두고 `deposit`, `getBalance` 같은 메서드로만 접근을 허용하면, "입금액은 0보다 커야 한다" 같은 검증 로직을 반드시 거치게 만들 수 있다 — 이게 객체지향의 **캡슐화(Encapsulation)** 다.

### | 생성자 단축 속성 선언 |

- 생성자 매개변수 앞에 접근 제한자를 바로 적으면, 필드 선언과 `this` 할당 과정을 자동으로 처리해준다.

```typescript
class CompactAccount {
  constructor(
    public owner: string,
    protected accountType: string,
    private balance: number
  ) {
    // this.owner = owner 같은 코드를 따로 쓸 필요가 없다
  }

  public printInfo(): void {
    console.log(`${this.owner} [${this.accountType}]: ${this.balance}원`);
  }
}

const compactAcc = new CompactAccount("박민수", "저축예금", 30000);
compactAcc.printInfo();
```

**실행 결과**
```
박민수 [저축예금]: 30000원
```

- 단축 문법이 없으면 `SecureAccount`처럼 필드 선언 3줄 + `this.x = x` 할당 3줄, 총 6줄을 매번 반복해야 한다. 단축 속성 선언은 똑같은 결과를 생성자 매개변수 한 줄로 줄여준다.

### | 클래스 상속과 super 키워드 |

- `extends`로 부모 클래스의 속성·메서드를 자식 클래스가 물려받아 재사용·확장할 수 있다. `super()`는 자식 생성자 안에서 부모 생성자를 호출할 때, `super.메서드()`는 부모의 기존 메서드에 직접 접근할 때 쓴다. 부모로부터 물려받은 메서드를 자식이 목적에 맞게 다시 정의하는 것을 **메서드 오버라이딩(Overriding)** 이라고 한다.

```typescript
class BaseAccount {
  constructor(
    public owner: string,
    protected balance: number
  ) {}

  public printDetails(): void {
    console.log(`소유자: ${this.owner}, 잔액: ${this.balance}원`);
  }
}

class SavingsAccount extends BaseAccount {
  private interestRate: number;

  constructor(owner: string, balance: number, interestRate: number) {
    // super()로 부모 생성자를 먼저 호출해 초기화
    super(owner, balance);
    this.interestRate = interestRate;
  }

  public addInterest(): void {
    const interest = this.balance * this.interestRate;
    // 부모의 balance는 protected라서 자식 클래스에서 접근 가능
    this.balance += interest;
    console.log(`이자 ${interest}원이 적립되었습니다.`);
  }

  // 부모의 printDetails를 재정의(오버라이딩)
  public printDetails(): void {
    // super.printDetails()로 부모의 기존 메서드를 그대로 실행
    super.printDetails();
    console.log(`적용 이자율: ${this.interestRate * 100}%`);
  }
}

const mySavings = new SavingsAccount("최유진", 100000, 0.05);
mySavings.addInterest();
mySavings.printDetails();
```

**실행 결과**
```
이자 5000원이 적립되었습니다.
소유자: 최유진, 잔액: 105000원
적용 이자율: 5%
```

- `super(owner, balance)`가 없다면 어떻게 될까. 자식 클래스가 부모 클래스를 상속(`extends`)하는 순간, TypeScript는 "부모의 생성자를 반드시 먼저 실행해서 부모 몫의 필드(`owner`, `balance`)를 초기화하라"고 강제한다. `super()` 호출 없이 `this.interestRate = interestRate`부터 쓰려고 하면 "'super'가 호출되기 전에는 'this'에 접근할 수 없다"는 컴파일 에러가 난다. 부모 쪽 데이터가 아직 준비되지 않은 상태에서 자식이 멋대로 `this`를 쓰는 걸 막기 위한 안전장치다.
- `protected`가 아니라 `private`로 `balance`를 선언했다면 어떻게 될까. 자식 클래스인 `SavingsAccount`의 `addInterest()` 안에서 `this.balance`에 접근하는 순간 컴파일 에러가 난다. `protected`는 "외부는 막되 상속 관계는 허용"하는 중간 지점이라서 이런 이자 계산 로직을 자식 클래스에 자연스럽게 구현할 수 있게 해준다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 캡슐화 | Encapsulation | 중요 데이터를 외부에서 직접 못 바꾸게 보호하고 허용된 방법으로만 접근하게 만드는 원리 |
| 접근 제한자 | Access Modifiers | 클래스 내부 데이터의 외부 공개 범위를 지정하는 키워드 |
| 상속 | Inheritance | 기존 클래스의 필드·메서드를 다른 클래스가 물려받아 재사용하는 기능 |
| 메서드 오버라이딩 | Method Overriding | 부모 클래스에서 물려받은 메서드를 자식 클래스에서 새로 재정의하는 것 |

# PART 10. 추상 클래스, 인터페이스 구현 및 static (7장 2강)

### | 추상 클래스(Abstract Class) |

- 직접 객체(인스턴스)를 생성할 수는 없지만, 하위 클래스들이 반드시 구현해야 할 공통 표준 구조를 제공하는 클래스다. `abstract` 키워드를 클래스와 메서드 앞에 붙인다. 본문이 없는 **추상 메서드**는 상속받는 하위 클래스에서 반드시 재정의(오버라이딩)해야 한다.

```typescript
abstract class ServiceUser {
    constructor(public id: string, public name: string) {}

    // 일반 메서드 — 하위 클래스가 공통으로 사용
    showProfile(): void {
        console.log(`[사용자 프로필] ID: ${this.id}, 이름: ${this.name}`);
    }

    // 추상 메서드 — 본문이 없으며 하위 클래스에서 반드시 구현해야 함
    abstract getRole(): string;
}

class CustomerUser extends ServiceUser {
    getRole(): string {
        return "일반 구매자";
    }
}

const customer = new CustomerUser("user123", "김철수");
customer.showProfile();
console.log(`권한: ${customer.getRole()}`);

// const user = new ServiceUser("admin01", "관리자");
// 에러: Cannot create an instance of an abstract class.
```

**실행 결과**
```
[사용자 프로필] ID: user123, 이름: 김철수
권한: 일반 구매자
```

- 추상 클래스가 없다면 어떻게 될까. "모든 사용자 타입은 반드시 `getRole()`을 구현해야 한다"는 규칙을 강제할 방법이 없어진다. 그냥 일반 클래스로 만들면 실수로 `getRole()` 구현을 빠뜨린 자식 클래스가 생겨도 컴파일러가 잡아주지 못하고, 실행 중에 `undefined is not a function` 같은 에러로 뒤늦게 발견하게 된다. 추상 클래스는 "이 설계도를 따르는 모든 하위 클래스는 이 메서드를 반드시 채워 넣어야 한다"는 계약을 컴파일 시점에 강제한다.

### | 인터페이스 구현(implements)과 다형성 |

- 클래스가 특정 인터페이스에 정의된 모든 속성·메서드를 포함하도록 강제한다.

```typescript
interface PaymentMethod {
    pay(amount: number): boolean;
}

class CreditCardPayment implements PaymentMethod {
    constructor(private cardNumber: string) {}

    pay(amount: number): boolean {
        console.log(`신용카드(${this.cardNumber})로 ${amount}원이 결제되었습니다.`);
        return true;
    }
}

const card = new CreditCardPayment("1234-5678-9012-3456");
card.pay(15000);
```

**실행 결과**
```
신용카드(1234-5678-9012-3456)로 15000원이 결제되었습니다.
```

- 쉼표(`,`)로 여러 인터페이스를 동시에 구현할 수도 있다.

```typescript
interface Notifiable {
    sendReceipt(message: string): void;
}

class MultiPaymentCard implements PaymentMethod, Notifiable {
    constructor(private cardNumber: string) {}

    pay(amount: number): boolean {
        console.log(`다중 구현 카드로 ${amount}원 결제 완료.`);
        return true;
    }

    sendReceipt(message: string): void {
        console.log(`영수증 발송: ${message}`);
    }
}

const multiCard = new MultiPaymentCard("9876-5432-1098-7654");
multiCard.pay(25000);
multiCard.sendReceipt("25,000원 결제 영수증이 발행되었습니다.");
```

**실행 결과**
```
다중 구현 카드로 25000원 결제 완료.
영수증 발송: 25,000원 결제 영수증이 발행되었습니다.
```

- **다형성(Polymorphism)**: 서로 다른 클래스의 객체들이라도 동일한 인터페이스를 구현했다면, 하나의 인터페이스 배열에 담아 동일한 메서드 이름으로 일괄 호출할 수 있다.

```typescript
class KakaoPayPayment implements PaymentMethod {
    constructor(private accountId: string) {}

    pay(amount: number): boolean {
        console.log(`카카오페이 계정(${this.accountId})에서 ${amount}원이 결제되었습니다.`);
        return true;
    }
}

function processPayment(processor: PaymentMethod, amount: number): void {
    processor.pay(amount);
}

const paymentList: PaymentMethod[] = [
    new CreditCardPayment("1111-2222-3333-4444"),
    new KakaoPayPayment("user@kakao.com"),
    new MultiPaymentCard("5555-6666-7777-8888")
];

processPayment(paymentList[0], 10000);
processPayment(paymentList[1], 20000);

paymentList.forEach((paymentItem) => {
    paymentItem.pay(5000);
});
```

**실행 결과**
```
신용카드(1111-2222-3333-4444)로 10000원이 결제되었습니다.
카카오페이 계정(user@kakao.com)에서 20000원이 결제되었습니다.
신용카드(1111-2222-3333-4444)로 5000원이 결제되었습니다.
카카오페이 계정(user@kakao.com)에서 5000원이 결제되었습니다.
다중 구현 카드로 5000원 결제 완료.
```

- `implements PaymentMethod`가 없다면 어떻게 될까. `processPayment` 함수나 `paymentList` 배열이 "인자로 받는 객체가 `pay` 메서드를 갖고 있다"는 보장을 받을 방법이 없어진다. 서로 다른 결제 클래스를 하나의 배열에 넣고 똑같은 `.pay()` 호출로 일괄 처리하는 이 패턴 자체가, 모든 클래스가 같은 인터페이스를 구현했다는 전제 위에서만 안전하게 성립한다.

### | 정적 멤버(static)와 Getter/Setter |

- `static` 멤버는 개별 객체(`this`)가 아니라 **클래스 자체**에 귀속되어, 메모리에 단 하나만 존재하며 모든 객체가 공유한다. 클래스명으로 직접 접근한다.

```typescript
class UserCounter {
    // static 변수 — 클래스 자체에 귀속, 모든 객체가 공유
    private static totalUsersCount: number = 0;

    constructor(public username: string) {
        // 객체가 생성될 때마다 공유되는 static 카운터를 1 증가
        UserCounter.totalUsersCount++;
    }

    // static 메서드 — 객체 생성 없이 클래스 이름으로 직접 호출
    static getTotalUsers(): number {
        return UserCounter.totalUsersCount;
    }
}

console.log(`[초기 상태] 등록된 사용자 수: ${UserCounter.getTotalUsers()}명`);

const user1 = new UserCounter("김철수");
const user2 = new UserCounter("이영희");

console.log(`[생성 후] 전체 사용자 수: ${UserCounter.getTotalUsers()}명`);
```

**실행 결과**
```
[초기 상태] 등록된 사용자 수: 0명
[생성 후] 전체 사용자 수: 2명
```

- `static`이 아니라 일반 속성이었다면 어떻게 될까. 객체마다 각자 독립적인 `totalUsersCount`를 갖게 되어 "전체 사용자 수"라는 하나의 공유 값을 셀 수 없다. "클래스 전체에서 공통으로 관리해야 하는 값"이라는 요구사항을 만족시키려면 `static`이 꼭 필요하다.

- **Getter/Setter**: private 속성에 안전하게 접근하고, 값을 바꿀 때 검증 로직을 끼워 넣을 수 있다.

```typescript
class ServerConfig {
    private _serverUrl: string;

    constructor(initialUrl: string) {
        this._serverUrl = initialUrl;
    }

    // Getter — 속성처럼 괄호 없이 읽음
    get serverUrl(): string {
        return this._serverUrl;
    }

    // Setter — 값 변경 시 검증을 거침
    set serverUrl(newUrl: string) {
        if (!newUrl.startsWith("https://")) {
            console.log("보안 접속(https://) 주소만 등록할 수 있습니다.");
            return;
        }
        this._serverUrl = newUrl;
        console.log(`서버 주소가 변경되었습니다: ${this._serverUrl}`);
    }
}

const config = new ServerConfig("https://api.service.com/v1");

console.log(`현재 접속 주소: ${config.serverUrl}`);

config.serverUrl = "http://insecure-api.com"; // 검증 실패
config.serverUrl = "https://secure-api.service.com/v2"; // 검증 통과
```

**실행 결과**
```
현재 접속 주소: https://api.service.com/v1
보안 접속(https://) 주소만 등록할 수 있습니다.
서버 주소가 변경되었습니다: https://secure-api.service.com/v2
```

- Getter/Setter 없이 `_serverUrl`을 그냥 `public`으로 열어뒀다면, `config._serverUrl = "http://안전하지않은주소"`처럼 검증을 거치지 않고 아무 값이나 바로 대입할 수 있게 된다. `set serverUrl`은 "값이 바뀌는 모든 경로를 메서드 하나로 좁혀서, 그 길목에서 반드시 검증을 거치게" 만드는 장치다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 추상 클래스 | Abstract Class | 직접 객체를 만들 수 없고, 하위 클래스의 구현을 강제하는 클래스 |
| 인터페이스 구현 | Interface Implementation | 클래스가 인터페이스의 모든 필드·메서드를 갖추도록 계약을 맺는 것 |
| 다형성 | Polymorphism | 하나의 타입·인터페이스로 여러 서로 다른 형태의 객체를 일관되게 조작하는 성질 |
| 정적 멤버 | Static Member | 개별 객체가 아닌 클래스 자체에 귀속되어 클래스명으로 접근하는 공유 변수·메서드 |
| 접근자 | Getter / Setter | private 변수에 안전하게 접근하거나 값을 수정하기 위한 특수 함수 |
