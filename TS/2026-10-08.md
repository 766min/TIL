# PART 1. 속성 변경 및 가시성 제어 유틸리티
### | 왜 유틸리티 타입이 필요한가 |

- 회원가입 화면과 프로필 수정 화면을 떠올려보면, 둘 다 "아이디·이름·이메일·비밀번호" 같은 거의 동일한 필드를 다룬다. 다만 회원가입에서는 전부 필수이고, 프로필 수정에서는 일부만 선택적으로 바꾼다. 이 둘을 위해 매번 구조가 거의 똑같은 타입을 따로 선언하면(`UserProfile`, `UpdateUserProfile` 각각 손으로 작성) 코드 중복이 생기고, 원본 `UserProfile`에 필드 하나를 추가·삭제할 때마다 복사해둔 타입도 똑같이 고쳐야 하는 동기화 부담이 생긴다.
- TypeScript는 이런 반복을 없애기 위해 이미 존재하는 객체 타입을 재료 삼아 "전부 선택적으로", "전부 필수로", "전부 읽기 전용으로", "일부만 추출", "일부만 제외"처럼 변형된 새 타입을 자동으로 만들어주는 **유틸리티 타입(Utility Type)**을 기본 제공한다. 원본 타입 하나만 정확히 관리하면 파생 타입들은 항상 자동으로 최신 상태를 유지한다.

### | 선택적 속성으로 바꾸는 Partial과 필수 속성으로 바꾸는 Required |

- `Partial<T>`는 타입 `T`의 모든 속성에 `?`를 붙여 선택적으로 바꾸고, `Required<T>`는 반대로 모든 `?`를 제거해 필수로 바꾼다.

```typescript
interface UserProfile {
  id: number; // 사용자 고유 식별자 (필수)
  name: string; // 사용자 이름 (필수)
  email: string; // 이메일 주소 (필수)
  age?: number; // 나이 (선택적 속성)
}

// Partial<T> 적용: 모든 속성이 선택적(?)으로 변경됨 — 프로필 수정에 유용
type UpdateUserProfile = Partial<UserProfile>;

const updateInput: UpdateUserProfile = {
  email: "newuser@example.com" // email만 선택하여 변경
};

// Required<T> 적용: 모든 속성이 필수(? 제거)로 변경됨 — 저장 전 검증에 유용
type FullUserProfile = Required<UserProfile>;

const completeUser: FullUserProfile = {
  id: 1,
  name: "김철수",
  email: "chulsoo@example.com",
  age: 25 // 원본에서는 선택적이었던 age도 이제 필수
};

console.log("부분 수정 데이터:", updateInput);
console.log("완전한 사용자 데이터:", completeUser);
```

**실행 결과**
```
부분 수정 데이터: { email: 'newuser@example.com' }
완전한 사용자 데이터: { id: 1, name: '김철수', email: 'chulsoo@example.com', age: 25 }
```

- `Partial`이 없다면 어떻게 될까. `UpdateUserProfile`을 `{ id?: number; name?: string; email?: string; age?: number; }`처럼 모든 필드에 `?`를 하나하나 다시 붙여 직접 작성해야 한다. `UserProfile`에 `phone` 같은 필드가 추가되면 이 복사본에도 똑같이 추가해줘야 하는데, 깜빡 잊으면 두 타입이 조용히 어긋나버린다. `Required`가 없다면, "저장 직전에는 모든 값이 채워져 있어야 한다"는 규칙을 강제할 방법이 없어 `age`가 빠진 불완전한 객체가 저장 로직까지 흘러들어갈 수 있다.

### | 데이터를 안전하게 보호하는 Readonly |

- `Readonly<T>`는 타입 `T`의 모든 속성을 읽기 전용으로 바꿔, 객체 생성 후 값이 임의로 수정되는 것을 컴파일 시점에 차단한다.

```typescript
interface UserConfig {
  theme: string; // 앱 테마 설정
  notifications: boolean; // 알림 수신 여부
}

type ReadonlyUserConfig = Readonly<UserConfig>;

const userConfig: ReadonlyUserConfig = {
  theme: "dark",
  notifications: true
};

// userConfig.theme = "light";
// 에러: Cannot assign to 'theme' because it is a read-only property.

console.log("읽기전용 설정:", userConfig);
```

**실행 결과**
```
읽기전용 설정: { theme: 'dark', notifications: true }
```

- `Readonly`가 없다면, 설정 객체를 여기저기 참조로 넘겨 쓰는 과정에서 코드 어딘가가 실수로 `userConfig.theme = "light"`처럼 값을 바꿔도 컴파일러가 전혀 잡아주지 못한다. 원본 인터페이스(`UserConfig`)를 고칠 필요 없이, "이 값이 쓰이는 이 맥락에서만큼은 수정 금지"라는 제약을 타입 하나로 덧씌울 수 있다는 게 `Readonly<T>`의 핵심 장점이다.

### | 필요한 속성만 골라내는 Pick |

- `Pick<T, K>`는 타입 `T`에서 지정한 속성 키 `K`만 골라내 새로운 객체 타입을 만든다. 마이페이지 요약 카드처럼 전체 정보 중 일부만 화면에 필요할 때 쓴다.

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
  description: string;
  stock: number;
}

// Product 타입에서 'name'과 'price' 속성만 선택하여 새로운 타입 생성
type ProductSummary = Pick<Product, "name" | "price">;

const itemSummary: ProductSummary = {
  name: "무선 마우스",
  price: 29000
};

console.log("상품 요약 카드:", itemSummary);
```

**실행 결과**
```
상품 요약 카드: { name: '무선 마우스', price: 29000 }
```

- `Pick`이 없다면 요약 카드 전용 타입을 `{ name: string; price: number; }`처럼 새로 작성해야 하는데, 이러면 `Product` 원본 인터페이스와의 연결고리가 끊어진다. 나중에 `Product`의 `name` 타입이 `string`에서 `string | null`로 바뀌어도 수작업으로 만든 요약 타입은 그 변화를 전혀 반영하지 못해 둘 사이에 불일치가 생긴다.

### | 불필요하거나 민감한 속성을 제거하는 Omit |

- `Omit<T, K>`는 타입 `T`에서 지정한 속성 키 `K`를 제외한 나머지로 새로운 객체 타입을 만든다. 서버가 자동으로 채워주는 `id`나 암호화된 `passwordHash`처럼, 클라이언트가 직접 입력하면 안 되는 필드를 제외할 때 유용하다.

```typescript
interface UserRegistration {
  id: number; // 시스템 자동 생성 ID
  username: string; // 아이디
  passwordHash: string; // 암호화된 비밀번호
  email: string; // 이메일
}

// UserRegistration 타입에서 'id'와 'passwordHash'를 제외한 타입 생성
type UserFormInput = Omit<UserRegistration, "id" | "passwordHash">;

const signupFormData: UserFormInput = {
  username: "user_kr",
  email: "user_kr@example.com"
};

console.log("회원가입 폼 데이터:", signupFormData);
```

**실행 결과**
```
회원가입 폼 데이터: { username: 'user_kr', email: 'user_kr@example.com' }
```

- `Omit`이 없다면 어떻게 될까. 입력 폼 타입을 `{ username: string; email: string; }`로 따로 작성해야 하는데, 이 경우 실수로 `id`나 `passwordHash`를 폼 타입에 다시 넣어버려도 컴파일러가 막지 못한다. `Omit<UserRegistration, "id" | "passwordHash">`는 "서버 전용 필드는 폼 타입에 아예 존재할 수 없다"는 사실을 타입 구조 자체로 증명해준다 — 민감 정보가 실수로 요청 바디에 섞여 들어가는 보안 사고를 원천 차단하는 셈이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 유틸리티 타입 | Utility Type | 기존 타입을 바탕으로 형태를 변환·재가공하도록 TypeScript가 기본 제공하는 전역 타입 도구 |
| 부분 타입 | Partial\<T> | 타입 T의 모든 속성을 선택적 속성(?)으로 변경하는 유틸리티 |
| 완전 타입 | Required\<T> | 타입 T의 모든 선택적 속성에서 ?를 제거해 필수로 변경하는 유틸리티 |
| 읽기 전용 타입 | Readonly\<T> | 타입 T의 모든 속성을 수정 불가능한 읽기 전용으로 변환하는 유틸리티 |
| 속성 추출 / 제외 | Pick\<T, K> / Omit\<T, K> | 지정한 속성 키만 골라내거나(Pick), 지정한 속성 키를 제외하여(Omit) 새 타입을 만드는 유틸리티 |

# PART 2. 매핑 및 타입 추출 유틸리티
### | Record\<K, T>로 키-값 타입을 한 번에 매핑하기 |

- `Record<K, T>`는 유니온 타입으로 정의된 키 집합 `K` 전체에 동일한 값 타입 `T`를 짝지어주는 타입 생성기다. 키 하나하나에 값 타입을 개별로 선언하지 않아도 된다.

```typescript
// 과목 키 목록을 유니온 타입으로 정의
type Subject = "Korean" | "Math" | "English";

// Record<Key, Value>로 각 과목이 점수(number)를 갖는 성적표 타입 작성
type ReportCard = Record<Subject, number>;

const myGrade: ReportCard = {
  Korean: 95,
  Math: 88,
  English: 100
};

console.log("학생 성적표 데이터:", myGrade);

// 쇼핑몰 카테고리별 재고 수량 관리 예시
type ProductCategory = "Electronics" | "Clothing" | "Food";
type Inventory = Record<ProductCategory, number>;

const currentStock: Inventory = {
  Electronics: 25,
  Clothing: 50,
  Food: 120
};

console.log("카테고리별 재고 현황:", currentStock);
```

**실행 결과**
```
학생 성적표 데이터: { Korean: 95, Math: 88, English: 100 }
카테고리별 재고 현황: { Electronics: 25, Clothing: 50, Food: 120 }
```

- `Record`가 없다면 `interface ReportCard { Korean: number; Math: number; English: number; }`처럼 키를 전부 손으로 나열해야 한다. 과목이 10개, 20개로 늘어날수록 반복 선언이 길어지고, `Subject` 유니온에 새 과목을 추가했을 때 `ReportCard` 쪽에도 똑같이 추가하는 걸 잊으면 둘이 어긋난다. `Record<Subject, number>`는 `Subject` 유니온 하나만 최신으로 유지하면 값 타입 매핑이 항상 자동으로 따라오게 만든다. 또한 `myGrade`를 만들 때 과목 하나라도 빠뜨리면(예: `English` 누락) "속성이 부족하다"는 컴파일 에러가 즉시 발생해, 성적표에 과목이 통째로 누락되는 실수를 사전에 막아준다.

### | Exclude와 Extract로 유니온 타입 가공하기 |

- `Exclude<T, U>`는 유니온 타입 `T`에서 `U`에 해당하는 요소를 제거하고, `Extract<T, U>`는 반대로 `T`에서 `U`와 공통되는 요소만 골라낸다. 둘 다 원본 유니온을 수정하지 않고 거기서 파생된 부분집합 타입을 만든다.

```typescript
// 전체 결제 수단 유니온 타입
type PaymentMethod = "CreditCard" | "BankTransfer" | "KakaoPay" | "CashOnDelivery";

// Exclude: 현금 결제(CashOnDelivery)를 제외한 온라인 결제 수단만 남김
type OnlinePayment = Exclude<PaymentMethod, "CashOnDelivery">;

const myPayment: OnlinePayment = "KakaoPay";
// "CashOnDelivery" 입력 시 컴파일 에러 발생
console.log("선택된 온라인 결제 수단:", myPayment);

// 전체 사용자 권한 목록
type UserRole = "Admin" | "Manager" | "Student" | "Guest";

// Extract: 관리자급 권한("Admin", "Manager")만 추출
type AdminRole = Extract<UserRole, "Admin" | "Manager">;

const activeAdmin: AdminRole = "Admin";
console.log("현재 접속한 관리자 권한:", activeAdmin);
```

**실행 결과**
```
선택된 온라인 결제 수단: KakaoPay
현재 접속한 관리자 권한: Admin
```

- 둘 다 없다면 어떻게 될까. `OnlinePayment`를 `"CreditCard" | "BankTransfer" | "KakaoPay"`처럼 직접 다시 타이핑해야 하고, 원본 `PaymentMethod`에 새 결제 수단(`"TossPay"` 등)이 추가되면 손으로 만든 `OnlinePayment`는 그 변화를 전혀 반영하지 못한다. `Exclude`/`Extract`는 원본 유니온을 "기준점"으로 삼아 파생 타입을 계산하므로, 원본만 고치면 파생 타입도 항상 최신 상태를 따라간다 — PART 1의 `Pick`/`Omit`이 객체 타입에서 하던 일을, 유니온 타입에 대해 하는 것과 같은 맥락이다.

### | ReturnType으로 함수의 반환 타입 역추적하기 |

- `ReturnType<T>`는 함수가 최종적으로 반환하는 값의 타입을 함수 선언으로부터 자동으로 계산해 가져온다. 함수 값 자체에서 타입을 추출하려면 `typeof 함수명` 형태로 함수를 타입의 자리로 끌어올린 뒤 `ReturnType`에 넘겨야 한다.

```typescript
// 사용자 프로필을 생성하여 반환하는 함수
function createStudentProfile(name: string, age: number, isEnrolled: boolean) {
  return {
    id: Date.now(),
    name: name,
    age: age,
    status: isEnrolled ? "Active" : "LeaveOfAbsence",
    createdAt: new Date().toISOString()
  };
}

// typeof 연산자와 ReturnType을 결합하여 함수의 반환 타입을 추출
type StudentProfile = ReturnType<typeof createStudentProfile>;

const studentA: StudentProfile = createStudentProfile("김철수", 20, true);

function printProfile(profile: StudentProfile): void {
  console.log(`[프로필] ID: ${profile.id} | 이름: ${profile.name} | 상태: ${profile.status}`);
}

printProfile(studentA);
```

**실행 결과** (id는 `Date.now()`로 만들어지는 타임스탬프라 실행할 때마다 달라지는 예시 값)
```
[프로필] ID: 1759900000000 | 이름: 김철수 | 상태: Active
```

- `ReturnType`이 없다면 `createStudentProfile`이 반환하는 객체 구조를 보고 `StudentProfile` 인터페이스를 손으로 따로 작성해야 한다. 이후 `createStudentProfile` 내부 로직이 바뀌어 반환 필드가 추가·삭제되면(예: `createdAt` 제거), 수작업으로 만든 `StudentProfile`은 여전히 옛날 구조를 가리키고 있어 둘이 어긋난다. `ReturnType<typeof 함수명>`은 함수 본문을 "진실의 원천"으로 삼아 타입을 역추적하므로, 함수가 바뀌면 타입도 자동으로 같이 바뀐다 — 특히 반환 타입을 따로 export 하지 않는 외부 라이브러리 함수의 결과 타입을 가져올 때 매우 유용하다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 레코드 타입 | Record Type | 유니온 키 집합 K의 각 키에 동일한 값 타입 T를 일괄 매핑해주는 유틸리티 |
| 익스클루드 | Exclude\<T, U> | 유니온 타입 T에서 U에 해당하는 요소를 제거하는 유틸리티 |
| 익스트랙트 | Extract\<T, U> | 유니온 타입 T에서 U와 공통되는 요소만 골라내는 유틸리티 |
| 리턴 타입 | ReturnType\<T> | typeof 함수명과 결합해 함수가 최종 반환하는 데이터 타입을 자동 추론하는 유틸리티 |

# PART 3. API 데이터 모델링과 DTO 설계
### | DTO(Data Transfer Object)란 무엇이고 왜 필요한가 |

- 배달 앱에서 주문을 넣으면, 클라이언트는 "메뉴·수량·배달지"를 서버로 보내고 서버는 "접수 여부·예상 소요 시간"을 응답한다. 이때 양쪽이 주고받는 데이터의 형태(어떤 키가 있고 각 값이 어떤 타입인지)가 정해진 규격 없이 제각각이라면, 클라이언트가 보낸 필드를 서버가 못 알아보거나 서버가 보낸 응답 구조를 클라이언트가 잘못 해석하는 사고가 생긴다.
- **DTO(Data Transfer Object, 데이터 전송 객체)**는 네트워크 통신 시 주고받을 데이터의 구조를 미리 정의해둔 "표준 서식지"다. DTO가 없다면 `response.json()`의 결과가 암묵적으로 `any` 타입이 되어버려서, 서버가 `email` 필드명을 `emailAddress`로 바꿔도 컴파일러가 전혀 경고하지 않는다. 이 상태로 코드를 배포하면 화면에 `undefined`가 찍히거나 최악의 경우 런타임 에러로 애플리케이션이 멈추는 문제가 사용자에게 노출된 뒤에야 발견된다. DTO로 응답 타입을 미리 지정해두면 이런 불일치를 코드 작성 시점(컴파일 시점)에 바로 잡아낼 수 있고, 자동 완성 지원도 받을 수 있다.

### | Request DTO와 Response DTO로 통신 규격 분리하기 |

- **Request DTO**는 프론트엔드가 서버로 보낼 데이터의 규격이고, **Response DTO**는 서버가 처리를 마치고 돌려주는 데이터의 규격이다. 보내는 쪽과 받는 쪽의 책임이 다르므로 타입도 따로 분리해서 관리한다.

```typescript
// JSONPlaceholder 사용자 정보 응답 규격 (Response DTO)
interface UserResponseDTO {
  id: number; // 사용자 고유 ID
  name: string; // 사용자 이름
  username: string; // 사용자 닉네임
  email: string; // 사용자 이메일 주소
}

// JSONPlaceholder 게시글 생성 요청 규격 (Request DTO)
interface CreatePostRequestDTO {
  title: string; // 작성할 게시글 제목
  body: string; // 작성할 게시글 본문 내용
  userId: number; // 작성자 ID
}

// JSONPlaceholder 게시글 응답 규격 (Response DTO)
interface PostResponseDTO {
  id: number; // 서버에서 생성된 게시글 ID
  title: string; // 게시글 제목
  body: string; // 게시글 본문 내용
  userId: number; // 작성자 ID
}
```

- 만약 `CreatePostRequestDTO`와 `PostResponseDTO`를 구분하지 않고 하나의 타입으로 합쳐버린다면 어떻게 될까. 요청을 보낼 때는 아직 존재하지 않는 `id`(서버가 생성해줄 값)를 억지로 채워야 하거나, `id`를 선택적 속성(`id?: number`)으로 느슨하게 풀어버려야 한다. 이러면 "응답에는 반드시 id가 있어야 한다"는 사실이 타입에서 사라져, 응답을 다룰 때마다 `id`가 없을 가능성을 매번 의심하고 체크해야 하는 불편함이 생긴다. Request와 Response를 분리하면 각 시점에 "확실히 존재하는 값"과 "아직 없는 값"이 타입만으로도 명확해진다.

### | fetch API와 타입 단언으로 DTO 검증하기 |

- `fetch`의 `response.json()`은 반환 타입이 `Promise<any>`로 고정되어 있어, TypeScript가 응답 데이터의 실제 구조를 전혀 알지 못한다. 그래서 `as DTO타입` 형태의 **타입 단언(Type Assertion)**을 붙여 "이 값은 분명 이 DTO 구조를 따른다"고 컴파일러에게 알려준다.

```typescript
// GET 요청: 사용자 데이터 조회 함수
async function getUser(id: number): Promise<UserResponseDTO> {
  const response = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`);
  // response.json()의 결과에 'as UserResponseDTO'를 붙여 타입을 단언
  const user = (await response.json()) as UserResponseDTO;
  return user;
}

// POST 요청: 새 게시글 작성 함수
async function createPost(newPost: CreatePostRequestDTO): Promise<PostResponseDTO> {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json; charset=UTF-8'
    },
    body: JSON.stringify(newPost) // 자바스크립트 객체를 JSON 문자열로 변환
  });
  const result = (await response.json()) as PostResponseDTO;
  return result;
}

async function runApiExample(): Promise<void> {
  const user = await getUser(1);
  console.log('조회된 유저 이름:', user.name);
  console.log('조회된 유저 이메일:', user.email);

  const createdPost = await createPost({
    title: 'TypeScript DTO 학습',
    body: 'JSONPlaceholder를 활용한 실제 fetch 실습입니다.',
    userId: 1
  });
  console.log('생성된 게시글 ID:', createdPost.id);
  console.log('생성된 게시글 제목:', createdPost.title);
}

runApiExample();
```

**실행 결과** (JSONPlaceholder는 테스트용 목업 API라서 1번 유저는 항상 고정된 더미 데이터를 반환하고, POST 요청은 실제로 저장되지 않은 채 id만 101번으로 응답해주는 특성이 있다)
```
조회된 유저 이름: Leanne Graham
조회된 유저 이메일: Sincere@april.biz
생성된 게시글 ID: 101
생성된 게시글 제목: TypeScript DTO 학습
```

- 타입 단언(`as UserResponseDTO`)이 없다면 `user` 변수는 `any` 타입이 되어, `user.name`뿐 아니라 존재하지도 않는 `user.nmae`(오타) 같은 접근도 컴파일 시점엔 아무 경고 없이 통과해버린다. 다만 타입 단언은 "진짜로 그 구조인지" 런타임에 검증해주는 게 아니라 컴파일러를 설득하는 선언일 뿐이라는 한계도 있다 — 서버가 실제로 다른 구조를 보내면 타입 단언을 걸어둬도 런타임에서는 `undefined`가 섞여 들어올 수 있다. 그래도 최소한 "이 응답은 이런 구조여야 한다"는 계약을 코드에 명시해두면, 이후 이 DTO를 사용하는 모든 곳에서 자동 완성과 오타 검출의 이득을 본다.

### | 제네릭으로 범용 응답 래퍼(Wrapper) DTO 설계하기 |

- 실무의 API 응답은 보통 `status`(상태 코드), `success`(성공 여부)처럼 모든 요청에 공통되는 "껍데기"와, 요청 종류마다 달라지는 실제 `data`로 구성된다. `data`의 타입을 제네릭 `<T>`로 열어두면 래퍼 DTO 하나로 모든 API 응답을 표현할 수 있다.

```typescript
// 서버의 공통 응답 포맷을 정의하는 제네릭 래퍼 DTO
interface ApiResponseDTO<T> {
  status: number; // HTTP 상태 코드 (예: 200, 201)
  success: boolean; // 통신 성공 여부
  data: T; // 실제로 전달되는 데이터 (제네릭 타입 T)
}

// 게시글 간략 데이터 DTO
interface SimplePostDTO {
  id: number;
  title: string;
}

// 제네릭을 적용한 범용 fetch 래퍼 함수
async function fetchWithWrapper<T>(url: string): Promise<ApiResponseDTO<T>> {
  const response = await fetch(url);
  // response.json()의 반환값을 as T로 타입 단언
  const rawData = (await response.json()) as T;

  return {
    status: response.status,
    success: response.ok,
    data: rawData
  };
}

async function runGenericExample(): Promise<void> {
  // JSONPlaceholder 게시글 3개만 조회하여 SimplePostDTO 배열 타입으로 전달
  const apiResult = await fetchWithWrapper<SimplePostDTO[]>(
    'https://jsonplaceholder.typicode.com/posts?_limit=3'
  );

  console.log('요청 성공 여부:', apiResult.success);
  console.log('HTTP 상태 코드:', apiResult.status);
  console.log('가져온 데이터 개수:', apiResult.data.length);
  console.log('첫 번째 게시글 제목:', apiResult.data[0].title);
}

runGenericExample();
```

**실행 결과** (JSONPlaceholder의 고정 더미 게시글 데이터 기준)
```
요청 성공 여부: true
HTTP 상태 코드: 200
가져온 데이터 개수: 3
첫 번째 게시글 제목: sunt aut facere repellat provident occaecati excepturi optio reprehenderit
```

- 제네릭 래퍼가 없다면 어떻게 될까. 게시글 목록 조회용 `PostListApiResponse`, 사용자 목록 조회용 `UserListApiResponse`처럼 `status`·`success`는 완전히 똑같고 `data` 타입만 다른 인터페이스를 API 종류 수만큼 전부 따로 작성해야 한다. `ApiResponseDTO<T>`는 공통 껍데기는 한 번만 정의해두고, 호출하는 쪽에서 `fetchWithWrapper<SimplePostDTO[]>(...)`처럼 그때그때 필요한 데이터 타입만 꽂아 넣는 방식으로 중복을 없앤다. PART 2에서 본 `Record<K, T>`가 키 집합에 값 타입을 매핑했다면, 이건 "공통 구조에 가변 데이터 타입을 매핑"하는 같은 발상의 응용이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 데이터 전송 객체 | DTO (Data Transfer Object) | 시스템 간 데이터를 주고받을 때 사용되는 규격화된 데이터 상자 |
| 요청/응답 DTO | Request DTO / Response DTO | 클라이언트가 서버로 보낼 데이터, 서버가 클라이언트로 돌려줄 데이터 각각의 규격 |
| 패치 API | Fetch API | 브라우저와 Node.js에 내장된 비동기 네트워크 요청 함수 |
| 타입 단언 | Type Assertion (as) | 타입을 알 수 없는 반환값(response.json() 등)에 개발자가 직접 타입을 지정하는 구문 |
| 제네릭 응답 스키마 | Generic Response Schema | 공통 껍데기는 고정하고 내부 data만 제네릭 T로 유동적으로 바꾸는 범용 응답 패턴 |

# PART 4. 비동기 함수 Promise\<T>와 에러 모델링
### | Promise\<T> — 비동기 결과의 타입을 미리 약속하기 |

- 서버에서 데이터를 받아오는 동안 화면이 멈추지 않고 다른 조작에 계속 반응하는 방식을 **비동기 처리(Asynchronous Processing)**라고 한다. `Promise<T>`는 "지금 당장은 값이 없지만, 비동기 작업이 끝나면 타입 `T`의 데이터를 반환하겠다"는 약속을 제네릭으로 표현한 타입이다. 비동기 함수는 내부에서 값을 그대로 `return`하더라도, 그 반환 타입은 항상 `Promise<T>` 형태로 감싸진다.

```typescript
// 사용자 데이터 인터페이스
interface User {
  id: number;
  name: string;
  email: string;
}

// Promise<User>를 반환하는 비동기 함수
function fetchUserData(): Promise<User> {
  return new Promise((resolve) => {
    // 1초 뒤에 User 객체를 반환하는 비동기 작업 실행
    setTimeout(() => {
      resolve({
        id: 1,
        name: "김철수",
        email: "chulsoo@example.com"
      });
    }, 1000);
  });
}

const user = await fetchUserData();
console.log("1초 후 조회된 사용자:", user);
```

**실행 결과** (setTimeout으로 1초 지연 후 출력됨)
```
1초 후 조회된 사용자: { id: 1, name: '김철수', email: 'chulsoo@example.com' }
```

- `Promise<User>`처럼 타입을 명시하지 않고 그냥 `Promise`라고만 적으면(또는 타입 추론에 완전히 맡겨 암묵적으로 `any`가 섞이면), `await fetchUserData()`로 꺼낸 `user`가 어떤 모양인지 컴파일러가 모르게 된다. 그러면 `user.name` 대신 `user.nam`처럼 오타를 내도 통과해버리고, 실제 실행 시점에야 `undefined`가 찍히며 문제를 발견하게 된다. `Promise<T>`에 결과 타입을 박아두면 "미래에 도착할 데이터의 모양"까지 컴파일 시점에 보장받을 수 있다.

### | async/await와 Top-level await |

- 함수 앞에 `async`를 붙이면 그 함수는 내부에서 무엇을 반환하든 무조건 `Promise`로 감싸서 반환한다. `await`는 `Promise`가 이행(완료)되기를 기다렸다가 그 안의 순수 데이터 `T`를 꺼내준다. tslab 주피터 노트북 환경에서는 `async` 함수로 감싸지 않고도 셀 최상위에서 바로 `await`를 쓸 수 있는데, 이를 **Top-level await**라고 한다.

```typescript
// async 함수는 리턴값에 자동으로 Promise 포장을 적용
async function getUserName(userId: number): Promise<string> {
  // 실제 백엔드 연동을 가정한 모의 비동기 처리
  return `사용자_${userId}`;
}

// tslab 환경에서는 최상위 셀에서 await를 바로 실행 가능
const userName = await getUserName(101);
// 추출된 결과는 Promise<string>이 아닌 string 타입
console.log(`조회된 사용자 이름: ${userName}`);
```

**실행 결과**
```
조회된 사용자 이름: 사용자_101
```

- `await` 없이 `getUserName(101)`을 바로 쓰면 결과는 `string`이 아니라 `Promise<string>` 객체 자체가 되어, 템플릿 리터럴 안에 그대로 넣었을 때 `"조회된 사용자 이름: [object Promise]"`처럼 의미 없는 문자열이 찍힌다. `await`는 이 `Promise` 포장을 풀어서 실제 값 하나만 꺼내주는 역할을 한다.

### | catch의 unknown 타입과 타입 가드로 안전하게 에러 다루기 |

- `fetch`는 일반적인 JavaScript 예외와 달리 특이한 성질이 있다. **네트워크 자체가 끊기는 경우(서버에 아예 연결이 안 되는 경우)에만 `catch`로 넘어가며, HTTP 404나 500 같은 에러 상태 코드는 `reject` 되지 않고 `response.ok`가 `false`로만 표시된다.** 그래서 `response.ok`를 직접 검증해 커스텀 에러를 `throw`해주는 로직이 필요하다.
- TypeScript는 `catch (error)`에서 `error`의 타입을 안전을 위해 기본적으로 `unknown`으로 지정한다. `unknown`은 `any`와 달리 "검증 없이는 아무 속성도 접근할 수 없는" 타입이라, `instanceof` 같은 **타입 가드**로 실제 타입을 좁힌 뒤에만 속성에 접근할 수 있다.

```typescript
// 백엔드 API의 공통 에러 응답 구조를 정의하는 인터페이스
interface ApiErrorResponse {
  statusCode: number; // HTTP 상태 코드 (예: 400, 404, 500)
  message: string; // 에러 상세 메시지
  errorCode: string; // 시스템 내부 에러 식별 코드
}

// 명확한 에러 처리를 위한 커스텀 HTTP 에러 클래스
class HttpError extends Error {
  statusCode: number;
  errorCode: string;

  constructor(statusCode: number, message: string, errorCode: string) {
    super(message);
    this.statusCode = statusCode;
    this.errorCode = errorCode;
    this.name = 'HttpError';
  }
}

// 에러 객체를 검증하고 처리하는 공통 함수
function handleServerError(error: unknown): void {
  // 사용자 정의 HttpError 인스턴스인지 검증
  if (error instanceof HttpError) {
    console.log(`[HTTP 에러 발생] 상태코드: ${error.statusCode}, 코드: ${error.errorCode}, 메시지: ${error.message}`);
  }
  // 일반 JavaScript Error 인스턴스인지 검증
  else if (error instanceof Error) {
    console.log(`[일반 에러 발생] ${error.message}`);
  }
  // 기타 알 수 없는 에러 처리
  else {
    console.log("알 수 없는 에러가 발생했습니다.", error);
  }
}

handleServerError(new HttpError(404, "리소스를 찾을 수 없습니다.", "NOT_FOUND"));
handleServerError(new Error("일반적인 자바스크립트 에러입니다."));
handleServerError("문자열이 그냥 던져진 경우");
```

**실행 결과**
```
[HTTP 에러 발생] 상태코드: 404, 코드: NOT_FOUND, 메시지: 리소스를 찾을 수 없습니다.
[일반 에러 발생] 일반적인 자바스크립트 에러입니다.
알 수 없는 에러가 발생했습니다. 문자열이 그냥 던져진 경우
```

- `catch` 절의 타입이 `unknown`이 아니라 과거 TypeScript 버전처럼 암묵적으로 `any`였다면 어떻게 될까. `error.statusCode`처럼 `HttpError`에만 있는 속성을 검증 없이 바로 접근해도 컴파일러가 전혀 막지 못한다. 그런데 실제로 던져진 값이 `HttpError`가 아니라 평범한 문자열이거나 `Error`였다면, `error.statusCode`는 `undefined`가 되고 이를 이용한 로직은 조용히 잘못된 값으로 흘러간다. `unknown` + `instanceof` 타입 가드 조합은 "검증을 통과한 블록 안에서만 그 타입 전용 속성에 접근할 수 있다"는 규칙을 강제해, 이런 사고를 원천 차단한다. 이는 앞서 배운 타입 좁히기와 같은 원리를, catch 블록이라는 실무상 가장 중요한 지점에 적용한 것이다.

### | fetch 기반 비동기 통신과 예외 처리 전체 흐름 |

- 위에서 만든 `HttpError`와 `handleServerError`를 실제 `fetch` 통신에 통합하면, 성공 응답과 실패 응답을 모두 안전하게 처리하는 전체 흐름을 구성할 수 있다.

```typescript
// API 성공 응답 데이터 구조 정의
interface TodoItem {
  userId: number; // 작성자 ID
  id: number; // 할 일 ID
  title: string; // 할 일 제목
  completed: boolean; // 완료 여부
}

// fetch 기반 비동기 데이터 조회 함수
async function fetchTodoById(todoId: number): Promise<TodoItem> {
  const response = await fetch(`https://jsonplaceholder.typicode.com/todos/${todoId}`);

  // HTTP 응답 상태가 200~299 범위가 아닌 경우 예외를 발생시킴
  if (!response.ok) {
    throw new HttpError(
      response.status,
      `요청 실패: 상태 코드 ${response.status}`,
      "FETCH_ERROR"
    );
  }

  // response.json() 결과는 알 수 없는 타입이므로 'as TodoItem'으로 타입 단언
  const data = (await response.json()) as TodoItem;
  return data;
}

// 정상 동작 케이스 테스트
try {
  const todoData = await fetchTodoById(1);
  console.log("=== 성공적으로 데이터를 가져왔습니다 ===");
  console.log(`제목: ${todoData.title}`);
  console.log(`완료 여부: ${todoData.completed}`);
} catch (error: unknown) {
  handleServerError(error);
}

// 에러 발생 케이스 테스트 (잘못된 URL 요청 시뮬레이션)
try {
  console.log("\n=== 예외 처리 테스트 실행 ===");
  const invalidUrl = "https://jsonplaceholder.typicode.com/invalid-endpoint-12345";
  const response = await fetch(invalidUrl);

  // 404 에러가 발생하면 response.ok가 false가 됨
  if (!response.ok) {
    throw new HttpError(
      response.status,
      "요청한 API 엔드포인트를 찾을 수 없습니다.",
      "NOT_FOUND"
    );
  }
} catch (error: unknown) {
  handleServerError(error);
}
```

**실행 결과** (JSONPlaceholder의 todos/1 더미 데이터 기준)
```
=== 성공적으로 데이터를 가져왔습니다 ===
제목: delectus aut autem
완료 여부: false

=== 예외 처리 테스트 실행 ===
[HTTP 에러 발생] 상태코드: 404, 코드: NOT_FOUND, 메시지: 요청한 API 엔드포인트를 찾을 수 없습니다.
```

- `if (!response.ok)` 검증이 없다면 어떻게 될까. 잘못된 URL로 요청해도 `fetch` 자체는 "통신에는 성공"했기 때문에 `catch`로 넘어가지 않는다. 그 결과 404 에러 페이지의 HTML 본문을 `TodoItem`으로 착각해 `as TodoItem`으로 단언해버리고, 존재하지도 않는 `todoData.title`에 접근해 `undefined`가 찍히는데도 아무 에러 로그 없이 코드가 계속 진행된다. `response.ok` 검증 후 `HttpError`를 명시적으로 `throw`하는 패턴은, fetch의 "HTTP 에러에도 조용히 넘어가는" 특이한 동작을 일반적인 try-catch 흐름으로 끌어들이는 안전장치다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| Promise | Promise\<T> | 비동기 작업의 최종 성공 또는 실패 결과를 나타내며, 성공 시 반환할 데이터 타입 T를 약속하는 객체 |
| response.ok | response.ok | HTTP 응답 상태가 성공(200~299) 범위인지 알려주는 boolean 속성 |
| Unknown 타입 | Unknown Type | 어떤 값이든 들어올 수 있지만 사용 전 타입 검증이 강제되는 안전한 타입 |
| 타입 가드 | Type Guard | instanceof 등 런타임 조건문으로 unknown/유니온 타입을 구체적인 타입으로 좁히는 기법 |
| 커스텀 에러 클래스 | Custom Error Class | Error를 상속받아 상태 코드·에러 코드 등 추가 정보를 구조화하는 에러 모델링 기법 |

# PART 5. ESM 모듈 시스템 이해
### | CommonJS에서 ESM으로 — 왜 모듈 시스템이 필요한가 |

- 지금까지는 tslab 주피터 노트북이라는 대화형 환경에서 셀 단위로 코드를 실행했다. 하지만 실제 서비스를 만들 때는 기능별로 파일을 나누고, 파일끼리 서로 필요한 코드를 불러다 쓰는 구조가 필요하다. 이렇게 하나의 독립된 기능을 별도 파일로 분리해 관리하는 단위를 **모듈(Module)**이라고 한다.
- Node.js는 과거 기본값으로 `require`/`module.exports`를 쓰는 **CommonJS** 방식을 사용했지만, 현재 자바스크립트 표준은 `import`/`export` 문법의 **ESM(ES Modules)**이다. 개별 파일에 `.mjs` 확장자를 붙여 ESM임을 표시할 수도 있지만, `package.json`에 `"type": "module"`을 한 번 지정해두면 프로젝트 내 모든 `.ts`/`.js` 파일이 표준 ESM 문법을 그대로 쓸 수 있다.

| 구분 | CommonJS (과거 방식) | ES Modules / ESM (현대 표준) |
| --- | --- | --- |
| 가져오기 Syntax | `const fs = require('fs');` | `import fs from 'fs';` |
| 내보내기 Syntax | `module.exports = { ... };` | `export const ...;` |
| 적용 방법 | Node.js 기본값 | package.json에 `"type": "module"` 추가 |

- 만약 모듈 시스템 자체가 없다면 어떻게 될까. 모든 코드를 하나의 거대한 파일에 전부 작성해야 하고, 변수·함수 이름이 프로젝트 전역에서 서로 충돌하지 않도록 매번 신경 써야 한다. 또한 재사용하려는 로직(`calculator.ts`의 `addNumbers` 같은)을 수정할 때마다 그걸 복사해 쓰고 있는 모든 위치를 찾아 똑같이 고쳐야 하는 유지보수 지옥에 빠진다.

### | Named Export와 Default Export |

- 모듈 내보내기는 파일 내부의 변수·함수·클래스·타입을 외부 파일에서 참조할 수 있도록 공개하는 기능이다. 한 파일에서 여러 요소를 각각 지정해 내보내는 **Named Export(이름 지정 내보내기)**와, 파일당 단 하나의 대표 요소만 내보내는 **Default Export(기본 내보내기)**로 나뉜다.

```typescript
// [src/utils/calculator.ts] — Named Export
// 변수를 이름 지정 내보내기로 공개
export const MAX_LIMIT: number = 100;

// 덧셈 함수를 이름 지정 내보내기로 공개
export function addNumbers(a: number, b: number): number {
  return a + b;
}

// 타입/인터페이스를 이름 지정 내보내기로 공개
export interface CalcResult {
  value: number;
}
```

```typescript
// [src/main.ts]
// 중괄호 { } 안에 calculator.ts에서 내보낸 이름과 동일하게 작성하여 가져옴
import { MAX_LIMIT, addNumbers, type CalcResult } from "./utils/calculator.js";

const total: number = addNumbers(10, 20);
const resultObj: CalcResult = { value: total };

console.log(`최대 제한: ${MAX_LIMIT}, 결과: ${resultObj.value}`);
```

**실행 결과** (`npx tsc src/main.ts` 컴파일 후 `node src/main.js` 실행 시)
```
최대 제한: 100, 결과: 30
```

```typescript
// [src/services/logger.ts] — Default Export
// 이 파일의 대표 함수 하나를 기본 내보내기로 지정
export default function logMessage(message: string): void {
  console.log(`[LOG]: ${message}`);
}
```

- Named Export를 가져올 때는 반드시 중괄호(`{ }`)를 쓰고 선언된 이름과 동일하게 작성해야 하지만, Default Export는 중괄호 없이 가져오는 쪽에서 원하는 이름을 임의로 붙일 수 있다는 차이가 있다.

| 비교 항목 | Named Export (export) | Default Export (export default) |
| --- | --- | --- |
| 파일당 가능 개수 | 제한 없음 (복수 가능) | 단 1개만 가능 |
| 가져오기 문법 | `import { 이름 } from '경로';` | `import 임의이름 from '경로';` |
| 중괄호 사용 | 필수 작성 | 작성하지 않음 |
| 가져올 때 식별자명 | 선언된 이름과 동일해야 함 (as로 변경 가능) | 임의로 변경 가능 |
| 주요 용도 | 유틸리티 함수 집합, 공통 상수, 타입 정의 | 단일 클래스, 단일 모듈, 핵심 기능 |

- 만약 모든 내보내기를 Default Export로만 처리한다면 어떻게 될까. 파일 하나당 요소 하나만 내보낼 수 있으므로, `calculator.ts`처럼 상수·함수·타입을 동시에 여러 개 공개해야 하는 유틸리티 파일을 만들 수 없게 된다. 반대로 모든 걸 Named Export로만 처리하면, 파일의 "대표 기능이 무엇인지"가 흐려지고 가져오는 쪽에서 매번 정확한 이름을 기억해 중괄호로 꺼내야 하는 번거로움이 생긴다. 두 방식을 상황에 맞게 구분해 쓰는 이유가 여기에 있다.

### | Named와 Default를 함께 쓰는 경우, 그리고 타입 전용 불러오기 |

- 한 파일 안에서 하나의 Default Export와 여러 개의 Named Export를 동시에 내보낼 수 있다. 가져올 때는 중괄호 바깥에 Default, 중괄호 안에 Named를 함께 적는다.

```typescript
// [src/utils/formatter.ts]
// Named Export로 언어 설정 상수를 내보냄
export const DEFAULT_LANGUAGE: string = "ko";

// Default Export로 이름 서식 변환 함수를 내보냄
export default function formatName(name: string): string {
  return `${name}님`;
}
```

- `import { MAX_LIMIT, addNumbers as sum, type CalcResult } from "./utils/calculator.js";`처럼 인터페이스나 타입을 불러올 때는 `type` 키워드를 명시한다. 타입은 컴파일 과정에서 완전히 삭제되는 존재이므로, "이건 런타임에 남지 않는 타입 전용 불러오기다"라는 사실을 명확히 표시해주는 것이다.
- 이 `type` 키워드가 없다면 어떻게 될까. `verbatimModuleSyntax`(PART 6에서 다룰 tsconfig 옵션) 같은 엄격한 설정이 켜진 환경에서는, 컴파일러가 `import` 구문을 "이 식별자는 자바스크립트 런타임에도 실제로 존재하는 값"으로 착각하고 그대로 남겨둘 위험이 있다. 그런데 인터페이스는 런타임에 아예 존재하지 않는 개념이라서, 실제로 실행되는 자바스크립트 파일에서 "존재하지 않는 걸 가져오려 한다"는 에러가 발생할 수 있다. `type` 키워드는 "이 import는 타입 검사 용도일 뿐, 실행 코드에는 영향이 없다"는 사실을 컴파일러에게 명확히 알려 이런 혼동을 막는다.
- 또한 Node.js의 ESM 규격에서는 로컬 모듈을 가져올 때 `./utils/calculator.js`처럼 확장자(`.js`)와 상대 경로 기호(`./`, `../`)를 반드시 명시해야 한다. 소스 파일이 `.ts`인데 import 경로에는 `.js`를 쓰는 이유는, TypeScript가 컴파일한 뒤 실제로 실행되는 결과물이 `.js` 파일이기 때문이다 — import 경로는 "컴파일 이후의 실제 실행 파일"을 기준으로 적어야 한다. 이 규칙을 지키지 않고 확장자를 생략하면(CommonJS 시절의 습관처럼) Node.js ESM 런타임이 모듈을 찾지 못해 "Cannot find module" 에러로 실행이 아예 멈춘다.

### | 여러 모듈을 조립하는 진입점(index.ts) |

- 분리해서 작성한 여러 모듈 파일을 하나의 진입점 파일(`src/index.ts`)에서 불러와 조립하고, `tsx` 도구로 즉시 실행해 전체 흐름을 검증한다.

```typescript
// [src/index.ts]
// calculator.ts에서 Named Export 모듈을 가져오며, addNumbers는 sum이라는 이름으로 변경
// 타입 전용 인라인 불러오기(type CalcResult)를 활용
import { MAX_LIMIT, addNumbers as sum, type CalcResult } from "./utils/calculator.js";

// logger.ts에서 Default Export 모듈을 임의의 이름(myLog)으로 가져옴
import myLog from "./services/logger.js";

// formatter.ts에서 Default Export와 Named Export를 동시에 가져옴
import formatName, { DEFAULT_LANGUAGE } from "./utils/formatter.js";

// 가져온 함수와 변수를 활용하여 로직을 실행
const resultValue: number = sum(30, 70);
const calcObj: CalcResult = { value: resultValue };

// 로그 출력 함수를 실행
myLog(`기본 언어 설정: ${DEFAULT_LANGUAGE}`);
myLog(`계산 결과: ${calcObj.value} (최대 제한: ${MAX_LIMIT})`);
myLog(`사용자명 서식: ${formatName("김철수")}`);
```

**실행 결과** (`npm run dev` → 내부적으로 `tsx src/index.ts` 실행)
```
[LOG]: 기본 언어 설정: ko
[LOG]: 계산 결과: 100 (최대 제한: 100)
[LOG]: 사용자명 서식: 김철수님
```

- `as` 별칭(`addNumbers as sum`)이 없다면 어떻게 될까. 서로 다른 파일에서 가져온 두 함수의 이름이 우연히 똑같을 경우(`calculator.ts`의 `addNumbers`와 다른 파일의 `addNumbers`) 이름 충돌로 아예 컴파일이 막혀버린다. `as`는 가져오는 쪽에서 이름을 자유롭게 바꿔치기할 수 있게 해줘서, 모듈 원본 코드는 건드리지 않고도 충돌을 해결하게 해준다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| ES 모듈 | ES Modules (ESM) | import/export 구문을 사용하는 자바스크립트 표준 모듈 시스템 |
| type: module | "type": "module" | package.json에서 프로젝트 전역을 ESM 환경으로 지정하는 속성 |
| 이름 지정 내보내기 | Named Export | 한 파일에서 여러 요소를 내보내며 가져올 때 중괄호가 필요한 방식 |
| 기본 내보내기 | Default Export | 한 파일에서 단 1개만 내보내며 가져올 때 식별자명을 임의로 정할 수 있는 방식 |
| 타입 전용 불러오기 | Type-only Import | 컴파일 시 지워지는 타입 구문임을 밝히기 위해 `type` 키워드를 함께 쓰는 import 기법 |

# PART 6. strict 모드와 tsconfig.json
### | 대화형 환경을 벗어나 독립 프로젝트 구조 만들기 |

- 지금까지는 tslab 주피터 노트북에서 셀 단위로 코드를 즉시 실행했지만, 실제 서비스는 다중 파일 구조와 모듈 의존성을 관리할 수 있는 독립된 프로젝트 환경이 필요하다. `tsc`로 자바스크립트를 만든 뒤 `node`로 실행하거나 `ts-node`를 쓰던 과거 방식 대신, 최근 현업에서는 esbuild 기반으로 변환 과정 없이 TypeScript를 즉시 실행해주는 **tsx**를 표준으로 쓴다.

```bash
# 프로젝트 전용 폴더 생성 및 이동
mkdir chapter10-1
cd chapter10-1

# Node.js 프로젝트 초기화 (package.json 생성)
npm init -y

# TypeScript 및 최신 실행 도구(tsx) 개발용 라이브러리 설치
npm i -D typescript tsx

# 소스 코드 디렉토리(src) 및 메인 파일 생성
mkdir src

# TypeScript 설정 파일(tsconfig.json) 자동 생성
npx tsc --init
```

```json
// [package.json]
{
  "name": "chapter10-1",
  "version": "1.0.0",
  "type": "module",
  "main": "dist/index.js",
  "scripts": {
    "dev": "tsx src/index.ts",
    "build": "tsc"
  },
  "devDependencies": {
    "tsx": "^4.23.1",
    "typescript": "^7.0.2"
  }
}
```

- `"dev": "tsx src/index.ts"`는 tsx로 메인 파일을 즉시 실행하는 명령어이고, `"build": "tsc"`는 배포용 자바스크립트로 컴파일하는 명령어다. 작성하는 코드는 `src` 폴더에, 컴파일된 결과물은 `dist` 폴더에 분리해 저장한다 — 소스와 산출물을 섞어두면 배포할 때 어떤 파일이 원본이고 어떤 게 빌드 결과인지 구분하기 어려워지기 때문이다.

### | strict 모드 — 7가지 엄격 검사를 한 번에 켜는 마스터 스위치 |

- `tsconfig.json`에 `"strict": true`를 설정하면, 타입 검사를 강화하는 7가지 핵심 옵션이 자동으로 일괄 활성화된다. 하나의 설정값으로 여러 세부 옵션을 한꺼번에 켜준다는 의미에서 이를 **마스터 스위치(Master Switch)**라고 부른다.

| 옵션명 | 주요 검사 내용 | 비활성화 시 발생하는 문제 |
| --- | --- | --- |
| noImplicitAny | 타입을 적지 않아 암묵적으로 any가 되는 코드를 거부 | 타입 추론을 포기해 TypeScript의 안전성이 무력화됨 |
| strictNullChecks | null/undefined를 일반 타입에 허용 없이 할당하는 것을 금지 | 런타임에 "Cannot read property of undefined" 에러 발생 가능 |
| strictFunctionTypes | 함수 매개변수 타입의 상속·호환성을 엄격하게 검사 | 잘못된 타입의 인자가 전달되어 실행 중 오류 발생 가능 |
| strictBindCallApply | bind/call/apply 호출 시 전달 인자 타입을 검사 | 잘못된 인자 전달로 런타임 에러 발생 |
| strictPropertyInitialization | 클래스 필드가 생성자에서 반드시 초기화되도록 강제 | 인스턴스 생성 후 필드 접근 시 undefined 반환 위험 |
| noImplicitThis | this의 타입이 명확하지 않고 암묵적 any가 되는 상황을 막음 | 실행 시점에 this가 전역 객체나 undefined를 가리킴 |
| alwaysStrict | 자바스크립트 엄격 모드('use strict')를 모든 파일에 적용 | 선언되지 않은 변수 사용 등 고질적 실수를 막지 못함 |

```typescript
// [src/index.ts]
// noImplicitAny 자동 적용 예시 (별도 설정 없이 strict: true에 의해 동작)
// 매개변수 a, b에 타입을 적지 않으면 "Implicit Any" 에러가 발생하므로 명시해야 함
function addNumbers(a: number, b: number): number {
  return a + b;
}

// strictNullChecks 자동 적용 예시
let userRole: string | null = "ADMIN";
// null 값이 들어올 수 있으므로 조건문으로 검증 후 사용
if (userRole !== null) {
  console.log(`권한: ${userRole.toLowerCase()}`);
}
```

**실행 결과** (`npm run dev`)
```
권한: admin
```

- strict 모드가 꺼져 있다면 `let userRole: string | null = "ADMIN"`로 선언해도 `userRole.toLowerCase()`를 아무 조건 없이 바로 호출하는 코드가 컴파일을 통과해버린다. 이후 `userRole`에 실제로 `null`이 들어온 상태에서 이 코드가 실행되면 "Cannot read properties of null"이라는 런타임 에러로 애플리케이션이 멈춘다. `strictNullChecks`는 `null`이 섞일 수 있는 변수에 메서드를 바로 호출하려는 순간 컴파일 단계에서 막아, 이런 사고를 사전에 차단한다.

### | noUncheckedIndexedAccess로 배열 접근까지 엄격하게 |

- `strict`의 7가지 옵션에는 포함되지 않지만 "Stricter Typechecking Options"로 별도 권장되는 옵션이다. 배열이나 동적 객체의 키에 접근할 때 자동으로 `undefined` 가능성을 타입에 추가해준다.

```typescript
// noUncheckedIndexedAccess 추가 검사 예시
const colors: string[] = ["red", "blue"];
// 0번 인덱스의 타입은 string이 아니라 string | undefined로 추론됨
const firstColor = colors[0];

// undefined 가능성을 체크해야 안전하게 사용할 수 있음
if (firstColor !== undefined) {
  console.log(firstColor.toUpperCase());
}
```

**실행 결과**
```
RED
```

- 이 옵션이 없다면 `colors[0]`의 타입은 그냥 `string`으로 추론된다. 문제는 `colors[99]`처럼 배열 범위를 벗어난 인덱스에 접근해도 타입상으로는 여전히 `string`이라서, 컴파일러는 안전하다고 착각하고 통과시켜버린다는 점이다. 실제로는 `undefined`가 반환되므로 `colors[99].toUpperCase()` 같은 코드가 배포된 뒤 런타임에서야 에러가 터진다. `noUncheckedIndexedAccess`는 "인덱스로 꺼낸 값은 존재하지 않을 수도 있다"는 현실을 타입에 강제로 반영해, 위 예시처럼 `if (firstColor !== undefined)` 체크 없이는 애초에 `.toUpperCase()` 호출 자체가 컴파일되지 않게 막는다.

### | 단축 경로(Path Alias)로 복잡한 상대경로 없애기 |

- 파일 구조가 깊어질수록 `../../../services/userService`처럼 상위 폴더를 몇 단계나 거슬러 올라가는 상대 경로가 반복된다. `tsconfig.json`의 `paths` 옵션으로 `@/`같은 단축 경로(Path Alias)를 지정하면, 파일이 어디에 있든 동일한 기호로 접근할 수 있다.

```json
// [tsconfig.json]
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

```typescript
// [src/services/userService.ts]
export interface User {
  id: number;
  name: string;
}

export function getUserInfo(): User {
  return { id: 101, name: "이민수" };
}
```

```typescript
// [src/index.ts]
// [단축 경로 방식] tsconfig.json의 paths 설정을 적용하여 모듈을 불러옴
import { getUserInfo, type User } from "@/services/userService.js";

const user: User = getUserInfo();

console.log(`회원 번호: ${user.id}, 회원 이름: ${user.name}`);
```

**실행 결과** (`npm run dev`)
```
회원 번호: 101, 회원 이름: 이민수
```

- `paths` 단축 경로가 없다면 어떻게 될까. `src/components/profile/edit/Form.ts`처럼 깊은 폴더에 있는 파일에서 `userService.ts`를 가져오려면 `../../../services/userService.js`처럼 상위 폴더 이동 기호를 몇 번이나 겹쳐 써야 한다. 이 코드를 다른 폴더로 옮기기라도 하면 import 경로의 `../` 개수를 전부 다시 세어 고쳐야 하는 번거로움이 생긴다. `@/services/userService.js`처럼 프로젝트 루트 기준의 절대 경로 스타일을 쓰면, 파일이 어느 깊이에 있든 import 문이 똑같이 유지되어 파일 이동에도 깨지지 않는다. 참고로 `tsx`는 이 `paths` 설정을 별도 추가 패키지 없이 그대로 읽어 실행해준다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| tsconfig.json | tsconfig.json | TypeScript 컴파일러의 동작 규칙과 환경을 정의하는 핵심 설정 파일 |
| strict 모드 | Strict Mode | noImplicitAny, strictNullChecks 등 7가지 핵심 엄격 검사를 일괄 활성화하는 마스터 스위치 |
| 인덱스 미검증 접근 차단 | noUncheckedIndexedAccess | 배열/동적 객체 접근 시 undefined 가능성을 타입에 자동 반영하는 옵션 |
| 단축 경로 | Path Alias | `../` 대신 `@/` 기호로 모듈 경로를 간결하게 표현하는 매핑 방식 |
| 타입 전용 불러오기 | Type-only Import | verbatimModuleSyntax 환경에서 타입만 불러올 때 `type` 키워드를 강제하는 규칙 |

# PART 7. ESLint, Prettier 연동 및 정적 분석 검사
### | 왜 코드 스타일과 정적 분석을 자동화해야 하는가 |

- 여러 개발자가 함께 코드를 작성할 때 따옴표 스타일이나 들여쓰기 칸 수가 사람마다 다르면 가독성이 크게 떨어진다. 더 큰 문제는 눈에 잘 띄지 않는 사용하지 않는 변수, `any` 남용 같은 실수가 코드 리뷰에서도 놓치기 쉽고, 이게 결국 런타임 에러로 이어질 수 있다는 점이다. 이런 문제를 사람이 매번 눈으로 검토하는 대신, 서식은 **Prettier**가 자동으로 정돈하고, 문법·품질 문제는 **ESLint**가 정적으로 검출하고, 타입 오류는 **tsc --noEmit**이 한 번에 검증하도록 자동화한다.

### | Prettier로 서식 자동 정돈하기 |

```bash
npm i -D typescript eslint prettier typescript-eslint eslint-config-prettier
```

| 옵션명 | 설정값 타입 | 기본값 | 주요 설명 |
| --- | --- | --- | --- |
| semi | boolean | true | 문장 끝 세미콜론(;)을 항상 붙일지 여부 |
| singleQuote | boolean | false | 큰따옴표(") 대신 작은따옴표(') 사용 여부 |
| tabWidth | number | 2 | 들여쓰기 시 적용할 공백 칸 수 |
| useTabs | boolean | false | 공백 대신 탭(Tab) 문자 사용 여부 |
| trailingComma | string | "all" | 객체/배열 마지막 원소 뒤 쉼표 추가 기준 |
| printWidth | number | 80 | 한 줄 최대 글자 수 (초과 시 자동 줄바꿈) |
| bracketSpacing | boolean | true | 객체 리터럴 괄호 안쪽에 공백 삽입 여부 |
| arrowParens | string | "always" | 화살표 함수 매개변수 1개일 때 괄호 생략 여부 |

```json
// [.prettierrc]
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "useTabs": false,
  "trailingComma": "es5",
  "printWidth": 80,
  "bracketSpacing": true,
  "arrowParens": "always"
}
```

```bash
# src 디렉토리 내 모든 파일의 스타일을 설정값대로 자동 교정
npx prettier --write "src/**/*.ts"
```

- `.prettierrc` 설정 없이 Prettier의 기본값만 쓴다면 어떻게 될까. 예를 들어 팀 내에서 작은따옴표(`'`)를 쓰기로 약속했는데 기본값은 큰따옴표(`"`)라서, 설정 파일 없이는 저장할 때마다 팀의 합의와 다른 스타일로 자동 정돈되어버린다. `.prettierrc`를 프로젝트에 명시해두면 어느 개발자의 컴퓨터에서 저장하든 똑같은 규칙으로 서식이 맞춰진다 — 코드 리뷰에서 "따옴표를 통일해달라"는 식의 불필요한 코멘트 자체가 사라진다.

### | ESLint Flat Config로 문법/품질 검사하기 |

- ESLint v9부터는 과거의 `.eslintrc` 형식 대신 자바스크립트 모듈 기반의 **Flat Config**(`eslint.config.mjs`)가 공식 표준이다.

```javascript
// [eslint.config.mjs]
import eslintConfigPrettier from "eslint-config-prettier";
import tseslint from "typescript-eslint";

export default tseslint.config(
  // TypeScript 권장 검사 규칙 세트 적용
  ...tseslint.configs.recommended,
  // Prettier와 충돌하는 ESLint 서식 규칙 무효화
  eslintConfigPrettier,
  // 프로젝트 전용 커스텀 규칙 설정
  {
    rules: {
      // 사용하지 않는 변수가 있으면 경고(warn) 표시
      "@typescript-eslint/no-unused-vars": "warn",
      // explicit any 사용 시 경고(warn) 표시
      "@typescript-eslint/no-explicit-any": "warn",
      // console.log 허용
      "no-console": "off",
    },
  },
);
```

```typescript
// [src/index.ts]
// 선언 후 사용하지 않은 변수 (ESLint 경고 대상)
const unusedMessage: string = "사용되지 않는 메시지입니다.";

// explicit any 타입을 사용한 함수 (ESLint 경고 대상)
function printData(data: any): void {
  console.log("입력 데이터:", data);
}

printData("테스트 데이터");
```

**실행 결과 — `npm run dev`로 실제 실행했을 때 (ESLint 경고는 실행을 막지 않음)**
```
입력 데이터: 테스트 데이터
```

**실행 결과 — `npx eslint .`로 정적 분석했을 때**
```
src/index.ts
  1:7  warning  'unusedMessage' is assigned a value but never used  @typescript-eslint/no-unused-vars
  4:29  warning  Unexpected any. Specify a different type  @typescript-eslint/no-explicit-any

✖ 2 problems (0 errors, 2 warnings)
```

- ESLint가 없다면 `unusedMessage`처럼 선언만 해두고 쓰지 않는 변수나 `data: any`처럼 타입 검사를 무력화하는 코드가 코드베이스에 계속 쌓여도 아무도 알아채지 못한다. 변수 자체는 문법적으로 틀린 게 아니라서 `tsc` 컴파일도 통과하고, 프로그램도 정상적으로 동작하기 때문이다(위 실행 결과처럼). 즉 ESLint는 "실행은 되지만 품질이 떨어지는 코드"를 잡아내는 역할을 하고, `.vscode/settings.json`에 `"editor.codeActionsOnSave": { "source.fixAll.eslint": "explicit" }`를 설정해두면 파일을 저장(Ctrl+S)할 때마다 고칠 수 있는 부분은 자동으로 정돈된다.

### | tsc --noEmit과 quality-check 통합 파이프라인 |

- `tsc --noEmit`은 실제 자바스크립트 변환 파일(.js)을 생성하지 않고, 프로젝트 전체의 타입 오류 존재 여부만 빠르게 검증하는 명령어다.

```json
// [tsconfig.json] — noEmit 옵션 발췌
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "outDir": "./dist",
    "rootDir": "./src",
    "esModuleInterop": true,
    "strict": true,
    "noEmit": false
  },
  "include": ["src/**/*"]
}
```

```json
// [package.json] — scripts 발췌
{
  "scripts": {
    "lint": "eslint .",
    "format": "prettier --write \"src/**/*.ts\"",
    "check": "tsc --noEmit",
    "quality-check": "npm run format && npm run lint && npm run check"
  }
}
```

```bash
npm run quality-check
```

- `tsc --noEmit`이 없다면 타입 오류만 확인하고 싶어도 매번 실제 `.js` 결과 파일을 `dist` 폴더에 생성하는 전체 컴파일 과정을 거쳐야 한다. 디스크에 불필요한 산출물이 계속 쌓이고, 단순히 "타입 에러가 있는지 없는지"만 빠르게 알고 싶은 상황에서도 느린 빌드 전체를 기다려야 하는 비효율이 생긴다.
- `quality-check`처럼 `format && lint && check`를 한 명령어로 묶어두지 않으면 어떻게 될까. 개발자마다 배포 전에 format만 돌리고 lint는 깜빡하거나, lint만 돌리고 타입 체크는 생략하는 식으로 검증 범위가 들쭉날쭉해진다. 하나의 스크립트로 묶어두면 "이 명령어 하나만 통과하면 서식·문법·타입 세 가지가 모두 안전하다"는 일관된 기준을 팀 전체가 공유하게 된다. 이는 PART 6에서 본 `"strict": true`가 7가지 옵션을 하나로 묶어 관리하던 것과 같은 발상 — 개별 검사를 사람이 하나씩 기억해 실행하는 대신, 통합된 진입점 하나로 전체 품질을 보장하는 방식이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| Prettier 옵션 | Prettier Options | 들여쓰기·따옴표·줄바꿈 등 세부 서식 기준을 지정하는 설정 항목 |
| Flat Config | Flat Config | ESLint v9에서 도입된 자바스크립트 모듈 기반의 최신 설정 파일 체계 (eslint.config.mjs) |
| 컴파일러 옵션 | Compiler Options | TypeScript 코드를 검사하거나 자바스크립트로 변환할 때 적용하는 tsconfig.json의 설정 항목 |
| No-Emit | No-Emit | 자바스크립트 변환 결과 파일(.js)을 생성하지 않고 타입 검사만 수행하는 옵션 |
| 통합 파이프라인 | Quality-check Pipeline | format·lint·check를 순차 실행해 서식·문법·타입을 한 번에 검증하는 스크립트 |
