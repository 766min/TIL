# PART 1. Client-Server 구조 & HTTP 개요
### | 클라이언트와 서버는 왜 역할을 나누나 |

- 웹은 서비스를 요청하는 **클라이언트(Client)**와 그 요청을 처리해서 응답하는 **서버(Server)**로 역할이 나뉜 구조로 동작한다. 식당에 비유하면 손님이 메뉴판을 보고 주문서를 작성해 전달하면 주방이 음식을 만들어 돌려주는 과정과 같다.

| 구분 | 역할 |
| --- | --- |
| 클라이언트 | 웹 브라우저나 모바일 앱처럼 사용자의 입력을 받아 서버에 데이터를 요청(Request)하는 주체 |
| 서버 | 요청을 받아 DB 조회나 로직 처리를 한 뒤 결과를 응답(Response)하는 시스템 |

- 화면을 보여주는 영역(클라이언트)과 데이터를 처리하는 영역(서버)을 분리하지 않으면 어떻게 될까. 둘이 한 덩어리로 묶여 있으면 화면 디자인을 바꾸는 작업과 데이터베이스 로직을 바꾸는 작업이 서로 얽혀서, 한쪽을 고치다가 다른 쪽까지 영향을 주는 사고가 자주 일어난다. 역할을 분리해두면 프런트엔드 개발자와 백엔드 개발자가 각자 담당 영역만 독립적으로 관리할 수 있고, 보안 측면에서도 민감한 로직(DB 접근, 인증)을 서버 안에 가둬둘 수 있다.

### | 요청이 먼저, 응답은 그다음 |

- 웹의 기본 대화는 항상 **[클라이언트의 요청 → 서버의 처리 → 서버의 응답]** 순서로만 진행된다. 식당에서 손님이 주문하기 전에 음식이 먼저 나오지 않는 것과 같은 원리다.
- 이 순서가 강제되지 않는다면 어떻게 될까. 서버가 아무 때나 클라이언트에게 데이터를 임의로 들이밀 수 있다면, 클라이언트는 지금 받은 데이터가 자신이 원했던 요청에 대한 응답인지 아니면 서버가 일방적으로 보낸 데이터인지 구분할 방법이 없어진다. "요청이 있어야만 응답이 온다"는 규칙 자체가, 브라우저가 받은 데이터를 어떤 요청의 결과로 해석해야 할지 명확하게 만들어주는 전제 조건이다.

### | 요청 전문과 응답 전문의 구조 |

- 클라이언트와 서버는 임의로 소통하지 않고, 정해진 서식(전문)을 갖춰 대화한다.

| 요청 전문(Request Message) | 응답 전문(Response Message) |
| --- | --- |
| **시작줄(Start Line)**: 어떤 방식(Method)으로 어디(URL)에 요청할지 | **상태줄(Status Line)**: 처리 결과를 숫자로 나타낸 상태 코드 |
| **헤더(Headers)**: 브라우저 정보, 데이터 타입, 쿠키 등 부가 정보 | **헤더(Headers)**: 서버 종류, 응답 데이터 길이, Content-Type 등 |
| **본문(Body)**: 서버로 보낼 실제 데이터 (생략 가능) | **본문(Body)**: 클라이언트가 받아볼 실제 화면 데이터(HTML, JSON 등) |

- 요청 전문을 "약속된 주문서", 응답 전문을 "약속된 영수증"에 비유할 수 있다. 서식이 정해져 있지 않다면 서버마다 응답을 "성공했어요" 같은 자연어 문장으로 돌려줄 수도 있는데, 그러면 클라이언트 프로그램이 이 문장을 해석해 성공/실패를 판단하는 로직을 서버마다 따로 만들어야 한다. 상태줄의 상태 코드처럼 숫자로 약속된 형식이 있어야, 어떤 클라이언트든 같은 방식으로 결과를 파싱할 수 있다.

### | 요청과 응답의 공통 헤더(General Headers) |

- 요청 전문과 응답 전문 어느 한쪽에만 귀속되지 않고 양쪽 메시지 모두에서 공통으로 쓰이는 헤더다.

| 헤더명 | 역할 | 예시 |
| --- | --- | --- |
| Content-Type | 본문(Body) 데이터의 종류를 기술 | application/json, text/html |
| Content-Length | 본문 데이터의 전체 크기(Byte) | 83, 1024 |
| Date | 메시지가 생성·전달된 일시 | Wed, 22 Jul 2026 12:00:00 GMT |
| Connection | 응답 완료 후 네트워크 연결 유지 여부 | keep-alive, close |

### | curl로 실제 전문 확인하기 |

```bash
# -v (verbose) 옵션을 붙여 터미널에서 요청 전문과 응답 전문을 직접 확인
curl -v https://jsonplaceholder.typicode.com/todos/1
```

**실행 결과**
```
# '>' 로 시작하는 줄: 클라이언트가 작성해 전달한 요청 전문
> GET /todos/1 HTTP/1.1
> Host: jsonplaceholder.typicode.com
> User-Agent: curl/7.81.0

# '<' 로 시작하는 줄: 서버가 처리 후 보내온 응답 전문
< HTTP/1.1 200 OK
< Content-Type: application/json; charset=utf-8
< Content-Length: 83

# 응답 전문 하단 본문(Body)에 담겨 돌아온 실제 데이터
{
  "userId": 1,
  "id": 1,
  "title": "delectus aut autem",
  "completed": false
}
```

- `>`로 시작하는 줄이 요청 전문(시작줄 + 헤더), `<`로 시작하는 줄이 응답 전문(상태줄 + 헤더)이고, 맨 마지막에 응답 본문(JSON)이 따라온다. 평소 브라우저가 알아서 처리해주던 "요청을 보내고 응답을 받는" 과정이, 실제로는 이런 텍스트 형태의 전문을 주고받는 일이라는 걸 눈으로 확인하는 실습이다.

### | HTTP의 비연결성(Connectionless)과 무상태성(Stateless) |

- **HTTP**는 HyperText Transfer Protocol의 약자로, 웹에서 문서나 데이터를 주고받기 위한 표준 통신 약속이다. HTTP는 응답이 끝나면 연결을 끊고, 이전 대화 상태를 기억하지 않는다는 두 가지 중요한 특성을 가진다.

| 특성 | 설명 | 장점 | 단점/영향 |
| --- | --- | --- | --- |
| 비연결성(Connectionless) | 응답을 마치면 즉시 TCP/IP 연결을 끊음 | 서버가 수많은 사용자와의 연결을 계속 유지하지 않아도 되어 자원을 아낌 | 다음 요청마다 매번 새로 연결을 맺어야 해서 통신 오버헤드 발생 |
| 무상태성(Stateless) | 서버가 이전 요청이나 상태를 저장하지 않고, 각 요청을 독립적으로 처리 | 서버 쪽 메모리 부담이 적고 서버를 여러 대로 쉽게 늘릴 수 있음 | 로그인 상태처럼 "기억해야 할 정보"를 서버가 자동으로 유지하지 못함 — 쿠키·세션·토큰(JWT) 같은 보완 기술 필요 |

- 만약 HTTP가 비연결성이 아니라 매 사용자와 연결을 계속 유지하는 방식이었다면 어떻게 될까. 동시 접속자가 수만 명인 서비스에서는 서버가 그 수만 개의 연결을 전부 메모리에 붙잡고 있어야 해서 자원이 금방 바닥난다. 대신 "응답하고 바로 끊는다"는 원칙 덕분에 서버는 한 번에 처리하고 다음 요청을 받을 준비를 바로 할 수 있다.
- 무상태성도 마찬가지다. 쇼핑몰에서 로그인한 후 다른 페이지로 이동해도, 서버 입장에서는 이 요청이 로그인된 사용자의 요청인지 아무 정보 없이는 알 수 없다. 그래서 로그인 상태를 유지하려면 클라이언트 쪽에 식별 정보를 저장해두고 매 요청마다 함께 보내는 방식(쿠키, 세션, 토큰)이 필요하다 — 이 내용은 PART 2에서 직접 실습으로 확인한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 클라이언트 | Client | 사용자 입력을 받아 서버에 데이터를 요청하는 프로그램 |
| 서버 | Server | 요청을 수신해 로직 처리 후 응답 결과를 제공하는 시스템 |
| 요청 전문 | Request Message | 클라이언트가 서버에 작성해 보내는 약속된 HTTP 서식 |
| 응답 전문 | Response Message | 서버가 처리 결과와 데이터를 담아 보내는 약속된 HTTP 서식 |
| 공통 헤더 | General Headers | Content-Type, Date 등 요청·응답 양쪽에서 쓰이는 헤더 |
| 비연결성 | Connectionless | 응답 후 연결을 즉시 해제하는 HTTP 특성 |
| 무상태성 | Stateless | 서버가 이전 요청 상태를 기억하지 않는 HTTP 특성 |

# PART 2. 크롬 Network 탭 & Headers/Cookies
### | Network 탭으로 통신 내역 들여다보기 |

- 크롬 개발자 도구의 **Network 탭**은 브라우저와 서버 간에 오가는 모든 데이터 통신 내역(HTML, CSS, JS, 이미지, API 데이터 등)을 실시간으로 확인하는 도구다.

| 항목 | 의미 |
| --- | --- |
| Name | 요청한 리소스 이름 또는 API 엔드포인트 주소 |
| Status | 서버 처리 결과를 나타내는 3자리 상태 코드 |
| Type | 불러온 리소스 종류(document, script, fetch, png 등) |
| Size & Time | 전달된 데이터 크기와 통신 소요 시간 |

- Request Headers(요청 헤더)에는 `Host`(수신 서버 도메인), `User-Agent`(브라우저·OS 정보), `Accept`(수신 가능한 데이터 형식)가 담기고, Response Headers(응답 헤더)에는 `Content-Type`(응답 본문 형식), `Server`(처리한 서버 소프트웨어 정보)가 담긴다.

### | 무상태성을 보완하는 클라이언트 저장소 |

- PART 1에서 본 HTTP 무상태성 때문에, 서버는 "이 요청이 어느 클라이언트에서 왔는지" 자체 정보만으로는 식별할 수 없다. 그래서 서버가 식별 정보를 클라이언트에게 전달해 브라우저 저장소에 보관하게 만드는 방식을 쓴다. 용도와 유지 기간에 따라 세 가지로 나뉜다.

| 구분 | Cookie | LocalStorage | SessionStorage |
| --- | --- | --- | --- |
| HTTP 자동 전송 | O (요청 헤더에 자동 포함) | X (클라이언트 전용) | X (클라이언트 전용) |
| 데이터 유지 기간 | 만료일 지정(미지정 시 세션 종료 시 삭제) | 영구 보관(수동 삭제 전까지) | 탭/창을 닫으면 즉시 삭제 |
| 저장 용량 | 도메인당 약 4KB | 도메인당 약 5MB 이상 | 도메인당 약 5MB 이상 |

- 셋 중에서 쿠키만 HTTP 요청에 자동으로 포함된다는 점이 핵심이다. LocalStorage나 SessionStorage는 용량이 훨씬 크지만, 서버가 "이 요청이 누구 것인지" 알아내려면 자바스크립트로 값을 읽어서 직접 요청에 실어 보내야 한다 — 로그인 상태 유지처럼 매 요청마다 자동으로 서버에 전달돼야 하는 정보는 쿠키가 아니면 번거로워진다.

### | 쿠키의 주요 속성(Attributes) |

| 속성명 | 설명 |
| --- | --- |
| Name / Value | 쿠키를 식별하는 이름과 실제 저장 데이터 |
| Domain / Path | 쿠키를 전송할 수 있는 도메인·URL 경로 범위 |
| Expires / Max-Age | 쿠키의 만료 일시 또는 유효 수명 |
| HttpOnly | 자바스크립트(document.cookie)의 접근을 차단해 XSS 공격 방지 |
| Secure | HTTPS 암호화 통신 환경에서만 쿠키를 전송하도록 제한 |
| SameSite | 서드파티 요청 시 쿠키 전송 여부를 제어해 CSRF 공격 방지 |

- `HttpOnly`가 없다면 어떻게 될까. 페이지에 악성 스크립트가 심어졌을 때(XSS) 그 스크립트가 `document.cookie`로 로그인 쿠키 값을 그대로 읽어 외부 서버로 빼돌릴 수 있다. `HttpOnly`를 켜두면 자바스크립트 자체가 쿠키 값에 접근할 수 없으므로, 이런 탈취 경로를 원천 차단한다.

### | Set-Cookie와 Cookie 헤더 추적 실습 |

- 시크릿 창으로 네이버에 접속해 개발자 도구 Network 탭에서 `www.naver.com` 문서 요청을 클릭하면, Response Headers 영역에 서버가 지정한 `Set-Cookie` 필드가 보인다. 이어서 Application 탭의 Storage → Cookies 항목으로 들어가면, 방금 `Set-Cookie`로 지정된 쿠키가 Name·Value·Domain·Path·Expires 형태로 브라우저에 실제 저장된 것을 확인할 수 있다.
- 이 상태에서 페이지 내 링크를 클릭하거나 새로고침(F5)하면, 새로 발생한 네트워크 요청의 Request Headers에 `Cookie` 필드가 자동으로 붙어 있는 것을 확인할 수 있다. 즉 "서버가 Set-Cookie로 저장을 지시 → 브라우저가 저장 → 같은 도메인으로 재요청할 때 Cookie 헤더에 자동으로 실어 보냄"이라는 한 사이클이, Network 탭과 Application 탭을 오가며 눈으로 검증된다. 이 자동 첨부 과정이 없다면, 로그인한 사용자가 페이지를 이동할 때마다 자바스크립트로 직접 로그인 정보를 매번 요청에 끼워 넣어야 하는 번거로움이 생긴다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 애플리케이션 탭 | Application Tab | 쿠키·웹 스토리지·캐시 등 클라이언트 데이터를 관리하는 개발자 도구 패널 |
| HttpOnly | HttpOnly | 자바스크립트의 쿠키 접근을 금지해 XSS를 방지하는 옵션 |
| Secure | Secure | HTTPS 연결에서만 쿠키를 전송하도록 제약하는 옵션 |
| 로컬 스토리지 | LocalStorage | 서버로 자동 전송되지 않고 영구 보관되는 클라이언트 저장소 |
| 세션 스토리지 | SessionStorage | 서버로 자동 전송되지 않고 탭이 열려 있는 동안만 유지되는 저장소 |

# PART 3. HTTP 메서드 & 상태 코드
### | HTTP 메서드와 CRUD 매핑 |

- HTTP 메서드는 클라이언트가 서버에게 요청의 '행위(목적)'를 명확히 알리는 표준 명령어다.

| 메서드 | CRUD | 역할 |
| --- | --- | --- |
| GET | Read | 리소스 조회. 데이터 변경 없이 가져오기만 해서 안전함 |
| POST | Create | 새 리소스 생성. 새 데이터를 Body에 담아 전송 |
| PUT | Update(전체) | 기존 리소스를 전체 교체. 교체할 전체 데이터를 Body에 담아 전송 |
| PATCH | Update(일부) | 기존 리소스의 특정 속성만 수정. 수정할 일부 데이터만 Body에 전송 |
| DELETE | Delete | 특정 리소스 삭제 |
| HEAD | - | GET과 동일하게 요청하되 응답 본문(Body) 없이 헤더만 받음 |

- 메서드를 구분하지 않고 전부 POST 하나로 처리한다면 어떻게 될까. 서버 입장에서는 이 요청이 "조회"인지 "삭제"인지 URL과 본문을 일일이 해석해야 하고, 중간에 있는 캐시 서버나 브라우저도 "이 요청은 안전하니 캐싱해도 된다"는 판단을 내릴 수 없다. GET처럼 데이터를 변경하지 않는 메서드를 구분해두면 캐싱·재시도 같은 최적화가 가능해진다.

### | OPTIONS와 CORS Preflight(교차 출처 사전 검증) |

- **출처(Origin)**는 프로토콜 + 도메인 + 포트번호 조합이다. `http://localhost:3000`과 `https://api.example.com`은 서로 다른 출처다.
- **CORS(Cross-Origin Resource Sharing)**는 내가 만든 웹사이트가 다른 출처의 서버에 데이터를 요청할 때, 브라우저가 보안상 허용된 요청인지 확인하는 규칙이다.
- **Preflight(예비 요청)**는 브라우저가 데이터 변경 가능성이 있는 본 요청(POST, PUT, PATCH 등)을 보내기 전, `OPTIONS` 메서드로 서버에 "다른 출처인 내가 요청을 보내도 되나요?"라고 먼저 확인하는 자동 보안 과정이다.
- Preflight가 없다면 어떻게 될까. 악성 사이트가 사용자 몰래 다른 은행 사이트로 송금 요청(POST)을 보내는 식의 공격(CSRF와 유사한 흐름)을 브라우저가 막을 방법이 사라진다. 브라우저가 본 요청 전에 "이 출처가 허용 목록에 있는지" OPTIONS로 먼저 확인하고, 서버가 거부하면 본 요청 자체를 보내지 않는 식으로 1차 방어선을 만드는 것이다.

### | HTTP 상태 코드 분류 |

| 분류 | 의미 | 대표 코드 |
| --- | --- | --- |
| 2xx (Successful) | 요청이 정상적으로 수신·처리됨 | 200 OK(성공), 201 Created(생성 성공) |
| 3xx (Redirection/Caching) | 추가 조치 필요, 또는 캐시 재사용 | 301/302(URL 변경), 304 Not Modified(캐시 재사용) |
| 4xx (Client Error) | 클라이언트 요청 오류 | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found |
| 5xx (Server Error) | 서버 내부 오류 | 500 Internal Server Error, 502/503(과부하·점검) |

- `304 Not Modified`가 없다면 어떻게 될까. 브라우저가 이미 받아서 저장해둔 이미지나 페이지를 서버 데이터가 전혀 바뀌지 않았는데도 매번 처음부터 다시 다운로드해야 한다. 304는 "데이터가 그대로니 네가 가진 캐시를 그대로 써라"라고 알려줘서 불필요한 네트워크 트래픽을 줄여준다.

### | Postman으로 메서드별 요청 실습 |

- Postman은 코드를 작성하지 않고도 버튼 클릭과 입력창만으로 HTTP 요청을 보내고 응답을 테스트할 수 있는 API 전용 도구다. `https://jsonplaceholder.typicode.com`을 대상으로 메서드별 실습을 진행했다.

```
# GET /posts/1
Method: GET
URL: https://jsonplaceholder.typicode.com/posts/1
```
**응답 결과**: `200 OK` — 1번 게시글 데이터 반환

```json
// POST /posts — Body(raw/JSON)
{
  "title": "Postman 테스트",
  "body": "새로운 글 생성하기",
  "userId": 1
}
```
**응답 결과**: `201 Created` — Body 탭에서 raw → JSON을 선택하면 Headers 탭에 `Content-Type: application/json`이 자동으로 추가된다.

```json
// PUT /posts/1 — 전체 필드를 다 채워서 전송
{
  "id": 1,
  "title": "완전히 교체된 제목",
  "body": "완전히 교체된 내용",
  "userId": 1
}
```
**응답 결과**: `200 OK` — 기존 데이터가 전체 교체됨

```json
// PATCH /posts/1 — 바꿀 필드만 전송
{
  "title": "제목만 쏙 수정하기"
}
```
**응답 결과**: `200 OK` — title만 변경되고 나머지 필드는 그대로 유지됨

- POST는 201(새로 생성됨), PUT/PATCH는 200(기존 리소스를 수정함)으로 상태 코드가 다르게 돌아온다는 점이 핵심이다. 같은 "성공"이라도 "새로 만들었다"와 "기존 것을 고쳤다"를 상태 코드로 구분해주기 때문에, 클라이언트 코드에서 응답을 처리할 때 이 둘을 섞어서 판단하는 실수를 줄일 수 있다.

# PART 4. Body 데이터 양식 & Content-Type 테스트
### | Content-Type 헤더가 하는 일 |

- `Content-Type`은 HTTP 요청 본문(Body)에 담긴 데이터의 포맷과 구조를 서버에 전달하는 헤더다. 서버가 수신한 본문을 올바르게 파싱(Parsing)할 수 있도록 데이터 규격을 알려주는 역할이고, 클라이언트가 요청을 전송할 때 설정한다. 명시한 타입과 실제 데이터 형식이 다르면 서버 처리 에러가 발생한다.
- Content-Type이 없다면 어떻게 될까. 서버는 받은 본문 문자열이 `key=value` 형태인지 `{"key":"value"}` 형태인지 스스로 추측해야 한다. 추측이 틀리면 파싱 자체가 실패하거나 엉뚱한 값을 읽어들이는 사고로 이어진다. Content-Type은 "이 본문을 이 방식으로 읽어라"는 지침을 미리 못 박아두는 역할을 한다.

### | x-www-form-urlencoded와 URL 인코딩 |

- 각 항목을 `키=값` 형태로 작성하고 여러 항목을 `&`로 연결한다. (`key1=value1&key2=value2`)
- **URL 인코딩(Percent Encoding)**: 한글, 공백, 특수문자 등이 구획용 예약어(`=`, `&`, `?` 등)와 혼동되지 않도록 `%`와 16진수 코드로 변환하는 규격이다. 예를 들어 '홍길동' → `%ED%9D%8D%EA%B8%B8%EB%8F%99`, 공백 → `%20`, `&` → `%26`으로 변환된다.
- 실제 전송되는 원시 문자열 예시: `username=%ED%9D%8D%EA%B8%B8%EB%8F%99&title=react%20%26%20next`
- URL 인코딩이 없다면 어떻게 될까. `title=react & next`처럼 값 자체에 `&`가 포함된 데이터를 그냥 보내면, 서버는 `&` 이후를 새로운 key로 오해해서 `title=react`와 알 수 없는 ` next`라는 두 개의 항목으로 잘못 쪼개 해석한다. URL 인코딩은 데이터 안의 특수문자가 구분 기호와 충돌하는 사고를 막기 위한 안전장치다.

### | application/json 포맷과의 비교 |

| 구분 | application/x-www-form-urlencoded | application/json |
| --- | --- | --- |
| 원시 데이터 형태 | key1=value1&key2=value2 | {"key1": "value1", "key2": "value2"} |
| 인코딩 처리 | 한글·특수문자가 URL 인코딩되어 전송됨 | 문자열 그대로 UTF-8 변환되어 전송됨 |
| 주요 사용처 | HTML `<form>` 태그 기반 전송 | REST API 통신, SPA(React, Next.js) |

### | HTML/JS로 두 방식을 직접 전송해보기 |

```html
<!DOCTYPE html>
<html lang="ko">
<body>
  <!-- 1. Form 방식 전송 영역 -->
  <form id="formSubmit">
    <input type="text" name="username" value="홍길동">
    <input type="text" name="title" value="react & next">
    <button type="submit">Form 방식으로 전송</button>
  </form>

  <!-- 2. JSON 방식 전송 영역 -->
  <button id="jsonSubmit">JSON 방식으로 전송</button>

  <script>
    // Form 제출 이벤트 처리
    document.getElementById('formSubmit').addEventListener('submit', function(e) {
      e.preventDefault(); // Form 기본 제출(페이지 새로고침) 방지

      const formData = new FormData(this);
      // Form 데이터를 urlencoded 형식 및 URL 인코딩 문자열로 변환
      const searchParams = new URLSearchParams(formData);

      fetch('https://httpbin.org/post', {
        method: 'POST',
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
        body: searchParams
      });
    });

    // JSON 전송 이벤트 처리
    document.getElementById('jsonSubmit').addEventListener('click', function() {
      const data = { username: '홍길동', title: 'react & next' };

      fetch('https://httpbin.org/post', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(data) // 객체를 JSON 문자열로 직렬화
      });
    });
  </script>
</body>
</html>
```

- 이 코드가 실제로 만드는 동작: 'Form 방식으로 전송' 버튼을 누르면 Network 탭에 새 `post` 요청이 생기고, Headers 탭에는 `Content-Type: application/x-www-form-urlencoded`가, Payload 탭에는 `username: 홍길동`, `title: react & next`가 Form Data 형태로 찍힌다. 'JSON 방식으로 전송' 버튼을 누르면 또 다른 `post` 요청이 생기는데, 이번엔 Headers가 `application/json`이고 Payload 탭에는 `{"username":"홍길동","title":"react & next"}`라는 문자열이 그대로 찍힌다. 같은 데이터인데 버튼에 따라 Content-Type과 Payload 형태가 완전히 달라지는 모습을 Network 탭 하나로 비교할 수 있다.

### | Postman으로 Body 데이터와 URL 인코딩 검증하기 |

- Body 탭에서 `x-www-form-urlencoded`를 선택하고 `username: 홍길동`, `title: react & next`를 입력해 전송하면, Postman 좌측 하단 Console 창에 실제 전송된 원시 Request Body가 `username=%ED%9D%8D%EA%B8%B8%EB%8F%99&title=react%20%26%20next` 형태로 URL 인코딩되어 찍히는 것을 확인할 수 있다. Headers 탭에는 `Content-Type: application/x-www-form-urlencoded`가 자동으로 설정된다.
- 같은 데이터를 Body 탭 raw → JSON으로 바꿔서 `{"username": "홍길동", "title": "react & next"}`를 입력해 전송하면, Console 창에는 URL 인코딩 없이 작성한 JSON 텍스트가 그대로 찍히고 Headers의 Content-Type은 `application/json`으로 바뀐다. 똑같은 "전송 버튼 클릭"이라도 Body 탭에서 고른 옵션에 따라 실제로 네트워크에 흘러가는 원시 데이터의 생김새 자체가 달라진다는 것을 Console 로그로 직접 비교했다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 컨텐트 타입 | Content-Type | HTTP 본문에 담긴 데이터 형식을 정의하는 헤더 필드 |
| URL 인코딩 | URL Encoding | 문자·기호를 `%XX` 형태의 안전한 코드로 변환하는 작업 |
| 포스트맨 콘솔 | Postman Console | 실제 HTTP 요청/응답의 원시 데이터 로그를 확인하는 창 |
| 응답 본문 | Response Body | 요청 처리 후 서버가 클라이언트로 반환하는 데이터 본문 |

Q5. tailwind-merge 유틸리티가 `px-4`와 `px-8`처럼 동일 속성에 대한 Tailwind 클래스가 동시에 존재할 때 수행하는 역할을 한 문장으로 설명하세요.

내 제출 답안 : 미제출 (오답 ❌)

[ 정답 ] 후순위 클래스로 충돌하는 기존 클래스를 정상적으로 덮어쓴다
