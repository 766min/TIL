# PART 1. Immer & 중첩 객체 불변성
배달 앱에서 주소를 바꿨는데 주문 화면에는 예전 주소가 그대로 남아있는 경우를 겪을 수 있다. React는 리렌더링 여부를 판단할 때 객체 내부 속성을 하나하나 비교하지 않고, 객체의 메모리 주소(참조값)만 빠르게 확인한다. 그래서 객체 내부 데이터를 직접 수정해도 메모리 주소가 그대로면 React는 변화를 감지하지 못하고 화면을 갱신하지 않는다. 이 문제를 이해하고 다루는 법을 오늘 첫 주제로 정리한다.

### | 리액트는 왜 "얕은 비교"만 하는가 — 직접 수정(Mutation)의 함정 |

- **얕은 비교(Shallow Compare)**: 객체의 깊은 내부 속성까지 검색하지 않고, 겉면의 메모리 참조 주소만 빠르게 비교하는 방식이다.
- **직접 수정(Mutation)의 문제**: 객체의 속성을 직접 수정하면 데이터는 변하지만 참조 주소는 유지되므로, 리액트가 상태 변화를 감지하지 못한다.

```tsx
'use client';

import { useState } from 'react';

interface User {
  name: string;
  address: {
    city: string;
  };
}

export default function NativeMutateTest(): React.JSX.Element {
  const [user, setUser] = useState<User>({
    name: '홍길동',
    address: {
      city: '서울',
    },
  });

  const handleMutateCity = () => {
    const prevRef = user; // 수정 전 참조를 따로 저장해서 비교해본다

    // 객체의 속성을 직접 수정한다. (메모리 주소 유지)
    user.address.city = '부산';

    setUser(user);

    console.log('참조 주소가 같은가?', prevRef === user);
    console.log('현재 user 객체 내 city 값:', user.address.city);
  };

  return (
    <div style={{ border: '1px solid #ff4d4f', padding: '15px', borderRadius: '8px', marginBottom: '20px' }}>
      <h3>직접 수정 테스트 (렌더링 미발생)</h3>
      <p>이름: {user.name}</p>
      <p>도시: {user.address.city}</p>
      <button onClick={handleMutateCity}>도시를 부산으로 직접 수정</button>
    </div>
  );
}
```

**콘솔 출력 (버튼 클릭 시)**
```
참조 주소가 같은가? true
현재 user 객체 내 city 값: 부산
```

- 화면에서 실제 벌어지는 일: 버튼을 눌러도 화면에 보이는 "도시: 서울"이라는 글자는 바뀌지 않는다. 콘솔에는 분명히 `city: 부산`이 찍히는데도 화면은 그대로다. `user.address.city = '부산'`으로 city 값 자체는 바뀌었지만 `user`라는 객체의 메모리 주소는 그대로이기 때문이다. `setUser(user)`로 "상태를 바꿔달라"고 요청해도, 리액트 입장에서는 이전 `user`와 새로 전달된 `user`가 같은 참조이므로 "상태가 그대로"라고 판단하고 리렌더링을 건너뛴다.
- **왜 불변성을 지켜야 하는가 (직접 수정하면 어떻게 되는가)**: 데이터는 실제로 바뀌었는데 화면만 낡은 상태를 계속 보여주는, 발견하기 매우 어려운 버그로 이어진다. 콘솔 로그상으로는 `city: 부산`이 멀쩡히 찍혀 있으니 "데이터는 맞는데 왜 화면만 안 바뀌지?"라는 디버깅 지옥에 빠지기 쉽다. 게다가 여러 컴포넌트가 같은 객체를 참조하고 있었다면, 한 곳에서 직접 수정한 값이 예고 없이 다른 곳까지 영향을 미치는 사이드 이펙트로 번져서 추적이 거의 불가능해진다. 이것이 "상태를 변경할 때는 항상 원본을 보존하고, 변경 사항이 반영된 새로운 객체를 만들어 전달해야 한다"는 불변성 규칙이 필요한 이유다.

### | 전개 연산자(Spread)로 중첩 객체 복사하기 — 그리고 그 한계 |

```tsx
'use client';

import { useState } from 'react';

interface UserProfile {
  name: string;
  details: {
    age: number;
    location: {
      city: string;
    };
  };
}

export default function NativeSpreadTest() {
  const [profile, setProfile] = useState<UserProfile>({
    name: '이영희',
    details: {
      age: 22,
      location: {
        city: '인천',
      },
    },
  });

  const handleUpdateCity = () => {
    setProfile((prev) => {
      const next = {
        ...prev, // 1단계 객체 복사
        details: {
          ...prev.details, // 2단계 객체 복사
          location: {
            ...prev.details.location, // 3단계 객체 복사
            city: '제주', // 변경할 속성만 덮어쓰기
          },
        },
      };

      console.log('1단계 참조가 다른가?', prev !== next);
      console.log('2단계 참조가 다른가?', prev.details !== next.details);
      console.log('3단계 참조가 다른가?', prev.details.location !== next.details.location);

      return next;
    });
  };

  return (
    <div style={{ border: '1px solid #1890ff', padding: '15px', borderRadius: '8px', marginBottom: '20px' }}>
      <h3>전개 연산자 복사 테스트 (정상 렌더링)</h3>
      <p>이름: {profile.name}</p>
      <p>나이: {profile.details.age}</p>
      <p>도시: {profile.details.location.city}</p>
      <button onClick={handleUpdateCity}>전개 연산자로 도시를 제주로 변경</button>
    </div>
  );
}
```

**콘솔 출력 (버튼 클릭 시)**
```
1단계 참조가 다른가? true
2단계 참조가 다른가? true
3단계 참조가 다른가? true
```

- 이번엔 화면의 "도시: 인천"이 "도시: 제주"로 바로 바뀐다. `city`가 들어있는 `location` 객체부터 그걸 감싸는 `details`, 최상위 `profile`까지 세 단계 모두 전개 연산자로 새로 복사했기 때문에 참조 주소가 전부 달라졌고, 리액트가 변화를 정확히 감지해서 리렌더링한다.
- 전개 연산자의 한계: 변경하려는 속성이 2단계(`details`)에 있으면 전개 연산자를 2번, 3단계(`location`)에 있으면 3번 중첩해서 써야 한다. 깊이가 5단계, 6단계로 더 깊어지면 `{ ...a, b: { ...a.b, c: { ...a.b.c, d: {...} } } }`처럼 코드가 피라미드 모양으로 계속 깊어지고, 어느 한 단계라도 전개(`...`)를 빠뜨리면 그 지점에서 다시 PART 1 첫 예제와 똑같은 "참조 유지" 버그가 생긴다.

### | Immer의 produce와 Draft — 중첩 객체를 "그냥 쓰듯" 수정하기 |

- **Draft State(임시 상태)**: 원본 데이터의 변경 사항을 수집하기 위해 Immer가 내부적으로 생성하는 프록시(Proxy) 객체다.
- **produce 함수**: `produce(현재상태, (draft) => { draft 수정 로직 })` 구조로 동작하며, 수정된 Draft 내용을 바탕으로 최종 불변 객체를 만들어낸다.

```tsx
'use client';

import { useState } from 'react';
import { produce } from 'immer';

interface UserSetting {
  id: number;
  info: {
    nickname: string;
    options: {
      darkMode: boolean;
    };
  };
}

export default function ImmerBasicTest() {
  const [setting, setSetting] = useState<UserSetting>({
    id: 1,
    info: {
      nickname: '코딩초보',
      options: {
        darkMode: false,
      },
    },
  });

  const handleToggleDarkMode = () => {
    setSetting((prevSetting) => {
      const nextSetting = produce(prevSetting, (draft) => {
        // 전개 연산자 없이 깊은 속성의 값을 직접 변경한다.
        draft.info.options.darkMode = !draft.info.options.darkMode;
      });

      console.log('수정 전 darkMode:', prevSetting.info.options.darkMode);
      console.log('수정 후 darkMode:', nextSetting.info.options.darkMode);
      console.log('참조 주소가 다른가?', prevSetting !== nextSetting);

      return nextSetting;
    });
  };

  return (
    <div style={{ border: '1px solid #52c41a', padding: '15px', borderRadius: '8px', marginBottom: '20px' }}>
      <h3>Immer produce 기초 테스트</h3>
      <p>닉네임: {setting.info.nickname}</p>
      <p>다크 모드: {setting.info.options.darkMode ? 'ON' : 'OFF'}</p>
      <button onClick={handleToggleDarkMode}>Immer로 다크 모드 토글</button>
    </div>
  );
}
```

**콘솔 출력 (버튼 클릭 시)**
```
수정 전 darkMode: false
수정 후 darkMode: true
참조 주소가 다른가? true
```

- 화면은 "다크 모드: OFF"에서 "다크 모드: ON"으로 즉시 바뀐다. 코드만 보면 `draft.info.options.darkMode = !draft.info.options.darkMode`는 PART 1 첫 예제의 `user.address.city = '부산'`과 똑같이 "직접 대입"하는 모양이다. 차이는 `draft`가 진짜 `setting` 객체가 아니라 Immer가 만든 가짜(Proxy) 객체라는 점이다. Immer는 이 Proxy에 가해진 변경을 전부 기록해뒀다가, `produce`가 끝나는 시점에 기존 객체는 그대로 둔 채 변경된 부분만 반영한 새 객체를 자동으로 만들어서 반환한다. 겉보기엔 mutation 코드처럼 생겼지만 실제로는 불변성이 지켜지는 이유다.
- **Immer가 없다면 어떻게 될까**: 지금 정도의 깊이(2단계)는 전개 연산자로도 버틸 만하지만, 아래처럼 객체 속에 배열까지 섞이면 전개 연산자만으로는 `push`, `splice` 같은 배열 메서드를 그대로 쓰지 못하고 매번 `[...prev.skills, newSkill]`처럼 새 배열을 직접 만들어야 한다. Immer는 불변성을 지켜야 한다는 사실 자체를 신경 쓰지 않고, 일반 자바스크립트 객체·배열을 다루듯 코드를 쓸 수 있게 해준다.

```tsx
'use client';

import { produce } from 'immer';
import { useState } from 'react';

interface ComplexProfile {
  username: string;
  contact: {
    email: string;
    location: {
      city: string;
      zipcode: string;
    };
  };
  skills: string[];
}

export default function ImmerUserProfile() {
  const [profile, setProfile] = useState<ComplexProfile>({
    username: '개발자A',
    contact: {
      email: 'user@example.com',
      location: { city: '서울', zipcode: '06100' },
    },
    skills: ['HTML', 'CSS', 'JavaScript'],
  });

  const handleAddSkill = (newSkill: string) => {
    setProfile((prev) => {
      const next = produce(prev, (draft) => {
        // 불변성 복사 없이 배열의 push 메서드를 직접 사용할 수 있다.
        draft.skills.push(newSkill);
      });

      console.log('수정 전 skills:', prev.skills);
      console.log('수정 후 skills:', next.skills);
      console.log('skills 배열 참조가 다른가?', prev.skills !== next.skills);
      console.log('안 건드린 contact의 참조는 그대로인가?', prev.contact === next.contact);

      return next;
    });
  };

  return (
    <div style={{ border: '1px solid #722ed1', padding: '15px', borderRadius: '8px', marginBottom: '20px' }}>
      <h3>2.2 Immer 활용 복합 중첩 프로필 관리</h3>
      <p>사용자명: {profile.username}</p>
      <p>기술 스택: {profile.skills.join(', ')}</p>
      <button onClick={() => handleAddSkill('TypeScript')}>기술 스택에 TypeScript 추가</button>
    </div>
  );
}
```

**콘솔 출력 (버튼 클릭 시)**
```
수정 전 skills: ["HTML", "CSS", "JavaScript"]
수정 후 skills: ["HTML", "CSS", "JavaScript", "TypeScript"]
skills 배열 참조가 다른가? true
안 건드린 contact의 참조는 그대로인가? true
```

- 마지막 로그가 핵심이다. `draft.skills`만 건드렸는데도 `contact`는 전혀 손대지 않았으므로, Immer는 `contact` 쪽은 원래 객체 참조를 그대로 재사용하고 `skills`가 바뀐 부분만 새로 만든다. 즉 Immer는 전체를 통째로 복제하는 게 아니라 실제로 바뀐 경로만 새 참조로 교체한다 — 그래서 `useMemo`나 `React.memo`(PART 3)로 "이 값은 안 바뀌었으니 재사용해도 된다"는 최적화를 걸 때도 안전하게 맞물려 동작한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 불변성 | Immutability | 데이터의 원본을 수정하지 않고 보존하는 성질 |
| 얕은 비교 | Shallow Compare | 메모리 참조 주소값만 비교하여 변경 여부를 판단하는 방식 |
| Draft | Draft State | Immer 내부에서 직접 수정을 허용하도록 생성된 임시 객체(Proxy) |
| Immer | Immer | 불변성 유지 코드를 간결하고 직관적으로 작성하도록 돕는 라이브러리 |

# PART 2. Context API
동아리 단톡방에만 전달하면 될 공지를 학과 전체방 → 연합방 → 회장단방을 거쳐 전달해야 한다면 비효율적이고 중간에 오류가 생기기도 쉽다. React에서도 하위 컴포넌트로 데이터를 전달하려고 중간 컴포넌트들을 거쳐야 하는 현상(Prop Drilling)이 코드의 가독성과 유지보수성을 떨어뜨린다. Context API는 중간 컴포넌트를 거치지 않고 데이터를 필요한 목적지 컴포넌트로 직접 전달하는 기능이다.

### | Props Drilling이란 — 그리고 왜 문제인가 |

```tsx
'use client';

function Child({ userName }: { userName: string }) {
  return (
    <div className="p-3 bg-red-100 border border-red-300 rounded">
      <p className="text-sm font-semibold text-red-800">최하위 자식 컴포넌트</p>
      <p className="text-base">수신된 사용자 이름: <strong>{userName}</strong></p>
    </div>
  );
}

// 중간 부모 컴포넌트: userName을 사용하지 않지만 자식에게 전달하기 위해 수신한다.
function Parent({ userName }: { userName: string }) {
  console.log('Parent 렌더링 — userName을 쓰지도 않는데 받아서 넘기기만 함:', userName);
  return (
    <div className="p-3 bg-yellow-100 border border-yellow-300 rounded space-y-2">
      <p className="text-sm font-semibold text-yellow-800">중간 부모 컴포넌트 (데이터 미사용)</p>
      <Child userName={userName} />
    </div>
  );
}

export default function PropDrillingDemo() {
  const userName = '김철수';

  return (
    <div className="p-4 bg-gray-50 border rounded space-y-3">
      <h3 className="font-bold text-lg">1.1 Prop Drilling 예제</h3>
      <p className="text-sm text-gray-600">최상위 → 부모 → 자식 순서로 Props가 전달된다.</p>
      <Parent userName={userName} />
    </div>
  );
}
```

**콘솔 출력**
```
Parent 렌더링 — userName을 쓰지도 않는데 받아서 넘기기만 함: 김철수
```

- 화면에는 "수신된 사용자 이름: 김철수"가 정상적으로 찍힌다. 동작 자체는 문제없다. 문제는 구조다. `Parent` 컴포넌트는 `userName`을 화면에 단 한 번도 쓰지 않는데도 props 타입에 `userName: string`을 선언해야 하고, 받은 값을 그대로 `Child`에 넘겨야 한다.
- **props drilling이 왜 문제인가 (구체적으로)**: 지금은 2단계(Parent → Child)뿐이라 괜찮아 보이지만, 실제 서비스에서는 `App → Layout → Sidebar → MenuList → MenuItem`처럼 5~6단계를 거치는 일이 흔하다. 이럴 때 데이터 하나를 추가하려면 중간 컴포넌트 5개의 props 타입을 전부 고쳐야 하고, 반대로 데이터 하나를 없애려 해도 5개를 전부 수정해야 한다. 또한 중간 컴포넌트들의 props 목록만 봐서는 "이 값이 왜 여기 있지?"를 알 수 없다 — 실제로 그 값을 쓰는 곳은 맨 끝 자식 컴포넌트 하나뿐인데, 코드만 봐서는 중간 컴포넌트들도 이 값을 쓰는 것처럼 착각하기 쉽다.

### | Context API로 중간 컴포넌트 건너뛰기 |

```tsx
// app/context/UserContext.tsx
'use client';

import { createContext } from 'react';

export interface UserInfo {
  name: string;
  role: string;
}

  name: '기본 사용자',
```

### | Context가 리렌더링을 일으키는 원리와 스코프 분리 |

```tsx
'use client';

import { createContext, use, useState } from 'react';

const CountContext = createContext<number>(0);

function DisplayChild() {
  const count = use(CountContext);

  const lastRenderedAt = new Date().toLocaleTimeString('ko-KR', {
    hour: '2-digit', minute: '2-digit', second: '2-digit', fractionalSecondDigits: 3,
  });

  console.log(`DisplayChild 리렌더링 — count: ${count}, 시각: ${lastRenderedAt}`);

  return (
    <div className="p-3 bg-purple-100 border border-purple-300 rounded space-y-1">
      <p className="text-purple-900 font-medium">카운트 값: {count}</p>
      <p className="text-xs text-purple-700">최근 렌더링 시각: {lastRenderedAt}</p>
    </div>
  );
}

export default function RenderTracker() {
  const [count, setCount] = useState(0);

  return (
    <div className="p-4 bg-gray-50 border rounded space-y-3">
      <h3 className="font-bold text-lg">Context 리렌더링 관찰</h3>
      <button onClick={() => setCount((prev) => prev + 1)}>상태 변경 (+1)</button>

      {/* Context 공급 */}
      <CountContext value={count}>
        <DisplayChild />
      </CountContext>
    </div>
  );
}
```

**콘솔 출력 (버튼을 3번 클릭)**
```
DisplayChild 리렌더링 — count: 0, 시각: 14:02:10.123
DisplayChild 리렌더링 — count: 1, 시각: 14:02:11.045
DisplayChild 리렌더링 — count: 2, 시각: 14:02:11.980
DisplayChild 리렌더링 — count: 3, 시각: 14:02:12.550
```

- 버튼을 누를 때마다 `count` state가 바뀌고 `<CountContext value={count}>`로 공급하는 값이 바뀌므로, 그 Context를 구독(`use(CountContext)`)하는 `DisplayChild`가 매번 다시 그려진다. 화면의 "최근 렌더링 시각"이 클릭할 때마다 갱신되는 것으로 직접 확인할 수 있다.
- 주의할 점: 지금은 `count`가 숫자 하나라서 문제가 없지만, `<Context value={{ count }}>`처럼 객체 리터럴을 그 자리에서 직접 만들어 전달하면 부모가 리렌더링될 때마다(`count`와 무관한 다른 state가 바뀌어도) 객체 리터럴이 매번 새로 생성되어 참조 주소가 달라진다. 그러면 Context를 구독하는 모든 자식이 "값이 바뀐 줄 알고" 불필요하게 리렌더링된다 — 이 문제는 PART 3의 `useMemo`/`useCallback`으로 해결한다.
- **스코프 분리(Context Splitting)**: 자주 바뀌는 데이터(예: `count`)와 거의 안 바뀌는 데이터(예: `theme`)를 하나의 Context에 합쳐두면, `count`만 바뀌어도 `theme`을 구독하는 컴포넌트까지 전부 리렌더링된다. `ThemeContext`를 별도 모듈로 분리하고 `ThemeProvider`로 그 영역만 감싸면, 테마와 무관한 컴포넌트는 테마가 바뀌어도 영향을 받지 않는다.

```tsx
// app/context/ThemeContext.tsx
'use client';

import { createContext, ReactNode, use, useState } from 'react';

type Theme = 'light' | 'dark';

interface ThemeContextType {
  theme: Theme;
  toggleTheme: () => void;
}

// 독립된 테마 전용 Context 생성
export const ThemeContext = createContext<ThemeContextType | null>(null);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');

  const toggleTheme = () => {
    setTheme((prev) => (prev === 'light' ? 'dark' : 'light'));
  };

  return <ThemeContext value={{ theme, toggleTheme }}>{children}</ThemeContext>;
}

// 안전한 데이터 인출을 위한 전용 훅
export function useTheme() {
  const context = use(ThemeContext);
  if (!context) {
    throw new Error('useTheme은 ThemeProvider 내부에서만 사용해야 한다.');
  }
  return context;
}
```

- `useTheme` 내부의 `if (!context) throw new Error(...)`가 왜 필요한가: `ThemeContext`의 기본값을 `null`로 뒀기 때문에, 혹시라도 `ThemeProvider`로 감싸지 않은 위치에서 `useTheme()`을 호출하면 `context`가 `null`이 된다. 이 체크가 없다면 `context.theme`에 접근하는 순간 "Cannot read properties of null"이라는, 원인을 바로 알기 어려운 런타임 에러가 터진다. 에러 메시지를 직접 던져두면 "ThemeProvider로 감싸는 걸 빠뜨렸다"는 원인을 즉시 알 수 있다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 프롭 드릴링 | Prop Drilling | 중간 컴포넌트들을 거쳐 하위 컴포넌트로 Props를 연쇄 전달하는 과정 |
| 컨텍스트 | Context | 컴포넌트 트리 내에서 원하는 영역에 데이터를 직접 공유하는 통로 |
| 컨텍스트 분리 | Context Splitting | 불필요한 전체 리렌더링을 방지하기 위해 데이터 종류에 따라 Context를 쪼개어 관리하는 설계 기법 |
| 구독 | Subscription | use(Context)를 사용해 특정 Context의 데이터 변화를 감지하고 참조하는 동작 |

# PART 3. React Compiler & 메모이제이션
계산기 앱을 쓸 때 복잡한 연산식을 매번 처음부터 새로 입력해야 한다면 비효율적이다. 스마트폰 계산기의 '메모리 저장(M+)' 기능이 이전 연산 결과를 저장해 두었다가 즉시 재활용하듯, React도 리렌더링 시 불필요한 재연산을 방지하고 이전 결과를 재사용하는 메모이제이션(Memoization) 메커니즘을 제공한다.

### | useMemo — 무거운 연산 결과를 기억해두기 |

- 의존성 배열에 지정한 값이 변경될 때만 연산을 다시 수행하고, 값이 바뀌지 않았다면 기존에 저장된 결과 값을 즉시 반환하는 훅이다. 기본 문법은 `const cachedValue = useMemo(() => calculate(), [dependency]);`다.

```tsx
'use client';

import { useMemo, useState } from 'react';

// 시간이 오래 걸리는 복잡한 연산을 가정한 함수
const heavyCalculation = (num: number) => {
  console.log('복잡한 연산 실행 중... (num =', num, ')');
  let result = 0;
  for (let i = 0; i < 1000000; i++) {
    result += num;
  }
  return result;
};

export default function HeavyCalculator() {
  const [count, setCount] = useState(1);
  const [isDark, setIsDark] = useState(false);

  // count 상태가 변경될 때만 heavyCalculation을 실행한다.
  const calculatedResult = useMemo(() => {
    return heavyCalculation(count);
  }, [count]);

  return (
    <div style={{
      border: '1px solid #ccc', padding: '15px', borderRadius: '8px', marginTop: '10px',
      backgroundColor: isDark ? '#333' : '#fff', color: isDark ? '#fff' : '#000',
    }}>
      <h2>1. HeavyCalculator (useMemo 실습)</h2>
      <p>연산 결과: {calculatedResult}</p>
      <button onClick={() => setCount((prev) => prev + 1)}>숫자 증가 (+1)</button>
      <button onClick={() => setIsDark((prev) => !prev)} style={{ marginLeft: '10px' }}>
        테마 변경 ({isDark ? '다크' : '라이트'})
      </button>
    </div>
  );
}
```

**콘솔 출력 (① "숫자 증가" 클릭 → ② "테마 변경" 클릭 순서로 진행)**
```
복잡한 연산 실행 중... (num = 1 )     ← 최초 렌더링
복잡한 연산 실행 중... (num = 2 )     ← ① count가 1→2로 바뀜, 의존성 [count] 변화 → 재연산
                                        ← ② isDark만 바뀜, [count]는 그대로 → heavyCalculation 자체가 생략됨
```

- "테마 변경" 버튼을 눌러도 "복잡한 연산 실행 중..." 로그가 다시 찍히지 않는다. `isDark`가 바뀌면 컴포넌트 전체는 다시 실행(리렌더링)되지만, `useMemo`의 의존성 배열이 `[count]`이고 `count`는 그대로이므로 `heavyCalculation(count)`를 다시 실행하지 않고 이전에 저장해둔 결과값을 그대로 돌려준다.
- **React Compiler/메모이제이션이 없으면 어떤 성능 문제가 생기는가 (1)**: `useMemo` 없이 `const calculatedResult = heavyCalculation(count);`처럼 그냥 호출했다면, 테마만 바꾸는 아무 상관 없는 조작을 할 때마다 100만 번짜리 반복문이 매번 다시 돌아간다. 연산이 무거울수록(실무에서는 대용량 배열 정렬·필터링 등) 화면이 버벅이는 체감 성능 저하로 직결된다.

### | useCallback과 React.memo — 함수 재생성과 자식 리렌더링 막기 |

- **useCallback**: 컴포넌트가 다시 그려질 때 내부 함수가 새로 만들어지는 것을 막아, 동일한 참조 주소를 유지하도록 돕는다.
- **React.memo**: 전달받는 props를 얕은 비교하여, 값이 변경되지 않았다면 이전 컴포넌트 출력 결과를 재사용한다.

```tsx
// app/components/ItemRow.tsx
'use client';

import React from 'react';

interface ItemRowProps {
  id: number;
  text: string;
  onRemove: (id: number) => void;
}

// React.memo에 함수를 전달하여 Props 변경이 없을 때 리렌더링을 차단한다.
const ItemRow = React.memo(({ id, text, onRemove }: ItemRowProps) => {
  console.log(`ItemRow 렌더링 - ID: ${id}`);

  return (
    <li style={{ marginBottom: '5px' }}>
      <span>{text} </span>
      <button onClick={() => onRemove(id)} style={{ marginLeft: '10px' }}>삭제</button>
    </li>
  );
});

ItemRow.displayName = 'ItemRow';

export default ItemRow;
```

```tsx
// app/components/OptimizedList.tsx
'use client';

import { useCallback, useState } from 'react';
import ItemRow from './ItemRow';

export default function OptimizedList() {
  const [items, setItems] = useState([
    { id: 1, text: '상품 1' },
    { id: 2, text: '상품 2' },
    { id: 3, text: '상품 3' },
  ]);
  const [inputText, setInputText] = useState('');

  // useCallback을 통해 삭제 함수 객체가 매번 새로 생성되는 것을 막는다.
  const handleRemove = useCallback((id: number) => {
    setItems((prevItems) => prevItems.filter((item) => item.id !== id));
  }, []);

  return (
    <div style={{ border: '1px solid #ccc', padding: '15px', borderRadius: '8px', marginTop: '10px' }}>
      <h2>OptimizedList (useCallback & React.memo 실습)</h2>
      <input
        type="text"
        value={inputText}
        onChange={(e) => setInputText(e.target.value)}
        placeholder="무관한 텍스트 입력..."
      />
      <ul>
        {items.map((item) => (
          <ItemRow key={item.id} id={item.id} text={item.text} onRemove={handleRemove} />
        ))}
      </ul>
    </div>
  );
}
```

**콘솔 출력 (최초 렌더링 후, input에 "a" 한 글자를 입력했을 때)**
```
ItemRow 렌더링 - ID: 1
ItemRow 렌더링 - ID: 2
ItemRow 렌더링 - ID: 3
                          ← "a" 입력 시점에는 ItemRow 로그가 하나도 찍히지 않는다
```

- `inputText`를 바꾸면 `OptimizedList` 컴포넌트 함수 자체는 다시 실행된다. 이때 `handleRemove`를 `useCallback(..., [])`으로 감싸지 않았다면 함수가 매번 새로 만들어져서 `ItemRow`에 "새 함수"가 props로 전달되고, `React.memo`가 얕은 비교를 했을 때 "달라졌다"고 판단해 자식 3개 전체가 다시 그려진다. `useCallback(..., [])`으로 함수 참조를 고정해뒀기 때문에 `inputText`가 바뀌어도 `onRemove`의 참조는 그대로이고, `id`·`text`도 그대로이므로 `React.memo`가 "props가 하나도 안 바뀌었다"고 판단해 `ItemRow` 3개 전부 리렌더링을 건너뛴다.
- **React Compiler/메모이제이션이 없으면 어떤 성능 문제가 생기는가 (2)**: `React.memo`만 없다면 `useCallback`으로 함수 참조를 고정해도 자식 컴포넌트는 부모가 리렌더링될 때마다 무조건 같이 리렌더링된다. 반대로 `React.memo`만 있고 `useCallback`이 없다면 `onRemove` 함수가 렌더링마다 새로 생성되므로 `React.memo`의 얕은 비교에서 "props가 바뀌었다"고 판단해 메모이제이션이 무력화된다. 리스트 항목이 수백 개인 상황에서 이 조합이 없으면, 입력창에 한 글자를 칠 때마다 화면과 무관한 리스트 항목 수백 개가 전부 다시 그려지는 성능 문제가 생긴다.

### | React Compiler — 수동 최적화를 자동화하기 |

- React Compiler는 빌드 단계에서 코드 흐름을 분석해서, 개발자가 `useMemo`·`useCallback`·`React.memo`를 직접 쓰지 않아도 자동으로 메모이제이션을 적용해주는 컴파일러다. 런타임 추가 비용 없이 빌드 시점에 최적화 코드가 주입되며, React 19부터 공식 생태계에 정식 도입됐다.
- 전제 조건은 **순수 함수(Pure Function)** 규칙이다 — 같은 입력(props, state)이 들어오면 항상 같은 출력(UI)을 내놓고, 함수 외부 데이터를 몰래 바꾸지 않는 컴포넌트여야 컴파일러가 안전하게 자동 메모이제이션을 적용할 수 있다. (PART 1에서 본 "직접 수정(mutation)"은 이 순수성 규칙을 깨는 대표적인 행동이다 — 그래서 불변성을 지키는 습관이 React Compiler의 자동 최적화를 제대로 받기 위한 전제 조건이기도 하다.)
- **React Compiler/메모이제이션이 없으면 어떤 성능 문제가 생기는가 (종합)**: React 18 이하, 또는 컴파일러가 최적화를 건너뛰는 예외 상황이라면 PART 3에서 본 것처럼 개발자가 일일이 "이 값은 `useMemo`로", "이 함수는 `useCallback`으로", "이 컴포넌트는 `React.memo`로" 감쌀지 말지를 직접 판단하고 작성해야 한다. 의존성 배열을 하나라도 빠뜨리면 메모이제이션이 깨지거나(최신 값을 못 읽는 버그), 반대로 꼭 필요한 곳에 빠뜨리면 성능 저하가 생긴다. React Compiler는 이 판단과 작성을 빌드 시점에 자동으로 대신 해준다 — 다만 지금도 기존 프로젝트(React 18 이하)를 유지보수하거나 컴파일러가 최적화를 건너뛴 예외 영역을 직접 고칠 때는 `useMemo`/`useCallback`/`React.memo`의 원리를 알고 있어야 한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 메모이제이션 | Memoization | 이전 연산 결과를 저장해 두었다가 동일한 요청 시 재사용하는 기법 |
| 순수 함수 | Pure Function | 같은 입력값에 항상 같은 출력값을 내며 외부 상태를 변경하지 않는 함수 |
| 의존성 배열 | Dependency Array | 훅의 재실행 여부를 판단하기 위해 감시하는 상태/변수들의 목록 배열 |
| React Compiler | React Compiler | React 19부터 정식 적용되어 순수 함수 컴포넌트를 자동으로 최적화하는 엔진 |

# PART 4. Zustand 스토어 & Persist 미들웨어
쇼핑몰 장바구니에 상품을 담은 후 새로고침해도 담아둔 목록이 그대로 유지되는 경험을 해본 적이 있을 것이다. 일반적인 자바스크립트 변수는 페이지가 새로고침되면 메모리가 초기화되어 모든 데이터가 사라진다. 전역 상태 관리 라이브러리와 브라우저 저장소(Web Storage)를 조합하면 앱 전체에서 데이터를 공유함은 물론, 새로고침 이후에도 상태를 지속적으로 유지할 수 있다.

### | Zustand는 왜 필요한가 — Redux와 비교 |

- PART 2에서 본 Context API는 Provider로 감싼 트리 안에서만 값을 공유할 수 있고, 값이 바뀌면 그 값을 구독하는 모든 컴포넌트가 리렌더링된다. 전역 상태를 더 가볍게 관리하고 싶을 때 Redux, Zustand 같은 전역 상태 관리 라이브러리를 쓴다.

| 구분 | Redux | Zustand |
| --- | --- | --- |
| 보일러플레이트 | 작성해야 할 설정 코드(Action, Reducer 등)가 많음 | create 함수 하나로 빠르게 정의 |
| Provider 필요 여부 | 최상위 컴포넌트에 `<Provider>` 감싸기 필수 | Provider 없이 어디서나 직접 호출 |
| 학습 난이도 | 개념 구조가 복잡함 | 직관적이며 간결함 |

- **Zustand 같은 전역 상태관리가 왜 필요한가**: Context API만으로 장바구니처럼 여러 페이지·여러 컴포넌트에서 동시에 읽고 써야 하는 상태를 관리하려면, Provider로 그 상태가 필요한 범위 전체를 감싸야 하고 PART 2에서 본 것처럼 `value={{ cart, addItem, ... }}` 객체가 렌더링마다 새로 생성되지 않도록 신경 써야 하는 등 챙길 게 많아진다. Zustand는 Provider 없이 `create`로 만든 스토어를 그냥 import해서 쓰면 되므로, 전역 상태를 다루는 코드량과 신경 써야 할 함정이 확 줄어든다.

### | create로 카운터 전역 스토어 만들기 |

```ts
// store/useCounterStore.ts
import { create } from 'zustand';

interface CounterState {
  count: number;
  increase: () => void;
  decrease: () => void;
}

export const useCounterStore = create<CounterState>((set) => ({
  count: 0,
  increase: () => set((state) => ({ count: state.count + 1 })),
  decrease: () => set((state) => ({ count: state.count - 1 })),
}));
```

```tsx
// app/components/CounterTest.tsx
'use client';

import { useCounterStore } from '@/store/useCounterStore';

export default function CounterTest() {
  const count = useCounterStore((state) => state.count);
  const increase = useCounterStore((state) => state.increase);
  const decrease = useCounterStore((state) => state.decrease);

  console.log('CounterTest 리렌더링 — 현재 count:', count);

  return (
    <div className="p-6 border rounded-xl bg-white shadow-sm space-y-4">
      <h2 className="text-xl font-bold text-blue-600">1단계: 기초 카운터 전역 스토어</h2>
      <p>현재 전역 카운트 값: <span className="font-bold text-2xl">{count}</span></p>
      <div className="flex gap-2">
        <button onClick={increase}>+1 증가</button>
        <button onClick={decrease}>-1 감소</button>
      </div>
    </div>
  );
}
```

**콘솔 출력 ("+1 증가" 버튼을 2번 클릭)**
```
CounterTest 리렌더링 — 현재 count: 0    ← 최초 렌더링
CounterTest 리렌더링 — 현재 count: 1    ← increase() 호출, set으로 count: 0 → 1
CounterTest 리렌더링 — 현재 count: 2    ← increase() 재호출, count: 1 → 2
```

- `create<CounterState>((set) => ({ ... }))`에서 `set`은 스토어 내부 상태를 바꾸는 함수다. `increase: () => set((state) => ({ count: state.count + 1 }))`는 "현재 스토어 상태(`state`)를 받아서, `count`만 1 증가시킨 새 객체를 반환해 상태를 교체하라"는 뜻이다. PART 1에서 배운 불변성 원칙이 여기서도 그대로 적용된다 — `set`에 넘기는 값은 기존 state를 직접 고치는 게 아니라 "이렇게 바꿔라"는 새 값(또는 병합할 조각)이다.
- `useCounterStore((state) => state.count)`처럼 선택자(Selector) 함수를 넘기는 이유: 스토어 전체(`count`, `increase`, `decrease`)를 통째로 구독하지 않고, 이 컴포넌트가 실제로 필요한 `count` 값 하나만 구독하기 위해서다. 스토어 전체를 구독했다면, 스토어 안에 다른 상태가 추가되고 그 상태만 바뀌어도 이 컴포넌트가 불필요하게 리렌더링될 수 있다.

### | 장바구니 스토어와 Selector 구독 |

```ts
// store/useCartStore.ts
import { create } from 'zustand';

export interface CartItem {
  id: number;
  name: string;
  price: number;
  quantity: number;
}

interface CartState {
  cart: CartItem[];
  addItem: (item: Omit<CartItem, 'quantity'>) => void;
  removeItem: (id: number) => void;
  clearCart: () => void;
}

export const useCartStore = create<CartState>((set) => ({
  cart: [],

  addItem: (item) =>
    set((state) => {
      const existingItem = state.cart.find((i) => i.id === item.id);
      if (existingItem) {
        return {
          cart: state.cart.map((i) =>
            i.id === item.id ? { ...i, quantity: i.quantity + 1 } : i
          ),
        };
      }
      return { cart: [...state.cart, { ...item, quantity: 1 }] };
    }),

  removeItem: (id) =>
    set((state) => ({
      cart: state.cart.filter((item) => item.id !== id),
    })),

  clearCart: () => set({ cart: [] }),
}));
```

- `addItem` 내부도 PART 1의 불변성 원칙을 그대로 따른다. 이미 담긴 상품이면 `state.cart.map(...)`으로 새 배열을 만들어 해당 항목만 `{ ...i, quantity: i.quantity + 1 }`로 교체하고, 새 상품이면 `[...state.cart, { ...item, quantity: 1 }]`로 기존 배열을 복사한 뒤 새 항목을 추가한다. `state.cart.push(...)`처럼 직접 수정하지 않는 이유는 PART 1에서 본 것과 동일하다 — 직접 수정하면 참조가 그대로라 Zustand를 구독하는 컴포넌트들이 변화를 감지하지 못한다.

```tsx
// app/components/CartTest.tsx
'use client';

import { useCartStore } from '@/store/useCartStore';

export default function CartTest() {
  const cart = useCartStore((state) => state.cart);
  const addItem = useCartStore((state) => state.addItem);

  console.log('CartTest 리렌더링 — 현재 cart 개수:', cart.length);

  const sampleProduct = { id: 101, name: '리액트 전문 서적', price: 32000 };

  return (
    <div className="p-6 border rounded-xl bg-white shadow-sm space-y-4">
      <h2 className="text-xl font-bold text-green-600">장바구니 전역 스토어 & Selector 구독</h2>
      <button onClick={() => addItem(sampleProduct)}>샘플 상품 추가</button>
      {cart.map((item) => (
        <p key={item.id}>{item.name} × {item.quantity}</p>
      ))}
    </div>
  );
}
```

**콘솔 출력 ("샘플 상품 추가"를 2번 클릭)**
```
CartTest 리렌더링 — 현재 cart 개수: 0    ← 최초 렌더링
CartTest 리렌더링 — 현재 cart 개수: 1    ← addItem 1회차: 새 상품이라 cart에 1개 추가
CartTest 리렌더링 — 현재 cart 개수: 1    ← addItem 2회차: 이미 있는 id라 배열 길이는 그대로, quantity만 2로 증가
```

- 두 번째 클릭에서 `cart.length`는 그대로 1이지만, 실제로는 `cart[0].quantity`가 1에서 2로 바뀐 "새 배열"이 들어왔다. `cart` 자체의 참조가 바뀌었기 때문에(map으로 새 배열을 만들었으므로) 리렌더링은 똑같이 일어난다 — 배열 길이만 보고 "안 바뀌었다"고 착각하면 안 된다는 점을 보여주는 예시다.

### | persist 미들웨어로 상태 영속화하기 |

```ts
// store/useCartStore.ts — persist 미들웨어 적용
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

export const useCartStore = create<CartState>()(
  persist(
    (set) => ({
      cart: [],
      addItem: (item) =>
        set((state) => {
          const existingItem = state.cart.find((i) => i.id === item.id);
          if (existingItem) {
            return {
              cart: state.cart.map((i) =>
                i.id === item.id ? { ...i, quantity: i.quantity + 1 } : i
              ),
            };
          }
          return { cart: [...state.cart, { ...item, quantity: 1 }] };
        }),
      removeItem: (id) =>
        set((state) => ({ cart: state.cart.filter((item) => item.id !== id) })),
      clearCart: () => set({ cart: [] }),
    }),
    {
      name: 'shopping-cart-storage', // LocalStorage에 저장될 Key 이름
    }
  )
);
```

- `persist` 미들웨어는 스토어의 상태가 바뀔 때마다 자동으로 LocalStorage(`shopping-cart-storage`라는 키)에 저장하고, 페이지를 처음 열 때는 LocalStorage에서 값을 읽어와 복원한다. 쇼핑몰 장바구니에 상품을 담고 새로고침해도 목록이 그대로 남아있는 익숙한 경험이 바로 이 미들웨어 덕분이다.
- **Zustand(persist)가 없으면 어떻게 될까**: 일반 자바스크립트 변수나 React state, 혹은 persist 없는 Zustand 스토어는 전부 메모리 위에만 존재한다. 브라우저를 새로고침하는 순간 메모리가 초기화되므로 방금 담았던 장바구니 상품이 전부 사라진다. `persist`는 메모리 상태를 LocalStorage라는 브라우저에 저장되는 공간과 동기화시켜서, 페이지를 벗어났다 돌아와도 데이터가 살아있게 만든다.
- **Hydration 불일치 문제**: Next.js는 서버에서 먼저 HTML을 만든다(Pre-render). 이 시점에 서버는 사용자의 LocalStorage에 접근할 수 없으므로 `cart: []`(초기값)로 HTML을 만든다. 그런데 브라우저에 도착한 뒤 Zustand가 LocalStorage에서 실제 장바구니 데이터를 읽어와 복원하면, 서버가 그려준 화면(빈 장바구니)과 클라이언트가 복원한 화면(상품이 담긴 장바구니)이 한순간 서로 달라지는 Hydration 불일치가 발생할 수 있다.

```tsx
// app/components/PersistCartTest.tsx
'use client';

import { useCartStore } from '@/store/useCartStore';
import { useSyncExternalStore } from 'react';

// Next.js SSR과 클라이언트 LocalStorage(Hydration) 상태를 동기화하는 훅
function useHasHydrated() {
  return useSyncExternalStore(
    () => () => {}, // 구독 등록 함수
    () => true,     // 클라이언트 렌더링 스냅샷 (true 반환)
    () => false     // 서버 사이드 렌더링 스냅샷 (false 반환)
  );
}

export default function PersistCartTest() {
  const isHydrated = useHasHydrated();
  const cart = useCartStore((state) => state.cart);

  console.log('isHydrated:', isHydrated, '/ cart 개수:', cart.length);

  // 클라이언트 마운트 완료 전에는 로딩 표시로 SSR/클라이언트 불일치 방지
  if (!isHydrated) {
    return (
      <div className="p-6 border rounded-xl bg-white shadow-sm space-y-4">
        <h2 className="text-xl font-bold text-purple-600">Persist 미들웨어 적용 장바구니</h2>
        <p className="text-gray-500 text-sm">로컬스토리지 데이터를 불러오는 중...</p>
      </div>
    );
  }

  return (
    <div className="p-6 border rounded-xl bg-white shadow-sm space-y-4">
      <h2 className="text-xl font-bold text-purple-600">Persist 미들웨어 적용 장바구니 (새로고침 테스트)</h2>
      {cart.map((item) => (
        <p key={item.id}>{item.name} × {item.quantity}</p>
      ))}
    </div>
  );
}
```

**콘솔 출력 (LocalStorage에 이미 상품 1개가 저장된 상태에서 새로고침)**
```
isHydrated: false / cart 개수: 0     ← 최초 렌더링 (서버와 동일하게 맞춘 상태)
isHydrated: true / cart 개수: 1      ← 브라우저에서 LocalStorage 복원이 끝난 다음 렌더링
```

- `isHydrated`가 `false`인 동안은 "로딩 중..." 문구만 보여주고 `cart`를 화면에 그리지 않는다. 서버가 그린 화면과 클라이언트의 첫 렌더링 결과를 일부러 동일하게(`false` 상태로) 맞춰둔 다음, LocalStorage 복원이 끝나면 `isHydrated`가 `true`로 바뀌면서 진짜 데이터를 보여준다.
- `useSyncExternalStore`가 왜 필요한가: `useEffect(() => setIsHydrated(true), [])`처럼 이펙트 안에서 state를 바꾸는 방식은 "effect 내부에서 동기적으로 setState를 호출하면 연쇄 렌더링(cascading render)을 유발할 수 있다"는 경고·에러를 최신 리액트에서 일으킬 수 있다. `useSyncExternalStore`는 "서버에서는 이 값, 클라이언트에서는 저 값"을 공식적으로 구분해서 알려주는 리액트 전용 API라서, 경고 없이 안전하게 Hydration 여부를 동기화할 수 있다.

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 전역 상태 | Global State | 앱 내의 여러 컴포넌트에서 공통으로 접근하고 공유할 수 있는 데이터 |
