# PART 1. App Router 라우팅 & Route Groups
### | 폴더가 곧 주소가 된다 — App Router란 |

- Next.js의 App Router는 app 폴더 안의 폴더 구조를 그대로 URL 경로로 매핑한다. 폴더를 만들고 그 안에 page.tsx 파일 하나만 넣으면, 별도의 라우팅 설정 파일 없이도 해당 폴더 이름이 곧 접속 가능한 주소가 된다.

```txt
app/
├── page.tsx              →  /
├── about/
│   └── page.tsx           →  /about
├── dashboard/
│   ├── layout.tsx          # /dashboard 전용 레이아웃
│   └── page.tsx             →  /dashboard
└── (auth)/
    ├── layout.tsx           # (auth) 그룹 전용 레이아웃
    └── login/
        └── page.tsx          →  /login  ((auth)는 URL에서 생략)
```

- 왜 필요한가: 과거 React(CSR) 환경에서는 react-router 같은 별도 라이브러리를 설치하고, "/about 경로가 오면 About 컴포넌트를 렌더링하라"는 매칭 규칙을 코드로 일일이 작성해야 했다. App Router는 "폴더 이름 = URL"이라는 규약 하나로 그 설정 코드 자체를 없애버렸다.
- 없으면 어떻게 될까: 폴더 기반 라우팅이 없다면, 페이지가 수십 개로 늘어날 때마다 라우팅 설정 파일(라우트 테이블)에 경로와 컴포넌트를 일일이 매핑하는 코드를 추가해야 한다. 파일 시스템의 폴더 구조와 실제 URL 구조가 따로 놀게 되어, 새 페이지를 찾을 때 라우팅 설정 파일과 컴포넌트 파일을 번갈아 봐야 하는 번거로움이 생긴다.

### | HTML \<a> 태그 vs Next.js \<Link> 컴포넌트 |

| 구분 | HTML `<a>` 태그 | Next.js `<Link>` 컴포넌트 |
| --- | --- | --- |
| 전환 방식 | 서버에 전체 페이지 재요청(풀 리로드) | 필요한 데이터만 비동기로 수신(클라이언트 사이드 이동) |
| 사용자 경험 | 화면 깜빡임 발생, 기존 상태 초기화 | 매끄러운 전환, 기존 상태 유지 |
| 최적화 | 기본 이동만 지원 | 프리페칭(Prefetching)으로 이동 속도 극대화 |

```tsx
import Link from "next/link";

export default function HomePage() {
  return (
    <div style={{ padding: "20px" }}>
      <nav>
        <ul style={{ lineHeight: "2" }}>
          <li>
            <Link href="/">홈 (현재 페이지)</Link>
          </li>
          <li>
            <Link href="/about">소개 페이지 (/about) 확인하기</Link>
          </li>
        </ul>
      </nav>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 브라우저 화면에는 "홈", "소개 페이지" 두 개의 링크가 세로로 나열된다. `/about` 링크를 클릭하면 브라우저 탭 상단의 새로고침 아이콘이 돌지 않고 페이지 내용만 바뀐다 — 화면에 `<Link>`가 보이는 순간 Next.js가 이동할 페이지의 코드를 백그라운드에서 미리 받아두기(프리페칭) 때문에, 실제 클릭 시점에는 대기 시간 없이 즉시 전환된다.
- `<a>` 태그를 그대로 썼다면 어떻게 될까: 클릭할 때마다 서버에 페이지 전체를 다시 요청하므로, 화면이 한 번 하얗게 깜빡이며 처음부터 다시 그려진다. React가 메모리에 들고 있던 상태(예: 입력 중이던 폼 값)도 전부 날아간다. `<Link>`는 이 두 가지 손실을 모두 막아준다.

### | layout.tsx — 페이지가 바뀌어도 유지되는 공통 틀 |

- `layout.tsx`는 하위 페이지들을 감싸는 틀이다. `{children}` 자리에 현재 주소에 해당하는 `page.tsx`(또는 하위 레이아웃)가 주입된다. 페이지를 이동해도 `layout.tsx` 자체는 다시 렌더링되지 않고 기존 상태를 그대로 유지한다.

```tsx
// app/layout.tsx
import React from "react";

export default function RootLayout({
  children, // 현재 접근한 주소에 상응하는 page.tsx 또는 하위 레이아웃이 주입됨
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="ko">
      <body style={{ margin: 0, padding: 0 }}>
        <header style={{ padding: "16px", backgroundColor: "#0f172a", color: "#ffffff" }}>
          <h3 style={{ margin: 0 }}>My App Router Service</h3>
        </header>
        <main>{children}</main>
      </body>
    </html>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/`, `/about`, `/dashboard` 등 어느 페이지로 이동해도 검은색 상단 헤더("My App Router Service")는 화면에 그대로 고정되어 있고, 그 아래 `<main>` 영역의 내용물만 페이지마다 바뀐다.
- `layout.tsx`와 `template.tsx`의 차이: `layout.tsx`는 페이지를 넘나들어도 인스턴스가 유지되지만, `template.tsx`는 겉보기엔 똑같이 동작해도 페이지를 이동할 때마다 매번 새 인스턴스가 생성되어 내부 상태가 초기화된다. "공통 헤더처럼 계속 유지되어야 하는 UI"는 layout, "페이지마다 애니메이션을 처음부터 다시 재생해야 하는 UI" 같은 경우는 template을 쓴다.
- layout.tsx가 없다면 어떻게 될까: 모든 page.tsx 파일 안에 `<header>`, `<html>`, `<body>` 같은 공통 뼈대 코드를 매번 똑같이 반복해서 작성해야 한다. 헤더 디자인을 하나 바꾸려면 페이지 파일 수만큼 전부 고쳐야 하는 유지보수 부담이 생긴다.

### | 중첩 레이아웃(Nested Layouts) — 대시보드 예시 |

- 상위 `layout.tsx` → 하위 `layout.tsx` → 하위 `page.tsx` 순서로 겹겹이 층을 이루며 렌더링된다. 전체 사이트의 틀(루트 레이아웃)은 유지하면서, 특정 기능 영역(예: 대시보드)에만 전용 사이드바를 추가로 씌울 수 있다.

```tsx
// app/dashboard/layout.tsx
import React from "react";

export default function DashboardLayout({
  children, // /dashboard/page.tsx가 들어올 자리
}: {
  children: React.ReactNode;
}) {
  return (
    <div style={{ display: "flex", minHeight: "80vh" }}>
      <aside style={{ width: "200px", backgroundColor: "#f1f5f9", padding: "16px" }}>
        <h4 style={{ marginTop: 0 }}>대시보드 메뉴</h4>
        <ul style={{ listStyle: "none", padding: 0 }}>
          <li style={{ marginBottom: "8px" }}>📊 통계 메인</li>
        </ul>
      </aside>
      <section style={{ flex: 1, padding: "20px" }}>{children}</section>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/dashboard` 접속 시, 루트 레이아웃의 검은색 상단 헤더 + 대시보드 레이아웃의 좌측 사이드바 + `app/dashboard/page.tsx`의 본문, 이렇게 세 겹이 한 화면에 레이어링되어 출력된다.
- 중첩 레이아웃이 없다면 어떻게 될까: 사이드바가 필요한 모든 페이지(`/dashboard`, `/dashboard/settings` 등)마다 사이드바 코드를 각 page.tsx에 직접 복사해 넣어야 한다. 사이드바 메뉴 항목이 하나 추가될 때마다 관련된 모든 페이지 파일을 찾아다니며 고쳐야 한다.

### | Route Groups (groupName) — URL에 영향 없이 폴더 정리하기 |

- 폴더명을 소괄호 `(groupName)`로 감싸면, 그 폴더는 웹 브라우저의 URL 주소 경로 계산에서 완전히 제외된다. 인증, 마케팅, 서비스 등 기능별로 폴더를 깔끔하게 분리해서 관리하면서도, 특정 그룹에만 독립된 레이아웃을 부여할 수 있다.

```txt
app/(auth)/login/page.tsx  →  http://localhost:3000/login   ((auth)는 주소에서 생략됨)
```

```tsx
// app/(auth)/layout.tsx
import React from "react";

export default function AuthLayout({
  children, // /login 페이지가 들어올 자리
}: {
  children: React.ReactNode;
}) {
  return (
    <div style={{ display: "flex", justifyContent: "center", paddingTop: "50px" }}>
      <div style={{ border: "1px solid #cbd5e1", padding: "24px", borderRadius: "8px", width: "320px" }}>
        {children}
      </div>
    </div>
  );
}
```

```tsx
// app/(auth)/login/page.tsx
export default function LoginPage() {
  return (
    <div>
      <h3 style={{ marginTop: 0 }}>로그인</h3>
      <form style={{ display: "flex", flexDirection: "column", gap: "12px" }}>
        <input type="email" placeholder="이메일 입력" style={{ padding: "8px" }} />
        <input type="password" placeholder="비밀번호 입력" style={{ padding: "8px" }} />
        <button type="button" style={{ padding: "8px", backgroundColor: "#2563eb", color: "#fff", border: "none" }}>
          로그인
        </button>
      </form>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/login` 링크를 클릭하면 주소창에는 `(auth)`가 전혀 붙지 않고 깔끔하게 `/login`만 표시되며, 화면 중앙에 테두리가 둘린 작은 카드 박스 안에 로그인 폼이 나타난다. 같은 폴더 아래 다른 페이지를 추가해도 URL 구조는 영향받지 않는다.
- Route Groups가 없다면 어떻게 될까: 인증 관련 페이지에만 카드형 레이아웃을 적용하고 싶어도, 그 페이지들을 물리적으로 다른 폴더 계층에 두는 순간 URL 자체가 `/auth/login`처럼 바뀌어버린다. "URL은 그대로 유지하면서 내부 폴더 구조만 기능별로 정리하고 싶다"는 요구를 만족시킬 방법이 없어서, 결국 레이아웃이 다른 페이지들이 전부 한 폴더에 뒤섞여 관리 난이도가 올라간다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| App Router | App Router | 폴더 구조가 곧 URL 주소로 매핑되는 Next.js의 파일 시스템 기반 라우팅 시스템 |
| 링크 컴포넌트 | `<Link>` | 전체 새로고침 없이 비동기로 화면을 전환하는 Next.js 전용 태그 |
| 프리페칭 | Prefetching | 화면에 보이는 링크의 이동 대상 코드를 미리 백그라운드에서 받아두는 기능 |
| 중첩 레이아웃 | Nested Layouts | 상위 레이아웃의 `{children}` 자리에 하위 레이아웃·페이지가 겹겹이 조립되는 구조 |
| 루트 그룹 | Route Groups | 소괄호 `()`로 URL 영향 없이 폴더를 묶고 독립 레이아웃을 부여하는 기법 |

# PART 2. Dynamic Routes & searchParams
### | 왜 동적 라우팅이 필요한가 |

- 온라인 쇼핑몰에 상품이 1,000개 있다고 해서 1,000개의 페이지 파일을 따로 만들지 않는다. 단 하나의 "상품 상세 페이지 템플릿"을 만들어두고, URL 경로의 가변값(ID)만 추출해서 해당하는 데이터를 동적으로 매핑하는 방식을 쓴다. 이를 가능하게 하는 것이 Dynamic Routes다.

```txt
app/
├── products/
│   └── [id]/
│       └── page.tsx      →  /products/1, /products/2, /products/999 ... 전부 이 파일 하나가 처리
├── shop/
│   └── [...slug]/
│       └── page.tsx       →  /shop/clothing/tops, /shop/electronics/audio/headphones 등 깊이 제한 없이 처리
└── search/
    └── page.tsx            →  /search?q=신발&sort=price_asc&page=1  (쿼리 스트링은 searchParams로 수신)
```

### | Dynamic Routes [id] — 대괄호 폴더와 params |

- 폴더명을 대괄호 `[id]`로 감싸면, 그 위치에 들어오는 값이 자동으로 변수에 할당된다. `/products/100`으로 접속하면 `id` 변수에 `"100"`이라는 값이 담긴다. App Router에서 `params`는 Promise 객체이므로 `await`로 풀어서 읽어야 한다.

```tsx
// app/products/[id]/page.tsx
interface ProductDetailPageProps {
  params: Promise<{
    id: string; // URL 경로에서 전달받은 가변 id 값
  }>;
}

export default async function ProductDetailPage({ params }: ProductDetailPageProps) {
  const { id } = await params; // Promise 형태의 params를 언래핑

  return (
    <div className="p-4 space-y-2">
      <h1 className="text-xl font-bold">상품 상세 페이지</h1>
      <p>수신된 상품 ID: <strong className="text-blue-600">{id}</strong></p>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/products/1`로 접속하면 "수신된 상품 ID: 1"이, `/products/2`로 접속하면 "수신된 상품 ID: 2"가 화면에 출력된다. 폴더/파일은 단 하나뿐이지만 URL의 숫자만 바뀌면 다른 내용이 나온다.
- Dynamic Routes가 없다면 어떻게 될까: 상품 1개마다 `app/products/1/page.tsx`, `app/products/2/page.tsx`, ... 식으로 실제 폴더와 파일을 1,000개 만들어야 한다. 상품이 추가될 때마다 배포 코드 자체를 새로 작성해야 하므로, 상품 데이터가 DB에서 동적으로 늘어나는 실제 서비스에서는 아예 불가능한 방식이다.

### | Catch-all Routes [...slug] — 깊이 제한 없는 다중 경로 수신 |

- 대괄호와 줄임표(`[...slug]`)를 쓰면 하위 경로를 깊이에 상관없이 전부 배열로 묶어서 받는다. `/shop/clothing/tops`로 접속하면 `slug`에는 `['clothing', 'tops']`가 담기고, `/shop/electronics/audio/headphones`처럼 3단계로 들어가도 같은 파일 하나가 처리한다.

```tsx
// app/shop/[...slug]/page.tsx
interface CatchAllPageProps {
  params: Promise<{
    slug: string[]; // 다중 하위 경로가 문자열 배열로 전달됨
  }>;
}

export default async function ShopCategoryPage({ params }: CatchAllPageProps) {
  const { slug } = await params;

  return (
    <div className="p-4 space-y-2">
      <h1 className="text-xl font-bold">카테고리 경로 분석</h1>
      <p>경로 깊이: {slug.length}단계</p>
      <p>전체 경로: <code className="bg-gray-100 p-1">/shop/{slug.join('/')}</code></p>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/shop/clothing/tops`로 가면 "경로 깊이: 2단계", "전체 경로: /shop/clothing/tops"가 출력되고, `/shop/electronics/audio/headphones`로 가면 "경로 깊이: 3단계"로 자동으로 바뀐다.
- `[...slug]`가 없다면 어떻게 될까: 카테고리 계층이 "의류", "의류/상의", "전자제품/음향/헤드폰"처럼 깊이가 제각각일 때, `[category]/page.tsx`, `[category]/[sub]/page.tsx`, `[category]/[sub]/[subsub]/page.tsx`처럼 깊이별로 폴더를 전부 따로 만들어야 한다. 카탈로그 구조가 몇 단계까지 깊어질지 미리 알 수 없는 쇼핑몰에서는 이 방식으로 대응이 불가능하다.

### | searchParams — 쿼리 스트링으로 필터링 조건 받기 |

- URL 끝의 물음표(`?key=value`) 뒤에 오는 데이터는 경로 자체를 바꾸지 않고 검색어·정렬·페이지 번호 같은 세부 조건을 전달할 때 쓴다. `params`처럼 Promise 형태이고, 값이 없을 수도 있으므로 각 속성을 선택적(`?`)으로 정의한다.

```tsx
// app/search/page.tsx
interface SearchPageProps {
  searchParams: Promise<{
    q?: string;      // 검색어
    sort?: string;   // 정렬 조건
    page?: string;   // 페이지 번호
  }>;
}

export default async function SearchPage({ searchParams }: SearchPageProps) {
  const { q, sort, page } = await searchParams;

  return (
    <div className="p-4 space-y-2">
      <h1 className="text-xl font-bold">검색 및 필터링 결과</h1>
      <ul className="list-disc pl-5 space-y-1">
        <li>검색어(q): <strong>{q || '없음'}</strong></li>
        <li>정렬(sort): <strong>{sort || '기본값'}</strong></li>
        <li>페이지(page): <strong>{page || '1'}</strong></li>
      </ul>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `/search?q=신발&sort=price_asc&page=1`로 접속하면 "검색어(q): 신발", "정렬(sort): price_asc", "페이지(page): 1"이 리스트로 출력된다. 쿼리 값을 하나도 안 주고 `/search`로만 접속하면 각각 "없음", "기본값", "1"로 대체 표시된다.
- searchParams가 없다면 어떻게 될까: 검색 조건(검색어·정렬·페이지)마다 URL 경로를 따로 만들어야 한다 — `/search/신발/price_asc/1`처럼. 조합 가짓수가 폭발적으로 늘어나는 데다, 경로 자체가 "검색 결과를 보여주는 화면"이라는 하나의 리소스를 가리키지 못하고 조건마다 다른 리소스처럼 취급되어 설계가 꼬인다.

### | useRouter() — 프로그래밍 방식 이동 |

| 메서드 | 핵심 기능 | 대표 활용 상황 |
| --- | --- | --- |
| push(href) | 새로운 URL로 이동하고 히스토리에 추가 | 일반적인 페이지 연결(상품 클릭 등) |
| replace(href) | 현재 URL을 새 URL로 덮어쓰기 | 로그인/결제 완료 후 뒤로가기 방지 |
| refresh() | 현재 페이지의 서버 컴포넌트 데이터만 재요청 | 댓글/좋아요 등록 후 서버 데이터 최신화 |
| back() | 브라우저 히스토리상의 이전 페이지로 이동 | 상단 '뒤로가기' 버튼 구현 |
| forward() | 브라우저 히스토리상의 다음 페이지로 이동 | '앞으로가기' 버튼 구현 |
| prefetch(href) | 특정 라우트의 데이터/코드를 사전에 수동 로드 | 마우스 호버 시 페이지 사전 로딩 |

```tsx
// app/components/Navigation.tsx
'use client'; // 클라이언트 이벤트 처리 및 useRouter 훅 사용을 위해 선언

import Link from 'next/link';
import { useRouter } from 'next/navigation';

export default function Navigation() {
  const router = useRouter();

  const handlePushNavigate = () => {
    const randomId = Math.floor(Math.random() * 10) + 1;
    router.push(`/products/${randomId}`); // 히스토리에 기록이 남음
  };

  const handleReplaceNavigate = () => {
    router.replace('/search?q=특가'); // 현재 히스토리를 덮어씀 — 뒤로가기 기록 안 남음
  };

  return (
    <div className="space-y-3">
      <Link href="/products/999" className="text-blue-600 underline">
        &lt;Link&gt;로 고정 ID (999) 이동하기
      </Link>
      <button onClick={handlePushNavigate}>push()로 랜덤 ID 이동</button>
      <button onClick={handleReplaceNavigate}>replace()로 검색 페이지 이동</button>
      <button onClick={() => router.refresh()}>refresh() 데이터 새로고침</button>
      <button onClick={() => router.back()}>back() 뒤로가기</button>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 버튼을 누르는 이벤트 핸들러 안에서 경로 이동을 직접 제어한다. "push()로 랜덤 ID 이동" 버튼을 누르면 `/products/숫자`로 이동하고 뒤로가기가 가능하지만, "replace()로 검색 페이지 이동" 버튼을 누르면 `/search?q=특가`로 이동한 뒤 뒤로가기를 눌러도 원래 있던 화면으로 돌아가지지 않는다.
- `push()` 대신 `replace()`를 꼭 써야 하는 상황: 로그인 성공 후 메인 페이지로 이동할 때 `push()`를 쓰면, 로그인 완료 화면에서 뒤로가기를 눌렀을 때 다시 로그인 폼이 나타나버린다. `replace()`로 로그인 화면 자체를 히스토리에서 지워버려야 이런 문제를 막을 수 있다.
- useRouter가 없다면 어떻게 될까: `<Link>`는 화면에 보이는 고정된 경로로만 이동시킬 수 있다. "폼 제출이 성공하면 그 결과에 따라 동적으로 계산된 경로로 이동시켜야 한다"처럼 조건에 따라 경로가 달라지는 상황에서는 `<Link>`만으로 처리할 방법이 없고, 반드시 이벤트 핸들러 안에서 호출할 수 있는 프로그래밍 방식 이동 수단이 필요하다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 동적 라우트 | Dynamic Routes | URL 경로 일부를 변수로 지정해 여러 페이지를 하나의 컴포넌트로 처리하는 구조 |
| 캐치 올 라우트 | Catch-all Routes | 하위 경로 전체를 깊이에 상관없이 배열로 수신하는 라우팅 방식 |
| 쿼리 스트링 | Query String | URL 끝에 `?` 뒤로 붙는 key=value 형태의 필터링 옵션 표기법 |
| 라우터 교체 | Router Replace | 현재 방문 기록을 새 주소로 대체해 뒤로가기를 차단하는 이동 방식 |

# PART 3. File-system conventions & UI 예외 처리
### | 약속된 파일명이 왜 필요한가 |

- 배달 앱에서 주문 버튼을 눌렀는데 화면이 그대로 멈춰 있으면 사용자는 오류로 판단해 앱을 강제 종료하거나 버튼을 중복 클릭한다. "처리 중..."이라는 로딩 안내와, 오류가 나면 "다시 시도" 버튼이 뜨는 것만으로 사용자 경험이 완전히 달라진다. App Router는 `loading.tsx`, `error.tsx` 같은 정해진 이름의 파일을 폴더 안에 넣기만 하면, 이런 로딩·에러 화면 전환을 Next.js가 자동으로 조율해준다.

```txt
app/
├── loading.tsx        # 자동 로딩 스켈레톤 UI
├── error.tsx           # 에러 포착 및 복구 UI ('use client')
├── not-found.tsx        # 404 리소스 미존재 안내 UI
├── unauthorized.tsx      # 401 로그인 필요 안내 UI
├── forbidden.tsx          # 403 권한 없음 안내 UI
├── layout.tsx              # 루트 레이아웃
└── page.tsx                 # 메인 라우트 페이지
```

| 파일명 | 역할 | 주요 특징 |
| --- | --- | --- |
| page.tsx | 경로(URL)의 메인 화면 UI | 특정 URL 접근 시 표시되는 필수 컴포넌트 |
| layout.tsx | 여러 페이지가 공유하는 공통 레이아웃 | 이동 시 상태 유지, 리렌더링 안 됨 |
| template.tsx | layout.tsx와 유사하나 매번 새로 생성됨 | 페이지 이동마다 상태 초기화할 때 사용 |
| loading.tsx | 데이터 조회 동안 표시되는 로딩 화면 | React Suspense로 페이지를 자동으로 감쌈 |
| error.tsx | 하위 컴포넌트 오류 발생 시 대체 화면 | 'use client' 필수, reset() 복구 기능 제공 |
| global-error.tsx | 루트 레이아웃 자체 오류를 포착 | `<html>`, `<body>` 태그를 직접 포함해야 함 |
| not-found.tsx | 존재하지 않는 경로 접근 시 404 화면 | notFound() 호출 시 자동 전환 |
| forbidden.tsx | 권한 없음(403) 화면 | forbidden() 호출 시 자동 전환 |
| unauthorized.tsx | 미인증(401) 화면 | unauthorized() 호출 시 자동 전환 |
| default.tsx | 병렬 라우트에서 일치 경로가 없을 때 기본 화면 | 슬롯(@slot) 복구 시 사용 |
| route.ts | HTML 대신 JSON을 반환하는 백엔드 API | GET, POST 등 HTTP 메서드 함수 작성 |

- 이 규약 자체가 없다면 어떻게 될까: 로딩 상태 하나를 처리하려 해도, 데이터를 기다리는 동안 보여줄 화면을 컴포넌트마다 `isLoading` 상태값으로 직접 관리하고 조건부 렌더링 코드를 작성해야 한다. 에러 처리도 마찬가지로 각 페이지마다 try/catch와 에러 상태 UI를 손으로 구현해야 하는데, 페이지 수가 많아질수록 똑같은 로딩/에러 처리 코드가 계속 중복된다. 파일명 규약은 "이 이름으로 파일만 만들면 나머지는 프레임워크가 자동으로 연결해준다"는 약속으로 이 반복을 없앤다.

### | loading.tsx — 자동으로 적용되는 로딩 UI |

- `loading.tsx`를 만들어두면, Next.js가 내부적으로 `page.tsx`를 `<Suspense fallback={<Loading />}>`으로 자동으로 감싸 처리한다. 데이터 조회(페칭)가 끝날 때까지는 `page.tsx` 대신 `loading.tsx`가 화면에 보인다.

```tsx
// app/loading.tsx
export default function Loading() {
  return (
    <div className="p-4 border rounded animate-pulse">
      <div className="h-4 bg-gray-200 rounded mb-2 w-1/3"></div>
      <div className="h-12 bg-gray-200 rounded mb-2"></div>
      <div className="h-12 bg-gray-200 rounded"></div>
      <p className="text-xs text-gray-400 mt-2">로딩 중...</p>
    </div>
  );
}
```

```tsx
// app/page.tsx
import DataCard from './components/DataCard';

async function fetchData() {
  await new Promise((resolve) => setTimeout(resolve, 2000)); // 2초 지연
  return { visitorCount: '1,250명', todaySales: '3,500,000원' };
}

export default async function Page() {
  const data = await fetchData(); // 이 조회가 끝날 때까지 loading.tsx가 보임

  return (
    <div className="p-4 border rounded">
      <h2 className="font-bold mb-4">대시보드 현황</h2>
      <DataCard title="오늘의 방문자 수" value={data.visitorCount} />
      <DataCard title="오늘의 총 매출" value={data.todaySales} />
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 페이지에 접속하는 순간 회색 애니메이션 박스(스켈레톤 UI)와 "로딩 중..." 문구가 2초간 보이다가, 데이터 조회가 끝나면 자연스럽게 실제 대시보드 카드(방문자 수, 매출)로 화면이 바뀐다.
- loading.tsx가 없다면 어떻게 될까: 2초짜리 `await fetchData()` 동안 브라우저 화면은 그냥 하얗게 멈춰 있다. 사용자는 페이지가 멈췄는지 느려서 로딩 중인지 구분할 수 없어 새로고침을 반복하거나 이탈하게 된다.

### | error.tsx — 에러 포착과 reset() 복구 |

- 하위 컴포넌트에서 에러가 발생하면 앱 전체가 중단되는 대신 `error.tsx`가 대체 화면으로 표시된다. 재시도 버튼의 클릭 이벤트(`reset()`)를 처리해야 하므로 반드시 `'use client'`를 선언해야 한다.

```tsx
// app/error.tsx
'use client';

import { useEffect } from 'react';

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    console.error('발생한 에러:', error);
  }, [error]);

  return (
    <div className="p-4 border border-red-400 bg-red-50 text-red-700 rounded">
      <h2 className="font-bold mb-2">오류 발생</h2>
      <p className="text-sm mb-4">{error.message}</p>
      <button onClick={() => reset()} className="px-3 py-1 bg-red-600 text-white text-xs rounded">
        다시 시도
      </button>
    </div>
  );
}
```

```tsx
// app/page.tsx (일부)
async function fetchData(statusMode: string) {
  await new Promise((resolve) => setTimeout(resolve, 1500));
  if (statusMode === 'error') {
    throw new Error('서버 데이터베이스 연결에 실패했습니다.'); // 이 에러를 error.tsx가 포착
  }
  return { visitorCount: '1,250명', todaySales: '3,500,000원' };
}
```

- 이 코드가 만드는 실제 화면/동작: `?mode=error` 쿼리로 접속하면 1.5초 후 빨간 테두리의 "오류 발생" 카드와 에러 메시지("서버 데이터베이스 연결에 실패했습니다."), "다시 시도" 버튼이 나타난다. 버튼을 누르면 `reset()`이 호출되어 서버 컴포넌트를 다시 렌더링 시도한다.
- `'use client'`가 없다면 어떻게 될까: "다시 시도" 버튼의 `onClick` 이벤트 핸들러 자체를 등록할 수 없다. 서버 컴포넌트는 브라우저에서 실행되는 이벤트 리스너를 가질 수 없기 때문에, 클라이언트 경계를 선언하지 않으면 애초에 이 버튼이 동작하지 않는다.
- error.tsx가 없다면 어떻게 될까: 하위 컴포넌트 하나에서 던진 에러가 처리되지 않은 채 상위로 계속 전파되어, 최악의 경우 애플리케이션 전체가 하얀 화면으로 멈춰버리는 "에러 전파"가 발생한다. error.tsx는 에러가 발생한 그 경계에서 피해를 멈추고 나머지 화면은 정상 동작하게 지켜주는 방화벽 역할을 한다.

### | notFound() / unauthorized() / forbidden() — 상황별 예외 함수 |

| 함수 | HTTP 상태 | 호출 상황 | 연결되는 화면 |
| --- | --- | --- | --- |
| notFound() | 404 Not Found | 리소스를 찾을 수 없을 때 | not-found.tsx |
| unauthorized() | 401 Unauthorized | 로그인하지 않은 사용자가 접근할 때 | unauthorized.tsx |
| forbidden() | 403 Forbidden | 로그인은 했지만 권한이 없을 때 | forbidden.tsx |

```tsx
// app/page.tsx (일부)
import { notFound, unauthorized, forbidden } from 'next/navigation';

async function fetchData(statusMode: string) {
  await new Promise((resolve) => setTimeout(resolve, 1500));

  if (statusMode === 'not-found') notFound();        // → app/not-found.tsx 화면으로 전환
  if (statusMode === 'unauthorized') unauthorized();  // → app/unauthorized.tsx 화면으로 전환
  if (statusMode === 'forbidden') forbidden();        // → app/forbidden.tsx 화면으로 전환

  return { visitorCount: '1,250명', todaySales: '3,500,000원' };
}
```

```ts
// next.config.mjs — unauthorized(), forbidden()을 쓰려면 반드시 활성화해야 하는 실험적 옵션
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: {
    authInterrupts: true, // 이 설정이 없으면 unauthorized()/forbidden() 호출 시 에러가 난다
  },
};

export default nextConfig;
```

- 이 코드가 만드는 실제 화면/동작: `?mode=not-found`로 접속하면 노란색 "404 Not Found" 안내 카드가, `?mode=unauthorized`로 접속하면 파란색 "401 Unauthorized - 로그인이 필요합니다" 카드가, `?mode=forbidden`으로 접속하면 보라색 "403 Forbidden - 접근 권한이 없습니다" 카드가 뜬다. 각각 "메인으로 이동" 링크가 함께 표시된다.
- notFound() 같은 함수가 없다면 어떻게 될까: 조건문으로 "이 데이터가 없으면 404 메시지를 직접 return한다"처럼 페이지마다 수동으로 예외 UI를 분기해야 한다. 동시에 실제 HTTP 응답 상태 코드는 200(정상)으로 나가버려서, 검색 엔진이나 모니터링 도구 입장에서는 "이 페이지는 존재하지 않는다"는 사실을 제대로 인식하지 못한다. notFound()/unauthorized()/forbidden()은 화면 전환과 올바른 HTTP 상태 코드 응답을 함수 호출 한 줄로 동시에 처리해준다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
