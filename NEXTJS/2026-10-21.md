# PART 1. 서버 데이터 조회 & 캐싱 전략
### | 서버 컴포넌트에서 비동기로 데이터 조회하기 |

- 서버 컴포넌트는 함수 자체를 `async`로 선언해서 내부에서 바로 `await fetch()`를 실행할 수 있다. 클라이언트 컴포넌트처럼 `useEffect`로 요청을 보내고 `useState`로 결과를 담아두는 과정이 필요 없다.

```tsx
// app/components/ServerFetch.tsx
interface Post {
  id: number;
  title: string;
  body: string;
}

// 서버 컴포넌트는 async 함수로 작성하여 내부에서 await fetch()를 바로 실행한다.
export default async function ServerFetch() {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts');
  const posts: Post[] = await response.json();

  return (
    <section className="p-4 border border-gray-300 bg-gray-50 rounded-lg mb-6">
      <h2 className="text-lg font-bold text-gray-800 mb-3">기본 서버 데이터 조회</h2>
      <ul className="space-y-3">
        {posts.slice(0, 2).map((post) => (
          <li key={post.id} className="p-3 bg-white border border-gray-200 rounded-md">
            <strong className="block text-gray-900 font-semibold mb-1">{post.title}</strong>
            <p className="text-sm text-gray-600">{post.body}</p>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

- 이 코드가 실제로 만드는 요청 흐름: `ServerFetch` 컴포넌트는 브라우저가 아니라 Next.js 서버(요청을 처리하는 노드 프로세스)에서 실행된다. 브라우저는 이 컴포넌트가 외부 API(`jsonplaceholder`)에 요청을 보낸다는 사실 자체를 전혀 모른다 — 서버가 데이터를 다 가져와서 HTML로 그려낸 결과물만 받는다. 이 덕분에 API 키나 요청 로직이 클라이언트 자바스크립트 번들에 전혀 노출되지 않는다.
- 기본 캐싱 옵션 주의: 옵션 없이 `fetch()`만 호출하면 **Next.js 14 이하에서는 기본값이 `force-cache`(SSG)**로 동작하지만, **Next.js 15부터는 `no-store`가 기본값**이다. 버전을 모르고 옵션을 생략하면 "캐싱되는 줄 알았는데 매번 새로 조회되더라" 같은 혼동이 생기기 쉽다.

### | 왜 서버에서 데이터를 조회하고 캐싱하는 전략이 필요한가 |

- 매 요청마다 데이터를 처음부터 다시 조회하면, 손님이 올 때마다 요리를 처음부터 새로 만드는 식당처럼 응답 속도가 느려지고 외부 API·DB 부하도 커진다. 반대로 데이터를 한 번 캐싱해두고 계속 재사용하기만 하면, 자주 바뀌는 데이터(재고, 주문 상태 등)의 최신성이 깨진다. 캐싱 전략이 없다면 개발자는 이 둘 중 하나를 선택할 수밖에 없다 — "항상 느리지만 항상 최신"이거나 "항상 빠르지만 가끔 틀린 데이터". Next.js는 데이터 성격별로 SSG/SSR/ISR 세 가지 옵션을 fetch 하나에 지정하는 것만으로 이 둘을 절충하게 해준다.

### | SSG·SSR·ISR — fetch 옵션으로 캐싱 전략 선택하기 |

| 전략 | 옵션 | 동작 | 적합한 데이터 |
| --- | --- | --- | --- |
| SSG (정적 생성) | `{ cache: 'force-cache' }` | 빌드 시점에 조회 후 디스크에 영구 보관 | 거의 바뀌지 않는 데이터(약관, 소개 페이지) |
| SSR (서버 사이드 렌더링) | `{ cache: 'no-store' }` | 요청이 올 때마다 매번 새로 조회 | 실시간성이 중요한 데이터(주식 시세, 재고) |
| ISR (증분 정적 재생성) | `{ next: { revalidate: 초 } }` | 정적 응답을 주되, 지정 주기가 지나면 백그라운드에서 갱신 | 어느 정도 지연을 허용할 수 있는 데이터(상품 목록, 블로그 글) |

```tsx
// app/components/StaticFetch.tsx — SSG
export default async function StaticFetch() {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts/1', {
    cache: 'force-cache',
  });
  const post = await response.json();
  // 이 결과는 서버 디스크에 영구 저장되고, 이후 요청들은 네트워크 호출 없이 이 캐시만 읽는다.
  ...
}
```

```tsx
// app/components/DynamicFetch.tsx — SSR
export default async function DynamicFetch() {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts/2', {
    cache: 'no-store',
  });
  const post = await response.json();
  const fetchedTime = new Date().toLocaleTimeString();
  // 캐시를 전혀 쓰지 않으므로, 페이지를 새로고침할 때마다 fetchedTime이 매번 달라진다.
  ...
}
```

```tsx
// app/components/RevalidatedFetch.tsx — ISR
export default async function RevalidatedFetch() {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts/3', {
    next: { revalidate: 10 },
  });
  const post = await response.json();
  // 10초 이내 요청은 저장된 응답을 그대로 재사용하고,
  // 10초가 지난 뒤 들어온 요청이 트리거가 되어 백그라운드에서 새 데이터로 교체한다.
  ...
}
```

- SSR(`no-store`)이 없다면 실시간 데이터를 다루는 화면도 전부 정적 캐시로만 서비스하게 되어 옛날 주가·재고가 그대로 노출되는 사고가 난다. 반대로 ISR(`revalidate`)이 없다면, 자주는 안 바뀌지만 가끔 갱신이 필요한 데이터까지도 "완전 정적(SSG)" 아니면 "매번 재조회(SSR)" 둘 중 하나를 억지로 골라야 해서, 서버 부하와 데이터 신선도 사이의 중간 지점을 만들 방법이 없다.

### | Request Memoization과 Data Cache |

| 구분 | Request Memoization | Data Cache |
| --- | --- | --- |
| 범위 | 하나의 페이지 렌더링 1회 | 여러 유저·여러 요청에 걸쳐 지속 |
| 수명 | 렌더링이 끝나면 즉시 삭제 | `no-store`나 `revalidate` 설정에 따라 유지 |
| 해결하는 문제 | 같은 렌더링 안에서 서로 다른 컴포넌트가 동일 URL을 중복 호출하는 것 | 같은 응답을 서버 디스크·메모리에 저장해 재사용하는 것 |

- Request Memoization이 없다면 어떻게 될까. 한 페이지 안에서 헤더 컴포넌트와 본문 컴포넌트가 각각 `fetch('/api/user')`를 호출하는 상황을 생각하면, 요청이 2번 나가서 외부 API에 불필요한 부하를 준다. Next.js는 같은 렌더링 사이클 안에서 동일한 URL로의 `fetch`를 자동으로 1번만 실제 네트워크 요청으로 처리하고 나머지는 그 결과를 재사용한다.
- Data Cache가 없다면, 캐싱 옵션을 아무리 `force-cache`나 `revalidate`로 지정해도 저장해둘 저장소 자체가 없는 셈이라 매 요청·매 유저마다 외부 API를 다시 호출해야 한다. Data Cache는 이 응답 결과를 서버 쪽에 실제로 보관해서 "다음 유저, 다음 요청"에도 재사용할 수 있게 만드는 저장소 계층이다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 서버 컴포넌트 | Server Component | 클라이언트로 JS를 보내지 않고 서버에서 실행되는 React 컴포넌트 |
| 정적 생성 | SSG (Static Site Generation) | 빌드 시점에 데이터를 가져와 영구 보관하는 캐싱 전략 |
| 서버 사이드 렌더링 | SSR (Server-Side Rendering) | 요청이 올 때마다 서버가 매번 새로 데이터를 가져오는 전략 |
| 증분 정적 재생성 | ISR (Incremental Static Regeneration) | 지정한 주기마다 백그라운드에서 데이터를 갱신하는 전략 |
| 요청 메모이제이션 | Request Memoization | 하나의 렌더링 안에서 동일 URL 요청을 1회로 합치는 최적화 |
| 데이터 캐시 | Data Cache | API 응답 결과를 서버 측에 지속적으로 저장해두는 캐시 레이어 |

# PART 2. Streaming SSR & PPR
### | 느린 SSR이 전체 화면을 막아버리는 문제 |

- 기존 SSR은 페이지 안의 모든 데이터 조회가 끝나야 HTML 전체를 한 번에 완성해서 보낸다. 즉 음식 하나가 조리에 3초 걸리면, 이미 완성된 다른 요리들도 다 같이 3초를 기다려야 식탁에 올라오는 셈이다. **Streaming SSR**은 서버에서 완성된 HTML 조각을 생성되는 즉시 브라우저로 흘려보내서, 느린 영역만 따로 떼어 처리한다.

```tsx
// app/components/SlowComponent.tsx — 3초 지연 서버 컴포넌트
async function fetchSlowData(): Promise<string> {
  await new Promise((resolve) => setTimeout(resolve, 3000));
  return "3초 뒤에 도착한 실시간 데이터입니다.";
}

export default async function SlowComponent() {
  const data = await fetchSlowData();
  return (
    <div className="p-4 border border-gray-200 rounded-lg bg-gray-50">
      <h3 className="mb-2 text-lg font-bold text-gray-900">실시간 데이터 영역</h3>
      <p className="text-gray-700">{data}</p>
    </div>
  );
}
```

```tsx
// app/components/LoadingSkeleton.tsx — Suspense 대기 중 보여줄 UI
export default function LoadingSkeleton() {
  return (
    <div className="p-4 border border-dashed border-slate-300 rounded-lg bg-slate-100">
      <p className="font-bold text-slate-500">데이터를 불러오는 중입니다...</p>
    </div>
  );
}
```

```tsx
// app/page.tsx
import { Suspense } from "react";
import SlowComponent from "./components/SlowComponent";
import LoadingSkeleton from "./components/LoadingSkeleton";

export default function HomePage() {
  return (
    <main className="max-w-2xl mx-auto p-8 font-sans">
      <header className="mb-6 pb-3 border-b-2 border-blue-500">
        <h1 className="text-2xl font-bold text-blue-900">Streaming SSR & PPR 실습</h1>
      </header>

      <section>
        <h2 className="mb-4 text-xl font-semibold text-gray-800">실시간 서버 정보</h2>
        {/* fallback에 대기 중 보여줄 스켈레톤을 전달한다 */}
        <Suspense fallback={<LoadingSkeleton />}>
          {/* 서버 처리가 끝나는 대로 이 조각만 스트리밍되어 교체된다 */}
          <SlowComponent />
        </Suspense>
      </section>
    </main>
  );
}
```

- 이 코드가 실제로 만드는 요청 흐름: 브라우저가 페이지에 접속하면 서버는 먼저 `<header>`가 포함된 HTML 조각을 즉시 전송한다. 이어서 `<Suspense>`가 감싼 자리에는 일단 `LoadingSkeleton`이 그려진 HTML이 먼저 나간다. 그동안 서버는 백그라운드에서 `SlowComponent`의 `fetchSlowData()`(3초 대기)를 계속 실행하고 있고, 3초 뒤 데이터가 준비되면 그 결과 HTML 조각을 같은 연결을 통해 추가로 스트리밍해서 스켈레톤 자리를 실제 데이터로 교체한다. 브라우저는 페이지를 새로고침하지 않고도 이 교체를 받아들인다.

### | Streaming SSR이 없으면 뭐가 느려지는가 |

- `<Suspense>` 없이 `SlowComponent`를 그냥 `page.tsx`에 배치했다면, 서버는 `fetchSlowData()`의 3초 대기가 끝날 때까지 `<header>`를 포함한 HTML 전체를 아예 전송하지 않는다. 즉 빠르게 보여줄 수 있었던 헤더까지도 느린 영역에 발목이 잡혀 **TTFB(Time To First Byte, 첫 바이트 수신 시각)** 가 3초로 늘어난다. 사용자는 그 3초 동안 완전히 빈 화면만 보게 되고, 느린 컴포넌트가 하나라도 있으면 페이지 전체가 그 속도에 맞춰진다. Streaming SSR은 "준비된 것부터 먼저 보여준다"는 원칙으로 이 전체 지연을 막는다.

### | PPR (Partial Prerendering) — 정적 쉘과 동적 영역의 결합 |

- **Static Shell(정적 쉘)**: 네비게이션 바처럼 바뀌지 않는 요소로, 빌드 시점에 미리 만들어둔다.
- **Dynamic Area(동적 영역)**: 실시간 데이터처럼 자주 바뀌는 요소로, `<Suspense>`로 감싸 접속 시점에 스트리밍 처리한다.

```tsx
// app/page.tsx
import { Suspense } from "react";
import LoadingSkeleton from "./components/LoadingSkeleton";
import SlowComponent from "./components/SlowComponent";

// PPR을 활성화하는 Next.js 설정 옵션
export const experimental_ppr = true;

export default function HomePage() {
  return (
    <main className="max-w-2xl mx-auto p-8 font-sans">
      {/* Static Shell: 빌드 타임에 미리 만들어져 즉시 출력된다 */}
      <header className="mb-6 pb-3 border-b-2 border-blue-500">
        <h1 className="text-2xl font-bold text-blue-900">Streaming SSR & PPR 실습</h1>
      </header>

      <section>
        <h2 className="mb-4 text-xl font-semibold text-gray-800">실시간 서버 정보</h2>
        {/* Dynamic Area: Suspense로 감싸 접근 시점에 스트리밍 처리된다 */}
        <Suspense fallback={<LoadingSkeleton />}>
          <SlowComponent />
        </Suspense>
      </section>
    </main>
  );
}
```

- 이 코드가 실제로 만드는 캐시 동작: `experimental_ppr = true`를 선언하면, Next.js는 빌드 시점에 `<header>`를 포함한 정적 쉘 부분을 이미 HTML로 구워서 CDN 등에 캐싱해둔다. 실제 사용자 요청이 들어오면 이 정적 쉘은 캐시에서 즉시 응답하고, `<Suspense>` 내부의 동적 영역만 그 요청 시점에 서버에서 실행되어 스트리밍으로 채워진다. 즉 한 페이지 안에서 "이 부분은 SSG처럼, 저 부분은 SSR처럼" 서로 다른 캐싱 전략이 동시에 적용되는 셈이다.
- PPR이 없다면 어떻게 될까. 정적인 부분과 동적인 부분이 한 페이지에 섞여 있을 때, 페이지 전체를 SSR로 설정하면 바뀌지 않는 헤더까지 매 요청마다 서버에서 다시 렌더링해야 해서 비효율적이다. 반대로 페이지 전체를 SSG로 설정하면 실시간 데이터를 애초에 보여줄 수 없다. PPR은 "변하지 않는 건 미리 굽고, 변하는 것만 그때그때 채운다"는 절충안으로 이 비효율을 없앤다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 스트리밍 | Streaming | 데이터를 통째로 전달하지 않고 연속된 조각 형태로 분할 전송하는 방식 |
| TTFB | Time To First Byte | 요청 후 첫 번째 데이터 조각을 수신할 때까지 걸리는 시간 |
| 정적 쉘 | Static Shell | 빌드 시점에 미리 완성하여 즉시 보여줄 수 있는 고정 UI 레이아웃 |
| 동적 영역 | Dynamic Area | 실시간 연산이 필요해 접근 시점에 스트리밍으로 채워지는 UI 영역 |
| 서스펜스 | Suspense | 하위 컴포넌트의 데이터가 준비될 때까지 로딩 상태를 제어하는 React 기능 |
| 부분 사전 렌더링 | PPR (Partial Prerendering) | 정적 쉘과 동적 영역을 한 페이지에서 결합하는 렌더링 기법 |

# PART 3. 'use server' Server Actions & 캐시 갱신
### | Server Components와 Server Actions의 차이 |

| 구분 | Server Components (기본값) | Server Actions ('use server') |
| --- | --- | --- |
| 실행 시점 | 페이지가 렌더링될 때 | 유저의 클릭·폼 제출 같은 이벤트가 발생할 때 |
| 역할 | 서버에서 화면(HTML)을 그림 | 브라우저에서 서버 로직을 직접 호출하게 해주는 통로 |
| 대체 효과 | — | `/app/api/...` 형태의 API Route 파일 작성을 생략 가능 |

### | 'use server'로 선언하는 Server Action이 왜 필요한가 |

- 기존 방식에서 웹사이트에 방명록을 남기려면, `/app/api/guestbook` 같은 API 엔드포인트 파일을 따로 만들고 — 그 안에서 HTTP 메서드를 분기하고, 요청 body를 파싱하고, 응답을 직렬화해서 돌려주는 코드를 전부 손으로 짜야 했다. 그리고 클라이언트 쪽에서는 그 URL로 `fetch` 요청을 보내는 코드를 또 따로 작성해야 했다 — 즉 같은 기능 하나를 위해 서버 파일과 클라이언트 파일 양쪽에 짝이 맞는 코드를 유지해야 한다.
- `'use server'`로 선언한 함수는 **일반 함수를 호출하듯 클라이언트 컴포넌트에서 바로 `import`해서 실행**할 수 있다. Next.js가 빌드 시점에 이 함수를 위한 API 통로를 자동으로 만들어주기 때문에, 개발자는 API 라우트 파일을 쓰지 않고도 "클라이언트 → 서버 함수 호출"이라는 결과를 그대로 얻는다. 즉 Server Action이 없다면 지금까지 당연하게 만들어오던 `/api/...` 레이어를 기능 하나마다 매번 새로 구축해야 한다는 뜻이다.

### | 'use server' 선언 규칙 |

- **별도 파일 최상단 선언(권장)**: 파일 맨 위에 `'use server'`를 적으면 그 파일의 모든 함수가 서버 액션이 된다. 클라이언트 컴포넌트에서 불러올 때 필수적인 방식이다.
- **서버 컴포넌트 내부 선언**: `'use client'`가 없는 서버 컴포넌트라면 함수 상단에 `'use server'`를 적어 인라인으로도 쓸 수 있다.
- 주의: `'use client'`가 선언된 파일 내부에서는 인라인으로 `'use server'` 함수를 정의할 수 없다. 반드시 외부 파일(`actions.ts`)에서 불러와야 한다.

```ts
// app/actions/guestbookActions.ts
'use server';

import { revalidatePath } from 'next/cache';

export interface GuestbookEntry {
  id: number;
  content: string;
}

const guestbookDb: GuestbookEntry[] = [
  { id: 1, content: '첫 번째 방명록 글입니다.' }
];

export async function getGuestbook() {
  return guestbookDb;
}

// <form action={...}> 사양에 맞춰 Promise<void> 타입으로 정의한다.
export async function addGuestbookEntry(formData: FormData): Promise<void> {
  const content = formData.get('content') as string;

  if (!content || content.trim() === '') {
    return;
  }

  const newEntry: GuestbookEntry = {
    id: Date.now(),
    content: content
  };

  guestbookDb.push(newEntry);

  // 메인 페이지('/')의 서버 캐시를 즉시 삭제하여 UI를 동기화한다.
  revalidatePath('/');
}
```

### | Form action 바인딩과 FormData 자동 전달 |

```tsx
// app/components/GuestbookForm.tsx
'use client';

import { addGuestbookEntry } from '../actions/guestbookActions';

export default function GuestbookForm() {
  return (
    // form의 action 속성에 서버 액션 함수를 직접 바인딩한다.
    <form action={addGuestbookEntry} className="flex gap-2 my-4">
      <input
        type="text"
        name="content" // FormData 객체의 key 이름이 된다.
        placeholder="방명록을 입력하세요"
        required
      />
      <button type="submit">등록</button>
    </form>
  );
}
```

- `<form action={addGuestbookEntry}>`로 설정하면, 폼 안의 입력값들이 자동으로 `FormData` 객체로 묶여 서버 함수의 인자로 전달된다. 개발자가 `onSubmit`에서 `event.preventDefault()`를 호출하고 입력값을 하나씩 모아 body로 직렬화하던 작업을 Next.js가 대신 처리해준다.
- **점진적 향상(Progressive Enhancement)**: 이 방식은 HTML 기본 `<form>` 제출 동작 위에 얹혀 있어서, 자바스크립트가 아직 다 로딩되지 않은 상태에서도 기본 HTML Submit으로 서버에 전송된다.

### | revalidatePath / revalidateTag — 캐시 무효화 |

| 함수 | 무효화 범위 | 사용 예 |
| --- | --- | --- |
| `revalidatePath('/')` | 해당 경로의 페이지 전체 캐시 | 방명록 등록 후 메인 페이지 전체를 최신화 |
| `revalidateTag('posts-tag')` | 지정한 태그가 달린 fetch 캐시만 선택적으로 | 특정 데이터 영역만 정밀하게 최신화 |

```ts
// 데이터 조회 시 태그를 부여
export async function getPosts() {
  const res = await fetch('https://api.example.com/posts', {
    next: { tags: ['posts-tag'] }
  });
  return res.json();
}

// Server Action에서 해당 태그 캐시만 선택 제거
'use server';
import { revalidateTag } from 'next/cache';

export async function addPost() {
  // ... 서버 데이터 추가 로직 ...
  revalidateTag('posts-tag');
}
```

- 이 코드가 실제로 만드는 캐시 동작: `addGuestbookEntry`가 메모리 배열(`guestbookDb`)에 새 데이터를 추가한 뒤 `revalidatePath('/')`를 호출하면, Next.js는 `/` 경로에 대해 저장해둔 Data Cache와 렌더링 결과를 즉시 폐기 표시한다. 그래서 다음 번에 `GuestbookList`(서버 컴포넌트)가 `getGuestbook()`을 호출할 때는 캐시된 옛 배열이 아니라 방금 갱신된 배열을 다시 읽어와 새 HTML을 만든다.
- `revalidatePath`/`revalidateTag`가 없다면 어떻게 될까. Server Action으로 서버 데이터는 분명히 바뀌었는데도, 캐시된 페이지는 그 변경을 전혀 모르고 계속 옛 데이터를 보여준다. 사용자가 방명록을 작성하고 나서 화면이 바뀌지 않아 "글이 등록됐나?" 하며 새로고침을 반복하거나, 혹은 애초에 캐싱 자체를 포기(`no-store`)해야 해서 PART 1에서 배운 캐싱 전략의 이점을 전부 잃게 된다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 서버 액션 | Server Actions | API 엔드포인트 파일 없이 클라이언트에서 서버 로직을 호출하는 기능 |
| 캐시 무효화 | Cache Invalidation | 데이터를 최신화하기 위해 기존 캐시를 만료시키는 작업 |
| 점진적 향상 | Progressive Enhancement | 자바스크립트 미지원 환경에서도 HTML 기본 동작만으로 기능을 제공하는 설계 기법 |
| 경로 기반 재검증 | revalidatePath | 특정 URL 경로의 서버 캐시 전체를 무효화하는 함수 |
| 태그 기반 재검증 | revalidateTag | 지정한 태그가 달린 fetch 캐시만 선택적으로 무효화하는 함수 |

# PART 4. Form 전용 Hooks & useOptimistic
### | useFormStatus — 폼 제출 진행 상태 추적 |

- 상위 `<form>`의 제출 진행 여부(`pending`)를 자식 컴포넌트에서 자동으로 추적하는 훅이다. 반드시 `<form>` 내부에서 호출되는 하위 컴포넌트로 작성해야 한다.

```tsx
// app/components/SubmitButton.tsx
'use client';
import { useFormStatus } from 'react-dom';

export function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? '서버 전송 중...' : '댓글 등록'}
    </button>
  );
}
```

- `useFormStatus`가 없다면, 폼이 제출되어 서버 액션이 처리되는 동안에도 버튼이 계속 클릭 가능한 상태로 남는다. 사용자가 응답을 기다리며 버튼을 여러 번 눌러 중복 제출이 발생할 수 있고, 로딩 표시를 하려면 부모 컴포넌트에서 별도의 state를 만들어 props로 하나하나 내려줘야 한다. `useFormStatus`는 이 state를 부모가 따로 관리하지 않아도 자식 버튼이 상위 `<form>`의 상태를 직접 구독하게 해준다.

### | useActionState — 서버 액션 결과·실행 함수·진행 상태 통합 |

```ts
// app/actions.ts
'use server';

export type FormState = {
  message: string;
  isSuccess: boolean;
};

// 이전 상태(prevState)와 FormData를 함께 받는 서버 액션
export async function submitComment(prevState: FormState, formData: FormData): Promise<FormState> {
  await new Promise((resolve) => setTimeout(resolve, 1500)); // 네트워크 지연 체감용

  const comment = formData.get('comment') as string;

  if (!comment || comment.trim() === '') {
    return { message: '댓글 내용을 입력해 주세요.', isSuccess: false };
  }

  return { message: `댓글이 성공적으로 등록되었습니다: "${comment}"`, isSuccess: true };
}
```

```tsx
// app/components/ActionStateForm.tsx
'use client';
import { useActionState } from 'react';
import { FormState, submitComment } from '../actions';
import { SubmitButton } from './SubmitButton';

export function ActionStateForm() {
  const initialState: FormState = { message: '', isSuccess: false };
  // state(결과), formAction(실행 함수), isPending(진행 여부)을 한 번에 받는다.
  const [state, formAction, isPending] = useActionState(submitComment, initialState);

  return (
    <div>
      <form action={formAction} className="space-y-4">
        <input id="comment" name="comment" placeholder="댓글을 입력하세요..." />
        <SubmitButton />
      </form>

      {state.message && (
        <div className={state.isSuccess ? 'text-green-700' : 'text-red-700'}>
          {state.message}
        </div>
      )}
    </div>
  );
}
```

- 이 코드가 실제로 만드는 흐름: 사용자가 댓글을 입력하고 제출 버튼을 누르면 `formAction`이 실행되어 `submitComment` 서버 액션이 호출된다. 이 서버 액션은 `prevState`(직전 상태)와 `FormData`를 받아 1.5초 후 새 `FormState` 객체를 반환하고, `useActionState`는 이 반환값을 자동으로 `state`에 반영해서 컴포넌트를 다시 그린다. `useActionState`가 없다면 `onSubmit` 핸들러 안에서 `event.preventDefault()`를 호출하고, 직접 `fetch`나 서버 함수를 호출한 뒤, 그 결과를 `useState`에 담는 과정을 전부 손으로 조립해야 한다.

### | useOptimistic — 낙관적 UI |

```tsx
// app/components/OptimisticComment.tsx (발췌)
'use client';
import { useActionState, useOptimistic, useRef, useState } from 'react';
import { FormState, submitComment } from '../actions';
import { SubmitButton } from './SubmitButton';

type CommentItem = { id: number; text: string; isSending?: boolean };

export function OptimisticComment() {
  const formRef = useRef<HTMLFormElement>(null);
  const [comments, setComments] = useState<CommentItem[]>([
    { id: 1, text: '첫 번째 기존 댓글입니다.' },
  ]);

  const initialState: FormState = { message: '', isSuccess: false };
  const [state, formAction] = useActionState(submitComment, initialState);

  // 실제 서버 데이터(comments)에 "낙관적 추가 규칙"을 더해 낙관적 목록을 만든다.
  const [optimisticComments, addOptimisticComment] = useOptimistic(
    comments,
    (currentComments: CommentItem[], newCommentText: string) => [
      ...currentComments,
      { id: Date.now(), text: newCommentText, isSending: true },
    ]
  );

  async function handleClientAction(formData: FormData) {
    const commentText = formData.get('comment') as string;
    if (!commentText || !commentText.trim()) return;

    // ① 서버 응답을 기다리지 않고 화면에 "전송 중" 댓글을 즉시 표시
    addOptimisticComment(commentText);
    formRef.current?.reset();

    // ② 실제 서버 액션을 비동기로 실행
    await formAction(formData);

    // ③ 서버 처리가 끝나면 진짜 데이터로 교체
    setComments((prev) => [...prev, { id: Date.now(), text: commentText }]);
  }

  return (
    <div>
      <ul>
        {optimisticComments.map((comment) => (
          <li key={comment.id}>
            {comment.text}
            {comment.isSending && <span>전송 중...</span>}
          </li>
        ))}
      </ul>
      <form ref={formRef} action={handleClientAction}>
        <input type="text" name="comment" />
        <SubmitButton />
      </form>
    </div>
  );
}
```

- 이 코드가 실제로 만드는 화면 흐름: 사용자가 댓글을 입력하고 제출하면, `addOptimisticComment(commentText)`가 먼저 실행되어 `optimisticComments` 목록에 `isSending: true`가 붙은 임시 댓글이 **그 즉시(0초 만에)** 나타난다. 입력창도 바로 비워진다. 그 다음에야 `formAction(formData)`가 실행되어 실제로는 1.5초가 걸리는 `submitComment` 서버 액션이 백그라운드에서 처리되고, 완료되면 `setComments`로 진짜 댓글 목록이 갱신되면서 "전송 중" 표시가 사라진 정식 댓글로 교체된다.

### | useOptimistic이 없으면 사용자 경험이 어떻게 달라지는가 |

- `useOptimistic` 없이 똑같은 기능을 구현하면, 사용자가 댓글을 입력하고 제출한 뒤 `submitComment`의 1.5초 네트워크 지연이 끝날 때까지 화면에는 아무런 변화가 없다. 그 1.5초 동안 사용자는 "내 댓글이 제대로 등록된 게 맞나?" 불안해하며 버튼을 다시 누르거나(중복 제출), 반응이 없다고 느껴 페이지를 이탈할 수도 있다. SNS의 '좋아요' 버튼이 누르자마자 바로 빨갛게 채워지는 것도 같은 원리다 — 서버가 실제로 처리를 끝내기 전에, "성공할 것"이라고 낙관하고 화면을 먼저 바꿔버리는 것이다. 만약 서버 처리 중 오류가 나면 React가 자동으로 이전 상태로 되돌린다(롤백). 결국 `useOptimistic`의 유무는 "네트워크 지연이 사용자 눈에 보이느냐 안 보이느냐"를 가르는 핵심 장치다.

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 서버 액션 | Server Actions | API 엔드포인트 없이 클라이언트 폼에서 직접 서버 함수를 호출하는 기능 |
| 팬딩 상태 | Pending State | 데이터 요청이나 폼 제출 작업이 진행 중인 대기 상태 |
