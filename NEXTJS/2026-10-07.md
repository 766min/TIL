# PART 1. React.js는 왜 만들어졌나 — 가상 DOM

### | 실제 DOM을 직접 건드리면 왜 느려지나 |

- 웹 페이지에서 HTML DOM을 직접 조작하는 일이 많아질수록 속도가 느려지고 사용자 경험이 떨어진다. 페이스북(현 Meta)이 이 문제를 해결하려고 만든 UI 라이브러리가 **React**다.

### | 가상 DOM(Virtual DOM)과 재조정(Reconciliation) |

- React는 실제 DOM을 바로 건드리지 않고, 메모리 위에 **가상 DOM**(DOM 구조를 흉내 낸 자바스크립트 객체)을 먼저 둔다.

| 단계 | 설명 |
| --- | --- |
| ① 상태 변경 | 컴포넌트의 데이터(state)가 바뀜 |
| ② 새 가상 DOM 생성 | 바뀐 상태를 반영한 가상 DOM 객체를 새로 만듦 |
| ③ 비교(Diffing) | 이전 가상 DOM과 새 가상 DOM을 메모리 안에서 비교해 차이점만 찾아냄 |
| ④ 최소 반영(Reconciliation) | 찾아낸 차이만 실제 DOM에 한꺼번에 반영 |

- 전체를 지우고 새로 그리는 게 아니라, 차이가 난 부분만 골라서 한 번에 업데이트하는 것이 핵심이다. 메모리 안의 객체끼리 비교하는 연산은 빠르고, 느린 실제 DOM 조작은 필요한 만큼만 최소화해서 하기 때문에 효율적이다. 이 비교·반영 과정 전체를 **재조정(Reconciliation)** 이라고 부른다.

### | 가상 DOM이 항상 빠른 건 아니다 |

- 화면이 자주 바뀌는 동적인 애플리케이션에는 가상 DOM 비교 방식이 적합하다. 반대로 내용이 거의 바뀌지 않는 정적인 페이지에서는, 애초에 비교할 변화가 없으니 가상 DOM을 만들고 비교하는 비용만 추가로 드는 셈이라 오히려 안 맞을 수 있다.

# PART 2. React.js와 Next.js — 라이브러리와 프레임워크

### | 라이브러리 vs 프레임워크 |

| 구분 | React.js | Next.js |
| --- | --- | --- |
| 정체 | UI를 만드는 **라이브러리** | React를 기반으로 라우팅·렌더링·빌드까지 갖춘 **프레임워크** |
| 기본 렌더링 방식 | CSR (브라우저에서 번역) | SSR 등 (서버에서 번역) |
| 렌더링 주체 | 브라우저 | 서버 |

- 라이브러리는 필요한 기능을 가져다 쓰는 도구에 가깝고, 프레임워크는 애초에 "이 틀 안에서 개발하라"고 전체 구조(라우팅, 렌더링 방식, 빌드 설정)를 미리 갖춰 제공한다. 지금 수강 중인 과정은 React 자체가 아니라 **Next.js**를 다룬다 — 즉 React 문법(JSX/TSX, 컴포넌트)은 그대로 쓰되, 렌더링·라우팅·빌드는 Next.js가 제공하는 체계를 따른다.

# PART 3. CSR (Client Side Rendering) — React의 기본 렌더링 방식

### | 번역(렌더링)의 주체는 브라우저 |

- React를 빌드하면 결과물은 거의 비어있는 HTML 파일 하나와 JS 파일(들)로 구성된다.

```html
<!-- index.html -->
<div id="root"></div>
<script src="bundle.js"></script>
```

- 브라우저가 `index.html`을 받아도 이 시점엔 화면에 보여줄 내용이 없다. 이어서 `bundle.js`(React 코드가 번역·압축된 자바스크립트 파일)를 다운로드해서 실행한 뒤에야, 그 JS 코드가 `<div id="root">` 안에 실제 화면 요소들을 동적으로 만들어 채워 넣는다. 번역(렌더링)의 주체가 **브라우저**이기 때문에 CSR이라고 부른다.

### | CSR 장점 |

| 장점 | 이유 |
| --- | --- |
| 화면 전환이 빠름 | 이미 받아둔 HTML·CSS·JS 리소스를 그대로 활용해서 화면만 다시 그리기 때문 |
| 한 번 로딩된 화면은 끊김 없이 동작 | 리소스를 이미 다운로드했으므로, 그 화면 자체를 보여주는 데는 서버와의 추가 통신이 필요 없음 (단, 새 데이터를 불러오는 API 요청은 별개로 네트워크가 필요하다) |

### | CSR 단점 |

| 단점 | 이유 |
| --- | --- |
| 초기 로딩 지연 | 자바스크립트 파일을 전부 받아서 실행한 뒤에야 화면이 그려지므로, 인터넷이 느리면 한동안 비어있는 `index.html`만 보임 |
| SEO(검색 엔진 최적화) 문제 | 검색 엔진 크롤러가 페이지를 읽는 시점에는 `<div id="root"></div>`만 있는 빈 HTML이라서, 실제 콘텐츠를 긁어가지 못해 검색 결과에 반영되지 않음 — 외부 사용자 유입이 중요한 서비스일수록 치명적인 단점 |

# PART 4. SSR (Server Side Rendering) — Next.js의 기본 렌더링 방식

### | Pre-render와 Hydration |

- SSR은 번역(렌더링)의 주체가 **서버**다. 크게 두 단계로 동작한다.

| 단계 | 설명 |
| --- | --- |
| ① Pre-render | 서버가 React/Next.js 문법을 미리 번역해서, **내용이 이미 채워진 HTML**을 브라우저로 전송한다 |
| ② Hydration | 브라우저가 받은(이미 내용이 있는) HTML에 자바스크립트를 연결해서, 클릭 등 동적인 상호작용 기능을 "살려"준다 |

```html
<!-- 서버가 Pre-render해서 보내주는 HTML -->
<div id="root">
  <h1>상품 목록</h1> <!-- 이미 내용이 채워져 있음 -->
</div>
```

- CSR은 빈 HTML을 먼저 받고 JS가 그 안을 채우는 순서였다면, SSR은 **내용이 이미 있는 HTML**을 먼저 받고, 그 위에 JS로 "동작"만 나중에 덧입히는 순서다. 그래서 검색 엔진 크롤러도 첫 응답부터 실제 콘텐츠를 읽을 수 있어 SEO에 유리하다.

### | SSR 장점/단점 |

| 장점 | 단점 |
| --- | --- |
| 내용이 채워진 HTML이 바로 오므로 첫 화면이 빠르게 보이고 검색 엔진에도 반영됨(SEO 유리) | 요청이 올 때마다 서버가 렌더링 연산을 해야 하므로, 그 연산 시간만큼 최초 응답에 약간의 지연이 생기고 서버 부담도 늘어남 |

### | CSR vs SSR 한눈에 비교 |

| 구분 | React.js (CSR) | Next.js (SSR 등) |
| --- | --- | --- |
| 렌더링 주체 | 브라우저 | 서버 |
| 첫 화면 | JS가 실행된 후에야 표시 | 내용이 있는 HTML이 바로 표시 |
| SEO | 불리 | 유리 |
| 화면 전환 | 빠름 | Hydration 이후 빠름 |

- 참고로 Next.js가 SSR만 쓰는 건 아니다. 페이지마다 빌드 시점에 미리 페이지를 만들어두는 SSG(Static Site Generation), 혹은 CSR 방식 등을 상황에 맞게 골라 쓸 수 있다.

# PART 5. 빌드 도구 — 트랜스파일과 번들링

### | 왜 트랜스파일과 번들링이 필요한가 |

- React는 `.jsx`/`.tsx`라는 React 전용 문법으로 작성한다. 브라우저는 이 문법을 그대로 이해하지 못하므로 자바스크립트로 "번역"하는 과정이 필요하다 — 이를 담당하는 것이 **트랜스파일러**다. 과거 React 생태계에서는 자바스크립트 기반 트랜스파일러인 **Babel**을 사용했다.
- React는 재사용성을 위해 공통 구성요소를 **컴포넌트** 단위로 쪼개 개발한다. 각 컴포넌트는 독립된 모듈 파일로 존재하는데, 배포하려면 이렇게 흩어진 여러 모듈 파일들을 하나(또는 몇 개)의 파일로 묶어야 한다. 이 "묶는다(pack)"는 작업을 하는 도구가 **번들러**이고, 대표적인 번들러가 **Webpack**이다.

```
.jsx/.tsx 컴포넌트(여러 모듈)
    ↓ 트랜스파일 (Babel) — JS 문법으로 번역
    ↓ 번들링 (Webpack) — 여러 모듈을 하나로 묶음(pack)
배포 가능한 js/css 파일
```

### | Next.js의 해결책 — Rust 기반 도구 |

- Babel과 Webpack은 둘 다 자바스크립트로 만들어진 프로그램이다. 문제는 프로젝트가 커질수록 "번역이 너무 느리다"는 점이었다.

| 역할 | 과거 (React 기본) | Next.js |
| --- | --- | --- |
| 트랜스파일러 | Babel | **SWC** (Speedy Web Compiler) |
| 번들러 | Webpack | **Turbopack** |
| 개발 언어 | JavaScript | **Rust** |
| 속도 | 느림 | 빠름 |

- Next.js는 트랜스파일·번들링 성능을 높이기 위해, 이 두 도구를 자바스크립트보다 훨씬 빠른 시스템 프로그래밍 언어인 **Rust**로 새로 만들었다. 그 결과물이 SWC와 Turbopack이며, 이름 그대로 "속도(Speedy)"를 핵심 목표로 설계됐다.

# PART 6. 프로젝트 설정 — package.json과 .prettierrc

### | package.json — 프로젝트 명세서 |

| 항목 | 역할 | 설치 명령 |
| --- | --- | --- |
| `dependencies` | 실제 서비스 배포 시 코드에 포함되어야 하는 의존성(예: React 자체) | `npm i 패키지명` |
| `devDependencies` | 개발할 때만 필요하고 배포 결과물에는 포함되지 않는 의존성(예: 타입 정의, 린터) | `npm i -D 패키지명` |
| `scripts` | `npm run 이름`으로 실행할 수 있는 명령어 모음(예: `dev`, `build`) | — |

- `npm i`만 단독으로 실행하면, `package.json`에 적힌 명세를 바탕으로 `dependencies`·`devDependencies`에 적힌 의존성을 한꺼번에 설치한다.
- `npm run dev`: `scripts`에 정의된 `dev` 명령을 실행해서 개발 서버를 띄우는 명령어다.
- `package.json`에는 보통 `"private": true`가 기본으로 들어있다. 이건 "이 프로젝트를 실수로 npm 공개 레지스트리에 배포(publish)하지 않도록 막는" 안전장치다. 우리가 만드는 건 npm에 공개 배포할 패키지가 아니라 서비스 앱이므로, 이 값을 `true`로 그대로 두는 것이 맞다 — `false`로 바꾸는 건 "이 프로젝트를 npm 패키지로 배포하겠다"는 의도가 있을 때만 하는 특수한 설정이다.

### | .prettierrc — 코드 스타일 통일 설정 |

- 여러 사람이 함께 작업할 때 들여쓰기 칸 수, 따옴표 종류 같은 코드 스타일이 제각각이면 diff(변경 비교)가 지저분해진다. `.prettierrc`는 이런 스타일 규칙을 프로젝트 전체에서 통일하기 위한 설정 파일이다.

```json
{
  "tabWidth": 2,
  "singleQuote": true
}
```

- `tabWidth`: Tab 키를 눌렀을 때 몇 칸 들여쓰기할지 지정한다.
- `singleQuote`: `true`로 설정하면 문자열을 큰따옴표(`"`)가 아니라 작은따옴표(`'`)로 통일해서 저장한다.

# PART 7. ES 모듈 — export와 import

### | export — 모듈 내보내기 |

- `export`는 **파일 단위**가 아니라 함수·클래스·변수·객체 등 **값 단위**로 다른 파일에서 가져다 쓸 수 있게 공유하는 문법이다. 한 파일 안에 `export`로 내보낸 것만 다른 파일에서 가져다 쓸 수 있다.

```typescript
// mathUtils.ts

// named export — 이름이 있는 내보내기, 한 파일에 여러 개 선언 가능
export function add(a: number, b: number): number {
  return a + b;
}

// default export — 한 파일에 단 하나만 가능
export default function multiply(a: number, b: number): number {
  return a * b;
}
```

| 구분 | export (named export) | export default |
| --- | --- | --- |
| 한 파일 내 개수 | 여러 개 가능 | 단 하나만 가능 |
| import 시 이름 | 내보낼 때 쓴 이름 그대로, 중괄호 `{ }`로 가져와야 함 | 가져오는 쪽에서 원하는 이름으로 자유롭게 지어서 가져올 수 있음 |

### | import — 모듈 가져오기 |

```typescript
// 다른 파일에서 가져오기
import multiply, { add } from "./mathUtils";

console.log(add(2, 3));       // named export — 반드시 원래 이름(add)과 중괄호로 가져옴
console.log(multiply(2, 3));  // default export — 이름을 자유롭게 바꿔서 가져와도 됨 (예: import calc from ...)
```

- `export`와 `export default`를 헷갈리면 안 된다. **named export는 내보낸 이름 그대로 중괄호에 담아 가져와야 하고, default export는 가져오는 쪽에서 원하는 이름을 마음대로 붙여도 된다.** 한 파일에 `export default`는 하나만 둘 수 있지만, named export(`export`)는 여러 개를 동시에 둘 수 있다.

### | 타입도 모듈화한다 |

- TypeScript에서는 타입(`type`, `interface`)도 일반 값과 똑같이 `export`/`import`할 수 있다. 여러 파일에서 반복해서 같은 타입을 재정의하는 대신, 타입 전용 파일(`types.ts` 등)에 한 번만 정의해두고 필요한 곳마다 `import`해서 재사용하는 방식을 쓴다.

# PART 8. JSX / TSX 문법 규칙

### | JSX(JavaScript XML)란 |

- JSX는 자바스크립트 코드 안에 `<태그>...</태그>` 형태의 마크업을 직접 쓸 수 있게 해주는 문법이다. TypeScript와 결합된 버전을 TSX(TypeScript XML)라고 부른다. 겉보기엔 HTML과 비슷하지만, HTML보다 **더 엄격한 규칙**을 따른다.

### | 규칙 1 — 단일 태그도 반드시 닫아야 한다 |

- HTML에서는 `<br>`, `<img>`처럼 닫는 태그가 없어도 되는 단독 태그가 있지만, JSX에서는 이런 단일 태그도 반드시 셀프 클로징(`/>`)으로 끝맺어야 한다.

```tsx
// HTML에서는 허용되지만 JSX에서는 문법 에러
// <br>

// JSX에서는 반드시 이렇게 닫아야 함
<br />
<img src="photo.jpg" />
```

### | 규칙 2 — 여러 줄이면 소괄호로 감싼다 |

```tsx
// 한 줄이면 소괄호 생략 가능
const title = <h1>환영합니다</h1>;

// 여러 줄이면 소괄호로 감싸야 함
const card = (
  <div>
    <h1>환영합니다</h1>
    <p>오늘도 좋은 하루 되세요.</p>
  </div>
);
```

### | 규칙 3 — 컴포넌트는 단일 루트 노드를 반환해야 한다 |

- [PART 1](#part-1-reactjs는-왜-만들어졌나--가상-dom)에서 본 재조정(Reconciliation) 과정이 변화를 효율적으로 감지하려면, 컴포넌트가 반환하는 결과물이 하나의 최상위 노드로 묶여 있어야 한다. 그렇다고 의미 없이 `<div>`로 감싸면 실제 DOM에 불필요한 노드가 하나 더 추가된다. 이럴 때 **Fragment**를 쓴다.

```tsx
// 화면에 보이지 않는 단일 컴포넌트 — 실제 DOM에 노드를 추가하지 않음
function Greeting() {
  return (
    <>
      <h1>안녕하세요</h1>
      <p>Next.js 공부 중입니다</p>
    </>
  );
}
// <Fragment>...</Fragment>와 완전히 같은 의미지만, <>...</>로 짧게 쓰는 경우가 더 많다.
```

### | 규칙 4 — JSX 안에서 자바스크립트 코드를 쓰려면 중괄호 `{ }` |

```tsx
const userName = "민지";

const greeting = <h1>안녕하세요, {userName}님!</h1>;
```

### | 규칙 5 — 조건부 렌더링 |

- `if`문을 JSX 안에 직접 쓸 수 없으므로, 한 줄로 끝나는 조건식을 주로 사용한다.

```tsx
const isLoggedIn = true;

// 삼항 연산자 — 두 경우를 모두 보여줘야 할 때
const message = <p>{isLoggedIn ? "환영합니다" : "로그인이 필요합니다"}</p>;

// && 단락 회로 평가 — 조건이 참일 때만 보여주면 될 때 (더 짧게 쓸 수 있음)
const notice = isLoggedIn && <p>오늘의 할 일을 확인하세요</p>;
```

### | 규칙 6 — 주석 작성법 |

```tsx
function Example() {
  return (
    <div>
      {/* 여러 줄도 가능한 JSX 주석 */}
      <h1>제목</h1>
      {
        // 한 줄 주석은 반드시 줄바꿈이 필요하다
      }
    </div>
  );
}
```

### | 규칙 7 — React.JSX.Element vs React.ReactNode |

| 타입 | 의미 |
| --- | --- |
| `React.JSX.Element` | 오직 JSX 요소만 반환한다는 뜻 — 이름 그대로 JSX만 포함 |
| `React.ReactNode` | JSX 요소뿐 아니라 문자열, 숫자, `null`, 함수, 객체 등 더 폭넓은 값을 포함할 수 있는 타입 |

### | 규칙 8 — className, 그리고 이중 중괄호 `{{ }}` |

```tsx
const highlightColor = "crimson";

const box = <div className="card" style={{ color: highlightColor }}>내용</div>;
```

- HTML의 `class` 속성 대신 `className`을 쓴다. `class`가 자바스크립트의 예약어(클래스 선언에 쓰는 키워드)이기 때문이다.
- `style={{ color: highlightColor }}`에서 중괄호가 두 개인 이유: **바깥쪽 `{ }`** 는 "지금부터 JSX 안에서 자바스크립트 값을 쓰겠다"는 JSX 자체의 문법이고, **안쪽 `{ }`** 는 `{ color: highlightColor }`라는 진짜 자바스크립트 객체 리터럴이다. 즉 "JSX 표현식 자리에, 마침 객체 하나를 그대로 넣은 것"일 뿐이다.

Q5. JSX/TSX 문법에서 자식 요소가 없는 단일 태그(예: `<br>`)를 작성할 때의 규칙으로 올바른 것은 무엇입니까?

[ 보기 ]

a. HTML과 동일하게 닫는 기호 없이 `<br>`로 작성해도 된다.

b. 반드시 `<br />`처럼 셀프 클로징(`/`) 형태로 닫아야 한다.

c. 닫는 기호 대신 주석 처리로 대체해야 한다.

d. 단일 태그는 JSX에서 아예 사용할 수 없다.

내 제출 답안 : 미제출 (오답 ❌)

[ 정답 ] b.

-> JSX는 엄격한 XML 규칙을 따르므로 자식이 없는 단일 태그도 반드시 `/>`로 닫아야 하며, 생략하면 구문 에러가 발생한다. HTML처럼 생략하는 것은 허용되지 않는다.
