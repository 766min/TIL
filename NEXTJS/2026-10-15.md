# PART 1. useEffect와 Cleanup 함수
### | useEffect와 의존성 배열(deps) |

- `useEffect`는 "화면이 그려진 뒤에 외부 시스템과 상호작용하는 작업(사이드 이펙트)"을 처리하는 훅이다. 데이터 요청, 타이머 설정, DOM 이벤트 등록처럼 "컴포넌트를 화면에 그리는 일" 자체와는 별개의 부수 작업들이 여기 해당한다. 두 번째 인자인 의존성 배열에 따라 실행 시점이 완전히 달라진다.

| 작성 방식 | 실행 시점 |
| --- | --- |
| `useEffect(fn)` (의존성 생략) | 컴포넌트가 렌더링될 때마다 매번 실행 |
| `useEffect(fn, [])` (빈 배열) | 컴포넌트가 화면에 처음 나타날 때(마운트) 딱 1회 실행 |
| `useEffect(fn, [dep1, dep2])` (특정 값 지정) | 마운트 시 1회 + 지정한 값이 바뀔 때마다 실행 |

```tsx
'use client';

import { useEffect, useState } from 'react';

export default function BasicEffect() {
  const [count, setCount] = useState<number>(0);
  const [text, setText] = useState<string>('');

  useEffect(() => {
    console.log('[1. 매번 실행] 컴포넌트가 렌더링되었습니다.');
  });

  useEffect(() => {
    console.log('[2. 1회 실행] 컴포넌트가 화면에 마운트되었습니다.');
  }, []);

  useEffect(() => {
    console.log(`[3. count 변경] 현재 카운트: ${count}`);
  }, [count]);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>카운트 증가 ({count})</button>
      <input value={text} onChange={(e) => setText(e.target.value)} />
    </div>
  );
}
```

**실행 결과 (콘솔, 마운트 직후)**
```
[1. 매번 실행] 컴포넌트가 렌더링되었습니다.
[2. 1회 실행] 컴포넌트가 화면에 마운트되었습니다.
[3. count 변경] 현재 카운트: 0
```

**실행 결과 (콘솔, "카운트 증가" 버튼을 한 번 눌렀을 때)**
```
[1. 매번 실행] 컴포넌트가 렌더링되었습니다.
[3. count 변경] 현재 카운트: 1
```

**실행 결과 (콘솔, 인풋에 글자를 한 글자 입력했을 때)**
```
[1. 매번 실행] 컴포넌트가 렌더링되었습니다.
```

- 렌더링 사이클 관점: 리액트는 JSX를 화면에 반영(커밋)한 **다음**에야 `useEffect` 콜백들을 실행한다. 그래서 같은 렌더링 한 번에 등록된 세 `useEffect` 중에서도, `[1]`은 조건 없이 매번 실행되고 `[2]`는 처음 한 번 실행된 뒤로는 의존성 배열이 빈 채로 고정이라 다시는 실행되지 않으며, `[3]`은 `count`가 실제로 바뀐 렌더링에서만 실행된다. 인풋에 글자를 입력하면 `text` 상태가 바뀌어 컴포넌트는 다시 렌더링되지만, `count`는 그대로이므로 `[3]`은 건너뛴다 — 의존성 배열에 적힌 값만 "감시 대상"이 되고, 그 외의 상태 변화는 해당 `useEffect`와 무관하다는 뜻이다.
- 의존성 배열이 없다면 어떻게 될까. `useEffect(fn, [])`처럼 빈 배열로 "마운트 시 1회만"이라는 제약을 걸 수 없다면, 데이터 요청처럼 "한 번만 실행하면 되는 작업"도 매 렌더링마다 다시 실행되어 같은 API를 끝없이 호출하는 등 불필요한 부작용이 반복된다.

### | Cleanup 함수와 메모리 누수 방지 |

- `useEffect` 콜백 안에서 함수를 `return`하면, 그 반환된 함수가 **Cleanup 함수**가 된다. Cleanup은 컴포넌트가 화면에서 사라지거나(언마운트), 다음 Effect가 다시 실행되기 바로 직전에 호출된다. 타이머(`setInterval`)나 이벤트 리스너(`addEventListener`)처럼 "한 번 등록하면 누군가 명시적으로 꺼주기 전까지 계속 살아있는" 자원을 정리할 때 반드시 필요하다.

```tsx
'use client';

import { useEffect, useState } from 'react';

function TimerLogic() {
  const [seconds, setSeconds] = useState<number>(0);

  useEffect(() => {
    console.log('타이머 동작이 시작되었습니다.');

    const intervalId = setInterval(() => {
      setSeconds((prev) => prev + 1);
      console.log('타이머 카운팅 중...');
    }, 1000);

    return () => {
      clearInterval(intervalId);
      console.log('Cleanup: 타이머가 정지되었습니다.');
    };
  }, []);

  return <p>경과 시간: {seconds}초</p>;
}

export default function CleanupTimer() {
  const [isMounted, setIsMounted] = useState<boolean>(true);

  return (
    <div>
      <button onClick={() => setIsMounted(!isMounted)}>
        {isMounted ? '타이머 제거 (언마운트)' : '타이머 생성 (마운트)'}
      </button>
      {isMounted && <TimerLogic />}
    </div>
  );
}
```

**실행 결과 (콘솔, 타이머가 3초 동작한 뒤 "타이머 제거" 버튼을 눌렀을 때)**
```
타이머 동작이 시작되었습니다.
타이머 카운팅 중...
타이머 카운팅 중...
타이머 카운팅 중...
Cleanup: 타이머가 정지되었습니다.
```

- 콜백 호출 시점: `TimerLogic`이 마운트되면서 `useEffect`가 실행되어 `setInterval`이 1초마다 `setSeconds`를 호출하도록 예약된다. 버튼을 눌러 `isMounted`가 `false`가 되면 `{isMounted && <TimerLogic />}` 조건이 꺼지면서 `TimerLogic`이 화면에서 사라지는데(언마운트), 이 순간 리액트가 직전에 등록해뒀던 Cleanup 함수(`() => { clearInterval(intervalId); ... }`)를 자동으로 호출해서 타이머를 멈춘다.
- Cleanup 함수가 없었다면 어떻게 될까. 버튼을 눌러 컴포넌트를 화면에서 치워도 `setInterval`이 등록해둔 타이머는 브라우저 메모리 안에서 계속 살아서 1초마다 `setSeconds`를 호출한다. 문제는 이 타이머가 참조하고 있는 `setSeconds`는 이미 사라진(언마운트된) 컴포넌트의 것이라서, 리액트가 "존재하지 않는 컴포넌트를 업데이트하려 한다"는 경고를 내거나, 더 심각하게는 이런 "유령 타이머"가 계속 쌓여 페이지가 느려지는 메모리 누수로 이어진다. Cleanup은 "이 Effect가 켜둔 건 이 Effect가 책임지고 끈다"는 규칙을 강제하는 장치다.

### | 이벤트 리스너의 Cleanup과 Strict Mode |

```tsx
function TrackerLogic() {
  const [position, setPosition] = useState<{ x: number; y: number }>({ x: 0, y: 0 });

  useEffect(() => {
    const handleMouseMove = (event: MouseEvent) => {
      setPosition({ x: event.clientX, y: event.clientY });
    };

    window.addEventListener('mousemove', handleMouseMove);
    console.log('mousemove 이벤트 리스너가 등록되었습니다.');

    return () => {
      window.removeEventListener('mousemove', handleMouseMove);
      console.log('Cleanup: mousemove 이벤트 리스너가 제거되었습니다.');
    };
  }, []);

  return <p>X 좌표: {position.x}px | Y 좌표: {position.y}px</p>;
}
```

- `window.addEventListener`로 전역에 등록한 핸들러도 타이머와 똑같은 문제를 가진다. 컴포넌트가 사라져도 `removeEventListener`로 명시적으로 떼어내지 않으면, 이미 존재하지 않는 컴포넌트의 상태(`setPosition`)를 업데이트하려는 핸들러가 `window`에 계속 매달려 있게 된다.
- 개발 환경(`next dev`)에서는 React의 **Strict Mode**가 Cleanup 로직 누락을 미리 잡아내기 위해 일부러 Effect를 "마운트 → 언마운트 → 마운트" 순서로 두 번 실행시킨다. 그래서 개발 중에 `mousemove 이벤트 리스너가 등록되었습니다`와 `Cleanup: ...제거되었습니다`가 번갈아 두 번씩 찍히는 걸 봐도 당황할 필요가 없다 — Cleanup이 제대로 작성되어 있다면 두 번 실행되어도 최종 상태는 깨지지 않는다.
- 참고로 `useEffect` 내부에서 자신이 감시하는 상태를 직접 변경하면(`useEffect(() => { setCount(count + 1); }, [count])`) 상태 변경이 리렌더링을 부르고, 리렌더링이 다시 같은 Effect를 실행시키는 무한 루프에 빠진다. 의존성 배열에 넣은 값은 "읽기만 하고 그 Effect 안에서 똑같은 값을 변경하지는 않는다"는 원칙을 지켜야 한다.

### | useLayoutEffect / useInsertionEffect — 실행 시점이 다른 Effect들 |

| 훅 명칭 | 실행 시점 | 동작 방식 | 주요 용도 |
| --- | --- | --- | --- |
| `useInsertionEffect` | DOM 변경 후, 레이아웃 계산 전 | 동기 | 동적 CSS 스타일 주입 (CSS-in-JS) |
| `useLayoutEffect` | 레이아웃 계산 후, 화면 그리기(Paint) 전 | 동기 | DOM 크기·위치 측정, 깜빡임 방지 |
| `useEffect` | 브라우저가 화면을 그린(Paint) 후 | 비동기 | 데이터 요청, 타이머, 이벤트 리스너 등록 |

```tsx
const effectRef = useRef<HTMLDivElement>(null);
const layoutRef = useRef<HTMLDivElement>(null);

useEffect(() => {
  if (effectRef.current) {
    setEffectWidth(Math.round(effectRef.current.getBoundingClientRect().width));
  }
}, []);

useLayoutEffect(() => {
  if (layoutRef.current) {
    setLayoutWidth(Math.round(layoutRef.current.getBoundingClientRect().width));
  }
}, []);
```

- 이 코드가 만드는 실제 동작: 두 훅 모두 `getBoundingClientRect()`로 DOM 요소의 실제 너비를 측정해서 상태로 저장한다. 차이는 "언제" 측정하느냐다. `useLayoutEffect`는 브라우저가 화면에 그 변화를 그리기(Paint) **전에** 동기적으로 실행되므로, 측정한 값으로 레이아웃을 즉시 고쳐도 사용자 눈에는 깜빡임 없이 한 번에 최종 모습만 보인다. `useEffect`는 Paint가 끝난 **뒤에** 비동기로 실행되므로, 만약 측정값에 따라 레이아웃을 다시 바꾼다면 "원래 모습 → 바뀐 모습"이 아주 짧게라도 순차적으로 눈에 보일 수 있다.
- `useInsertionEffect`는 한 단계 더 이르게, DOM이 바뀐 직후·레이아웃 계산이 시작되기도 전에 실행된다. CSS-in-JS 라이브러리가 `<style>` 태그를 동적으로 주입할 때 이 시점을 쓰는 이유는, 스타일이 적용되기도 전에 레이아웃 계산이 먼저 끝나버리면 스타일 없는 모습이 한순간 노출될 수 있기 때문이다 — 스타일 삽입을 레이아웃 계산보다 먼저 끝내버리면 이 깜빡임 자체가 생기지 않는다.
- 이 세 훅의 구분이 없다면 어떻게 될까. 모든 부수 작업을 `useEffect` 하나로만 처리해야 한다면, DOM 크기를 재서 즉시 레이아웃을 보정해야 하는 작업도 Paint 이후에나 실행되어 화면이 한 번 그려졌다가 바로 다시 그려지는 깜빡임(Flicker)을 피할 수 없다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 사이드 이펙트 | Side Effect | 데이터 요청, 타이머 설정 등 렌더링 외에 외부와 상호작용하는 작업 |
| 마운트 / 언마운트 | Mount / Unmount | 컴포넌트가 화면에 처음 나타나는 과정 / 화면에서 제거되는 과정 |
| Cleanup 함수 | Cleanup Function | 타이머·이벤트 등을 해제해 메모리 누수를 막는, useEffect가 반환하는 정리용 함수 |
| 메모리 누수 | Memory Leak | 사용하지 않는 타이머·이벤트가 해제되지 않아 메모리가 계속 낭비되는 현상 |

# PART 2. 사용자 정의 훅 Custom Hooks
### | Custom Hook이 필요한 이유 |

- 여러 컴포넌트에서 "입력값 상태 관리 + onChange 핸들러"나 "브라우저 창 크기 감지"처럼 똑같은 `useState`/`useEffect` 조합을 반복해서 작성하게 되는 경우가 많다. 이걸 매번 복사·붙여넣기하면 코드 중복이 쌓이고, 나중에 로직을 하나 고칠 때 모든 컴포넌트를 일일이 찾아다니며 고쳐야 한다. **Custom Hook**은 리액트의 기본 훅들을 조합한 로직을 별도의 함수로 뽑아내서, 여러 컴포넌트가 그 함수 하나만 호출해 재사용할 수 있게 만든 것이다.

| 구분 | 일반 자바스크립트 함수 | Custom Hook |
| --- | --- | --- |
| 이름 규칙 | 자율 지정 | 반드시 `use`로 시작 |
| 내부 훅 호출 | 불가능 | `useState`, `useEffect` 등 자유롭게 호출 가능 |
| 주요 목적 | 순수 데이터 연산 | 상태 및 사이드 이펙트 로직의 재사용 |

- 이름이 왜 꼭 `use`로 시작해야 할까. 리액트는 "훅은 조건문이나 반복문 안에서 호출하면 안 된다"는 규칙(Rules of Hooks)을 강제로 검사해주는 린트 도구를 제공하는데, 이 도구가 "이 함수가 훅인지 아닌지"를 식별하는 유일한 단서가 바로 함수 이름이 `use`로 시작하는지 여부다. `use`로 시작하지 않으면 내부에서 `useState`를 쓰더라도 린트가 규칙 위반을 잡아내지 못한다.

### | 폼 입력 제어 Custom Hook — useInput |

```ts
// hooks/useInput.ts
import { ChangeEvent, useState } from 'react';

export function useInput(initialValue: string) {
  const [value, setValue] = useState<string>(initialValue);
  console.log(`[useInput] 현재 값: "${value}"`); // 호출 시점/상태 확인용 로그

  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    setValue(e.target.value);
  };

  const reset = () => {
    setValue(initialValue);
  };

  return { value, onChange: handleChange, reset };
}
```

```tsx
'use client';

import { useInput } from '@/hooks/useInput';

export default function InputTest() {
  const nameInput = useInput('');
  const emailInput = useInput('');

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    alert(`제출 완료! 이름: ${nameInput.value}, 이메일: ${emailInput.value}`);
    nameInput.reset();
    emailInput.reset();
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={nameInput.value} onChange={nameInput.onChange} placeholder="이름을 입력하세요" />
      <input value={emailInput.value} onChange={emailInput.onChange} placeholder="이메일을 입력하세요" />
      <button type="submit">제출하기</button>
    </form>
  );
}
```

**실행 결과 (콘솔, 이름 입력창에 "민"을 입력했을 때)**
```
[useInput] 현재 값: ""
[useInput] 현재 값: ""
[useInput] 현재 값: "민"
[useInput] 현재 값: ""
```

- 이 출력이 왜 네 줄이나 찍히는지가 Custom Hook의 핵심을 보여준다. `InputTest` 컴포넌트 하나가 `useInput('')`을 **두 번** 호출했기 때문에(`nameInput`, `emailInput`), 매 렌더링마다 `[useInput]` 로그가 두 줄씩 찍힌다. 이름 입력창에 "민"을 타이핑하면 `nameInput`의 내부 `value`가 바뀌어 `InputTest` 전체가 리렌더링되는데, 이때 `nameInput`용 `useInput` 호출과 `emailInput`용 `useInput` 호출이 둘 다 새로 실행되므로 "민"이 찍힌 줄과 여전히 빈 문자열인 줄이 나란히 나온다. 즉 Custom Hook은 호출될 때마다 **자신만의 독립된 `useState` 상태**를 새로 만드는 게 아니라, 그 컴포넌트 인스턴스 안에서 호출된 위치마다 각각 독립적인 상태 슬롯을 유지한다 — `nameInput`과 `emailInput`은 같은 `useInput` 함수를 썼지만 완전히 분리된 값을 가진다.
- `useInput`이 없었다면 어떻게 될까. `InputTest` 안에 `const [name, setName] = useState('')`와 그 `onChange` 핸들러, `const [email, setEmail] = useState('')`와 그 `onChange` 핸들러를 입력 필드 개수만큼 전부 따로 작성해야 한다. 입력창이 5개짜리 회원가입 폼이라면 거의 동일한 코드 블록을 5번 반복하게 된다.

### | 이벤트 감지 로직 분리 — useWindowSize |

```ts
// hooks/useWindowSize.ts
import { useEffect, useState } from 'react';

interface WindowSize {
  width: number;
  height: number;
}

export function useWindowSize(): WindowSize {
  const [windowSize, setWindowSize] = useState<WindowSize>({ width: 0, height: 0 });

  useEffect(() => {
    const handleResize = () => {
      setWindowSize({ width: window.innerWidth, height: window.innerHeight });
      console.log(`[useWindowSize] 창 크기 갱신: ${window.innerWidth} x ${window.innerHeight}`);
    };

    handleResize(); // 마운트 시 1회 즉시 측정
    window.addEventListener('resize', handleResize);

    return () => {
      window.removeEventListener('resize', handleResize);
      console.log('[useWindowSize] Cleanup: resize 리스너 제거');
    };
  }, []);

  return windowSize;
}
```

**실행 결과 (콘솔, 마운트 직후 + 브라우저 창 크기를 한 번 조절했을 때)**
```
[useWindowSize] 창 크기 갱신: 1280 x 800
[useWindowSize] 창 크기 갱신: 1024 x 800
```

- 콜백 호출 시점: `useEffect(fn, [])`로 마운트 시 1회 `handleResize()`를 직접 호출해서 초기 창 크기를 먼저 잰 다음, `resize` 이벤트가 발생할 때마다 같은 함수가 다시 실행되어 상태를 갱신한다. PART 1에서 배운 Cleanup 패턴이 그대로 쓰였다 — 이 훅을 쓰는 컴포넌트가 언마운트되면 `removeEventListener`가 호출되어 리스너가 깨끗이 정리된다.
- 이 훅이 없다면 어떻게 될까. 반응형 레이아웃을 창 크기에 따라 자바스크립트로 직접 제어해야 하는 컴포넌트마다 `useState` + `useEffect` + `addEventListener` + Cleanup 함수까지, PART 1에서 배운 전체 패턴을 매번 그대로 복붙해야 한다. 이 로직을 `useWindowSize`라는 함수 하나로 캡슐화해두면, 사용하는 쪽은 `const { width, height } = useWindowSize();` 한 줄로 끝난다 — 화면(UI)을 그리는 컴포넌트 코드와, 창 크기를 재고 관리하는 로직이 완전히 분리된다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 커스텀 훅 | Custom Hook | 리액트 기본 훅들을 조합해 개발자가 직접 정의하는 재사용 가능한 상태 로직 함수 |
| 관심사의 분리 | Separation of Concerns | 화면 UI 작성과 비즈니스 데이터 처리를 서로 다른 모듈로 나누어 관리하는 원칙 |
| 훅 규칙 | Rules of Hooks | 훅은 최상단에서만 호출하고 이름은 use로 시작해야 한다는 리액트의 공식 규칙 |

# PART 3. use() API와 비동기 언래핑
### | Suspense와 fallback — 로딩 상태 처리 자동화 |

- 과거에는 데이터를 불러오는 동안 보여줄 로딩 화면을 `isLoading` 상태 변수를 직접 만들어 `if (isLoading) return <Loading />`처럼 손수 제어해야 했다. `<Suspense>`는 비동기 작업을 하는 자식 컴포넌트를 감싸는 "대기실" 역할을 해서, 이 제어를 자동화한다. `fallback` 속성에 데이터가 준비되기 전까지 대신 보여줄 JSX를 넘겨주면 된다.

```tsx
'use client';

import React, { Suspense, useState } from 'react';

const LazyBanner = React.lazy(() =>
  new Promise<{ default: React.ComponentType }>((resolve) => {
    setTimeout(() => {
      resolve({ default: () => <div>2초 대기 후 배너 컴포넌트 로딩이 완료되었습니다!</div> });
    }, 2000);
  })
);

export default function SimpleLoadingDemo() {
  const [showDemo, setShowDemo] = useState(false);

  return (
    <section>
      <button onClick={() => setShowDemo(true)}>지연 배너 불러오기 (2초 소요)</button>
      {showDemo && (
        <Suspense fallback={<div>[Suspense Fallback] 배너를 로딩 중입니다...</div>}>
          <LazyBanner />
        </Suspense>
      )}
    </section>
  );
}
```

- 이 코드가 만드는 실제 동작: 버튼을 누르면 화면에는 곧바로 "[Suspense Fallback] 배너를 로딩 중입니다..."라는 문구가 뜬다. 내부적으로는 `React.lazy()`가 컴포넌트 코드를 비동기로 "로딩"하는 2초짜리 Promise를 만들고, `<Suspense>`가 그 Promise의 완료 여부를 감지하면서 아직 끝나지 않았으면 `fallback`을 대신 그려둔다. 2초가 지나 Promise가 resolve되면, `<Suspense>`는 `fallback` 대신 실제 `<LazyBanner />`(완료 배너)로 화면을 자동으로 교체한다.
- `<Suspense>`가 없다면 어떻게 될까. 데이터를 요청하는 모든 컴포넌트마다 `isLoading` 상태를 따로 만들고, 요청 시작 시 `true`로, 완료 시 `false`로 직접 바꿔주는 코드를 반복해서 작성해야 한다. 로딩 상태를 가진 컴포넌트가 늘어날수록 이 보일러플레이트 코드도 똑같이 늘어난다.

### | use(Promise) — 비동기 데이터 직접 언래핑하기 |

- `use()`는 Promise나 Context처럼 "포장된" 자원을 건네받아서, 그 안의 실제 값만 꺼내 돌려주는 API다. Promise가 아직 완료되지 않았다면 `use()`는 그 사실을 상위 `<Suspense>`에 알려서 `fallback`이 뜨도록 만든다.

```tsx
'use client';

import { use } from 'react';

export interface UserData {
  id: number;
  name: string;
  role: string;
}

export default function UserProfile({ userPromise }: { userPromise: Promise<UserData> }): React.JSX.Element {
  const user = use(userPromise); // Promise의 포장을 풀어 실제 UserData 값을 꺼냄

  return (
    <div>
      <p>ID: {user.id}</p>
      <p>이름: {user.name}</p>
      <p>직책: {user.role}</p>
    </div>
  );
}
```

```tsx
'use client';

import { Suspense, useState } from 'react';
import UserProfile, { UserData } from './UserProfile';

function fetchUserData(): Promise<UserData> {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve({ id: 1, name: '김철수', role: '프론트엔드 개발자' });
    }, 1500);
  });
}

export default function UserProfileDemo() {
  const [userPromise, setUserPromise] = useState<Promise<UserData> | null>(null);

  return (
    <section>
      <button onClick={() => setUserPromise(fetchUserData())}>프로필 데이터 불러오기 (1.5초 소요)</button>
      {userPromise && (
        <Suspense fallback={<div>프로필 데이터를 언래핑하는 중입니다...</div>}>
          <UserProfile userPromise={userPromise} />
        </Suspense>
      )}
    </section>
  );
}
```

- 이 코드가 만드는 실제 동작: 버튼을 누르면 `fetchUserData()`가 즉시 Promise 객체를 반환하고, 그 Promise는 아직 데이터를 들고 있지 않은 "포장 상자" 상태로 `userPromise` 상태에 저장된다. `<UserProfile userPromise={userPromise} />`가 렌더링되면서 내부의 `use(userPromise)`가 호출되는데, 이 시점엔 아직 1.5초가 지나지 않았으므로 `use()`는 "아직 준비 안 됐다"는 신호를 상위 `<Suspense>`로 보내고, 화면엔 "프로필 데이터를 언래핑하는 중입니다..."가 먼저 뜬다. 1.5초 뒤 Promise가 resolve되면 `use()`가 그 결과값(`UserData` 객체)을 즉시 꺼내 반환하고, `<Suspense>`가 `fallback`을 실제 프로필 카드로 자동 교체한다.
- `use(Promise)`가 없다면 어떻게 될까. 기존 방식으로는 `useEffect` 안에서 `fetchUserData().then((data) => setUser(data))`처럼 비동기 요청을 걸고, 별도의 `user` 상태와 `isLoading` 상태를 같이 관리해야 했다. `use()`는 "Promise를 컴포넌트 함수 본문 안에서 마치 동기 값처럼 바로 꺼내 쓴다"는 방식으로, 이 상태 관리 보일러플레이트를 `<Suspense>` 쪽으로 위임해버린다.

### | use(Context) — 조건문 안에서 전역 값 선택적으로 읽기 |

- 기존 `useContext`는 다른 훅들과 마찬가지로 컴포넌트 최상단에서만 호출해야 했다. 즉 "특정 조건일 때만 Context 값을 읽고 싶다"는 요구를 구현할 수 없었다. `use(Context)`는 `if` 문 내부처럼 조건부 블록 안에서도 자유롭게 호출할 수 있다는 점이 가장 큰 차이다.

```tsx
'use client';

import { createContext, use, useState } from 'react';

export interface ThemeConfig {
  mode: 'light' | 'dark';
}

export const ThemeContext = createContext<ThemeConfig | null>(null);

function ThemeInfo({ shouldReadContext }: { shouldReadContext: boolean }): React.JSX.Element {
  let message = 'Context 조회가 비활성화된 상태입니다.';

  if (shouldReadContext) {
    const config = use(ThemeContext); // 조건이 참일 때만 선택적으로 Context를 읽음
    if (config) {
      message = `현재 공용 설정에 저장된 테마: ${config.mode.toUpperCase()}`;
    }
  }

  return <p>{message}</p>;
}

export default function ThemeDemo(): React.JSX.Element {
  const [shouldReadContext, setShouldReadContext] = useState<boolean>(false);
  const [theme] = useState<ThemeConfig>({ mode: 'light' });

  return (
    <ThemeContext value={theme}>
      <button onClick={() => setShouldReadContext((prev) => !prev)}>
        Context 조회 토글 ({shouldReadContext ? 'ON' : 'OFF'})
      </button>
      <ThemeInfo shouldReadContext={shouldReadContext} />
    </ThemeContext>
  );
}
```

- 이 코드가 만드는 실제 동작: 토글 버튼이 "OFF"인 동안은 "Context 조회가 비활성화된 상태입니다"라는 고정 문구만 보인다. 버튼을 눌러 "ON"으로 바뀌면 `shouldReadContext`가 `true`가 되고, `if (shouldReadContext)` 블록 안의 `use(ThemeContext)`가 실행되어 "현재 공용 설정에 저장된 테마: LIGHT"로 문구가 바뀐다.
- `use(Context)`가 없다면 어떻게 될까. 기존 `useContext(ThemeContext)`는 컴포넌트가 렌더링될 때마다 조건과 무관하게 항상 최상단에서 호출돼야 한다. 그러면 `shouldReadContext`가 `false`인 경우에도 Context 값을 일단 읽어와서 변수에 담아두기만 하고 쓰지 않는 식으로 우회해야 하는데, 이 경우 그 컴포넌트는 Context 값이 바뀔 때마다 실제로는 안 쓰더라도 무조건 리렌더링 대상이 되어버린다(Context를 구독하고 있으므로). `use()`를 조건문 안에 넣으면 "지금 정말 필요한 순간에만" Context를 구독하도록 범위를 좁힐 수 있다.
