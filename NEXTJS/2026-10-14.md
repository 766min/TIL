# PART 1. 컴포넌트 반복과 Unique Key
### | Array.map()으로 리스트를 화면에 그리기 |

- 화면에 보여줄 데이터가 배열 형태로 여러 개 있을 때, `<li>사과</li>`, `<li>바나나</li>`처럼 항목 수만큼 JSX 태그를 일일이 손으로 적는 건 비효율적이다. 자바스크립트의 `Array.map()`을 JSX 중괄호 `{}` 안에서 쓰면, 배열의 각 데이터를 순회하며 JSX 요소로 변환한 새 배열을 만들 수 있다. 리액트는 중괄호 안에 배열이 들어오면 그 안의 요소들을 순서대로 화면에 출력해준다.

```tsx
import React from 'react';

export default function FruitList(): React.JSX.Element {
  const fruits: string[] = ['사과', '바나나', '포도', '오렌지'];

  return (
    <div>
      <h3>과일 목록 (기본 map 예제)</h3>
      <ul>
        {fruits.map((fruit: string, index: number): React.JSX.Element => (
          <li key={index}>{fruit}</li>
        ))}
      </ul>
    </div>
  );
}
```

- 콘솔 출력이 없는 순수 화면 렌더링 코드다. 이 코드가 실제로 만드는 동작: `fruits` 배열의 4개 문자열이 각각 `<li>` 태그로 변환되어, 브라우저에는 "사과, 바나나, 포도, 오렌지"가 세로로 나열된 리스트가 그려진다. 배열에 다섯 번째 과일을 추가하면 코드 수정 없이 `<li>`가 자동으로 하나 더 늘어난다.
- `map()`이 없다면 어떻게 될까. 과일이 4개면 `<li>`를 4줄, 40개면 40줄을 전부 직접 타이핑해야 한다. 데이터 개수가 바뀔 때마다(서버에서 받아오는 목록처럼 미리 몇 개인지 알 수 없는 경우) 코드 자체를 매번 고쳐야 하니 애초에 동적인 리스트를 구현할 방법이 없다.

### | Virtual DOM 재조정과 key가 필요한 이유 |

- 재조정(Reconciliation) 원리를 다시 가져오면, 리액트는 상태가 바뀔 때마다 이전 가상 DOM과 새 가상 DOM을 비교해서 달라진 부분만 실제 DOM에 반영한다. 그런데 리스트처럼 같은 모양의 태그(`<li>`)가 여러 개 반복될 때는, 리액트 입장에서 "이게 아까 그 항목인지, 아니면 새로 추가된 항목인지"를 구분할 방법이 없다. `key` 속성은 각 리스트 항목에 고유한 "이름표"를 붙여서, 리액트가 리스트 전체를 다시 그리지 않고 변경된 항목만 선별해서 업데이트할 수 있게 해준다.

| 식별자 종류 | key로서의 적절성 | 이유 |
| --- | --- | --- |
| 고유 ID (`item.id`) | 적절 | 데이터가 추가/삭제/순서 변경되어도 각 항목의 id 자체는 바뀌지 않음 |
| 배열 인덱스(`index`) | 조건부 사용 | 순서가 바뀌거나 중간 항목이 삭제되면 인덱스 값 자체가 밀려서 상태 오류 가능성 있음 |
| `Math.random()` | 부적절 | 렌더링될 때마다 새 값이 나와서, 바뀐 게 없어도 매번 전체가 재렌더링됨 |

- key가 아예 없다면 어떻게 될까. 예를 들어 "할 일 3개" 중 맨 앞 항목을 삭제했다고 하자. key 없이(혹은 index를 key로 써서) 렌더링하면 리액트는 "1번 자리의 내용이 바뀌었다"고만 인식하지, "1번 항목이 삭제되고 2·3번이 한 칸씩 당겨졌다"는 사실을 모른다. 그 결과 체크박스 상태나 입력 중이던 텍스트 같은 "항목에 딸린 상태"가 엉뚱한 자리로 옮겨 붙는 버그가 생긴다. 특히 index를 key로 쓰면, 리스트 중간에 항목을 추가·삭제할 때 그 아래 모든 항목의 index가 한 칸씩 밀리면서 전부 "다른 항목"으로 오인되어 불필요한 재렌더링이 발생할 수 있다.

### | Index Key vs 고유 ID Key 비교 |

```tsx
interface User {
  id: number;
  name: string;
  role: string;
}

export default function KeyComparison(): React.JSX.Element {
  const users: User[] = [
    { id: 101, name: '김철수', role: '개발자' },
    { id: 102, name: '이영희', role: '디자이너' },
    { id: 103, name: '박민수', role: '기획자' },
  ];

  return (
    <div>
      <h4>Index를 Key로 사용 (순서 변경 시 문제 가능성)</h4>
      <ul>
        {users.map((user: User, index: number): React.JSX.Element => (
          <li key={index}>[{index}] {user.name} ({user.role})</li>
        ))}
      </ul>

      <h4>고유 ID를 Key로 사용 (권장 방식)</h4>
      <ul>
        {users.map((user: User): React.JSX.Element => (
          <li key={user.id}>[ID: {user.id}] {user.name} ({user.role})</li>
        ))}
      </ul>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면: 같은 데이터(users 3명)를 두 가지 방식으로 각각 리스트업한 두 개의 목록이 나란히 보인다. 화면상 결과물은 지금 당장은 똑같아 보이지만, 나중에 `users` 배열 맨 앞에 새 사용자가 추가되는 상황을 가정하면 차이가 드러난다. index 방식은 기존 "김철수(index=0)"가 "index=1"로 밀려나면서 리액트가 그 항목을 "새로운 항목"으로 착각할 수 있고, id 방식은 `key={101}`이 그대로 유지되므로 리액트가 "이건 그대로고 새 항목만 추가됐다"고 정확히 인식한다.

### | Unique Key가 적용된 Todo List |

```tsx
export interface Todo {
  id: number;
  text: string;
  done: boolean;
}

export default function TodoList(): React.JSX.Element {
  const todos: Todo[] = [
    { id: 1, text: 'Next.js 교안 읽기', done: true },
    { id: 2, text: 'Array.map() 실습하기', done: true },
    { id: 3, text: 'Unique Key 이해하기', done: false },
  ];

  return (
    <div>
      <h3>오늘의 할 일 목록 (Unique Key 완전 적용)</h3>
      <ul style={{ listStyle: 'none', padding: 0 }}>
        {todos.map((todo: Todo): React.JSX.Element => (
          <li key={todo.id}>
            <span style={{ textDecoration: todo.done ? 'line-through' : 'none' }}>
              {todo.text}
            </span>
            <span style={{ color: todo.done ? 'green' : 'orange' }}>
              {todo.done ? '완료' : '진행 중'}
            </span>
          </li>
        ))}
      </ul>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면: 할 일 3개가 리스트로 그려지는데, `done`이 `true`인 두 항목(교안 읽기, map 실습)은 취소선과 초록색 "완료" 라벨이 붙고, `done`이 `false`인 마지막 항목은 주황색 "진행 중" 라벨이 붙는다. `key={todo.id}`를 썼기 때문에, 나중에 체크박스를 눌러 `done` 값이 바뀌거나 항목이 삭제돼도 각 `<li>`가 정확히 자기 자신의 상태만 갱신한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 배열 순회 변환 | Array.map() | 배열의 각 요소를 가공해 새로운 배열로 반환하는 메서드 |
| 고유 식별자 속성 | key prop | 리액트가 리스트 항목의 변경 사항을 추적하기 위해 부여하는 속성 |
| 재조정 | Reconciliation | 변경 전후의 Virtual DOM을 비교해 실제 DOM에 반영할 차이만 계산하는 과정 |

# PART 2. Next.js의 다양한 스타일링 기법
### | CSS Modules로 스타일 충돌 막기 |

- 전역(Global) CSS 파일 하나에 모든 클래스를 몰아넣으면, 프로젝트가 커질수록 다른 컴포넌트가 우연히 같은 클래스명(`.badge`, `.card` 등)을 쓰다가 스타일이 서로 덮어써지는 사고가 생긴다. CSS Modules(`[이름].module.css`)는 빌드 시점에 클래스명 뒤에 고유한 난수를 자동으로 붙여서, 해당 파일을 불러온 컴포넌트에만 스타일이 적용되도록 스코프를 격리한다.

```css
/* Badge.module.css */
.badge {
  display: inline-block;
  padding: 6px 12px;
  background-color: #e0e7ff;
  color: #3730a3;
  border-radius: 20px;
}
```

```tsx
import styles from './Badge.module.css';

interface BadgeProps {
  text: string;
}

export function Badge({ text }: BadgeProps) {
  return <span className={styles.badge}>{text}</span>;
}
```

- 이 코드가 만드는 실제 화면: "카테고리: 전자기기"라는 글자가 연보라색 배경에 둥근 모서리를 가진 작은 뱃지 형태로 표시된다. 실제로 브라우저에 그려지는 HTML을 보면 `class="badge"`가 아니라 `class="Badge-module__IxwMoq__badge"`처럼 난수가 섞인 클래스명이 붙는다.
- CSS Modules가 없다면 어떻게 될까. 다른 팀원이 작성한 컴포넌트에서도 `.badge`라는 클래스명을 썼다면, 나중에 로드되는 CSS가 먼저 로드된 CSS를 덮어써서 의도치 않은 스타일이 뒤섞인다. 프로젝트가 커질수록 "이 클래스명은 이미 누가 쓰고 있나"를 계속 확인해야 하는 소모적인 작업이 반복된다.
- 참고로 CSS Modules는 서버 컴포넌트에서도 그대로 지원되므로, 상태나 이벤트 핸들러가 없는 순수 UI라면 `'use client'` 선언 없이 작성할 수 있다.

### | SCSS 중첩(Nesting) 문법 |

- SCSS는 일반 CSS 위에 변수, 중첩 같은 기능을 더한 문법이다. `&` 기호로 자기 자신이나 `hover` 같은 상태를 표현하고, 자식 선택자를 부모 블록 안에 중첩해서 쓸 수 있다.

```scss
// Card.module.scss
.cardBox {
  padding: 20px;
  border: 1px solid #cbd5e1;
  border-radius: 12px;
  transition: all 0.2s ease-in-out;

  &:hover {
    border-color: #3b82f6;
    transform: translateY(-2px);
  }

  .title {
    font-size: 18px;
    font-weight: 700;
  }
}
```

- 이 코드가 만드는 실제 화면: 테두리가 있는 카드 UI가 그려지고, 마우스를 카드 위에 올리면(`&:hover`) 테두리 색이 파란색으로 바뀌면서 카드가 위로 살짝 떠오르는 애니메이션이 재생된다. 중첩 문법이 없었다면 `.cardBox`와 `.cardBox:hover`, `.cardBox .title`을 매번 바깥 선택자 이름을 반복해서 따로따로 작성해야 해서 코드가 길어지고, 어떤 규칙이 어떤 부모에 속하는지 한눈에 파악하기 어려워진다.

### | Tailwind CSS — 유틸리티 우선(Utility-first) 스타일링 |

- Tailwind는 별도의 CSS 파일을 만들지 않고, `className`에 미리 정의된 유틸리티 클래스 조합만으로 스타일을 완성하는 방식이다. 수치 체계는 `1 unit = 0.25rem = 4px` 공식을 따른다(`p-4` = 16px 패딩). 규격에 없는 값은 대괄호(`[...]`)로 직접 지정한다(`w-[140px]`).

```tsx
<button className="p-4 w-32 bg-blue-600 text-white rounded-md">
  표준 규격 (w-32)
</button>
<button className="p-[14px] w-[140px] bg-[#10b981] rounded-[10px]">
  임의 값 (w-[140px])
</button>
```

- 레이아웃은 Flexbox(`flex`, `justify-between`, `items-center`)와 Grid(`grid`, `grid-cols-1 md:grid-cols-3`)를 조합해서 짠다. 상태 변형자(`hover:`, `focus:`)와 부모 상태 연동(`group`, `group-hover:`)을 쓰면 별도의 자바스크립트 이벤트 핸들러 없이도 인터랙션을 구현할 수 있다.

```tsx
<div className="group p-6 shadow-sm hover:shadow-lg hover:-translate-y-1 transition-all">
  <h4 className="group-hover:text-blue-600 transition-colors">
    인터랙티브 카드 타이틀
  </h4>
  <p className="line-clamp-2">
    두 줄을 넘는 본문은 line-clamp-2 클래스로 말줄임 처리된다.
  </p>
</div>
```

- 이 코드가 만드는 실제 화면: 카드에 마우스를 올리면(`group` + `hover:`) 그림자가 짙어지고 카드가 위로 1px만큼 떠오르며, 동시에 제목 글자색이 파란색으로 바뀐다(`group-hover:text-blue-600`). 이 색상 변화는 `<h4>` 자신이 아니라 부모 `<div>`에 마우스가 올라갔을 때 반응하는 것이라서, `group`을 부모에 선언하지 않으면 `group-hover:`는 아무 효과도 내지 못한다.
- 유틸리티 클래스가 없다면 어떻게 될까. `hover:shadow-lg`에 해당하는 효과를 순수 CSS로 구현하려면 `.card:hover { box-shadow: ... }`처럼 CSS 파일에 선택자를 따로 정의해야 한다. 새 컴포넌트를 만들 때마다 CSS 파일을 오가며 클래스 이름을 짓고 연결하는 수고가 반복되는데, Tailwind는 그 과정 자체를 생략하고 HTML 안에서 바로 완결시킨다.

### | clsx + tailwind-merge로 조건부 클래스와 충돌 해결하기 |

- `clsx`는 `true`/`false` 조건에 따라 필요한 클래스만 골라 문자열로 합쳐주고, `tailwind-merge`는 `px-4`와 `px-10`처럼 같은 속성을 가리키는 Tailwind 클래스가 동시에 섞였을 때 뒤에 오는 값으로 깔끔하게 정리해준다. 이 둘을 합친 `cn()` 유틸리티 함수를 `lib/utils.ts`에 한 번 만들어두고 프로젝트 전체에서 재사용한다.

```ts
// lib/utils.ts
import { ClassValue, clsx } from 'clsx';
import { twMerge } from 'tailwind-merge';

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

```tsx
<button
  className={cn(
    'px-4 py-2 rounded-lg bg-slate-200 text-slate-800',
    variant === 'primary' && 'bg-blue-600 text-white hover:bg-blue-700',
    variant === 'danger' && 'bg-red-600 text-white hover:bg-red-700',
    className // 외부에서 주입한 커스텀 클래스
  )}
>
  {children}
</button>
```

- `cn()`이 없다면 어떻게 될까. 조건부 스타일을 문자열 템플릿(`` `base ${variant === 'primary' ? 'bg-blue-600' : ''}` ``)으로 직접 이어 붙여야 해서 코드가 지저분해질 뿐 아니라, 외부에서 `className="px-10"`을 넘겨줘도 기존 `px-4`와 글자 그대로 나란히 쌓여서 둘 다 살아있는 상태가 된다. CSS 명세에서는 나중에 선언된 속성이 이기는 게 보통이지만, Tailwind가 생성하는 CSS는 클래스 선언 순서가 빌드 결과물 안에서 보장되지 않기 때문에 `px-4`가 의도와 다르게 이겨버릴 수 있다. `tailwind-merge`는 "같은 속성을 가리키는 클래스 중 나중 것만 남긴다"는 규칙을 코드 레벨에서 강제로 적용해서 이 문제를 없앤다.

### | react-icons로 아이콘 가져오기 |

- `https://react-icons.github.io/react-icons/`에서 아이콘을 검색하고 클릭하면, 우측 슬라이드 패널에 바로 쓸 수 있는 `import` 구문과 JSX 태그가 뜬다. 그걸 그대로 복사해서 붙여넣으면 된다.

```tsx
import { FaHeart, FaShoppingBag } from 'react-icons/fa';
import { MdShoppingCart } from 'react-icons/md';

export function IconButton(): React.JSX.Element {
  return (
    <div>
      <button><FaShoppingBag /> FaShoppingBag</button>
      <button><MdShoppingCart /> MdShoppingCart</button>
      <button aria-label="좋아요"><FaHeart /></button>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면: 쇼핑백 아이콘이 붙은 남색 버튼, 장바구니 아이콘이 붙은 초록색 버튼, 하트 아이콘만 있는 원형 버튼 세 개가 나란히 보인다. 아이콘 이름을 외워서 직접 타이핑하는 대신, 레퍼런스 사이트의 복사 기능을 쓰는 이유는 수천 개에 달하는 아이콘 이름(`FaShoppingBag`처럼 접두사+이름 조합)을 정확히 외우는 것 자체가 비효율적이고 오타가 나기 쉽기 때문이다.

# PART 3. useState와 Automatic Batching
### | useState의 동작 원리 |

- `useState`는 컴포넌트 내부에서 "시간에 따라 변하는 데이터(상태)"를 관리하는 훅이다. `const [count, setCount] = useState<number>(0)`처럼 호출하면, 현재 값(`count`)과 그 값을 바꾸는 전용 함수(`setCount`)를 한 쌍으로 돌려받는다.

```tsx
'use client';

import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState<number>(0);
  console.log(`[렌더링] 현재 count 값: ${count}`); // 렌더링 시점 확인용으로 추가한 로그

  return (
    <div>
      <p>현재 카운트: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1 증가</button>
    </div>
  );
}
```

**실행 결과 (콘솔, [+1 증가] 버튼을 두 번 눌렀을 때)**
```
[렌더링] 현재 count 값: 0
[렌더링] 현재 count 값: 1
[렌더링] 현재 count 값: 2
```

- 렌더링 사이클 관점에서 벌어지는 일: 컴포넌트 함수 `Counter()` 자체가 처음 호출될 때 `count`는 0이고, 이 시점에 `console.log`가 한 번 실행되며 화면에도 "현재 카운트: 0"이 그려진다. 버튼을 클릭하면 `setCount(count + 1)`이 호출되는데, 이건 `count` 변수를 그 자리에서 직접 바꾸는 게 아니라 "다음 렌더링에서는 이 값을 써 달라"고 리액트에 예약을 거는 것이다. 리액트는 이 예약을 받으면 `Counter()` 함수 전체를 처음부터 다시 실행한다 — 그래서 `console.log`도, JSX도 다시 처음부터 다 새로 만들어지며 이번엔 `count`가 1인 상태로 돈다.
- `setCount`가 일반 변수 할당(`count = count + 1`)과 다른 결정적인 이유: 일반 변수를 바꾸는 것만으로는 리액트가 "화면을 다시 그려야 한다"는 사실 자체를 알 길이 없다. `useState`의 setter 함수는 값을 바꾸는 동시에 "리렌더링 요청"까지 함께 리액트에 전달하는 전용 창구다. 이게 없다면 데이터는 바뀌었는데 화면은 그대로인 상태가 된다.

### | Automatic Batching과 함수형 업데이트 |

- 한 이벤트 핸들러 안에서 `setState` 계열 함수를 여러 번 호출해도, 리액트는 이를 모아뒀다가 딱 한 번만 리렌더링한다 — 이를 **Automatic Batching**이라고 한다. 문제는 일반 업데이트(`setNumber(number + 1)`) 방식을 쓰면, 세 줄을 연달아 써도 `number`가 같은 렌더링 시점의 "스냅샷 값"을 계속 참조하기 때문에 결과가 의도와 다르게 나온다는 점이다.

```tsx
'use client';

import { useState } from 'react';

export default function BatchTest() {
  const [number, setNumber] = useState<number>(0);
  console.log('[렌더링] number:', number); // 몇 번 리렌더링되는지 확인용 로그

  const handleNormalAdd = () => {
    console.log('--- 일반 업데이트 핸들러 시작, number:', number);
    setNumber(number + 1);
    setNumber(number + 1);
    setNumber(number + 1);
    console.log('--- 일반 업데이트 핸들러 끝 (아직 리렌더링 전)');
  };

  const handleFunctionalAdd = () => {
    console.log('--- 함수형 업데이트 핸들러 시작, number:', number);
    setNumber((prev) => prev + 1);
    setNumber((prev) => prev + 1);
    setNumber((prev) => prev + 1);
    console.log('--- 함수형 업데이트 핸들러 끝 (아직 리렌더링 전)');
  };

  return (
    <div>
      <p>결과 숫자: {number}</p>
      <button onClick={handleNormalAdd}>일반 +3 테스트</button>
      <button onClick={handleFunctionalAdd}>함수형 +3 테스트</button>
      <button onClick={() => setNumber(0)}>초기화</button>
    </div>
  );
}
```

**실행 결과 (콘솔, 초기화 후 [일반 +3 테스트]를 한 번 눌렀을 때)**
```
[렌더링] number: 0
--- 일반 업데이트 핸들러 시작, number: 0
--- 일반 업데이트 핸들러 끝 (아직 리렌더링 전)
[렌더링] number: 1
```

**실행 결과 (콘솔, 초기화 후 [함수형 +3 테스트]를 한 번 눌렀을 때)**
```
[렌더링] number: 0
--- 함수형 업데이트 핸들러 시작, number: 0
--- 함수형 업데이트 핸들러 끝 (아직 리렌더링 전)
[렌더링] number: 3
```

- 콜백 호출 시점을 뜯어보면: `handleNormalAdd` 안의 `setNumber(number + 1)` 세 줄은 전부 "이번 렌더링에서 고정된 `number`(=0)" 하나만 참조한다. 클로저가 함수가 정의될 당시의 `number` 값을 그대로 기억하고 있기 때문에, 세 번을 호출해도 리액트 입장에서는 "number를 1로 바꿔라"는 요청이 세 번 반복해서 들어온 것과 같다. 반면 `handleFunctionalAdd`의 `(prev) => prev + 1`은 호출될 때마다 "그 직전까지 예약된 최신 값"을 매개변수로 직접 전달받으므로, 0 → 1 → 2 → 3으로 순차적으로 누적된다.
- 또한 `[렌더링]` 로그가 핸들러 하나당 딱 한 번만 찍힌다는 점이 Automatic Batching의 증거다. `setNumber`를 세 번 호출했는데도 컴포넌트 함수가 세 번이 아니라 한 번만 다시 실행됐다.
- Automatic Batching이 없다면 어떻게 될까. `setNumber`를 호출할 때마다 매번 즉시 리렌더링이 일어난다고 가정하면, 한 이벤트 핸들러 안에서 상태를 5번 바꾸는 코드는 컴포넌트를 5번 통째로 다시 실행시킨다. 사용자 입장에서 버튼 클릭 한 번의 결과로 화면이 여러 차례 깜빡이거나, 불필요한 연산이 여러 번 반복되어 성능이 눈에 띄게 떨어진다. Automatic Batching은 "최종 결과만 한 번에 반영하면 충분하다"는 전제로 이 낭비를 없앤 최적화다.

### | 불변성(Immutability)을 지켜야 하는 이유 |

- 리액트는 상태가 "바뀌었는지" 판단할 때, 객체나 배열 내부를 하나하나 깊게 들여다보지 않고 메모리 주소(참조)만 비교하는 **얕은 비교(Shallow Compare)**를 한다. 그래서 배열에 `push()`나 `splice()`처럼 원본을 직접 수정하는 메서드를 쓰면, 내용물은 바뀌었어도 메모리 주소 자체는 그대로이기 때문에 리액트는 "아무것도 안 바뀌었다"고 오판하고 화면을 다시 그리지 않는다.

| 작업 | 불변성을 지키는 방법 |
| --- | --- |
| 추가 (Create) | `[...prev, newItem]` (전개 연산자) 또는 `prev.concat(newItem)` |
| 수정 (Update) | `prev.map(...)` — 해당 요소만 바꾼 새 배열 생성 |
| 삭제 (Delete) | `prev.filter(...)` — 조건에 맞는 요소만 남긴 새 배열 생성 |

```tsx
const handleAddTodo = (text: string) => {
  const newTodo: Todo = { id: Date.now(), text, completed: false };
  setTodos([...todos, newTodo]); // 전개 연산자로 완전히 새로운 배열 주소를 만듦
};

const handleToggleTodo = (id: number) => {
  setTodos(
    todos.map((todo) =>
      todo.id === id ? { ...todo, completed: !todo.completed } : todo
    )
  );
};

const handleDeleteTodo = (id: number) => {
  setTodos(todos.filter((todo) => todo.id !== id));
};
```

- 불변성을 지키지 않았다면 어떻게 될까. 만약 `handleAddTodo`를 `todos.push(newTodo); setTodos(todos);`로 작성했다면, `push()`가 원본 `todos` 배열 자체를 직접 수정하긴 하지만 `setTodos`에 넘기는 `todos`는 여전히 "수정 전과 같은 메모리 주소"를 가리킨다. 얕은 비교만 하는 리액트는 "주소가 그대로니 바뀐 게 없다"고 판단해서 화면을 다시 그리지 않고, 데이터는 분명히 추가됐는데 화면엔 반영되지 않는 버그가 발생한다. 전개 연산자나 `map`/`filter`는 항상 "완전히 새로운 배열(새 주소)"을 반환하기 때문에, 리액트가 이 변화를 확실히 감지하게 만드는 안전장치다.

### | 불변성 조작을 종합한 Todo 리스트 |

- 위의 세 함수(`handleAddTodo`, `handleToggleTodo`, `handleDeleteTodo`)를 `TodoInput`(입력 폼)과 `TodoItem`(개별 항목, 체크 아이콘·취소선·삭제 버튼 포함) 컴포넌트와 묶으면, 추가·수정(토글)·삭제가 모두 불변성을 지키며 동작하는 Todo 앱이 완성된다. 각 `<TodoItem key={todo.id} ... />`에 PART 1에서 배운 Unique Key까지 적용되어 있어서, 항목 하나를 삭제해도 나머지 항목들의 상태(체크 여부 등)가 엉뚱하게 섞이지 않는다.
- 이 코드가 만드는 실제 화면: 입력창에 할 일을 쓰고 "추가" 버튼을 누르면 목록 맨 아래에 새 항목이 나타나고, 항목을 클릭하면 체크 아이콘과 취소선이 토글되며, 휴지통 아이콘을 누르면 해당 항목만 사라진다. PART 1의 key 원리와 PART 3의 불변성 원리가 실제 CRUD 동작 하나하나에 전부 녹아 있는 구조다.

| 용어 | 영어 표현 | 설명 |
