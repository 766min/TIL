# PART 1. Asset 최적화, SEO & Middleware
### | public 폴더는 왜 따로 있나 |

- `public` 폴더는 이미지·폰트·파비콘처럼 서버에서 내용이 바뀌지 않는 정적 자원(Static Assets)을 넣어두는 전용 공간이다. `app/` 폴더의 App Router 경로 규칙(폴더 구조 = URL 경로)에는 전혀 영향을 받지 않고, `public`이라는 폴더 이름 자체도 URL에 나타나지 않는다. 예를 들어 `public/example.jpg`는 코드에서 `src="/example.jpg"`처럼 루트 경로(`/`)로 바로 접근한다.
- 만약 이 규칙이 없다면 어떻게 될까. 정적 파일마다 `app/` 라우팅 규칙과의 충돌 여부를 매번 신경 써야 하고, 실제 폴더 경로(`/public/example.jpg`)를 그대로 URL에 노출해야 해서 폴더 구조가 곧 서비스의 내부 구현을 드러내는 꼴이 된다.

### | next/image가 없으면 어떤 성능 문제가 생기는가 |

- 일반 `<img>` 태그로 이미지를 넣으면 브라우저는 원본 파일(보통 jpg/png)을 그대로 받는다. 용량이 큰 원본을 그대로 전송하면 페이지 로딩이 느려지고, 이미지 크기를 미리 지정해두지 않으면 이미지가 로딩되는 도중 그 아래 콘텐츠가 밀려 내려가는 **레이아웃 시프트(CLS, Cumulative Layout Shift)** 가 발생해 사용자 경험이 나빠진다. 모바일에서 스크롤하다가 화면이 덜컥 밀리는 그 현상이다.
- `next/image`의 `<Image>` 컴포넌트는 이 문제들을 자동으로 해결한다.

| 기능 | 하는 일 | 없으면 생기는 문제 |
| --- | --- | --- |
| WebP/AVIF 자동 변환 | 원본 이미지를 최신 압축 포맷으로 바꿔 전송 | 원본 jpg/png 그대로 전송되어 다운로드 용량·시간이 늘어남 |
| `priority` 속성 | 화면 최상단 핵심 이미지를 우선 로딩 — LCP(Largest Contentful Paint) 개선 | 핵심 이미지가 늦게 떠서 "체감 로딩 속도"가 떨어짐 |
| `width`/`height` 명시 | 이미지 자리(비율)를 미리 확보 | 로딩 중 레이아웃이 밀리는 CLS 발생 |

- `<Image>`는 보안 목적으로 외부 서버 이미지를 기본적으로 차단한다. `picsum.photos`처럼 외부 URL 이미지를 쓰려면 `next.config.ts`의 `images.remotePatterns`에 허용 도메인을 등록해야 한다. 이 허용 목록이 없다면 아무 외부 이미지 서버나 요청해 버릴 수 있어, 악의적인 이미지 URL을 통한 리소스 남용(이미지 최적화 서버를 거쳐 임의 서버에 요청을 보내는 공격)에 노출될 위험이 있다. `next.config.ts`를 고치고 나면 반드시 `npm run dev`를 재시작해야 설정이 반영된다.

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  images: {
    // 외부 이미지 서버 도메인을 등록한다.
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'picsum.photos',
        port: '',
        pathname: '/**', // 모든 하위 이미지 경로 허용
      },
    ],
  },
};

export default nextConfig;
```

```ts
// app/components/ImageOptimization.tsx
import Image from 'next/image';

export default function ImageOptimization() {
  return (
    <section className="my-4 p-4 border rounded-lg bg-gray-50">
      <h2 className="text-xl font-semibold mb-2">Image 최적화 테스트</h2>
      <p className="text-sm text-gray-600 mb-4">WebP 자동 변환 및 레이아웃 시프트 방지가 적용된 이미지입니다.</p>

      {/* Next.js Image 컴포넌트를 이용해 이미지를 렌더링한다. */}
      <Image
        src="https://picsum.photos/800/400" // 외부 예시 이미지 URL
        alt="실습용 테스트 이미지" // SEO 및 접근성을 위한 대체 텍스트
        width={800} // 표시할 이미지 너비 (필수)
        height={400} // 표시할 이미지 높이 (필수)
        priority // 첫 화면 핵심 이미지 우선 로딩 설정
        className="rounded-md object-cover"
      />
    </section>
  );
}
```

- 이 컴포넌트는 콘솔 출력이 없는 UI 코드라서 "실행 결과" 대신 설명으로 대체한다. 브라우저에서 확인하면 이미지가 WebP로 변환되어 내려오고, `width`/`height` 비율만큼 자리가 먼저 잡혀 있어 로딩 중에도 레이아웃이 흔들리지 않는다.

### | next/font가 없으면 폰트 로딩이 왜 번거로워지는가 |

- 구글 폰트를 `<link>` 태그로 직접 불러오면, 브라우저가 매번 구글 서버에 요청을 보내야 하고(외부 네트워크 왕복 지연), 폰트가 로딩되기 전까지는 시스템 기본 폰트로 먼저 그렸다가 폰트가 도착하면 글자 체형이 바뀌면서 문단이 움직이는 현상(이것도 레이아웃 시프트의 일종)이 생긴다.
- `next/font/google`은 빌드 시점에 폰트 파일을 프로젝트 내부로 가져와(자체 호스팅) 외부 서버 호출 자체를 없애고, Zero Layout Shift를 보장한다. 사용할 때는 폰트 이름의 공백을 언더바(`_`)로 바꿔서 import한다 — 예: `Noto Sans KR` → `Noto_Sans_KR`, `Open Sans` → `Open_Sans`.

```ts
// app/components/FontOptimization.tsx
// next/font/google 모듈에서 원하는 폰트를 불러온다. (공백은 _로 대체)
import { Noto_Sans_KR } from 'next/font/google';

// 폰트 설정 객체를 생성한다.
const notoSansKr = Noto_Sans_KR({
  subsets: ['latin'], // 지원 언어 서브셋 지정
  weight: ['400', '700'], // 사용할 폰트 굵기 지정
});

export default function FontOptimization() {
  return (
    <section className="my-4 p-4 border rounded-lg bg-gray-50">
      <h2 className="text-xl font-semibold mb-2">2. Font 최적화 테스트</h2>
      {/* 폰트 클래스 이름을 엘리먼트에 직접 적용한다. */}
      <div className={notoSansKr.className}>
        <p className="font-normal text-base text-gray-800">
          이 문장은 구글 Noto Sans KR Regular(400) 폰트가 적용되었습니다.
        </p>
        <p className="font-bold text-base text-blue-600 mt-1">
          이 문장은 구글 Noto Sans KR Bold(700) 폰트가 적용되었습니다.
        </p>
      </div>
    </section>
  );
}
```

### | SEO를 위한 메타데이터 설정이 왜 필요한가 |

- CSR 방식은 검색 엔진 크롤러가 페이지를 읽는 시점에 `<div id="root"></div>`만 있는 빈 HTML을 보게 되어 콘텐츠가 검색 결과에 반영되지 않는 문제가 있었다. Next.js는 SSR로 이미 이 문제를 어느 정도 해결했지만, "어떤 제목과 설명으로 검색 결과에 노출시킬지"는 또 별개의 설정이 필요하다 — 이걸 담당하는 것이 **Metadata API**다.
- 메타데이터가 없으면 어떻게 될까. 검색 엔진은 페이지 제목을 추측하거나 본문 일부를 임의로 끌어와 설명으로 쓰는데, 이러면 검색 결과에 엉뚱한 제목·설명이 노출되어 클릭률이 떨어진다. 카카오톡 같은 메신저에 링크를 공유했을 때 뜨는 미리보기 카드(Open Graph)도 메타데이터가 없으면 아예 생성되지 않거나 빈 카드로 뜬다.

```ts
// app/page.tsx — 정적 메타데이터
import { Metadata } from 'next';

// 정적 메타데이터를 선언하고 export 한다.
export const metadata: Metadata = {
  title: '메인 페이지 | 프론트엔드 응용',
  description: 'Next.js 에셋 최적화, SEO, 미들웨어를 학습하는 메인 페이지입니다.',
};

export default function HomePage() {
  // ...
}
```

- `page.tsx`에서 `title`·`description`을 정적으로 고정할 수도 있지만, 상품 상세 페이지처럼 URL 파라미터(`id`)에 따라 내용이 매번 달라지는 페이지는 `generateMetadata` 함수로 **동적 메타데이터**를 만든다. 여기서 `openGraph` 객체까지 함께 채워주면 메신저 공유 카드의 제목·설명·대표 이미지가 상품마다 다르게 뜬다.

```ts
// app/products/[id]/page.tsx
import { Metadata } from 'next';

interface ProductPageProps {
  params: Promise<{ id: string }>;
}

// 동적 메타데이터 생성 함수
export async function generateMetadata({ params }: ProductPageProps): Promise<Metadata> {
  const resolvedParams = await params;
  const productId = resolvedParams.id;

  const title = `특가 상품 ${productId}호 상세 정보`;
  const description = `현재 조회 중인 ${productId}번 상품의 한정 수량 할인 페이지입니다.`;

  return {
    title,
    description,
    // Open Graph (SNS 공유 카드) 설정
    openGraph: {
      title,
      description,
      images: [
        {
          url: `https://picsum.photos/seed/${productId}/1200/630`,
          width: 1200,
          height: 630,
          alt: `${productId}번 상품 대표 이미지`,
        },
      ],
    },
  };
}

export default async function ProductDetailPage({ params }: ProductPageProps) {
  const resolvedParams = await params;

  return (
    <div className="p-8 max-w-xl mx-auto border rounded-lg my-8">
      <h2 className="text-2xl font-bold text-blue-600 mb-2">동적 SEO 적용 페이지</h2>
      <p className="text-gray-700">조회 중인 상품 번호: <strong>{resolvedParams.id}</strong></p>
    </div>
  );
}
```

- 정적이든 동적이든 메타데이터가 실제로 들어가는 자리는 HTML `<head>` 영역이다. `page.tsx`에서 `metadata`를 export만 하면, Next.js가 자동으로 `<head>` 태그 안에 `<title>`, `<meta name="description">`, `<meta property="og:*">`를 생성해 넣어준다 — 개발자가 직접 `<head>`를 건드릴 필요가 없다.

### | Middleware가 하는 일과 없으면 뭐가 번거로워지는가 |

- `middleware.ts`는 프로젝트 루트에 단 하나만 두며, 사용자의 요청이 **페이지 컴포넌트에 도달하기 전** 서버 단계에서 먼저 가로채 검사한다. 이 시점에 들어오는 요청 정보는 `NextRequest` 객체로, 통과·이동 처리는 `NextResponse` 객체로 다룬다.

| 객체 / 메서드 | 역할 |
| --- | --- |
| `request.cookies.get('key')` | 클라이언트가 보낸 쿠키 조회 |
| `request.nextUrl.pathname` | 요청 URL의 경로 정보 확인 |
| `NextResponse.next()` | 검사를 통과시켜 원래 페이지로 진행 |
| `NextResponse.redirect(url)` | 지정한 URL로 강제 이동 (예: `/login`) |
| `NextResponse.rewrite(url)` | 브라우저 주소는 그대로 두고 내부 화면만 바꿔치기 |

- Middleware가 없다면 어떻게 될까. "로그인 안 한 사용자는 `/dashboard`에 못 들어간다"는 규칙을, `/dashboard` 페이지 컴포넌트 **내부**에서 직접 쿠키를 확인하고 리다이렉트해야 한다. 보호해야 할 페이지가 10개, 20개로 늘어나면 그 로직을 페이지마다 전부 복사해 넣어야 하고, 어느 한 곳에서 깜빡 빠뜨리면 그 페이지는 보호되지 않은 채로 뚫려버린다. Middleware는 이런 접근 제어 로직을 라우트별로 흩어두지 않고, 요청의 공통 진입점 한 곳에 모아서 처리하는 "문지기" 역할을 한다 — `config.matcher`로 적용 경로(`/dashboard/:path*`)만 지정하면 끝이다.

```ts
// middleware.ts — 루트 디렉터리에 작성
import type { NextRequest } from 'next/server';
import { NextResponse } from 'next/server';

export function middleware(request: NextRequest) {
  // 요청 쿠키 목록에서 'auth-token'을 가져온다.
  const authToken = request.cookies.get('auth-token');

  // 인증 토큰이 없으면 /login 페이지로 리다이렉트한다.
  if (!authToken) {
    const loginUrl = new URL('/login', request.url);
    return NextResponse.redirect(loginUrl);
  }

  // 인증 토큰이 있으면 다음 단계로 요청을 통과시킨다.
  return NextResponse.next();
}

// 미들웨어를 적용할 경로를 설정한다.
export const config = {
  matcher: ['/dashboard/:path*'],
};
```

- 쿠키 없이 `/dashboard`로 들어가는 링크를 누르면, 미들웨어가 요청을 가로채 `/login`으로 돌려보낸다. 사용자 입장에서는 페이지 자체가 로딩되지도 않고 바로 로그인 화면으로 전환되는 것으로 보인다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 정적 자원 폴더 | Static Assets Directory (public) | App Router와 독립적으로 동작하며, 루트(/) 경로로 정적 자원에 접근하게 해주는 폴더 |
| 외부 이미지 패턴 | Remote Patterns | `next.config.ts`에서 이미지 최적화를 허용할 외부 도메인을 지정하는 보안 옵션 |
| 레이아웃 시프트 | Layout Shift (CLS) | 이미지·폰트 로딩 지연으로 화면 요소가 갑자기 밀리는 현상 |
| 오픈 그래프 | Open Graph (OG) | 메신저·SNS에 링크 공유 시 나타나는 미리보기 카드 표준 규격 |
| NextRequest / NextResponse | NextRequest / NextResponse | 미들웨어에서 요청 정보를 읽고(cookies, nextUrl), 응답(redirect, next)을 제어하는 서버 객체 |

# PART 2. Supabase DB 연동 & CRUD 구성
### | 데이터는 왜 메모리가 아니라 DB에 저장해야 하나 |

- 앱을 새로고침하거나 서버를 재시작해도 작성한 게시글이 그대로 남아있는 이유는, 스마트폰이나 PC의 메모리(RAM)가 아니라 영구 저장소인 **데이터베이스(Database)** 에 데이터를 보관하기 때문이다. 직접 백엔드 서버와 DB를 구축하려면 서버 인프라, 인증, API 설계를 전부 손으로 만들어야 하는데, **Supabase**는 이런 백엔드 인프라를 클라우드 서비스 형태로 미리 갖춰 제공해서 DB 연동을 빠르게 끝낼 수 있게 해준다.
- 오늘 다루는 CRUD는 데이터 처리의 4가지 기본 연산이다: Create(생성), Read(조회), Update(수정), Delete(삭제). 실습은 `todos` 테이블(컬럼: `id`, `created_at`, `title`, `is_completed`)에 대한 할 일 목록 앱으로 진행한다.

### | 서버 전용 Supabase 클라이언트는 왜 따로 만드나 |

- `@supabase/ssr`의 `createServerClient`는 Next.js 서버 환경(서버 컴포넌트, Server Actions)에서 쿠키를 통해 안전하게 Supabase에 접속하는 클라이언트를 만든다. 쿠키를 직접 다루는 이유는, 나중에 인증(Auth) 세션을 쿠키로 동기화하기 위한 준비이기도 하다.

```ts
// utils/supabase/server.ts
// Next.js SSR 전용 Supabase 클라이언트 생성 함수 임포트
import { createServerClient } from '@supabase/ssr'
// Next.js 서버 쿠키 관리 함수 임포트
import { cookies } from 'next/headers'

// 서버 환경에서 호출할 Supabase 클라이언트 생성 함수
export async function createClient() {
  // 현재 요청의 쿠키 저장소 객체를 가져온다.
  const cookieStore = await cookies()

  // Supabase 클라이언트 인스턴스를 생성하여 반환한다.
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        // 모든 쿠키 데이터를 가져오는 메서드
        getAll() {
          return cookieStore.getAll()
        },
        // 변경된 쿠키 데이터를 설정하는 메서드
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            )
          } catch {
            // Server Component 내부에서의 쿠키 변경 호출 예외 처리
          }
        },
      },
    }
  )
}
```

- `.env.local`에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 담아두고 `process.env`로 꺼내 쓴다. 키를 코드에 직접 하드코딩하면 깃허브 같은 공개 저장소에 그대로 노출될 위험이 있어, 민감한 설정값은 항상 코드 밖(`.env.local`)으로 분리해서 관리한다.

### | 데이터 조회 (Read) — 서버 컴포넌트에서 select |

```ts
// app/components/TodoList.tsx
import { createClient } from '@/utils/supabase/server'

export interface Todo {
  id: number
  created_at: string
  title: string
  is_completed: boolean
}

export default async function TodoList() {
  const supabase = await createClient()

  // todos 테이블에서 모든 컬럼을 가져오고 생성일 기준 내림차순 정렬한다.
  const { data: todos, error } = await supabase
    .from('todos')
    .select('*')
    .order('created_at', { ascending: false })

  if (error) {
    return <p style={{ color: 'red' }}>데이터 로딩 실패: {error.message}</p>
  }

  return (
    <div style={{ marginTop: '20px' }}>
      <h3>할 일 목록 (Read)</h3>
      {todos && todos.length > 0 ? (
        <ul style={{ listStyle: 'none', padding: 0 }}>
          {todos.map((todo: Todo) => (
            <li key={todo.id} style={{ padding: '10px', borderBottom: '1px solid #eee', display: 'flex', justifyContent: 'space-between' }}>
              <span>{todo.title}</span>
              <span>{todo.is_completed ? '완료' : '진행 중'}</span>
            </li>
          ))}
        </ul>
      ) : (
        <p style={{ color: '#888' }}>등록된 데이터가 없습니다. DB에 데이터를 추가해 보세요.</p>
      )}
    </div>
  )
}
```

- `supabase.from('todos').select('*').order('created_at', { ascending: false })`를 호출하면 `{ data, error }` 형태의 객체가 돌아온다. 예를 들어 `todos` 테이블에 세 건이 있다면 아래처럼 응답이 온다(값은 예시).

```
// { data: todos, error } 응답 예시
data: [
  { id: 3, created_at: '2026-10-22T09:12:00Z', title: 'Next.js 복습', is_completed: false },
  { id: 2, created_at: '2026-10-21T18:40:00Z', title: '알고리즘 문제풀이', is_completed: true },
  { id: 1, created_at: '2026-10-21T10:05:00Z', title: 'TIL 작성', is_completed: true }
]
error: null
```

- `error`를 꼭 확인해야 하는 이유: 네트워크 문제나 쿼리 오류가 나도 Supabase는 예외(throw)를 던지지 않고 `{ data: null, error: {...} }` 형태로 응답한다. `if (error)` 체크가 없으면, `data`가 `null`인 채로 `todos.map(...)`을 그대로 실행하다가 "null의 속성을 읽을 수 없다"는 런타임 에러로 화면 전체가 깨져버린다.

### | 데이터 추가 (Create) — Server Actions |

- Server Actions는 별도의 API 라우트(`app/api/...`)를 만들지 않고도, 클라이언트 영역(폼)에서 서버 로직을 직접 호출할 수 있게 해주는 Next.js 기능이다. `'use server'` 지시어를 파일 맨 위에 적으면 그 안의 함수들은 전부 서버에서만 실행된다.

```ts
// app/actions.ts
'use server'

import { createClient } from '@/utils/supabase/server'
import { revalidatePath } from 'next/cache'

// 새로운 할 일을 추가하는 Server Action 함수
export async function addTodo(formData: FormData) {
  const supabase = await createClient()

  // 폼 입력값에서 title 데이터를 추출한다.
  const title = formData.get('title') as string

  // 입력값이 빈 문자열이면 처리를 중단한다.
  if (!title || title.trim() === '') {
    return
  }

  // todos 테이블에 데이터 행을 삽입한다.
  const { error } = await supabase
    .from('todos')
    .insert([{ title: title.trim(), is_completed: false }])

  if (error) {
    console.error('데이터 추가 에러:', error.message)
    return
  }

  // 데이터 변경 후 메인 페이지 캐시를 갱신하여 최신 리스트를 보여준다.
  revalidatePath('/')
}
```

```ts
// app/components/TodoInput.tsx
import { addTodo } from '@/app/actions'

export default function TodoInput() {
  return (
    <form action={addTodo} className="flex gap-2 mt-6">
      <input
        type="text"
        name="title"
        placeholder="새 할 일을 입력하세요"
        required
        className="flex-1 p-2 border border-gray-300 rounded text-sm focus:outline-none focus:border-blue-500"
      />
      <button type="submit" className="px-4 py-2 bg-blue-600 text-white rounded text-sm font-medium hover:bg-blue-700 transition">
        추가
      </button>
    </form>
  )
}
```

- `supabase.from('todos').insert([{ title: 'TIL 작성', is_completed: false }])`를 호출하면 DB는 `id`(자동 증가)와 `created_at`(now())을 알아서 채워 한 행을 만든다 — 예시 응답: `{ data: null, error: null }`(기본 insert는 삽입된 행을 반환하지 않으므로 `data`가 비어있고, 성공 여부는 `error`가 `null`인지로 확인한다).
- `revalidatePath('/')`가 없다면 어떻게 될까. Next.js는 서버 컴포넌트 결과를 캐싱하는데, DB에 새 행을 넣어도 메인 페이지(`/`)가 캐시된 이전 목록을 그대로 보여줘서 "방금 추가한 할 일이 화면에 안 보인다"는 상황이 생긴다. `revalidatePath`는 "이 경로의 캐시를 비우고 다시 그려라"라고 명시적으로 알려주는 역할이다.

### | 데이터 수정(Update)·삭제(Delete) |

```ts
// app/actions.ts (하단에 추가)

// 할 일 완료 상태를 토글하는 Server Action
export async function toggleTodo(id: number, isCompleted: boolean) {
  const supabase = await createClient()

  // id가 일치하는 행의 is_completed 상태를 반전시킨다.
  const { error } = await supabase
    .from('todos')
    .update({ is_completed: !isCompleted })
    .eq('id', id)

  if (error) {
    console.error('데이터 수정 에러:', error.message)
    return
  }

  revalidatePath('/')
}

// 할 일을 삭제하는 Server Action
export async function deleteTodo(id: number) {
  const supabase = await createClient()

  // id가 일치하는 행을 테이블에서 삭제한다.
  const { error } = await supabase
    .from('todos')
    .delete()
    .eq('id', id)

  if (error) {
    console.error('데이터 삭제 에러:', error.message)
    return
  }

  revalidatePath('/')
}
```

```ts
// app/components/TodoItem.tsx
import { Todo } from './TodoList'
import { deleteTodo, toggleTodo } from '@/app/actions'

interface TodoItemProps {
  todo: Todo
}

export default function TodoItem({ todo }: TodoItemProps) {
  return (
    <li className="py-3 flex items-center justify-between border-b border-gray-100">
      <span className={todo.is_completed ? 'line-through text-gray-400' : 'text-gray-800'}>
        {todo.title}
      </span>

      <div className="flex gap-2">
        {/* Update 버튼 Form — bind로 매개변수를 미리 고정 */}
        <form action={toggleTodo.bind(null, todo.id, todo.is_completed)}>
          <button type="submit" className="px-2.5 py-1 text-xs bg-gray-100 hover:bg-gray-200 text-gray-700 rounded transition">
            {todo.is_completed ? '취소' : '완료'}
          </button>
        </form>

        {/* Delete 버튼 Form */}
        <form action={deleteTodo.bind(null, todo.id)}>
          <button type="submit" className="px-2.5 py-1 text-xs bg-red-50 hover:bg-red-100 text-red-600 rounded transition">
            삭제
          </button>
        </form>
      </div>
    </li>
  )
}
```

- `.eq('id', id)`가 왜 꼭 필요한가. 이게 없으면 `update()`나 `delete()`가 **테이블 전체 행**에 적용되어, 할 일 하나를 완료 처리하려다 전체 목록이 몽땅 "완료" 상태로 바뀌거나, 삭제 버튼 한 번에 테이블 전체가 비어버리는 대형 사고로 이어진다. `.eq('id', id)`는 "이 조건을 만족하는 행에만" 적용하라는 필터다.
- `toggleTodo.bind(null, todo.id, todo.is_completed)`처럼 `bind`를 쓰는 이유: Server Action은 기본적으로 `(formData: FormData)` 하나만 인자로 받는 구조인데, `id`나 `isCompleted`처럼 각 항목마다 달라지는 값을 미리 고정해서 넘기고 싶을 때 `bind`로 매개변수를 박아둔다.

### | 지금은 RLS를 꺼둔 상태 — 왜 위험한가 |

- 테이블을 만들 때 **Row Level Security(RLS, 행 수준 보안)** 체크를 해제해야 외부에서 데이터 추가가 가능했다. RLS를 켜둔 채로 정책(Policy) 없이 테이블에 접근하면 "new row violates row-level security policy" 에러가 나기 때문이다.
- 하지만 RLS가 꺼진 상태는 "로그인 여부와 무관하게 누구나 `todos` 테이블의 모든 행을 읽고 쓰고 지울 수 있다"는 뜻이다. 지금 단계는 인증 기능이 아직 없어 임시로 꺼둔 것일 뿐, 실제 서비스라면 다른 사람이 내 할 일을 마음대로 삭제할 수 있는 심각한 보안 구멍이다. 이 문제는 Supabase Auth와 RLS 정책을 붙여야 해결할 수 있다.
