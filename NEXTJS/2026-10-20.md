# PART 1. Tailwind 기반 shadcn/ui 연동
### | shadcn/ui란 — 설치가 아니라 소스 코드를 받아오는 방식 |

- shadcn/ui 공식 사이트(https://ui.shadcn.com/)는 완성도 높은 UI 컴포넌트가 모여 있는 카탈로그다. 일반적인 UI 라이브러리처럼 `npm install`로 패키지를 설치해 블랙박스로 가져다 쓰는 게 아니라, CLI 명령으로 컴포넌트의 실제 소스 코드 파일을 내 프로젝트의 `components/ui/` 폴더 안에 직접 복사해온다.

```txt
chapter05-4/
├── app/
│   ├── components/
│   │   ├── SearchInput.tsx    # Input 활용 실시간 검색 컴포넌트
│   │   ├── InfoCard.tsx       # Button 및 Card 활용 정보 카드 컴포넌트
│   │   └── AddUserModal.tsx   # Dialog 활용 모달 컴포넌트
│   └── page.tsx
├── components/
│   └── ui/                    # shadcn/ui CLI가 컴포넌트 소스 코드를 그대로 생성하는 폴더
└── lib/
    └── utils.ts               # clsx와 tailwind-merge를 결합한 cn 유틸리티 함수
```

```bash
# 1단계: 프로젝트 생성 후 shadcn/ui 초기 설정
npx create-next-app@latest chapter05-4
cd chapter05-4
npx shadcn@latest init
# 프롬프트 선택: Base UI (Recommended) → Nova 프리셋

# 2단계: 공식 사이트에서 검색(Ctrl+K)해 확인한 설치 명령어 실행
npx shadcn@latest add button card
npm i lucide-react
```

- 왜 이런 방식을 쓰는가: 일반 라이브러리는 `node_modules` 안에 코드가 숨어 있어서, 디자인을 조금이라도 바꾸려면 라이브러리 자체의 설정 옵션(props) 안에서만 커스터마이징이 가능하다. shadcn/ui는 코드가 내 프로젝트 안에 그대로 존재하므로, Tailwind 클래스 한 줄까지 전부 직접 수정할 수 있는 완전한 제어권을 갖는다.
- 없으면 어떻게 될까: Button, Card, Dialog 같은 기본 UI 요소를 매번 처음부터 직접 만들어야 한다. 특히 Dialog(모달)처럼 포커스 트랩, 키보드 접근성, 배경 스크롤 방지 같은 세부 동작까지 신경 써야 하는 컴포넌트는 직접 구현하면 버그가 생기기 쉬운데, shadcn/ui는 이런 검증된 구현체를 그대로 가져다 쓰게 해준다.

### | Button, Card 연동 — InfoCard 컴포넌트 |

```tsx
// app/components/InfoCard.tsx
import { Button } from '@/components/ui/button';
import {
  Card, CardContent, CardDescription, CardFooter, CardHeader, CardTitle,
} from '@/components/ui/card';
import { Mail, User } from 'lucide-react';

interface InfoCardProps {
  name: string;
  email: string;
  role: string;
}

export default function InfoCard({ name, email, role }: InfoCardProps) {
  return (
    <Card className="w-full max-w-sm shadow-sm bg-white">
      <CardHeader>
        <div className="flex items-center gap-2">
          <User className="w-5 h-5 text-indigo-600" />
          <CardTitle className="text-xl font-semibold">{name}</CardTitle>
        </div>
        <CardDescription>{role}</CardDescription>
      </CardHeader>
      <CardContent>
        <div className="flex items-center gap-2 text-sm text-slate-600">
          <Mail className="w-4 h-4" />
          <span>{email}</span>
        </div>
      </CardContent>
      <CardFooter>
        <Button className="w-full" variant="outline">상세 정보 보기</Button>
      </CardFooter>
    </Card>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 흰 배경의 카드 안에, 사람 아이콘과 이름("홍길동"), 역할("프론트엔드 개발자") 설명, 메일 아이콘과 이메일 주소, 그리고 하단에 테두리만 있는 "상세 정보 보기" 버튼이 순서대로 쌓인 레이아웃이 그려진다. `InfoCard`를 여러 개 나란히 렌더링하면 사용자 카드 목록 화면이 완성된다.
- `lucide-react`를 쓰는 이유: shadcn/ui 공식 문서와 생성 코드가 기본으로 채택한 아이콘 라이브러리라서, 모든 아이콘이 같은 선 두께와 24x24 그리드로 통일되어 있다. 아이콘마다 스타일이 제각각인 라이브러리를 섞어 쓰면 화면의 시각적 일관성이 깨진다.

### | Input 연동 — 실시간 검색 구현 |

```tsx
// app/components/SearchInput.tsx
'use client';

import { Input } from '@/components/ui/input';
import { Search } from 'lucide-react';

interface SearchInputProps {
  searchTerm: string;
  onSearchChange: (value: string) => void;
}

export default function SearchInput({ searchTerm, onSearchChange }: SearchInputProps) {
  return (
    <div className="relative w-full max-w-md">
      <Search className="absolute left-3 top-1/2 -translate-y-1/2 w-4 h-4 text-slate-400" />
      <Input
        type="text"
        value={searchTerm}
        onChange={(e) => onSearchChange(e.target.value)}
        placeholder="이름 또는 직책으로 검색..."
        className="pl-9 bg-white"
      />
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 돋보기 아이콘이 달린 입력창에 "디자이너"를 입력하면, 입력하는 즉시(글자 하나가 바뀔 때마다) 카드 목록이 "김철수 - UI/UX 디자이너" 한 장만 남도록 실시간으로 걸러진다. 검색어와 맞는 사용자가 없으면 "검색 결과가 없습니다." 문구가 대신 출력된다.

### | Dialog 연동 — 모달 팝업 |

```tsx
// app/components/AddUserModal.tsx
'use client';

import { Button } from '@/components/ui/button';
import {
  Dialog, DialogContent, DialogDescription, DialogFooter, DialogHeader, DialogTitle, DialogTrigger,
} from '@/components/ui/dialog';
import { useState } from 'react';

export default function AddUserModal() {
  const [isOpen, setIsOpen] = useState(false);

  const handleSave = () => {
    alert('신규 사용자가 성공적으로 추가되었습니다.');
    setIsOpen(false);
  };

  return (
    <Dialog open={isOpen} onOpenChange={setIsOpen}>
      <DialogTrigger render={<Button variant="default">+ 사용자 추가</Button>} />
      <DialogContent className="sm:max-w-[425px]">
        <DialogHeader>
          <DialogTitle>신규 사용자 등록</DialogTitle>
          <DialogDescription>등록할 사용자의 기본 정보를 확인한다.</DialogDescription>
        </DialogHeader>
        <div className="py-4 space-y-2">
          <p className="text-sm text-slate-500">새로운 사용자를 시스템에 등록할지 묻는 확인 문구가 들어가는 자리다.</p>
        </div>
        <DialogFooter>
          <Button variant="ghost" onClick={() => setIsOpen(false)}>취소</Button>
          <Button onClick={handleSave}>저장하기</Button>
        </DialogFooter>
      </DialogContent>
    </Dialog>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: "+ 사용자 추가" 버튼을 누르면 화면 중앙에 반투명 배경과 함께 "신규 사용자 등록" 대화상자가 떠오른다. "저장하기"를 누르면 알림창이 뜨고 모달이 닫히며, "취소"를 누르면 그냥 모달만 닫힌다.
- Dialog 컴포넌트가 없다면 어떻게 될까: 모달을 직접 구현하려면 배경 클릭 시 닫히는 처리, ESC 키 눌렀을 때 닫히는 처리, 모달이 열려 있는 동안 배경 스크롤을 막는 처리, 포커스가 모달 밖으로 나가지 않도록 가두는 처리(포커스 트랩)까지 전부 손으로 구현해야 한다. shadcn/ui의 Dialog는 이런 세부 사항이 이미 구현된 상태로 제공된다.

# PART 2. Parallel & Intercepting Routes
### | 왜 필요한가 — 인스타그램 모달 경험 |

- 인스타그램 피드에서 사진을 누르면 화면 전체가 이동하지 않고 피드 위에 모달 창이 뜬다. 그런데 그 상태에서 새로고침을 하거나 URL을 복사해 접속하면, 피드는 사라지고 사진 상세 페이지가 단독으로 렌더링된다. Next.js는 이 복잡한 화면 전환 패턴을 Parallel Routes(병렬 라우팅)와 Intercepting Routes(경로 가로채기)라는 라우팅 규칙만으로 구현한다.

```txt
app/
├── @modal/
│   ├── (.)photo/
│   │   └── [id]/
│   │       └── page.tsx      # 가로채기 모달 컴포넌트 — 클릭 이동 시에만 나타남
│   └── default.tsx            # 슬롯 기본 예비 컴포넌트
├── photo/
│   └── [id]/
│       └── page.tsx             # 직접 접속(새로고침/URL 입력) 시 나타나는 전면 상세 페이지
├── data.ts                       # 공유 사진 데이터
├── layout.tsx                     # 루트 레이아웃 (children + modal 슬롯 동시 배치)
└── page.tsx                        # 메인 피드
```

### | Parallel Routes — @slot으로 한 레이아웃에 여러 화면 동시 출력 |

- `@` 기호로 시작하는 폴더(예: `@modal`)는 URL 경로에는 전혀 나타나지 않지만, 부모 `layout.tsx`에 컴포넌트 Props 형태로 전달되어 원하는 위치에 자유롭게 배치할 수 있다.

```tsx
// app/@modal/default.tsx — 슬롯에 일치하는 페이지가 없을 때 보여줄 기본 화면
export default function ModalDefault() {
  return null; // 아무것도 출력하지 않음
}
```

```tsx
// app/layout.tsx
import React from "react";
import "./globals.css";

export default function RootLayout({
  children,
  modal,
}: {
  children: React.ReactNode; // 메인 page.tsx
  modal: React.ReactNode;    // @modal 슬롯
}) {
  return (
    <html lang="ko">
      <body className="p-5 font-sans">
        <h2 className="text-2xl font-bold mb-4">사진 갤러리</h2>
        <main>{children}</main>
        <div>{modal}</div>
      </body>
    </html>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: `http://localhost:3000`에 접속하면 평소대로 `app/page.tsx`의 갤러리 피드만 화면에 보인다. `@modal` 슬롯은 아직 일치하는 하위 경로가 없으므로 `default.tsx`가 `null`을 반환해 화면에 아무것도 추가되지 않는다.
- `default.tsx`가 왜 필요한가: 슬롯에 보여줄 페이지가 없는 상황에서 이 파일이 누락되면, Next.js는 그 슬롯을 채우지 못해 페이지 이동 시 전체 화면에 404 에러를 띄워버린다. `default.tsx`는 "슬롯이 비었을 때는 그냥 아무것도 보여주지 않아도 된다"는 예비 규칙을 정해주는 안전장치다.
- Parallel Routes가 없다면 어떻게 될까: 메인 피드와 모달을 한 화면에 동시에 띄우려면, 모달의 열림/닫힘 상태를 React state로 직접 관리하고 모달 컴포넌트를 조건부로 렌더링하는 코드를 손으로 짜야 한다. 이 경우 모달이 열려 있다는 사실이 URL에는 전혀 반영되지 않아서, 사용자가 모달이 뜬 상태의 링크를 복사해 다른 사람에게 보내도 받는 사람은 그냥 메인 피드만 보게 된다.

### | Intercepting Routes — (.)photo로 경로 가로채기 |

| 표기법 | 가로채는 범위 |
| --- | --- |
| (.) | 동일한 계층의 폴더 경로 |
| (..) | 한 단계 상위 계층의 폴더 경로 |
| (..)(..) | 두 단계 상위 계층의 폴더 경로 |
| (...) | app 최상위 디렉터리 기준의 경로 |

```tsx
// app/@modal/(.)photo/[id]/page.tsx — /photo/[id] 링크를 가로채어 팝업으로 띄움
"use client";

import { PHOTOS } from "@/app/data";
import { useRouter } from "next/navigation";
import React from "react";

export default function PhotoModal({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const router = useRouter();
  const resolvedParams = React.use(params);
  const photo = PHOTOS.find((p) => p.id === resolvedParams.id);

  if (!photo) return null;

  const handleClose = () => {
    router.back(); // 이전 방문 기록(메인 피드)으로 복귀
  };

  return (
    <div onClick={handleClose} className="fixed inset-0 bg-black/60 flex items-center justify-center z-50">
      <div onClick={(e) => e.stopPropagation()} className="bg-white p-5 rounded-lg max-w-xs text-center shadow-lg">
        <h4 className="font-bold text-lg mb-2">{photo.title} (모달 화면)</h4>
        <img src={photo.imageUrl} alt={photo.title} className="w-64 h-64 object-cover rounded mx-auto" />
        <button onClick={handleClose} className="mt-4 px-4 py-2 bg-gray-800 text-white rounded hover:bg-gray-700 transition">
          닫기
        </button>
      </div>
    </div>
  );
}
```

```tsx

}
```

- 이 코드가 만드는 실제 화면/동작: 메인 피드에서 사진을 클릭하면 주소창은 `/photo/1`로 바뀌지만, 기존 피드는 뒤에 그대로 남은 채 어두운 반투명 배경 위에 모달 팝업이 중앙에 떠오른다. 모달이나 배경을 클릭하거나 "닫기" 버튼을 누르면 `router.back()`이 호출되어 원래 피드 화면으로 돌아간다. 반면 모달이 열린 상태에서 F5로 새로고침하거나, `/photo/1`을 주소창에 직접 입력하면 가로채기가 해제되고 `app/photo/[id]/page.tsx`의 전면 상세 페이지가 단독으로 출력된다.
- 클라이언트 이동과 직접 접속의 동작이 왜 다른가: `<Link>` 클릭은 Next.js의 클라이언트 사이드 내비게이션이라서, 현재 화면(피드)을 유지한 채 가로채기 규칙이 적용된다. 반면 새로고침이나 URL 직접 입력은 서버에 처음부터 다시 요청하는 것이라서, 메모리에 남아있던 "피드가 떠 있던 상태" 자체가 없다 — 그래서 가로채기가 적용될 대상(유지할 배경 화면)이 없으므로 원본 전면 페이지가 그대로 나온다.
- Intercepting Routes가 없다면 어떻게 될까: 사진 클릭 시 모달을 띄우는 것과, URL 직접 접속 시 전면 페이지를 보여주는 것, 이 두 가지 동작을 하나의 URL(`/photo/1`)로 구현하려면 "현재 어떻게 이 페이지에 도달했는가"를 직접 판별하는 로직을 짜야 한다. Intercepting Routes는 "클라이언트 이동이냐 직접 접속이냐"를 폴더 표기법만으로 자동 구분해준다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 병렬 라우팅 | Parallel Routes | 한 화면 내에서 두 개 이상의 독립적인 슬롯 페이지를 동시에 렌더링하는 기법 |
| 경로 가로채기 | Intercepting Routes | 클라이언트 이동 시 지정된 주소 대신 가로채기 화면을 보여주는 기술 |
| 슬롯 | Slot | `@` 표기법 폴더로, 부모 레이아웃에 주입되어 병렬 렌더링을 가능하게 하는 영역 |
| 기본값 컴포넌트 | default.tsx | 슬롯에 표시할 일치 페이지가 없을 때 렌더링되는 기본 대체 파일 |

# PART 3. React Server Components(RSC)
### | 왜 Server Component가 등장했는가 — 기존 CSR과 뭐가 다른가 |

- React의 기본 렌더링 방식인 CSR은 거의 빈 HTML과 번들 JS 파일만 먼저 보내고, 브라우저가 그 JS를 전부 다운로드·실행해야 비로소 화면이 채워지는 구조였다. 이 구조에서는 "데이터 계산 로직을 설명하는 컴포넌트 코드" 자체가 전부 번들에 포함되어 브라우저로 전송되어야 한다.
- React Server Components(RSC)는 이 전제를 깬다. Next.js App Router의 모든 컴포넌트는 기본적으로 **서버 컴포넌트**로 동작한다 — 즉 컴포넌트의 실행(데이터 조회, HTML 생성)이 전부 서버에서 끝나고, 그 결과물만 브라우저로 전달된다. 완성된 요리를 바로 받는 것과, 재료를 받아 직접 요리해야 하는 것의 차이와 같다.

```tsx
// app/components/ServerCard.tsx — 별도 지시어가 없으므로 기본적으로 Server Component
async function fetchServerData(): Promise<{ title: string; content: string }> {
  // 실제 환경에서는 DB 접근이나 서버 간 API 호출이 이 자리에서 실행됨
  return {
    title: '서버 데이터 레포트',
    content: '이 텍스트는 서버에서 미리 생성되었으며 브라우저 용량을 차지하지 않는다.',
  };
}

export default async function ServerCard() {
  const data = await fetchServerData(); // 서버 안에서 데이터 처리가 끝날 때까지 대기

  return (
    <div className="p-4 bg-blue-50 border border-blue-200 rounded-lg shadow-sm">
      <h2 className="text-lg font-semibold text-blue-900">{data.title}</h2>
      <p className="text-sm text-blue-700 mt-1">{data.content}</p>
    </div>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 브라우저는 "서버 데이터 레포트"라는 제목과 설명 문구가 이미 채워진 완성된 HTML을 그대로 받아서 그린다. `fetchServerData` 함수의 코드 자체, 그리고 그 함수를 실행하는 과정은 전부 서버 안에서만 벌어지고 브라우저로는 전송조차 되지 않는다 — 이를 **Zero Client Bundle Size**라고 부른다.
- 없으면 어떻게 될까(=기존 CSR이라면): 똑같은 데이터를 보여주려 해도 `fetchServerData` 함수 코드, `useEffect`로 데이터를 가져오는 로직, 로딩 상태 처리 코드까지 전부 JS 번들에 포함되어 브라우저로 전송되어야 한다. 브라우저는 그 코드를 전부 다운로드하고 실행한 뒤에야 API를 호출하고, 응답이 와야 비로소 화면을 채운다 — 번들 용량도 늘고 초기 로딩도 느려진다.

### | 'use client' — 서버와 클라이언트의 경계 설정 |

- 클릭, 입력 같은 사용자 상호작용이 필요한 최소한의 영역에만 파일 최상단에 `'use client'`를 선언한다. 이 지시어가 적힌 파일부터는 서버가 아니라 브라우저에서 실행되는 클라이언트 컴포넌트로 전환되며, 그 지점을 **클라이언트 경계(Client Boundary)**라고 부른다.

```tsx
// app/components/ClientCounter.tsx
'use client'; // 이 파일이 클라이언트 경계의 시작점임을 선언

import { useState } from 'react';

interface ClientCounterProps {
  initialCount: number;
}

export default function ClientCounter({ initialCount }: ClientCounterProps) {
  const [count, setCount] = useState<number>(initialCount);

  return (
    <div className="p-4 bg-emerald-50 border border-emerald-200 rounded-lg">
      <h2 className="text-lg font-semibold text-emerald-900">클라이언트 카운터</h2>
      <p className="text-sm text-emerald-700 my-2">
        현재 카운트: <span className="font-bold">{count}</span>
      </p>
      <button
        onClick={() => setCount(count + 1)}
        className="px-3 py-1.5 bg-emerald-600 text-white text-sm rounded hover:bg-emerald-700 transition"
      >
        카운트 증가
      </button>
    </div>
  );
}
```

```tsx
// app/page.tsx — 서버 컴포넌트가 클라이언트 컴포넌트에 초기값을 Props로 전달
import ClientCounter from './components/ClientCounter';

export default function HomePage() {
  return (
    <main className="p-8 max-w-2xl mx-auto space-y-6">
      <section>
        <h2 className="text-lg font-bold mb-2">클라이언트 컴포넌트 경계</h2>
        <ClientCounter initialCount={10} />
      </section>
    </main>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: 화면에는 "현재 카운트: 10"과 "카운트 증가" 버튼이 보인다. 버튼을 클릭할 때마다 숫자가 1씩 실시간으로 늘어난다 — 이 반응은 브라우저 메모리 위에서 즉시 일어나는 클라이언트 쪽 동작이다.
- `'use client'`가 없다면 어떻게 될까: `useState`나 `onClick` 같은 훅·이벤트 핸들러는 서버 컴포넌트 안에서는 아예 사용할 수 없다(컴파일 에러가 난다). 서버는 HTML을 한 번 그려서 응답으로 보내고 끝나는 역할이라, "버튼을 누르면 즉시 반응한다"는 동작 자체를 서버가 담당할 수 없기 때문이다. `'use client'`는 "이 지점부터는 브라우저에서 실행돼야 한다"는 사실을 명시적으로 표시하는 경계선이다.
- `page.tsx`(서버 컴포넌트)가 `ClientCounter`(클라이언트 컴포넌트)를 자식으로 품을 수 있는 이유: 서버 컴포넌트는 클라이언트 컴포넌트를 자유롭게 가져와 쓸 수 있다. 다만 반대로 클라이언트 컴포넌트 안에서 서버 컴포넌트를 직접 import해서 쓸 수는 없다 — 경계는 한쪽 방향으로만 자유롭게 통과된다.

### | 직렬화 가능(Serializable) Props 규칙 |

- 서버 컴포넌트가 클라이언트 컴포넌트에게 Props를 넘겨줄 때, 그 값은 네트워크로 전송 가능한 형태(JSON 형태)여야 한다. 이 변환 과정을 **직렬화(Serialization)**라고 한다.

| 전달 가능 | 전달 불가능 |
| --- | --- |
| string, number, boolean, array, plain object | function(이벤트 핸들러 함수), class instance |

```tsx
// app/components/UserProfile.tsx
'use client';

interface UserProfileProps {
  user: {
    name: string;    // 직렬화 가능 (string)
    age: number;     // 직렬화 가능 (number)
    roles: string[]; // 직렬화 가능 (array)
  };
}

export default function UserProfile({ user }: UserProfileProps) {
  return (
    <div className="p-4 bg-purple-50 border border-purple-200 rounded-lg">
      <h2 className="text-lg font-semibold text-purple-900">사용자 프로필 정보</h2>
      <ul className="text-sm text-purple-700 mt-2 space-y-1">
        <li><strong>이름:</strong> {user.name}</li>
        <li><strong>나이:</strong> {user.age}세</li>
        <li><strong>권한:</strong> {user.roles.join(', ')}</li>
      </ul>
    </div>
  );
}
```

```tsx
// app/page.tsx
import UserProfile from './components/UserProfile';

export default function HomePage() {
  const userData = { name: '김철수', age: 22, roles: ['수강생', '개발자'] }; // 직렬화 가능한 순수 객체

  return (
    <main className="p-8 max-w-2xl mx-auto space-y-6">
      <section>
        <h2 className="text-lg font-bold mb-2">직렬화(Serializable) Props 검증</h2>
        <UserProfile user={userData} />
      </section>
    </main>
  );
}
```

- 이 코드가 만드는 실제 화면/동작: "이름: 김철수", "나이: 22세", "권한: 수강생, 개발자"가 리스트로 출력된다. `userData`는 서버 컴포넌트(`page.tsx`)에서 만들어졌지만, 문자열·숫자·배열로만 구성된 순수 객체이기 때문에 클라이언트 컴포넌트(`UserProfile`)로 아무 문제 없이 건너갈 수 있다.
- 함수를 Props로 넘기면 왜 안 되는가: 자바스크립트 함수는 메모리 주소를 직접 참조하는 실행 코드 덩어리다. 서버의 메모리 주소는 브라우저(클라이언트)의 메모리 공간과 완전히 분리되어 있어서, "이 주소를 열어서 실행해라"라는 참조값을 그대로 보내봐야 클라이언트 쪽에서는 아무 의미가 없다. 그래서 서버에서 만든 이벤트 핸들러 함수를 그대로 클라이언트 컴포넌트에 Props로 넘기려 하면 에러가 난다 — 클릭 이벤트 처리가 필요하면, 그 핸들러는 애초에 `'use client'` 컴포넌트 내부에서 직접 정의해야 한다.
- 이 규칙이 없다면 어떻게 될까: 서버와 클라이언트가 같은 메모리 공간에 있다고 착각한 코드를 작성하게 되어, "함수를 Props로 넘겼는데 왜 실행이 안 되지"와 같은 혼란스러운 런타임 에러를 디버깅하는 데 시간을 쓰게 된다. 직렬화 규칙은 "서버와 클라이언트는 물리적으로 분리된 두 환경이며, 그 경계를 넘나드는 데이터는 반드시 순수한 값이어야 한다"는 사실을 타입 수준에서 강제한다.

### | 용어 정리 |

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 서버 컴포넌트 | Server Component | 서버에서 실행되어 완성된 HTML만 전달하는, App Router의 기본 컴포넌트 |
| 클라이언트 컴포넌트 | Client Component | 브라우저에서 실행되어 상태·이벤트 등 상호작용을 처리하는 컴포넌트 |
| 제로 번들 사이즈 | Zero Client Bundle Size | 컴포넌트 실행 코드가 브라우저로 전송되지 않아 번들 용량에서 제외되는 구조 |
| 클라이언트 경계 | Client Boundary | 'use client' 지시어로 서버 영역과 클라이언트 영역을 구분하는 지점 |
| 직렬화 | Serialization | 메모리상의 데이터를 네트워크 전송이 가능한 JSON 형태로 변환하는 과정 |
