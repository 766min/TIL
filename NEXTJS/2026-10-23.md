# PART 1. Supabase Auth & RLS 보안 정책
### | 왜 지금 다시 보안을 손봐야 하나 |

- 지금까지 만든 할 일 앱은 RLS(행 수준 보안)를 꺼둔 채로 CRUD 로직 구현에만 집중했다. 그 상태 그대로라면, 누구든 내 할 일을 마음대로 조회·수정·삭제할 수 있다. 오늘은 **사용자 인증(Auth)** 으로 신원을 확인하고, **RLS**로 "내 데이터는 나만 건드릴 수 있게" 막는 작업을 진행한다.
- 전체 흐름은 두 축이다: ① Supabase Auth로 로그인/회원가입 기능을 붙이고, ② `todos` 테이블에 `user_id` 컬럼과 RLS 정책을 추가해서 DB 엔진 차원에서 데이터 소유권을 검증한다.

### | 클라이언트용 Supabase 유틸리티와 로그인 폼 |

- 앞서 만든 `utils/supabase/server.ts`는 서버 전용이었다. 로그인 폼처럼 브라우저에서 직접 실행되는 컴포넌트를 위해 `createBrowserClient`로 별도 클라이언트 유틸리티를 만든다.

```ts
// utils/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr';

// 클라이언트 컴포넌트에서 사용할 Supabase 객체를 생성해 반환한다.
export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!
  );
}
```

### | 인증 전용 Server Actions — login / signup / logout |

```ts
// app/actions.ts
'use server'

import { createClient } from '@/utils/supabase/server'
import { revalidatePath } from 'next/cache'
import { redirect } from 'next/navigation';

// 로그인 Server Action
export async function login(formData: FormData) {
  const supabase = await createClient();
  const email = formData.get('email') as string;
  const password = formData.get('password') as string;

  const { error } = await supabase.auth.signInWithPassword({ email, password });

  if (error) {
    console.error('로그인 에러:', error.message);
    redirect('/login?error=login_failed');
  }

  revalidatePath('/', 'layout');
  redirect('/'); // 로그인 성공 시 메인 보호 페이지로 이동
}

// 회원가입 Server Action
export async function signup(formData: FormData) {
  const supabase = await createClient();
  const email = formData.get('email') as string;
  const password = formData.get('password') as string;

  const { error } = await supabase.auth.signUp({ email, password });

  if (error) {
    console.error('회원가입 에러:', error.message);
    redirect('/login?error=signup_failed');
  }

  revalidatePath('/', 'layout');
  redirect('/'); // 회원가입 완료 후 메인 페이지로 이동
}

// 로그아웃 Server Action
export async function logout() {
  const supabase = await createClient();
  await supabase.auth.signOut();
  revalidatePath('/', 'layout');
  redirect('/login'); // 로그아웃 시 로그인 페이지로 이동
}
```

- `supabase.auth.signInWithPassword({ email, password })`가 성공하면 Supabase는 세션(Session) 정보를 발급하고, `@supabase/ssr`가 이 세션을 **쿠키**에 담아 응답에 실어 보낸다. 예시로 회원가입이 성공하면 Supabase Auth 내부 테이블에 아래와 비슷한 유저 레코드가 하나 생긴다(값은 예시).

```
// supabase.auth.signUp() 성공 응답 예시
data: {
  user: {
    id: 'b3f1c2a0-5e2d-4a91-9c3e-7a1f2d8e6b44',
    email: 'student@example.com',
    created_at: '2026-10-23T02:14:00Z'
  },
  session: { access_token: '...', refresh_token: '...', expires_in: 3600 }
}
error: null
```

- 왜 LocalStorage가 아니라 쿠키에 세션을 담는가. 서버 컴포넌트와 Middleware는 브라우저의 LocalStorage에 접근할 수 없다. 반면 쿠키는 요청마다 브라우저가 자동으로 서버에 실어 보내므로, 서버 쪽 코드(서버 컴포넌트, Server Actions, Middleware)에서도 "지금 요청을 보낸 사람이 로그인했는지"를 똑같이 확인할 수 있다. SSR 환경에서 인증 상태를 서버와 클라이언트가 공유하려면 쿠키가 사실상 유일한 선택지다.

### | Middleware로 세션 쿠키 동기화와 라우트 가드 하기 |

- 앞서 다룬 미들웨어는 단순히 쿠키 존재 여부만 확인했다. 오늘은 한 단계 더 나아가 미들웨어 내부에서 Supabase 클라이언트를 직접 생성해 **실제 로그인 세션**을 검증하고, 세션이 곧 만료될 때 쿠키를 자동으로 갱신(동기화)하는 역할까지 맡긴다.

```ts
// utils/supabase/middleware.ts
import { createServerClient } from '@supabase/ssr';
import { NextResponse, type NextRequest } from 'next/server';

export async function updateSession(request: NextRequest) {
  let supabaseResponse = NextResponse.next({ request });

  // 미들웨어 전용 Supabase 클라이언트를 생성한다.
  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value));
          supabaseResponse = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) =>
            supabaseResponse.cookies.set(name, value, options)
          );
        },
      },
    }
  );

  // 접속 유저 정보를 확인한다.
  const { data: { user } } = await supabase.auth.getUser();

  // 미인증 유저가 보호된 메인 라우트(/)에 접근한 경우 -> /login으로 리다이렉트
  if (!user && request.nextUrl.pathname === '/') {
    const url = request.nextUrl.clone();
    url.pathname = '/login';
    return NextResponse.redirect(url);
  }

  // 이미 로그인한 유저가 /login 페이지에 접근한 경우 -> 메인(/)으로 리다이렉트
  if (user && request.nextUrl.pathname.startsWith('/login')) {
    const url = request.nextUrl.clone();
    url.pathname = '/';
    return NextResponse.redirect(url);
  }

  return supabaseResponse;
}
```

- 이 미들웨어가 없으면 어떻게 될까. 로그인 여부 체크 로직을 `app/page.tsx`와 `app/login/page.tsx` 등 보호가 필요한 페이지 컴포넌트마다 각각 심어야 한다. 또한 세션 쿠키가 만료 직전일 때 자동으로 갱신해주는 로직도 없으므로, 사용자가 작업 도중 세션이 끊겨서 갑자기 로그아웃되는 경험을 할 수 있다. 미들웨어가 모든 요청의 진입점에서 세션을 검사·갱신해주기 때문에, 개별 페이지는 "미들웨어를 통과했다면 이미 인증된 사용자다"라고 안심하고 로직을 짤 수 있다.

### | PostgreSQL RLS 정책 적용 — 본인 데이터만 CRUD 가능하게 |

- 지금까지는 `auth.uid()`(현재 로그인한 유저의 UUID를 꺼내는 SQL 함수)로 데이터 소유자를 구분할 방법이 없어서 RLS를 꺼둔 채였다. 이제 로그인 기능이 생겼으니 `todos` 테이블에 `user_id` 컬럼을 추가하고 RLS를 다시 켠다.

```sql
-- todos 테이블에 user_id 컬럼 추가 (기본값: 현재 로그인한 유저의 auth.uid())
ALTER TABLE todos
ADD COLUMN user_id UUID DEFAULT auth.uid() NOT NULL;

-- 해제(Disable)했던 RLS(행 수준 보안) 다시 활성화(Enable)
ALTER TABLE todos ENABLE ROW LEVEL SECURITY;

-- [SELECT 정책] 로그인한 사용자가 '본인의 데이터'만 조회하도록 허용
CREATE POLICY "Users can view their own todos"
ON todos FOR SELECT TO authenticated
USING ((SELECT auth.uid()) = user_id);

-- [INSERT 정책] 로그인한 사용자가 '본인의 UID'로만 데이터를 추가하도록 허용
CREATE POLICY "Users can create their own todos"
ON todos FOR INSERT TO authenticated
WITH CHECK ((SELECT auth.uid()) = user_id);

-- [UPDATE 정책] 로그인한 사용자가 '본인의 데이터'만 수정하도록 허용
CREATE POLICY "Users can update their own todos"
ON todos FOR UPDATE TO authenticated
USING ((SELECT auth.uid()) = user_id);

-- [DELETE 정책] 로그인한 사용자가 '본인의 데이터'만 삭제하도록 허용
CREATE POLICY "Users can delete their own todos"
ON todos FOR DELETE TO authenticated
USING ((SELECT auth.uid()) = user_id);
```

- RLS 정책이 없으면(혹은 꺼져 있으면) 무슨 일이 생기는가. `select('*')` 같은 평범한 조회 쿼리를 그 누가 보내도 테이블 전체 행이 그대로 응답에 담겨 돌아온다. API 키만 알면 로그인 여부와 무관하게 다른 사용자의 할 일 목록을 전부 읽고, `.eq('id', 아무번호)`로 지정해서 남의 데이터를 수정·삭제하는 것까지 가능해진다. RLS는 애플리케이션 코드(Server Actions)가 아니라 **PostgreSQL 엔진 자체**에서 "이 행의 `user_id`가 지금 요청자의 `auth.uid()`와 같은가"를 강제로 검사하기 때문에, 설령 서버 코드에 `.eq('user_id', ...)` 필터를 깜빡 빠뜨리는 실수를 하더라도 DB 단에서 한 번 더 막아준다는 점이 핵심이다 — 코드 실수에 기대지 않는 이중 안전장치인 셈이다.
- `WITH CHECK`와 `USING`의 차이: `USING`은 "이미 있는 행에 이 조건으로 접근 가능한가"(SELECT/UPDATE/DELETE 대상 필터링), `WITH CHECK`는 "새로 쓰려는 값이 이 조건을 만족하는가"(INSERT/UPDATE 시 반영될 값 검증)를 확인한다. INSERT 정책에 `WITH CHECK`가 없다면, 로그인한 사용자가 자기 `user_id`가 아닌 다른 사람의 UUID를 끼워 넣어 데이터를 추가하는 것도 막지 못한다.

# PART 2. 프로덕션 빌드, 환경변수 & Vercel 배포
### | 환경변수를 분리하는 이유 |

- DB 접속 URL이나 API 키를 소스 코드에 직접 적어 넣으면(하드코딩), 그 코드가 GitHub 같은 공개 저장소에 올라가는 순간 키 값이 그대로 노출된다. **환경변수**는 이런 민감한 설정값을 코드 밖의 별도 파일(`.env.local`, `.env.production`)로 분리해서, 코드 자체에는 "이 자리에 환경변수를 넣어 쓴다"는 참조만 남기는 방식이다.
- Next.js는 접두사로 노출 범위를 구분한다: `NEXT_PUBLIC_` 접두사가 붙은 변수는 브라우저(클라이언트) 번들에 그대로 포함되어 누구나 볼 수 있고, 접두사가 없는 변수는 서버에서만 접근 가능하다. 그래서 외부에 공개돼도 되는 값(Supabase 프로젝트 URL, Publishable Key)에는 `NEXT_PUBLIC_`을 붙이고, 절대 공개되면 안 되는 값(Secret Key 등)에는 접두사를 붙이지 않는다.

```bash
# .env.local — 로컬 개발용 환경변수
NEXT_PUBLIC_SUPABASE_URL=https://your-supabase-project-id.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-supabase-anon-key
```

```bash
# .env.example — 팀원 공유용 템플릿 (실제 값 없이 키 이름만 적어 Git에 함께 올림)
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

```bash
# .gitignore — 보안 파일 제외 설정
.env*.local
.env
.vercel
```

- 환경변수 분리가 없다면 어떻게 될까. 개발 환경과 운영(프로덕션) 환경은 보통 서로 다른 DB·키를 쓰는데, 코드에 값을 직접 박아두면 환경이 바뀔 때마다 소스 코드를 고쳐야 하고, 실수로 개발용 키가 운영 서버에 그대로 배포되거나 반대의 사고가 생길 수 있다. 또한 `.env.local`을 `.gitignore`에 넣지 않으면 키가 커밋 이력에 영구히 남아, 나중에 파일을 지워도 과거 커밋만 뒤지면 키를 복원할 수 있다 — 그래서 키가 노출됐다면 삭제가 아니라 키 자체를 재발급(폐기)해야 한다.

### | npm run build — 배포 전 사전 검증이 왜 필요한가 |

- `npm run build`는 개발용 코드를 실제 서비스에 맞게 압축·최적화하면서, TypeScript 타입 오류와 ESLint 규칙을 엄격하게 검사하는 과정이다. 개발 서버(`npm run dev`)는 타입 에러가 있어도 일단 화면은 띄워주는 경우가 많지만, 프로덕션 빌드는 이런 문제를 가차없이 걸러낸다.
- 로컬에서 먼저 빌드하지 않으면 어떻게 될까. Vercel에 코드를 푸시한 뒤에야 비로소 빌드가 실행되므로, 타입 에러 하나 때문에 배포가 실패했다는 사실을 몇 분 뒤 Vercel 로그를 열어봐야 알게 된다. 로컬에서 미리 `npm run build`를 돌려보면 이 피드백 시간을 훨씬 단축할 수 있다.

```bash
npm run build
```

### | GitHub·Vercel 연동과 CI/CD 자동 배포 |

```bash
# Git 저장소 상태 확인
git status

# 모든 변경 파일을 스테이징 영역에 추가
git add .

# 배포 준비 커밋 메시지 작성
git commit -m "feat: todo앱 프로덕션 배포"

# 기본 브랜치 이름을 main으로 변경
git branch -M main

# GitHub 원격 저장소 주소 연결
git remote add origin git@github.com:<계정명>/nextjs_todo.git

# GitHub 원격 저장소로 코드 전송
git push origin main
```

- Vercel 배포 단계 요약: ① Vercel에 GitHub 계정으로 로그인 → ② `[Add New...] → [Project]`로 새 프로젝트 생성 → ③ 방금 푸시한 저장소(`nextjs_todo`)를 Import → ④ Environment Variables 메뉴에 `.env.local`에 적었던 키들을 그대로 등록 → ⑤ `[Deploy]` 클릭하면 약 1분 내로 빌드와 배포가 완료되어 라이브 URL이 생성된다.
- 배포 후 Supabase 대시보드의 `Authentication → URL Configuration`에서 **Site URL**과 **Redirect URLs**를 Vercel이 발급한 실제 도메인으로 등록해야 한다. 이걸 빠뜨리면 어떻게 되는가. 로그인/회원가입 요청 자체는 성공하더라도, Supabase가 인증 완료 후 되돌려보낼 주소를 여전히 `localhost`로 알고 있어서 배포된 사이트에서는 로그인 후 엉뚱한 주소(로컬호스트)로 리다이렉트되거나 리다이렉트가 거부되는 문제가 생긴다.
- CI/CD(지속적 통합/배포)의 핵심은 "GitHub에 코드를 Push할 때마다 Vercel이 자동으로 빌드하고 배포한다"는 점이다. 이 자동화가 없다면 코드를 수정할 때마다 서버에 직접 접속해서 코드를 받아오고, 빌드하고, 재시작하는 과정을 매번 수작업으로 반복해야 한다 — 변경 사항을 운영 환경에 반영하는 데 걸리는 시간과 실수 가능성이 훨씬 커진다.
