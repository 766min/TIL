# PART 1. 이벤트란 정확히 무엇인가

### | "이벤트가 발생한다"는 말의 진짜 의미 |

- **이벤트(Event)**는 브라우저 안에서 "어떤 일이 일어났다"는 사실 그 자체다. 학교 종이 "땡땡땡" 울리는 것과 같다 — 종이 울리는 행위 자체가 이벤트 발생이고, 그 소리를 듣고 반응하는 학생이 이벤트 핸들러다.

| 실제 용어 | 비유 |
| --- | --- |
| 브라우저 내부에서 이벤트가 발생함(fires) — "클릭됐다", "다 읽혔다" 같은 사실이 생김 | 학교 종이 "땡땡땡" 울림 |
| 그 일이 실제로 일어난 순간 | 종이 울리는 행위 자체 |
| 이벤트 핸들러(Event Handler) — 이벤트가 발생했을 때 실행되도록 등록해둔 함수 | 종소리를 듣고 반응하는 학생 |

- 핵심은, 이벤트는 "누가 듣든 말든" 그냥 일어난다는 점이다. 종이 울리는 것과 그 소리를 듣고 반응하는 건 완전히 별개의 두 단계다.

```
1단계: HTML 다 읽음
2단계: DOM(화면 구조) 다 만들어짐
3단계: 브라우저가 속으로 "DOMContentLoaded 이벤트 발생!" 하고 신호를 쏨
4단계: 그 신호를 듣겠다고 등록해둔 함수가 있으면 → 실행
       없으면 → 그냥 조용히 지나감
```

```javascript
window.addEventListener("DOMContentLoaded", function () {
    // 이 함수가 바로 "이벤트 핸들러"
});
```

### | 이벤트 처리기(핸들러) 또는 리스너 |

- 이벤트(Event)란 웹 페이지 내에서 발생하는 모든 사용자 행동을 뜻하며, 이를 알아채고 실행되는 함수를 **이벤트 처리기(Event Handler)** 또는 **이벤트 리스너**라고 한다.

# PART 2. 요소 선택 — document.querySelector 완전 정리

### | 무엇을 하는 함수인가 |

- CSS에서 쓰던 선택자 문법을 그대로 써서, 해당하는 요소를 딱 하나만 찾아오는 함수다.

### | 왜 나왔나 |

| 옛날 방식 | 문제 |
| --- | --- |
| `getElementById` | id로만 찾음 |
| `getElementsByClassName` | class로만 찾음 |

- 종류마다 전용 함수가 따로 있어서 번거로웠다. `querySelector`는 CSS 선택자 문법 하나로 통합해서, id든 class든 태그든 전부 같은 방식으로 찾을 수 있게 만든 것이다.

```javascript
document.getElementById("price");  // 옛날 방식, id 전용
document.querySelector("#price");  // 요즘 방식, #을 붙이면 id도 찾아줌
```

### | 왜 querySelector는 무조건 document에 붙이나 |

| 실제 용어 | 비유 |
| --- | --- |
| `document` = 지금 보는 이 HTML 페이지 자체를 가리키는 객체 | "이 집(페이지) 안에서 가구 찾아줘" |
| `window` = 페이지 하나보다 더 큰, 브라우저 탭 전체를 가리키는 객체 | "온 동네(브라우저 탭 전체)" |

- `querySelector`가 하는 일은 "이 HTML 페이지 **안에서** 태그를 찾는 것"이다. "페이지 안에서"가 핵심이고, 페이지 자체를 가리키는 게 `document`이니 당연히 `document`에게 물어본다. `window`에는 애초에 `querySelector`라는 기능 자체가 없다 — `window`는 타이머·주소·콘솔처럼 페이지보다 더 큰 범위를 담당하는 객체이기 때문이다.

### | 왜 addEventListener는 window에도, document에도 둘 다 쓰이나 |

| 실제 용어 | 비유 |
| --- | --- |
| `DOMContentLoaded` 이벤트가 실제로 발생하는 자리는 `document` | 집 안에서 초인종이 울림 |
| 이벤트가 버블링(bubbling)되어 `document` 바깥의 `window`까지 전달됨 | 그 소리가 담장 밖까지 들림 |

- 이벤트는 "터진 자리에서 위로 올라가면서 퍼지는" 성질(버블링)이 있다. 그래서 `window.addEventListener("DOMContentLoaded", ...)`도 작동은 한다. 하지만 더 정확하고 관례적인 방식은 `document.addEventListener(...)`다 — 사건이 실제로 일어난 바로 그 자리(`document`)에서 직접 듣는 게 더 맞는 방식이다. (교재에서 `window`를 쓴 건 틀린 게 아니라, 한 다리 건너서 듣는 방식일 뿐이다.)

# PART 3. 이벤트를 등록하는 3가지 방법

### | 방법 1 — HTML 태그 안에 직접 쓰기 (비권장) |

```html
<button type="button" onclick="alert('메세지!');" id="btn">클릭</button>
```

- CSS를 `style=""`로 HTML 태그 안에 직접 박아넣지 말라고 배운 것과 같은 이유로 비권장이다. HTML은 HTML끼리, JS는 JS끼리 분리해야 관리하기 편하고 코드가 중복되지 않는다.

### | 방법 2 — .onclick 속성에 함수 대입 (문제 있음) |

```javascript
const buttonEl2 = document.getElementById("btn2");

buttonEl2.onclick = function () {
    alert("클릭2 --- 1");
};

buttonEl2.onclick = function () {
    alert("클릭2 --- 2");
};
// 결과: 버튼을 클릭하면 "클릭2 --- 2"만 뜬다. "클릭2 --- 1"은 아예 안 뜬다.
```

| 비유 | 실제 용어 |
| --- | --- |
| 우편함에 이름표를 붙였는데, 새 이름표를 덮어씌움 | `.onclick`은 속성(값 하나만 담는 상자)이라서, 나중에 대입한 함수가 이전 것을 덮어씀(overwrite) |

- `.onclick`은 상자(변수)와 똑같다. 상자에 물건을 넣고 또 다른 물건을 넣으면 원래 있던 건 사라지고 새 것만 남는다. 두 방식(HTML 속성 / DOM 프로퍼티) 모두 **하나의 요소에 하나의 이벤트 처리기만** 등록할 수 있어서, 두 번째로 대입한 함수가 첫 번째 것을 지워버린다.

### | 방법 3 — addEventListener (권장, 표준) |

```javascript
const buttonEl = document.getElementById("btn");

buttonEl.addEventListener("click", function () {
    console.log("클릭1");
});
buttonEl.addEventListener("click", function () {
    console.log("클릭2");
});
// 결과: 버튼을 클릭하면 "클릭1"과 "클릭2"가 둘 다, 순서대로 출력된다.
```

| 실제 용어 | 비유 |
| --- | --- |
| `addEventListener`는 목록(리스트)에 콜백을 쌓아두는 방식이라 덮어쓰지 않고 누적됨 | 우편함이 아니라 "줄 서서 기다리는 목록"에 이름을 추가하는 것 |

- "add(추가)"라는 이름 그대로, 기존 것을 지우는 게 아니라 계속 더해지는 구조다.

```javascript
// 구문 구조
target.addEventListener(type, listener, useCapture);
// target: 이벤트를 등록할 DOM 노드
// type: 이벤트 유형 문자열 (예: "click", "keyup")
// listener: 이벤트 발생 시 실행할 콜백 함수의 참조
// useCapture: 이벤트 전파 단계 설정 (기본값 false = 버블링 단계)
```

### | 3가지 방법 비교 |

| 방법 | 권장 여부 | 같은 이벤트에 여러 개 등록하면 |
| --- | --- | --- |
| HTML `onclick="..."` 속성 | 비권장 (관심사 분리 안 됨) | — |
| `.onclick = 함수` | 비권장 | 덮어씀 (마지막 것만 남음) |
| `.addEventListener("click", 함수)` | 표준/권장 | 누적됨 (전부 다 실행) |

### | 서로 다른 파일에서 덮어써지는 위험한 실제 사례 |

```javascript
// 1.js 파일
window.onload = function () {
    console.log("웹페이지 로드 후 매우 중요한 작업 ...");
};
```
```javascript
// 2.js 파일
window.onload = function () {
    console.log("다른 작업자의 중요한 처리 내용...");
};
```
```html
<script src="1.js"></script>
<script src="2.js"></script>
<!-- 결과: 1.js의 작업은 실행조차 안 되고, 2.js의 콘솔 로그만 찍힌다. -->
```

| 비유 | 실제 용어 |
| --- | --- |
| 같은 우편함에 두 사람이 각자 이름표를 붙임 | 같은 `window.onload`라는 상자에 두 파일이 각각 함수를 대입함 |
| 나중에 붙인 이름표가 이긴다 | 나중에 로드된 2.js의 함수가 1.js의 함수를 덮어씀 |

- 팀 프로젝트에서 여러 사람이 각자 다른 파일을 만들 때, 누군가 `window.onload`를 쓰면 다른 사람이 작성한 중요한 초기화 코드가 **에러 하나 없이 조용히 사라진다.** 그래서 원인을 찾기 매우 어렵다. 전역(global) 환경에서는 `.onload`/`.onclick` 같은 속성 방식을 절대 쓰면 안 된다. 함수 안에서 지역적으로 쓰는 건 비교적 안전하지만, 바깥(전역)에 노출된 상태로 쓰면 언제든 누군가에 의해 덮어써질 위험이 있다.

```javascript
// 그래서 써야 하는 표준 방법 — addEventListener는 몇 명이 각자 등록하든 전부 다 실행된다
document.addEventListener("load", function () {
    console.log("1.js의 작업");
});
document.addEventListener("load", function () {
    console.log("2.js의 작업");
});
```

### | 이벤트 리스너 제거하기 |

```javascript
function processEvent() {
    alert("처리가 완료되었습니다.");
    onceButton.removeEventListener("click", processEvent, false); // 자기 자신을 삭제
}
onceButton.addEventListener("click", processEvent, false);
```

- `removeEventListener`로 등록된 리스너를 삭제할 수 있다. 단 **익명 함수로 등록한 리스너는 삭제할 수 없으므로**, 삭제가 필요하면 함수의 참조를 변수에 저장하거나 기명 함수로 정의해야 한다.

### | 어떤 이벤트를 쓸 수 있는지 모를 때 |

```javascript
const buttonEl = document.getElementById("btn");
console.dir(buttonEl);
```

- `console.dir`로 요소를 펼쳐보면 `on`으로 시작하는 속성들(`onclick`, `onmouseover`, `ondrop` 등)이 쭉 나온다. 그게 그 요소에서 쓸 수 있는 이벤트 종류 전부다. 외울 필요 없이 필요할 때마다 `console.dir`로 찾아보면 된다.

# PART 4. DOMContentLoaded vs load

| 이벤트 | 기다리는 것 |
| --- | --- |
| `DOMContentLoaded` | HTML 태그 구조만 다 읽히면 즉시 발생. 이미지·CSS·폰트는 안 기다림 |
| `load` | 이미지, CSS, 폰트까지 전부 다 완전히 로딩된 뒤에 발생 |

```
html을 다 읽음 → DOM 다 만듦 → "DOMContentLoaded!" (이미지는 아직 로딩중이어도 상관없음)
                                     ↓ (시간이 더 지나서)
이미지·CSS까지 다 받아짐 → "load!"
```

- 버튼에 클릭 이벤트를 거는 것처럼 "요소만 찾으면 되는 작업"은 `DOMContentLoaded`로 충분하다.

# PART 5. 이벤트의 종류와 이벤트 객체

### | 마우스 이벤트 |

| 이벤트명 | 발생 시점 및 특징 |
| --- | --- |
| `mousedown` | 마우스 버튼을 누르는 순간 |
| `mouseup` | 누르고 있던 버튼에서 손을 떼는 순간 |
| `click` | `mousedown`과 `mouseup`이 동일 요소 위에서 모두 완료됐을 때 최종 발생 |
| `dblclick` | 짧은 시간 안에 두 번 연속 클릭했을 때 |
| `mousemove` | 포인터가 요소 내부에서 움직이는 동안 계속 |
| `mouseover` | 포인터가 바깥에서 요소 내부로 진입하는 순간 |
| `mouseout` | 포인터가 요소 내부에서 바깥으로 벗어나는 순간 |
| `scroll` | 요소나 페이지의 스크롤 바를 움직일 때 |

### | 마우스 좌표 프로퍼티 — 기준점이 다 다르다 |

| 프로퍼티 | 기준 원점 위치 | 설명 |
| --- | --- | --- |
| `screenX`, `screenY` | 모니터 화면의 왼쪽 위 모서리 | 디스플레이 전체 화면 기준 |
| `clientX`, `clientY` | 브라우저 뷰포트의 왼쪽 위 모서리 | 스크롤과 무관하게 현재 가시 화면 기준 |
| `pageX`, `pageY` | HTML 문서 전체의 왼쪽 위 모서리 | 스크롤되어 숨겨진 영역까지 포함한 전체 문서 기준 |
| `offsetX`, `offsetY` | 이벤트가 발생한 요소의 왼쪽 위 모서리 | 해당 요소 박스 기준 상대 좌표 |

### | 키보드 이벤트 |

| 이벤트명 | 발생 시점 및 특징 |
| --- | --- |
| `keydown` | 자판을 누르는 순간. 누르고 있으면 연속 발생 |
| `keypress` | 글자가 실제로 입력될 때. 기능 키(Alt, Ctrl, Shift, 방향키 등)엔 반응 안 함. 표준에서 제외되는 추세라 `keydown` 사용 권장 |
| `keyup` | 손을 떼는 순간 1회 발생 |

### | 키보드 이벤트 객체 프로퍼티 |

| 프로퍼티 | 설명 | 타입 |
| --- | --- | --- |
| `key` | 눌린 키가 나타내는 실제 문자 값 (예: `"a"`, `"Enter"`, `"ArrowUp"`) | 문자열 |
| `code` | 자판의 물리적 위치 코드 (예: `"KeyA"`, `"Enter"`) | 문자열 |
| `keyCode` | 눌린 키의 고유 아스키/유니코드 숫자 값 | 정수 |
| `altKey`/`ctrlKey`/`shiftKey` | 입력 시 Alt/Ctrl/Shift가 함께 눌려 있었는지 | 논리값 |

### | 그 외 주요 이벤트 |

| 이벤트명 | 발생 시점 및 특징 |
| --- | --- |
| `DOMContentLoaded` | DOM 트리 완성 시점. 스크립트가 요소를 안전하게 조작할 수 있는 시점 |
| `focus` | 요소가 포커스를 얻었을 때 (버블링 발생 안 함) |
| `blur` | 요소가 포커스를 잃었을 때 (버블링 발생 안 함) |
| `change` | input/select 등에서 값 변경 후 포커스를 잃거나 선택 완료했을 때 |
| `submit` | form 데이터가 서버로 전송되기 직전 |

# PART 6. 이벤트 전파 — 캡처링·타깃·버블링

### | 세 번째 인수: 캡처링 vs 버블링 |

```javascript
addEventListener(이벤트명, 이벤트핸들러함수, 캡처링여부);
```

- 세 번째 자리에 `true`/`false`를 넣을 수 있는데, 이건 "이벤트가 어느 방향으로 전파되는지"를 정하는 옵션이다.

| 전파 방향 | 값 |
| --- | --- |
| 버블링 — 안쪽에서 바깥으로 | `false` (기본값, 생략해도 됨) |
| 캡처링 — 바깥에서 안쪽으로 | `true` |

### | 이벤트 전파의 3단계 |

| 단계 | 설명 |
| --- | --- |
| 캡처링 단계 | 이벤트가 Window 객체에서 출발해 상위 요소부터 이벤트 타깃까지 하향 전파 |
| 타깃 단계 | 이벤트가 실제 발생한 요소에 도달해 등록된 리스너가 실행 |
| 버블링 단계 | 이벤트가 타깃 요소에서 출발해 상위 조상 요소들을 거쳐 Window까지 상향 전파 (`focus`, `blur` 등 일부 제외) |

```html
<div class="box1">
  <div class="box2">
    <div class="box3"></div>
  </div>
</div>
```

```
box3(제일 안쪽)를 클릭하면:

캡처링 (바깥 → 안쪽으로 내려감):  window → box1 → box2 → box3
       ↓ (box3에 도달, 여기가 진짜 클릭된 지점 = 타깃 단계)
버블링 (안쪽 → 바깥으로 올라감):  box3 → box2 → box1 → window
```

| 비유 | 실제 용어 |
| --- | --- |
| 돌을 연못 가운데 던지면 물결이 바깥으로 퍼짐 | 버블링(bubbling) — 클릭된 자리에서 바깥(부모)으로 이벤트가 퍼짐 (기본값) |
| 바깥에서 안쪽으로 먼저 신호가 훑고 지나감 | 캡처링(capturing) — 세 번째 인수를 `true`로 설정했을 때의 전파 방향 |

```javascript
box1.addEventListener("click", () => console.log("box1 클릭!"));
box2.addEventListener("click", () => console.log("box2 클릭!"));
box3.addEventListener("click", () => console.log("box3 클릭!"));
// 세 번째 인수를 안 썼으니 기본값(false, 버블링). box3를 클릭하면:
// 출력 순서: box3 클릭! → box2 클릭! → box1 클릭!
```

- box3를 클릭한 사건이 버블링 성질 때문에 box3에서 끝나지 않고 부모인 box2, 그 부모인 box1까지 타고 올라가면서 각자의 리스너를 전부 건드린다. (`DOMContentLoaded`가 `document`에서 `window`까지 버블링되는 것과 같은 원리다 — PART 2에서 본 바로 그 현상이다.)

### | 전파·기본 동작을 제어하는 메서드 |

| 메서드 | 설명 |
| --- | --- |
| `e.stopPropagation()` | 이벤트가 현재 요소 이후 다른 요소로 전파되는 것을 차단 |
| `e.preventDefault()` | 링크 이동이나 폼 제출 등 브라우저의 기본 동작을 취소 |

```javascript
childBtn.addEventListener("click", function (e) {
    console.log("자식 버튼이 클릭되었습니다.");
    e.stopPropagation(); // 부모의 클릭 이벤트 실행을 차단
}, false);

link.addEventListener("click", function (e) {
    const userChoice = confirm("페이지를 이동하시겠습니까?");
    if (!userChoice) e.preventDefault(); // 취소 선택 시 이동을 취소
}, false);
```

# PART 7. 이벤트 리스너 안의 this, 그리고 추가 데이터 전달

### | this 참조 문제와 해결 |

- 이벤트 리스너 내부의 `this`는 기본적으로 이벤트가 발생해 처리를 담당하는 **HTML 요소 객체**를 가리킨다. 그래서 객체의 메서드를 그대로 리스너로 연결하면 `this`가 객체 본연이 아니라 HTML 요소를 가리키는 문제가 생긴다.

```javascript
function Person(name) { this.name = name; }
Person.prototype.sayHello = function () { console.log("Hello! " + this.name); };
const user = new Person("Tom");

// 해결책 1: bind로 this를 user 객체에 고정
btnBind.addEventListener("click", user.sayHello.bind(user), false);

// 해결책 2: 익명 함수로 감싸서 user 인스턴스 기준 스코프 유지
btnWrapper.addEventListener("click", function () { user.sayHello(); }, false);
```

### | 이벤트 리스너에 추가 인자 넘기기 |

- 이벤트 리스너에는 이벤트 객체 외에 임의의 매개변수를 직접 넘길 수 없으므로, 익명 함수를 중간 래퍼로 써서 원하는 인수를 함께 전달한다.

```javascript
block.addEventListener("click", function (e) {
    changeStyle(e, "crimson"); // 래퍼 함수 안에서 추가 인자(color)를 같이 넘김
}, false);

function changeStyle(e, color) {
    e.currentTarget.style.backgroundColor = color;
}
```

# PART 8. 비동기 프로그래밍과 스레드

### | 왜 이벤트는 비동기인가 |

| 실제 용어 | 비유 |
| --- | --- |
| 뭔가를 요청했는데 언제 응답이 올지 모르니, 기다리는 동안 다른 작업을 계속 진행 | 문자 보내고 답장 기다리는 동안 다른 거 함 |
| 응답이 왔을 때 이벤트가 발생하고, 등록해둔 핸들러가 실행됨 | "띵동" 하고 답장이 옴 |

- 이벤트가 비동기인 이유는, 클릭이 언제 될지, 서버 응답이 언제 올지 미리 알 수 없기 때문이다. 그래서 "일단 등록만 해두고, 그 사건이 실제로 터지면 그때 알려달라"는 이벤트 기반 방식을 쓴다.
- **비동기식 처리**란 특정 작업의 완료를 기다리지 않고 다음 코드를 즉시 실행하는 방식이다.

### | 스레드(Thread)란 |

| 실제 용어 | 비유 |
| --- | --- |
| 스레드(Thread) = 코드를 실제로 실행하는 작업 단위 | 일을 처리하는 "일꾼" 한 명 |
| 호출 스택(Call Stack) = 그 스레드가 실행 중인 함수들을 쌓아두는 공간 | 일꾼이 일하는 작업대 |

- 자바스크립트는 기본적으로 일꾼(스레드)이 딱 한 명인 **싱글 스레드** 언어다.

| 싱글 스레드 (Single Thread) | 구분 | 멀티 스레드 (Multi Thread) |
| --- | --- | --- |
| 코드를 실행하는 주체가 1개인 구조 | 개념 | 코드를 실행하는 주체가 여러 개인 구조 |
| 자원 충돌 문제가 없고 흐름 제어가 단순함 | 장점 | 여러 작업을 동시에 처리해 시간 효율성 높음 |
| 연산이 긴 작업 시 다음 작업이 대기해야 함 | 단점 | 동시 제어 시 순서가 꼬이거나 자원 충돌 가능성 |

### | 왜 자바스크립트는 스레드를 하나만 쓰나 |

| 비유 | 실제 용어 |
| --- | --- |
| 일꾼 한 명을 고용할 때마다 돈(자리)이 듦 | 스레드를 하나 만들 때마다 메모리를 차지함 |
| 일꾼이 너무 많으면 돈이 바닥남 | 스레드를 너무 많이 만들면 메모리가 부족해짐 |

- 브라우저 환경에서 여러 스레드가 동시에 화면(DOM)을 수정하면 충돌이 발생할 수 있다. 이를 방지하기 위해 자바스크립트는 단일 흐름을 유지하되, 긴 작업은 비동기 방식으로 외부 창구에 위임한다.
- 싱글 스레드의 장점은 메모리를 적게 써서 동시 접속자가 아주 많아도 감당 가능하다는 것, 단점은 한 번에 하나씩만 처리하므로 일이 몰리면 지연이 생길 수 있다는 것이다. 그래서 자바스크립트는 "무거운 계산(CPU를 많이 쓰는 작업)"보다 "응답을 기다리는 일(I/O)이 많은 작업"에 강하다 — 요청이 많이 와도 각각 기다리는 동안 다른 요청을 처리할 수 있기 때문이다. 이것이 비동기 처리를 권장하는 이유다.

### | 비동기 처리의 특징: 실행 순서 ≠ 종료 순서 |

```javascript
function work(title, time) {
    setTimeout(function () {
        console.log(`${title} 종료 (${time}ms 소요)`);
    }, time);
}

console.log("--- 전체 작업 시작 ---");
work('A 작업', 2000);
work('B 작업', 1000);
work('C 작업', 3000);
console.log("--- 코드 실행 접수 완료 ---");
// 실행(접수)은 A→B→C 순서지만, 종료는 B(1초)→A(2초)→C(3초) 순서다.
```

- 비동기 함수는 호출된 순서대로 실행(접수)되지만, 종료 시점은 작업마다 소요되는 시간에 따라 결정된다.

# PART 9. setTimeout / setInterval과 Task Queue

### | setTimeout — n초 뒤에 딱 한 번 실행 |

```javascript
setTimeout(이벤트핸들러함수, 지연시간);
```

| 비유 | 실제 용어 |
| --- | --- |
| "3시에 알람 맞춰놓고 딴짓하기" | `setTimeout`으로 지연 실행을 예약하는 것 |
| 알람이 울림 | 지정한 시간이 지나서 이벤트 핸들러 함수가 실행됨 |

```javascript
setTimeout(function () {
    console.log("지연 실행");
}, 3000);
console.log("실행 완료!");
// 출력 순서: "실행 완료!" 먼저, 3초 뒤에 "지연 실행"
```

- "실행 완료!"가 먼저 나오는 이유는, `setTimeout`이 "3초 뒤에 해줘"라고 예약만 걸어두고 그 자리에서 기다리지 않은 채 바로 다음 줄로 넘어가기 때문이다. 비동기의 가장 전형적인 예다.

### | 왜 3초인데 더 오래 걸릴 수 있나 — Task Queue |

| 실제 용어 | 비유 |
| --- | --- |
| 시간이 다 되면 콜백이 태스크 큐(Task Queue)라는 대기줄에 들어감 | 알람이 울렸는데, 바로 처리 안 해주고 대기줄에 세움 |
| 호출 스택(Call Stack)이 완전히 비어야만 태스크 큐에서 꺼내 실행함 | 지금 하던 일을 다 끝내야 대기줄 사람을 받아줌 |

- `setTimeout`의 시간은 "최소 이 시간은 기다려라"는 뜻이지, "정확히 이 시간에 실행해준다"는 보장이 아니다. 호출 스택에서 다른 동기 코드가 실행 중이면 그게 끝날 때까지 기다려야 하므로, 실제로는 지정한 시간보다 더 걸릴 수 있다.

### | 타이머 취소하기 |

```javascript
const timeoutId = setTimeout(function () { console.log("지연 실행"); }, 3000);
clearTimeout(timeoutId); // 취소!

const intervalId = setInterval(function () { console.log("반복 실행"); }, 3000);
clearInterval(intervalId); // 반복을 멈춤
```

| 비유 | 실제 용어 |
| --- | --- |
| 예약증(번호표)을 받아둠 | `setTimeout`/`setInterval`이 등록 번호(타이머 ID)를 반환값으로 돌려줌 |
| 번호표를 보여주며 "이 예약 취소해주세요" | `clearTimeout`/`clearInterval`(그 번호)로 등록된 예약을 취소 |

- 나중에 "이 예약 취소해줘"라고 하려면 어떤 예약인지 특정할 방법이 있어야 한다. 그 특정하는 수단이 반환값(타이머 ID)이다.

| 함수 | 실행 횟수 | 취소 함수 |
| --- | --- | --- |
| `setTimeout` | 1번 | `clearTimeout(번호)` |
| `setInterval` | 계속 반복 | `clearInterval(번호)` |

```javascript
// 실전 예시: 300px 넘게 스크롤하면 반복 체크 없이 조건에 따라 종료
let seconds = 0;
const customInterval = setInterval(function () {
    seconds++;
    console.log(`현재 진행 시간: ${seconds}초`);
    if (seconds === 3) {
        clearInterval(customInterval); // 타이머 ID를 넘겨 반복을 정지
    }
}, 1000);
```

- 실행 중인 타이머를 그대로 방치하면 메모리 자원을 계속 소모하므로, 목적을 달성하면 반드시 해제해야 한다.

# PART 10. 콜백 함수와 콜백 지옥

### | 콜백 함수를 통한 순서 보장 |

- 콜백 함수는 비동기 작업의 실행 순서를 보장하기 위해 다른 함수의 인자로 전달되는 함수다. 비동기 작업은 종료 시점이 일정하지 않기 때문에, 특정 작업이 끝난 뒤 다음 작업을 순차적으로 실행하려면 함수의 실행 권한을 넘겨주는 방식이 필요하다.

```javascript
function work(title, time, callback) {
    setTimeout(function () {
        console.log(`${title} 종료`);
        if (typeof callback === 'function') callback();
    }, time);
}

// A -> B -> C 순서를 함수 중첩으로 제어
work('A 작업', 2000, function () {
    work('B 작업', 1000, function () {
        work('C 작업', 3000);
    });
});
```

### | 콜백 지옥(Callback Hell) |

- 순차적 처리가 필요한 비동기 작업이 늘어날수록 콜백 함수의 중첩 단계가 점점 깊어지는 현상이다. 코드 구조가 복잡해져 가독성이 낮아지고, 에러 발생 시 디버깅과 유지보수가 어려워진다.

# PART 11. Promise 객체

### | Promise란 |

- Promise는 비동기 작업의 완료 또는 실패 상태를 추적하고, 콜백의 다중 중첩 문제를 해결하는 객체다. ES6에서 도입됐으며, 비동기 작업의 흐름을 연속적인 마침표(`.`) 메서드로 연결하는 형태로 가독성을 높여준다.

### | Promise의 3가지 상태 |

| 상태 | 설명 |
| --- | --- |
| Pending (대기) | 비동기 처리가 완료되지 않은 초기 상태 |
| Fulfilled (이행) | 성공적으로 완료되어 결과 값을 반환한 상태. `.then()`으로 연결 |
| Rejected (거부) | 실패하거나 에러가 발생한 상태. `.catch()`로 연결 |

### | Promise 기반 순차 실행 — .then()/.catch() |

```javascript
function work(title, time) {
    return new Promise((resolve, reject) => {
        setTimeout(() => {
            if (time < 0) {
                reject(`${title} 수행 시간 설정 오류`);
            } else {
                console.log(`${title} 종료`);
                resolve(`${title} 결과 데이터`);
            }
        }, time);
    });
}

// 콜백 지옥을 수평적인 체이닝 구조로 펼쳐냄
work('A 작업', 2000)
    .then((resultA) => work('B 작업', 1000))
    .then((resultB) => work('C 작업', 3000))
    .catch((error) => console.log(`오류 처리 블록: ${error}`));
```

- 함수가 콜백을 인자로 받지 않고, 비동기 작업의 약속 정보가 담긴 Promise 객체를 즉시 `return`한다. 앞선 작업이 성공하면 `.then()` 내부에서 다음 `work()`를 호출·반환해서 체인을 이어간다.

### | Promise.resolve() / Promise.reject() |

```javascript
const successPromise = Promise.resolve("성공 데이터 전달");
successPromise.then((result) => console.log(result));

const failPromise = Promise.reject("에러 발생 원인");
failPromise.catch((error) => console.log(error));
```

- 성공 또는 실패 상태의 Promise 객체를 즉시 생성할 때 사용한다.

### | Promise.all() / Promise.race() — 병렬 처리 |

```javascript
const delay1 = new Promise((res) => setTimeout(() => res("1등 완료"), 1000));
const delay2 = new Promise((res) => setTimeout(() => res("2등 완료"), 2000));
const delay3 = new Promise((res) => setTimeout(() => res("3등 완료"), 3000));

Promise.all([delay1, delay2, delay3]).then((results) => {
    console.log("Promise.all 결과:", results); // 모든 작업이 끝날 때까지 대기 후 배열로 반환
});

Promise.race([delay1, delay2, delay3]).then((winner) => {
    console.log("Promise.race 결과:", winner); // 가장 먼저 끝난 것의 결과만 반환
});
```

| 메서드 | 동작 |
| --- | --- |
| `Promise.all([배열])` | 전달된 모든 Promise가 **전부** 이행될 때까지 기다린 뒤 결괏값을 배열로 반환. 하나라도 거부되면 즉시 실패 처리 |
| `Promise.race([배열])` | 전달된 Promise 중 **가장 먼저 완료**되는 작업의 결과 또는 에러만 반환 |

# PART 12. async와 await

- `async`/`await`는 Promise 기반의 코드를 마치 일반 동기식 코드처럼 직관적인 구조로 작성하게 돕는 제어 구문이다. `.then()` 체이닝도 작업이 많아지면 줄이 길어지고 흐름 파악이 어려워질 수 있는데, 이를 문법적으로 한 단계 더 개선한 방식이다.

| 규칙 | 설명 |
| --- | --- |
| 내부적인 Promise 활용 | 문법만 개선됐을 뿐, `async` 함수가 제어하고 반환하는 건 여전히 Promise 객체다 |
| `await`의 실행 조건 | `await`는 반드시 `async` 함수 **내부**에서만 실행될 수 있다. 일반 전역 코드나 일반 함수 내부에서 쓰면 문법 에러 |
| 예외 처리의 통합 | `.catch()`의 역할이 자바스크립트 표준 `try~catch` 블록으로 통합 관리된다 |

```javascript
async function startProcess() {
    try {
        console.log("--- 비동기 프로세스 시작 ---");
        const resultA = await work('A 작업', 2000); // 완료될 때까지 일시정지 후 결과를 직접 받음
        const resultB = await work('B 작업', 1000);
        const resultC = await work('C 작업', 3000);
        console.log("--- 모든 프로세스 종료 ---");
    } catch (error) {
        console.log(`try~catch 블록에서 감지된 오류: ${error}`);
    }
}
startProcess();
```

# PART 13. fetch API — 원격 서버와의 네트워크 통신

- fetch API는 브라우저 환경에서 원격 서버로 HTTP 요청을 전송하고 응답을 수신하는 웹 API다. GET/POST의 깊은 개념은 이후 React/Next.js 과정에서 다루고, 지금은 fetch API의 기본 사용법 위주로 익힌다.

### | GET 요청 — 데이터 조회 |

```javascript
const getUrl = "https://jsonplaceholder.typicode.com/posts/1";

async function loadPostData() {
    try {
        const response = await fetch(getUrl);       // 요청 전송, 응답 패키지 수신까지 대기
        const post = await response.json();          // 원시 응답을 자바스크립트 객체로 변환
        console.log(`제목: ${post.title}`);
        console.log(`본문: ${post.body}`);
    } catch (error) {
        console.log(`데이터 조회 중 오류 발생: ${error}`);
    }
}
loadPostData();
```

### | POST 요청 — 데이터 전송 |

```javascript
const postUrl = "https://jsonplaceholder.typicode.com/posts";

async function createPostData() {
    const newPost = { title: "신입생 공지사항", body: "금요일 학과실에서 행사가 개최됩니다.", userId: 101 };
    try {
        const response = await fetch(postUrl, {
            method: "POST",
            headers: { "Content-Type": "application/json; charset=UTF-8" },
            body: JSON.stringify(newPost) // 객체를 JSON 문자열로 직렬화
        });
        const resultData = await response.json();
        console.log("서버 응답 결과:", resultData);
    } catch (error) {
        console.log(`데이터 등록 중 오류 발생: ${error}`);
    }
}
createPostData();
```

- `fetch`의 두 번째 인자로 HTTP 메서드(`method`)·헤더(`headers`)·바디 데이터(`body`)를 설정한다. 보낼 객체는 `JSON.stringify()`로 직렬화해서 담고, 받은 응답은 `.json()`으로 역직렬화해서 쓴다.

Q5. Promise.all()과 Promise.race()의 동작 차이를 가장 올바르게 설명한 것은 무엇입니까?

[ 보기 ]

a. Promise.all()은 가장 먼저 완료된 작업만 반환하고, Promise.race()는 모든 작업의 완료를 기다린다.

b. Promise.all()은 모든 Promise가 이행될 때까지 기다리고, Promise.race()는 가장 먼저 완료되는 작업의 결과만 반환한다.

c. Promise.all()과 Promise.race() 모두 가장 먼저 거부(Reject)된 작업만을 기준으로 동작한다.

d. Promise.all()은 배열이 아닌 단일 Promise만 인자로 받고, Promise.race()는 배열 형태의 인자만 받는다.

내 제출 답안 : 미제출 (오답 ❌)

[ 정답 ] b.

-> `Promise.all()`은 배열 내 모든 Promise가 전부 이행될 때까지 기다린 후 결괏값을 배열로 반환하며, 하나라도 거부되면 즉시 실패 처리된다. `Promise.race()`는 가장 먼저 완료되는 작업의 결과나 에러만을 반환한다. 두 메서드 모두 Promise 배열을 인자로 받으므로 단일 Promise만 받는다는 설명은 틀렸다.
