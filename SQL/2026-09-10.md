- 이번주 내내 SQL 문법을 하나씩 익혔는데, 오늘은 새 문법을 배우기보다 그동안 배운 내용 중에서 "몰랐으면 틀렸을 뻔한" 주의사항들만 따로 모아서 정리하는 날이다.

- 실제로 실무나 시험에서 자주 헷갈리는 포인트 위주로, 왜 헷갈리는지 + 어떻게 기억하면 되는지를 함께 정리했다.

### | ① 기본 조회 관련 주의사항

- `SELECT *`는 학습할 땐 편하지만 실무에서는 지양한다. 이유는 성능 저하 가능성, 테이블 구조 변경시 예상 못한 열 포함, 가독성 저하 세가지다.

- 문자열 비교시 따옴표 규칙을 헷갈리면 안된다.

  - `' '` (작은따옴표) : 문자열을 나타낼 때 (가장 흔하게 사용)

  - `" "` (큰따옴표) : DB마다 쓰임이 다른 식별자 표기용

  - `` ` ` `` (백틱) : MySQL에서만, 예약어를 이름처럼 쓰고 싶을 때

- `IN`과 `LIKE`는 결과가 비슷해보여도 다르다. `IN('전소현')`은 완전히 일치하는 값만, `LIKE('%전소현%')`는 그 문자열이 포함되기만 해도(부분일치) 걸린다.

- `CASE WHEN`은 위에서부터 순서대로 조건을 검사하다가 처음 만족하는 조건에서 멈춘다. 조건 순서를 잘못 두면 의도와 다른 값이 나올 수 있다.

### | ② 집계·그룹화 관련 주의사항

- `COUNT(*)`와 `COUNT(열명)`은 다르다. `COUNT(*)`는 NULL 포함 전체 행 수, `COUNT(열명)`은 NULL을 제외한 행 수다.

- **SELECT절에 집계함수가 아닌 일반 열을 함께 쓴다면, 그 열은 반드시 GROUP BY에도 명시해야 한다.** 안 그러면 에러가 난다. (SQL을 짜다가 가장 자주 만나는 에러 중 하나)

- `WHERE`로는 집계함수 결과(`AVG`, `COUNT` 등)를 조건으로 쓸 수 없다. 집계 결과에 조건을 걸고 싶으면 반드시 `HAVING`을 써야 한다.

  - WHERE : GROUP BY 되기 전, 개별 행 필터링 (먼저 실행됨, 성능에 유리)

  - HAVING : GROUP BY 된 후, 집계 결과 필터링

### | ③ 테이블 결합(JOIN/UNION) 관련 주의사항

- UNION을 쓰려면 두 SELECT문의 **열 개수와 데이터 타입**이 일치해야 한다. 열 이름은 달라도 상관없다. (결과 열 이름은 첫번째 SELECT문 기준)

- UNION은 기본적으로 중복을 제거한다. 중복까지 그대로 다 보고 싶으면 `UNION ALL`을 써야 하고, 이쪽이 정렬/중복제거 연산이 없어서 더 빠르다.

- JOIN 종류를 헷갈릴 때는 "어느 쪽을 무조건 다 보여줄지"로 기억한다.

  - INNER : 양쪽 다 있는것만 (교집합)

  - LEFT : 왼쪽은 무조건 다 나옴

  - RIGHT : 오른쪽은 무조건 다 나옴

  - FULL OUTER : 양쪽 다 무조건 다 나옴 (합집합)

- UNION(행을 세로로 쌓기)과 JOIN(열을 가로로 연결하기)은 목적 자체가 다르다는걸 헷갈리면 안된다.

### | ④ 서브쿼리 관련 주의사항

- `NOT IN` + 서브쿼리 조합은 서브쿼리 결과에 **NULL이 하나라도 섞이면 전체 결과가 텅 비어버리는 함정**이 있다. NULL이 있을 가능성이 있다면 `NOT EXISTS`를 쓰는게 안전하다.

- `EXISTS`/`IN`은 결과가 같아 보여도 동작 방식이 다르다. EXISTS는 "존재하는지"만 확인하고 첫 매치에서 바로 끝나서 대량 데이터에 유리하고, IN은 값 목록 전체를 비교한다.

- FROM절 서브쿼리(인라인 뷰)는 **반드시 별칭(AS)을 붙여야 한다.** 안 붙이면 에러가 난다.

- SELECT절 서브쿼리(스칼라 서브쿼리)는 **반드시 값을 딱 하나만 반환해야 한다.** 여러 행이 나오면 "more than one row returned" 오류가 난다. -> 집계함수나 조건으로 결과를 하나로 좁혀야 한다.

### | ⑤ 트랜잭션(TCL) 관련 주의사항

- `COMMIT`을 하지 않으면 그 변경은 아직 확정되지 않은 상태다. 연결이 끊기거나 ROLLBACK되면 전부 사라진다. -> **작업 후 COMMIT을 빼먹지 않았는지 항상 확인하는 습관**이 중요하다.

- 같은 세션 안에서는 COMMIT 전에도 내가 만든 변경이 보이지만, 다른 사용자/연결에서는 COMMIT을 해야만 보인다.

- PostgreSQL은 트랜잭션 도중 오류가 하나라도 나면 그 트랜잭션 전체가 실패 상태가 되어, ROLLBACK 전까지는 다른 명령을 실행할 수 없다.

- **서로 연결된 여러 INSERT/UPDATE 작업(하나가 실패하면 나머지도 의미 없어지는 작업들)은 절대 따로따로 실행하지 말고, 반드시 `BEGIN ~ COMMIT/ROLLBACK`으로 하나의 트랜잭션으로 묶을 것.** 안 그러면 반쪽짜리 데이터가 남고, 이건 사람이 직접 찾아서 지워야 해서 훨씬 번거롭다.

### | ⑥ 🔴 실무에서 하면 진짜 큰일나는 실수 (사고 등급)

#### - WHERE 없이 UPDATE / DELETE 실행하기 — 이번 리스트에서 가장 위험한 실수

- 조건을 빼먹으면 테이블의 모든 행이 한번에 수정되거나 삭제된다. 실무에서 실제로 벌어지는 대형 장애의 단골 원인이다.

```sql
-- 사고 예시 : WHERE를 빼먹으면 전체 행이 삭제된다
DELETE FROM users;  -- 조건이 없음 = 전체 삭제!

UPDATE orders SET status = 'cancelled';  -- 조건이 없음 = 모든 주문이 취소 처리됨!

-- 올바른 방법
DELETE FROM users WHERE id = 123;
UPDATE orders SET status = 'cancelled' WHERE id = 456;
```

- 예방법 1 : UPDATE/DELETE를 실행하기 전에, **같은 조건으로 SELECT를 먼저 실행**해서 "몇건이, 어떤 행이 영향받는지"를 눈으로 확인하는 습관을 들여야 한다.

```sql
-- 삭제하기 전에 먼저 확인
SELECT * FROM users WHERE id = 123;
-- 결과가 내가 원하는 행이 맞다면, 그제서야 DELETE로 바꿔서 실행
DELETE FROM users WHERE id = 123;
```

- 예방법 2 : 트랜잭션(`BEGIN`)으로 감싸서 실행한 뒤, 결과를 SELECT로 다시 확인하고 나서 COMMIT/ROLLBACK을 결정하는 방식도 안전하다.

#### - DROP TABLE, TRUNCATE를 잘못된 DB에 실행하기

- 개발 DB인 줄 알고 실행했는데 알고보니 운영(production) DB에 연결되어 있었다는 사고가 실무에서 실제로 자주 벌어진다.

- DDL은 배운 것처럼 `ROLLBACK`이 불가능해서 복구가 매우 어렵거나 불가능하다.

- 예방법 : 위험한 명령을 실행하기 전에 "지금 내가 어떤 DB/환경에 접속해 있는지"를 반드시 확인하는 습관을 들인다. (운영 DB는 접속 화면 색을 다르게 해두는 등 시각적으로 구분해두는 팀도 많다.)

#### - SQL 인젝션(SQL Injection) — 사용자 입력을 그대로 쿼리에 이어붙이기

- 사용자 입력값을 문자열로 그대로 이어붙여 쿼리를 만들면, 악의적인 사용자가 SQL 구문 자체를 조작해서 인증을 우회하거나 전체 데이터를 유출시킬 수 있다.

```python
# 위험한 코드 (문자열을 그대로 이어붙임)
query = f"SELECT * FROM users WHERE email = '{user_input}'"
# user_input에 " ' OR '1'='1 " 이 들어가면 조건이 항상 참이 되어 전체 회원정보가 유출될 수 있음

# 안전한 코드 (파라미터 바인딩 / SDK 메서드 사용)
supabase.table("users").select("*").eq("email", user_input).execute()
```

- SDK의 `.eq()`, `.insert()` 같은 메서드나 `?`, `%s` 같은 파라미터 바인딩(placeholder)을 쓰면, 입력값이 SQL 구문으로 해석되지 않도록 자동으로 이스케이프 처리해준다. **절대 사용자 입력을 문자열 그대로 SQL에 이어붙이면 안된다.**

#### - 비밀번호 같은 민감정보를 평문으로 저장하기

- `password` 컬럼에 사용자가 입력한 값을 그대로(평문으로) 저장하면, DB가 유출되는 사고가 났을 때 모든 사용자의 비밀번호가 바로 노출된다.

- 반드시 bcrypt 같은 해시 알고리즘으로 암호화해서 저장해야 하고, 원본 비밀번호는 어디에도 남기지 않는다.

#### - ON DELETE CASCADE의 위력을 모르고 사용하기

- `ON DELETE CASCADE`를 걸어두면, 부모 행 하나만 삭제해도 거기에 연결된 자식 데이터 수천~수만건이 한번에 통째로 사라질 수 있다.

- 예를 들어 documents 하나를 지웠는데, 거기 달린 queries·query_logs·feedbacks까지 전부 같이 삭제되는 식이다. 삭제 전에 "이 부모를 지우면 얼마나 많은 자식 데이터가 함께 사라지는지" 미리 조회해서 확인하는 습관이 필요하다.

#### - 인덱스 없이 대용량 테이블을 방치하기

- 실무에서 자주 검색하거나 JOIN에 쓰이는 컬럼(외래키 등)에 인덱스가 없으면, 테이블 데이터가 많아질수록 조회 속도가 기하급수적으로 느려진다.

- 처음 만들 땐 데이터가 적어서 문제를 못 느끼다가, 서비스가 커진 뒤에야 "왜 이렇게 느려졌지?"하고 뒤늦게 알아채는 경우가 많다.

### | ⑦ 🟡 결과가 이상하게 나오는데 원인 찾기 힘든 실수

#### - NULL을 `=`로 비교하기

- `WHERE column = NULL`은 **항상 아무 결과도 반환하지 않는다.** NULL은 "값이 없다"가 아니라 "알 수 없음"이라는 개념이라서, `=`나 `!=`로 비교하는 것 자체가 불가능하다.

- 반드시 `IS NULL` / `IS NOT NULL`을 사용해야 한다.

```sql
-- 잘못된 예 (항상 결과 없음)
SELECT * FROM documents WHERE content = NULL;

-- 올바른 예
SELECT * FROM documents WHERE content IS NULL;
```

#### - BETWEEN의 경계값을 착각하기

- `BETWEEN A AND B`는 A **이상** B **이하**(양쪽 다 포함)인데, 습관적으로 "A 초과 B 미만"이라고 착각하고 쓰는 경우가 많다.

- 특히 날짜 범위를 다룰 때 문제가 잘 생긴다. 예를 들어 `created_at BETWEEN '2026-09-01' AND '2026-09-30'`이라고 쓰면, '2026-09-30' 그 날짜의 자정(00:00:00) 이후 시각은 포함되지 않아서 그 날 발생한 데이터를 놓칠 수 있다.

#### - JOIN 후 중복 행이 생기는걸 못 알아채기 (fan-out 문제)

- 1:N 관계에서 JOIN을 하면, 부모쪽 행이 자식 개수만큼 그대로 중복되어 나온다. 이걸 모르고 그대로 SUM이나 COUNT를 하면 값이 실제보다 부풀려진다.

```sql
-- 위험 예시 : 문서 하나에 질문이 3개 달려있으면, 그 문서 정보가 3번 중복돼서 나온다
SELECT d.title, d.id
FROM documents d
JOIN queries q ON q.document_id = d.id;
-- "문서가 총 몇개야?" 하고 이 결과에 COUNT(*)를 걸면, 실제 문서 수가 아니라
-- (문서 수 x 평균 질문 수)만큼 부풀려진 값이 나온다
```

- 이런 경우 집계를 먼저 인라인 뷰(서브쿼리)로 끝내놓고 나서 JOIN하거나, `COUNT(DISTINCT d.id)`처럼 중복을 제거하고 세야 한다.

#### - 모호한 컬럼명 에러 (ambiguous column)

- 두 테이블에 같은 이름의 컬럼(`id` 등)이 있는데, JOIN에서 별칭 없이 그냥 컬럼명만 쓰면 "column reference is ambiguous"(어느 테이블의 컬럼인지 모르겠다) 에러가 난다.

```sql
-- 에러 발생 (id가 documents에도, queries에도 있음)
SELECT id, title FROM documents JOIN queries ON documents.id = queries.document_id;

-- 올바른 예 : 별칭으로 어느 테이블의 컬럼인지 명확히 지정
SELECT d.id, d.title FROM documents d JOIN queries q ON d.id = q.document_id;
```

#### - 대소문자·공백을 무시하고 문자열을 비교하기

- 'Seoul'과 'seoul'은 DB 설정에 따라 다르지만 기본적으로는 서로 다른 문자열로 취급된다.

- 'Seoul '처럼 뒤에 공백이 붙은 값도 'Seoul'과 다르게 취급되어, 눈으로는 똑같아 보이는데 조회가 안되는 상황이 생길 수 있다.

#### - 타입 자동 변환을 무조건 믿고 비교하기

- 문자열 `'1'`과 숫자 `1`을 비교할 때, DB나 상황에 따라 자동으로 형변환을 해주기도 하고 안 해주기도 한다.

- 이 동작을 믿고 대충 비교하기보다는, 필요하면 `CAST(컬럼 AS 자료형)`으로 명시적으로 타입을 맞춰주는게 안전하다.

#### - 시간대(timezone)를 혼동하기

- `timestamp`(시간대 정보 없음)와 `timestamptz`(시간대 정보 포함)를 헷갈려서 쓰면, 여러 나라 사용자를 다루는 서비스에서 저장된 시각이 실제와 몇시간씩 어긋나는 문제가 생길 수 있다.

### | ⑧ 🟢 사소하지만 은근히 자주 하는 실수

- 세미콜론(`;`)을 빼먹기 : 여러 쿼리를 한번에 실행할 때 어디서 끝나는지 구분이 안돼서 엉뚱한 에러 메시지가 나온다.

- SELECT 목록 마지막 항목 뒤에 콤마(`,`)를 남기거나, 반대로 항목 사이에 콤마를 빼먹기.

- 별칭(alias)을 `a`, `b`, `t1`, `t2`처럼 의미없이 짓기 : 쿼리가 길어지면 나중에 본인도 뭐가 뭔지 못 알아본다. `c`(customers), `o`(orders)처럼 원래 이름을 짐작할 수 있는 별칭을 쓰는게 좋다.

- 쿼리 안에서 대문자/소문자 스타일을 섞어쓰기(`SELECT`, `select`를 한 쿼리 안에서 혼용) : 동작에는 문제 없지만, 팀 전체의 가독성과 일관성이 떨어진다.

- 들여쓰기 없이 한 줄로 쭉 이어서 쓰기 : 쿼리가 조금만 길어져도 어디가 SELECT절이고 어디가 WHERE절인지 한눈에 안 들어와서, 나중에 본인이 디버깅할 때 더 오래 걸린다.

- `ORDER BY` 없이 "당연히 이 순서로 나오겠지"라고 정렬 순서를 기대하기 : 데이터베이스는 ORDER BY가 없으면 결과 순서를 보장하지 않는다. 지금 순서대로 나온다고 해도 우연일 뿐, 나중에 데이터가 늘어나거나 DB 버전이 바뀌면 순서가 달라질 수 있다.

- 조건에 왜 이 값을 썼는지 주석을 안 남기기 : `WHERE status != 3`처럼 매직넘버(3이 무슨 상태인지 알 수 없는 숫자)를 그냥 써두면, 한달 뒤의 본인조차 이게 무슨 조건이었는지 까먹는다. `WHERE status != 3 -- 3 = 취소된 주문 제외`처럼 짧게라도 남겨두는게 좋다.

Q1. 다음 중 SQL을 작성할 때 저지르기 쉬운 실수가 아닌 것은 ?

[ 보기 ]

a. SELECT절에 집계함수가 아닌 열을 쓰면서 GROUP BY에는 빠뜨리는 것

b. NOT IN 서브쿼리에 NULL이 섞여있는지 확인하지 않는 것

c. BEGIN으로 트랜잭션을 시작한 뒤 COMMIT을 실행하는 것

d. 스칼라 서브쿼리가 여러 행을 반환하도록 조건 없이 작성하는 것

A. c.

-> BEGIN으로 시작한 트랜잭션을 정상적으로 COMMIT하는 것은 올바른 사용법이지, 실수가 아니다. 나머지 보기는 모두 이번 주에 배운 대표적인 SQL 작성 실수 사례다.

Q2. `WHERE` 절과 `HAVING` 절을 혼동해서, 집계 결과(AVG, COUNT 등)에 조건을 걸고 싶은데 WHERE를 쓰면 어떻게 되나요 ?

A. 에러가 발생한다. WHERE절은 GROUP BY보다 먼저 실행되기 때문에, 아직 계산되지 않은 집계 결과를 조건으로 사용할 수 없다.

-> 집계된 값을 기준으로 필터링하고 싶을 때는 반드시 GROUP BY 뒤에 오는 HAVING을 사용해야 한다.

---

Q3. `NOT IN (SELECT customer_id FROM orders)`처럼 작성했는데 orders.customer_id에 NULL 값이 하나라도 있으면 어떤 문제가 생기나요 ?

A. 전체 결과가 아예 0건(빈 결과)으로 나올 수 있다.

-> NOT IN은 비교 대상 목록에 NULL이 섞이면 비교 자체가 알 수 없는(UNKNOWN) 상태가 되어 결과가 통째로 비어버리는 함정이 있다. 이런 상황에서는 NOT EXISTS를 쓰는게 안전하다.

---

Q4. FROM절 서브쿼리(인라인 뷰)를 작성할 때, 다음 중 반드시 지켜야 하는 규칙은 무엇인가요 ?

A. 서브쿼리 결과에 반드시 별칭(alias)을 붙여야 한다.

-> 인라인 뷰는 마치 하나의 임시 테이블처럼 취급되기 때문에, 이름(별칭)이 없으면 외부 쿼리에서 그 결과를 참조할 방법이 없어 오류가 발생한다.

---

Q5. 서로 연결된 두 개의 INSERT 작업 중 하나만 실행하고 COMMIT을 하지 않은 채로 트랜잭션 창을 닫아버렸다면, 그 데이터는 어떻게 되나요 ?

A. 저장되지 않고 사라진다.

-> COMMIT 전의 변경 사항은 아직 확정되지 않은 임시 상태이기 때문에, 연결이 끊기면 트랜잭션 시작(BEGIN) 이전 상태로 되돌아가며 그 변경은 사라진다. 데이터를 남기려면 반드시 COMMIT을 실행해야 한다.

---

Q6. 실무에서 발생하는 SQL 사고 중 가장 위험한 유형으로 꼽히는 것은 무엇이며, 그 이유는 ?

A. WHERE절 없이 UPDATE나 DELETE를 실행하는 것

-> 조건절을 빼먹으면 테이블의 모든 행이 한번에 수정되거나 삭제되는데, 특히 DELETE는 되돌리기 어렵다. 실행 전에 같은 조건으로 SELECT를 먼저 돌려 영향받는 행을 눈으로 확인하는 습관이 이런 사고를 막는 가장 확실한 방법이다.

Q7. 다음 코드처럼 사용자가 입력한 값을 문자열에 그대로 이어붙여 쿼리를 만들면 어떤 보안 문제가 발생할 수 있나요 ?

```python
query = f"SELECT * FROM users WHERE email = '{user_input}'"
```

A. SQL 인젝션(SQL Injection) — 사용자가 `' OR '1'='1` 같은 값을 입력하면 조건이 항상 참이 되도록 쿼리 구조 자체를 조작해서, 인증을 우회하거나 전체 데이터를 유출시킬 수 있다.

-> 이를 막으려면 문자열을 직접 이어붙이지 말고, SDK의 `.eq()` 같은 메서드나 파라미터 바인딩(placeholder)을 사용해서 사용자 입력이 SQL 구문으로 해석되지 않도록 해야 한다.
