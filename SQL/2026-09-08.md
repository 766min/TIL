## 공부한 내용 | SQL - 서브쿼리 (WHERE절, FROM절, SELECT절)

- SQL을 처음 배울 때는 하나의 테이블에서 단순하게 데이터를 가져오는 법을 배운다. 그런데 실제 데이터 분석 현장에서는 "평균보다 높은 주문만 보여줘", "특정 고객이 구매한 상품 목록에 없는 상품만 골라줘"처럼 복잡한 조건이 필요하다.

- 이런 상황에서 쿼리 안에 또 다른 쿼리를 넣는 서브쿼리(Subquery)가 강력한 해결책이 된다.

### | 서브쿼리란 ?

- 서브쿼리는 하나의 SQL 쿼리 안에 포함된 또 다른 SELECT 쿼리다.

- 바깥쪽 쿼리를 외부 쿼리(Outer Query), 안쪽 쿼리를 서브쿼리(Inner Query)라고 부른다.

- 서브쿼리는 괄호 `( )`로 감싸며, 외부 쿼리가 필요로 하는 값을 미리 계산해서 전달하는 역할을 한다.

- 마치 수학에서 `f(g(x))`처럼, 안쪽 함수(서브쿼리)의 결과가 바깥쪽 함수(외부 쿼리)의 입력이 되는 구조다.

- 서브쿼리를 꼭 써야할까 ? JOIN으로는 안될까 ?

  - JOIN으로도 비슷한 결과를 낼 수 있는 경우가 많다. 하지만 서브쿼리는 "조건을 먼저 계산한 뒤 적용"하는 방식이라, 코드 읽기가 직관적이고 특정 상황에서는 더 간결하다.

### | 위치에 따른 서브쿼리 종류

- 서브쿼리는 SQL 구문 안에서 어디에 위치하느냐에 따라 역할과 특성이 달라진다.

| 명칭 | 위치 | 특징 |
| --- | --- | --- |
| WHERE절 서브쿼리 | WHERE절 | 조건값을 동적으로 계산 |
| 인라인 뷰(Inline View) | FROM절 | 가상의 임시 테이블처럼 사용 |
| 스칼라 서브쿼리(Scalar Subquery) | SELECT절 | 단일 값(하나의 열, 하나의 행)을 반환 |

### | WHERE절 서브쿼리

- WHERE절 서브쿼리는 조건에 사용할 값을 동적으로 계산할 때 쓴다. 예를 들어 "평균 주문 금액보다 많이 주문한 고객"을 찾으려면, 먼저 평균값을 구해야 한다.

```sql
-- 평균 주문 금액보다 큰 주문만 조회
SELECT order_id, customer_id, amount
FROM orders
WHERE amount > (
    SELECT AVG(amount)
    FROM orders
);
```

- 여기서 `(SELECT AVG(amount) FROM orders)`가 서브쿼리다. 먼저 실행되어 평균값을 계산한 뒤, 외부 쿼리의 WHERE 조건에 그 값이 들어간다.

- 서브쿼리는 외부 쿼리보다 먼저 실행될까 ?

  - 그렇다. WHERE절 서브쿼리는 외부 쿼리가 실행되기 전에 먼저 실행된다. 그 결과값을 외부 쿼리의 조건에 전달하는 방식이다. PostgreSQL의 실행계획(`EXPLAIN`)으로 이 순서를 직접 확인할 수도 있다.

### | IN / NOT IN + 서브쿼리

- 서브쿼리가 여러 행을 반환할 때는 `=` 대신 `IN`을 사용한다. IN은 서브쿼리가 반환한 값 목록 중 하나라도 일치하면 조건을 만족한다.

```sql
-- 주문을 한 번 이상 한 고객만 조회
SELECT customer_id, name
FROM customers
WHERE customer_id IN (
    SELECT DISTINCT customer_id
    FROM orders
);

-- 한 번도 주문하지 않은 고객 조회
SELECT customer_id, name
FROM customers
WHERE customer_id NOT IN (
    SELECT DISTINCT customer_id
    FROM orders
);
```

### | SQL 작성할 때 주의할 점 ① : NOT IN과 NULL의 함정

- `NOT IN` 사용시 서브쿼리 결과에 NULL이 포함되면 전체 결과가 빈 값으로 나올 수 있다.

- 이런 경우 `NOT EXISTS`를 사용하는게 더 안전하다. 서브쿼리의 열에 NULL이 없는지 미리 확인하는 습관을 갖는게 좋다.

### | EXISTS / NOT EXISTS

- `EXISTS`는 서브쿼리의 결과가 한 행이라도 존재하면 TRUE를 반환한다. 값 자체보다 "데이터가 존재하는지 여부"만 판단할 때 사용한다.

```sql
-- 주문 이력이 있는 고객만 조회
SELECT customer_id, name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

-- 주문 이력이 없는 고객 조회 (NOT EXISTS)
SELECT customer_id, name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

### | SQL 작성할 때 주의할 점 ② : EXISTS와 IN, 결과가 같아도 동작 방식은 다르다

- 결과가 같을 때도 많지만 동작 방식이 다르다.

- IN은 서브쿼리의 결과 목록 전체를 가져온 뒤 비교하고, EXISTS는 조건을 만족하는 행이 하나라도 있으면 바로 TRUE를 반환한다.

- 데이터가 많을 때 EXISTS가 더 효율적인 경우가 많고, NULL 처리에서도 EXISTS가 더 예측 가능하게 동작한다.

| 구분 | EXISTS | IN |
| --- | --- | --- |
| 비교 방식 | 존재 여부 확인 | 값 목록 비교 |
| NULL 처리 | NULL에 영향 없음 | NOT IN 사용시, NULL이 포함되면 결과가 비어있을 수 있음 |
| 성능 | 대량 데이터에 유리 | 소량 데이터에 유리 |

### | FROM절 서브쿼리 : 인라인 뷰

- FROM절에 위치한 서브쿼리를 인라인 뷰라고 부른다. 서브쿼리의 결과가 마치 하나의 테이블처럼 동작하기 때문에 붙여진 이름이다. 데이터베이스에 저장되지 않는 임시 테이블이라고 생각하면 이해하기 쉽다.

```sql
-- 고객별 총 주문 금액을 먼저 계산한 뒤, 100만원 이상인 고객만 조회
SELECT customer_id, total_amount
FROM (
    SELECT customer_id, SUM(amount) AS total_amount
    FROM orders
    GROUP BY customer_id
) AS customer_totals
WHERE total_amount >= 1000000;
```

- 여기서 `( ... ) AS customer_totals` 부분이 인라인 뷰다. GROUP BY로 집계한 결과를 외부 쿼리에서 다시 필터링할 수 있다.

- HAVING을 쓰면 되는거 아닌가 ? 왜 굳이 인라인 뷰를 쓸까 ?

  - HAVING으로 해결할 수 있는 경우도 많다. 하지만 인라인 뷰는 집계 결과를 다시 JOIN하거나, 집계된 값을 기준으로 추가 계산을 해야 할 때 더 유연하다. 예를 들어 집계 결과를 다른 테이블과 JOIN해야 한다면 인라인 뷰 없이는 구현이 어렵다.

### | SQL 작성할 때 주의할 점 ③ : 인라인 뷰의 규칙

- 반드시 별칭(alias)을 붙여야 한다. (`AS 별칭명`)

- 여러 열을 포함할 수 있다.

- 외부 쿼리에서 인라인 뷰의 열을 자유롭게 참조할 수 있다.

### | SELECT절 서브쿼리 : 스칼라 서브쿼리

- SELECT절에 위치한 서브쿼리를 스칼라 서브쿼리라고 한다. '스칼라(Scalar)'는 수학에서 단일 값을 의미하는데, 이 서브쿼리는 반드시 하나의 행, 하나의 열만 반환해야 한다.

- 각 행마다 계산된 값을 새 열로 추가할 때 유용하다.

```sql
-- 각 고객의 이름과 함께 전체 평균 주문 금액을 나란히 조회
SELECT
    customer_id,
    name,
    (SELECT AVG(amount) FROM orders) AS avg_order_amount
FROM customers;
```

- 상관 서브쿼리(Correlated Subquery) : 외부 쿼리의 각 행 정보를 서브쿼리 안에서 참조하는 방식

```sql
-- 각 주문과 함께 해당 고객의 총 주문 횟수를 열로 추가
SELECT
    o.order_id,
    o.customer_id,
    o.amount,
    (
        SELECT COUNT(*)
        FROM orders o2
        WHERE o2.customer_id = o.customer_id
    ) AS total_orders_by_customer
FROM orders o;
```
  - 위 쿼리에서 서브쿼리 안의 `o2.customer_id = o.customer_id`처럼 바깥 쿼리의 값(`o.customer_id`)을 안쪽 서브쿼리가 매 행마다 참조하기 때문에 상관 서브쿼리라고 부른다.

### | SQL 작성할 때 주의할 점 ④ : 스칼라 서브쿼리는 반드시 값 하나만 반환해야 한다

- 스칼라 서브쿼리가 여러 행을 반환하면 오류가 발생한다.

- PostgreSQL에서는 "more than one row returned by a subquery used as an expression" 오류가 나온다.

- 스칼라 서브쿼리를 작성할 때는 항상 단일 값이 반환되도록 WHERE 조건이나 집계함수(AVG, COUNT, SUM 등)를 사용해야 한다.

### | 서브쿼리 vs JOIN 비교

- 서브쿼리와 JOIN은 서로 대체할 수 있는 경우가 많다. 어떤 방법을 선택할지는 가독성, 성능, 상황에 따라 달라진다.

| 비교 항목 | 서브쿼리 | JOIN |
| --- | --- | --- |
| 가독성 | 조건/계산 로직이 명확하게 분리됨 | 여러 테이블 관계를 한눈에 파악 가능 |
| 반환 구조 | 외부 쿼리 기준의 열만 선택 가능 | 여러 테이블의 열을 자유롭게 선택 가능 |
| 성능 | 단순 조건 필터링에 유리 | 대용량 데이터 JOIN에 최적화된 경우 많음 |
| NULL 처리 | EXISTS 사용시 안전 | OUTER JOIN으로 NULL 제어 가능 |
| 적합한 상황 | 집계 결과를 조건으로 사용, 존재 여부 확인 | 두 테이블의 열을 함께 조회, 복잡한 관계 표현 |

```sql
-- 서브쿼리 방식: 주문이 있는 고객 조회
SELECT customer_id, name
FROM customers
WHERE customer_id IN (SELECT DISTINCT customer_id FROM orders);

-- JOIN 방식: 같은 결과
SELECT DISTINCT c.customer_id, c.name
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id;
```

- 이 경우 두 방식의 결과는 같다. 소규모 데이터라면 가독성이 좋은 방식을 선택하고, 대규모 데이터라면 `EXPLAIN ANALYZE`로 실행계획을 비교해서 선택하는게 좋다.

### | 실습 문제

1. products 테이블에서 list_price가 전체 상품의 평균 가격보다 큰 상품을 조회하세요.
```sql
SELECT product_id, product_name, list_price
FROM products
WHERE list_price > (SELECT AVG(list_price) FROM products);
```

2. products 테이블에서 stocks 테이블에 해당 상품의 재고 기록이 존재하는 상품만 조회하세요.
```sql
SELECT p.product_id, p.product_name
FROM products p
WHERE EXISTS (
    SELECT 1 FROM stocks s WHERE s.product_id = p.product_id
);
```

3. stocks 테이블에서 매장별 재고 합계를 인라인 뷰로 구하고, 그 결과가 매장 평균 재고 이상인 매장만 조회하세요.
```sql
SELECT store_id, total_stock
FROM (
    SELECT store_id, SUM(quantity) AS total_stock
    FROM stocks
    GROUP BY store_id
) AS store_stock
WHERE total_stock >= (
    SELECT AVG(total_stock)
    FROM (
        SELECT store_id, SUM(quantity) AS total_stock
        FROM stocks
        GROUP BY store_id
    ) AS avg_sub
);
```

4. customers 테이블에서 각 고객마다 orders 테이블에서 본인의 주문 건수를 세는 서브쿼리를 추가해 조회하세요.
```sql
SELECT c.customer_id, c.first_name, c.last_name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS order_count
FROM customers c;
```

### | 이번 강의 핵심 정리

1. 서브쿼리는 SQL 쿼리 안에 포함된 또 다른 SELECT 쿼리로, 괄호 `( )`로 감싼다.
2. 위치에 따라 WHERE절, FROM절(인라인 뷰), SELECT절(스칼라 서브쿼리)로 구분된다.
3. WHERE절 서브쿼리는 조건값을 동적으로 계산할 때 사용하며, 외부 쿼리보다 먼저 실행된다.
4. IN은 여러 값과 비교, NOT IN은 포함되지 않는 행 조회, EXISTS는 존재 여부 확인에 사용한다. NULL이 포함된 경우 NOT IN보다 NOT EXISTS가 더 안전하다.
5. 인라인 뷰는 반드시 별칭을 붙여야 하고, 스칼라 서브쿼리는 반드시 하나의 값만 반환해야 한다.
6. 서브쿼리와 JOIN은 많은 경우 서로 대체 가능하며, 가독성·성능·상황에 따라 적절한 방법을 선택한다.

### | 데일리 퀘스트 |

Q1. 다음 쿼리에서 서브쿼리에 해당하는 부분은 어디인가요 ?

```sql
SELECT order_id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);
```

A. `(SELECT AVG(amount) FROM orders)`

-> 괄호로 감싸인 이 부분이 외부 쿼리보다 먼저 실행되어 평균값을 계산한 뒤, 그 결과를 외부 쿼리의 WHERE 조건에 전달하는 서브쿼리다.

---

Q2. 한 번도 주문하지 않은 고객을 찾을 때, orders 테이블의 customer_id 열에 NULL 값이 섞여 있다면 `NOT IN` 대신 어떤 방법을 쓰는게 더 안전한가요 ?

A. NOT EXISTS

-> NOT IN은 서브쿼리 결과에 NULL이 하나라도 포함되면 비교 자체가 불명확해져서 전체 결과가 빈 값으로 나올 수 있는 함정이 있다. NOT EXISTS는 NULL에 영향을 받지 않고 예측 가능하게 동작하므로 더 안전하다.

---

Q3. FROM절에 있는 서브쿼리(인라인 뷰)를 작성할 때 반드시 지켜야 하는 규칙은 무엇인가요 ?

A. 반드시 별칭(alias, AS 별칭명)을 붙여야 한다.

-> 인라인 뷰는 결과가 마치 하나의 임시 테이블처럼 동작하기 때문에, 다른 테이블처럼 이름(별칭)을 붙여줘야 외부 쿼리에서 그 열들을 참조할 수 있다.

---

Q4. 다음 스칼라 서브쿼리를 실행했을 때 PostgreSQL에서 오류가 발생하는 이유로 가장 적절한 것은 ?

```sql
SELECT customer_id,
       (SELECT amount FROM orders WHERE customer_id = c.customer_id) AS last_amount
FROM customers c;
```

A. 한 고객이 여러 건의 주문을 가지고 있을 경우, 서브쿼리가 여러 행(amount 값 여러 개)을 반환하게 되어 스칼라 서브쿼리의 '단일 값 반환' 규칙을 어기기 때문

-> 스칼라 서브쿼리는 반드시 하나의 행, 하나의 열만 반환해야 하는데, 조건 없이 여러 주문이 걸리면 여러 값이 반환되어 "more than one row returned" 오류가 발생한다. 이걸 방지하려면 집계함수(예: MAX, AVG)를 쓰거나 조건을 추가해서 값을 하나로 좁혀야 한다.

---

Q5. 서브쿼리와 JOIN이 같은 결과를 낼 수 있는 상황에서, 어떤 기준으로 둘 중 하나를 선택하는게 좋은가요 ?

A. 가독성, 성능, 데이터 규모를 기준으로 선택한다. 소규모 데이터라면 가독성이 좋은 방식을, 대규모 데이터라면 EXPLAIN ANALYZE로 실행계획을 비교해서 더 효율적인 방식을 선택한다.

-> 서브쿼리는 조건/계산 로직이 분리되어 읽기 편하고, JOIN은 여러 테이블의 관계와 열을 한번에 다룰 수 있어 유리한 상황이 다르므로, 정답이 하나로 정해져 있지 않고 상황에 맞게 판단해야 한다.

Q1. 서브쿼리의 위치에 따른 종류와 명칭의 연결이 옳지 않은 것은 ?

[ 보기 ]

a. WHERE절 - WHERE절 서브쿼리

b. FROM절 - 인라인 뷰

c. SELECT절 - 스칼라 서브쿼리

d. GROUP BY절 - 그룹 서브쿼리

내 제출 답안 : d. (정답 ✅)

-> 서브쿼리 위치는 WHERE절, FROM절(인라인 뷰), SELECT절(스칼라 서브쿼리) 세 가지로만 구분한다. "GROUP BY절 서브쿼리"라는 명칭은 존재하지 않는다.

Q2. 서브쿼리 결과에 NULL이 포함되어 있을 때 결과가 예기치 않게 빈 값으로 나올 수 있어 사용을 피해야 하는 연산자는 무엇인가요 ? (대신 사용을 권장하는 것도 함께 고려)

내 제출 답안 : NOT IN (정답 ✅)

-> NOT IN은 서브쿼리 결과에 NULL이 포함되면 전체 결과가 빈 값으로 나올 수 있어 주의가 필요하다. 이런 경우 NULL에 영향받지 않는 NOT EXISTS를 사용하는 것이 더 안전하다.

---

Q3. 다음 중 스칼라 서브쿼리에 대한 설명으로 옳은 것은 ?

[ 보기 ]

a. 여러 행과 여러 열을 자유롭게 반환할 수 있다

b. FROM절에 위치하며 반드시 별칭을 붙여야 한다

c. SELECT절에 위치하며 반드시 하나의 행, 하나의 열만 반환해야 한다

d. IN 연산자와 함께 사용하여 여러 값을 비교할 때 사용한다

내 제출 답안 : c. (정답 ✅)

-> 스칼라 서브쿼리는 SELECT절에 위치하며 단일 값(하나의 행, 하나의 열)만 반환해야 한다. 여러 행이 반환되면 오류가 발생하며, 별칭이 필요한 것은 인라인 뷰(FROM절 서브쿼리)의 특징이다.

Q4. 외부 쿼리의 각 행 정보를 서브쿼리 안에서 참조하여, 외부 쿼리와 서로 연관되어 실행되는 서브쿼리를 무엇이라고 부르나요 ?

내 제출 답안 : JOIN (오답 ❌)

[ 정답 ] 상관 서브쿼리

-> 외부 쿼리의 행 정보(예: o.customer_id)를 서브쿼리 내부에서 참조하는 방식을 상관 서브쿼리(Correlated Subquery)라고 한다. 각 주문마다 해당 고객의 총 주문 횟수를 구하는 예시가 대표적이다. -> JOIN과 헷갈리기 쉬운데, JOIN은 두 표를 옆으로 붙이는 것이고 상관 서브쿼리는 "서브쿼리 안에서 바깥 쿼리 값을 매 행마다 다시 참조"하는 것이라 동작 방식이 다르다.

Q5. IN과 EXISTS의 차이에 대한 설명으로 가장 적절한 것은 ?

[ 보기 ]

a. IN은 존재 여부만 확인하고, EXISTS는 값 목록 전체를 비교한다

b. IN은 대량 데이터에서 항상 EXISTS보다 빠르다

c. EXISTS는 조건을 만족하는 행이 하나라도 있으면 바로 TRUE를 반환하며 NULL에 영향받지 않는다

d. IN과 EXISTS는 문법 구조만 다를 뿐 내부 동작 방식은 완전히 동일하다

내 제출 답안 : c. (정답 ✅)

-> EXISTS는 조건을 만족하는 행이 하나라도 존재하면 즉시 TRUE를 반환하고 NULL의 영향을 받지 않는다. 반면 IN은 서브쿼리의 값 목록 전체를 가져와 비교하는 방식이며, 대량 데이터에서는 오히려 EXISTS가 더 유리한 경우가 많다.
