# PART 1. 함수(Function) vs 프로시저(Procedure), 스냅샷 패턴, 대용량 배치 처리

- 이 파트는 09-11 실제 강의 퀴즈에 나온 내용인데, 이 파일의 실습 코드들과는 다른 주제라서 따로 뽑아 앞쪽에 정리했다. 온라인 쇼핑몰(주문·결제) 시나리오를 예시로 최대한 쉽게 풀어본다.

## | 함수(Function)와 프로시저(Procedure) — 둘 다 "미리 저장해둔 SQL 코드 뭉치"인데 뭐가 다를까

- 둘 다 "자주 쓰는 SQL 로직을 이름 붙여서 DB 안에 저장해두고, 나중에 이름만 불러서 재사용하는 것"이라는 점은 똑같다. 09-12 노트에서 이미 만들어봤던 `ask_and_log` 함수가 바로 이 '함수'의 예시였다.

- 근데 **"언제, 왜 쓰느냐"**가 서로 다르다.

| 구분 | 함수(Function) | 프로시저(Procedure) |
| --- | --- | --- |
| 호출 방법 | `SELECT 함수명(...);` | `CALL 프로시저명(...);` |
| 값을 꼭 돌려줘야 하나 | 그렇다 (`RETURNS 자료형`으로 반드시 명시) | 아니다 (기본적으로 반환 없음) |
| 트랜잭션 처리 | 호출하면 자동으로 하나의 트랜잭션으로 통째로 묶임. 중간에 스스로 COMMIT을 할 수 없다 | 내부에서 직접 COMMIT/ROLLBACK을 실행할 수 있다. 즉 작업을 몇 단계로 쪼개서 중간중간 확정할 수 있다 |
| 실무에서 주로 쓰는 곳 | 프론트엔드 앱이 실시간으로 호출하는 짧은 로직 (주문 생성, 결제 처리 등) | 사람 없이 서버가 혼자 돌리는 대용량 배치 작업 (야간 정산, 로그 정리 등) |

- 왜 이렇게 나눠져 있을까 ?

  - 함수는 "하나의 완결된 작업을 한 방에 안전하게 끝내야 하는 상황"(예: 주문 하나 저장하기)에 맞는 구조라서, 트랜잭션이 자동으로 통째로 묶이는게 오히려 안전하다.

  - 반면 프로시저는 "데이터가 너무 많아서 한 번에 다 처리하면 문제가 생기는 상황"(예: 로그 5만건 정리하기)에 맞는 구조라서, 중간중간 COMMIT을 직접 찍어가며 작업을 나눠서 처리할 수 있게 만들어져 있다.

```sql
-- 함수 예시 : 호출하면 SELECT로 값을 받아온다
CREATE FUNCTION add_numbers(a INT, b INT)
RETURNS INT AS $$
BEGIN
  RETURN a + b;
END;
$$ LANGUAGE plpgsql;

SELECT add_numbers(3, 5);  -- 결과: 8

-- 프로시저 예시 : CALL로 실행하고, 보통 값을 안 돌려준다
CREATE PROCEDURE say_hello()
AS $$
BEGIN
  RAISE NOTICE '안녕!';
END;
$$ LANGUAGE plpgsql;

CALL say_hello();
```

## | 함수로 묶으면 왜 "유령 주문"이 안 생길까

- 온라인 쇼핑몰에서 주문 하나가 들어오면 보통 두 단계로 저장된다 : ① `orders`(주문 기본정보) 저장 → ② `order_items`(주문한 상품 목록) 저장.

- 만약 이 두 단계를 **각각 따로** 실행하다가, ①은 성공했는데 ②에서 네트워크 문제로 실패하면 어떻게 될까 ?

  - `orders`에는 "이 사람이 주문했다"는 기록이 남아있는데, `order_items`에는 "뭘 주문했는지"가 하나도 없는 **반쪽짜리 주문(유령 주문)**이 생겨버린다. (09-09 노트에서 배운 "트랜잭션 없을 때 생기는 문제"와 완전히 같은 상황)

- 근데 이 두 단계를 **하나의 함수 안에 넣어서** 호출하면, 함수 전체가 자동으로 하나의 트랜잭션으로 묶이기 때문에, 중간에(②에서) 오류가 나면 이미 저장됐던 ①(`orders`)까지 **자동으로 통째로 취소(ROLLBACK)**된다.

```sql
CREATE FUNCTION create_order(p_user_id INT, p_items JSON)
RETURNS INT AS $$
DECLARE
  v_order_id INT;
BEGIN
  -- 1) 주문 기본정보 저장
  INSERT INTO orders (user_id) VALUES (p_user_id) RETURNING id INTO v_order_id;

  -- 2) 주문 상품 목록 저장 (여기서 오류가 나면?)
  INSERT INTO order_items (order_id, ...) VALUES (v_order_id, ...);

  RETURN v_order_id;
  -- 2단계에서 오류가 나면, 이미 실행된 1단계 INSERT까지 자동으로 롤백된다.
END;
$$ LANGUAGE plpgsql;
```

- 즉 "함수로 묶어서 처리한다" = "①②를 따로따로 실행하지 않고, 한 덩어리(트랜잭션)로 실행해서 반쪽짜리 데이터가 생기지 않게 한다"는 뜻이다.

## | 스냅샷 패턴(Snapshot Pattern) — "그때 그 가격 그대로" 사진 찍듯 저장해두기

- 상황을 생각해보자. `products`(상품) 표에 "티셔츠 - 15,000원"이라고 저장되어 있고, 홍길동이 오늘 이 티셔츠를 주문했다.

- 근데 한달 뒤에 사장님이 가격을 20,000원으로 올렸다면? 홍길동의 "과거 주문 영수증"에 찍히는 가격도 덩달아 20,000원으로 바뀌어버리면 큰일난다. **홍길동은 분명 15,000원에 샀는데, 나중에 조회하면 20,000원짜리를 산 것처럼 보이는 것.**

- 왜 이런 문제가 생기냐면, `order_items`(주문한 상품 목록) 표에 상품의 **가격을 직접 저장하지 않고, `products` 표의 `product_id`(상품 번호)만 저장**해뒀기 때문이다. 그러면 나중에 `products.price`가 바뀔 때마다, 과거 주문들까지 덩달아 다 바뀐 것처럼 보이게 된다.

```sql
-- 잘못된 예 : 가격을 저장 안 하고, 상품 번호만 저장 (나중에 가격이 바뀌면 과거 기록도 왜곡됨)
CREATE TABLE order_items (
  id INT PRIMARY KEY,
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),
  quantity INT
);
```

- **해결법 : 주문이 들어온 그 순간의 상품명·가격을 통째로 복사해서, `order_items`에 따로 저장해둔다.** 마치 그 순간을 "사진(스냅샷)"으로 찍어서 남겨두는 것과 같다고 해서 스냅샷 패턴이라고 부른다.

```sql
-- 올바른 예 : 주문 시점의 상품명·가격을 그대로 복사해서 저장(스냅샷)
CREATE TABLE order_items (
  id INT PRIMARY KEY,
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),  -- 어떤 상품인지 연결은 계속 해둠
  product_name VARCHAR(100),               -- 주문 당시의 상품명을 복사
  price_at_order DECIMAL(10,2),            -- 주문 당시의 가격을 복사
  quantity INT
);
```

- 이렇게 하면 나중에 `products.price`가 20,000원으로 바뀌어도, `order_items.price_at_order`에는 그때 그 값(15,000원)이 그대로 남아있어서 과거 영수증이 절대 왜곡되지 않는다.

## | 대용량 데이터를 한 번에 처리하면 안되는 이유 — 락(Lock)

- `service_logs`라는 표에 로그가 5만건 쌓여있고, 이걸 전부 "정리完료" 상태로 한번에 UPDATE 하려고 한다.

```sql
-- 위험한 예 : 5만건을 한 방에 UPDATE
UPDATE service_logs SET archived = true WHERE created_at < now() - interval '1 year';
```

- **락(Lock)이란** : "지금 이 행(row)은 누가 수정 중이니, 다른 사람은 이 행이 끝날 때까지 손대지 마"라고 DB가 잠가두는 것. UPDATE문이 실행되는 동안, 그 UPDATE가 건드리는 행들은 다른 사용자가 동시에 수정할 수 없게 잠긴다.

- 그런데 5만건을 한 번의 UPDATE로 처리하면, **그 UPDATE가 끝날 때까지(몇 초~몇 분) 5만개 행이 전부 잠겨있는 상태**가 된다. 그 사이에 다른 사용자가 그 로그들 중 하나를 조회하거나 수정하려고 하면, UPDATE가 끝날 때까지 그냥 멈춰서(Hang) 기다려야 한다.

- **해결법 : 한번에 다 하지 않고, 조금씩 나눠서 처리하고 그때그때 COMMIT으로 확정(=락 해제)한다.**

```sql
CREATE PROCEDURE batch_archive_logs()
AS $$
DECLARE
  v_rows_affected INT;
BEGIN
  LOOP
    -- 한 번에 5000건만 업데이트
    UPDATE service_logs
    SET archived = true
    WHERE archived = false
    LIMIT 5000;

    -- 방금 UPDATE가 몇 건에 영향을 줬는지 확인
    GET DIAGNOSTICS v_rows_affected = ROW_COUNT;

    COMMIT;  -- 여기서 확정! 지금까지 잠겨있던 5000건의 락이 풀린다

    -- 더 이상 업데이트할 행이 없으면 반복 종료
    EXIT WHEN v_rows_affected = 0;
  END LOOP;
END;
$$ LANGUAGE plpgsql;

CALL batch_archive_logs();
```

- `LOOP ... END LOOP` : "안에 있는 내용을 반복해서 계속 실행해라"는 뜻 (프로그래밍의 반복문과 같음)
- 5000건씩 처리하고 바로 `COMMIT`을 찍기 때문에, 그 5000건에 대한 락은 금방 풀리고, 다음 5000건으로 넘어간다. 그 사이사이에 다른 사용자들도 정상적으로 작업할 수 있는 틈이 생긴다.
- 이게 가능한 이유가 바로 위에서 배운 **"프로시저는 내부에서 직접 COMMIT을 실행할 수 있다"**는 특징 때문이다. (함수는 이게 안 됨 — 그래서 이런 배치 작업엔 프로시저를 쓴다)

## | GET DIAGNOSTICS — "방금 그 SQL이 몇 줄을 건드렸지?" 물어보기

```sql
UPDATE service_logs SET archived = true WHERE archived = false LIMIT 5000;
GET DIAGNOSTICS v_rows_affected = ROW_COUNT;
```

- `GET DIAGNOSTICS 변수명 = ROW_COUNT;` : "바로 직전에 실행한 SQL 문장이 몇 개의 행(row)에 영향을 줬는지 숫자로 알려줘서, 그 값을 변수명 상자에 담아둬라"는 뜻
- `ROW_COUNT`는 PL/pgSQL이 자동으로 기억해두는 값으로, 사람이 직접 세지 않아도 "방금 UPDATE/INSERT/DELETE가 몇 줄을 바꿨는지"를 바로 알려준다.
- 왜 필요하냐면, 위 배치처리 예시처럼 **"이번에 업데이트할 행이 0개면(더 이상 처리할 로그가 없으면) 반복을 멈춰라"**는 조건을 만들 때, "방금 몇 건 처리했는지"를 알아야 판단할 수 있기 때문이다. (`EXIT WHEN v_rows_affected = 0;`)

# PART 2. SQL 교안(1장~3장) 실습 코드 하나하나 뜯어보기

## | 1장 : SQL 기초 ~ 테이블 생성

```sql
CREATE TABLE 테이블이름 (
  컬럼명 자료형 제약조건, ...
);
```
- `CREATE TABLE` : "새 표를 만들어라"라는 명령어 두 단어
- 괄호 안에는 "이 표 안에 어떤 칸(컬럼)들이 있을지"를 콤마로 구분해서 하나씩 적는다
- 각 컬럼은 `컬럼명 자료형 제약조건` 순서로 적는다 (이름 → 어떤 종류의 값인지 → 지켜야 할 규칙)

```sql
ALTER TABLE 테이블명 ADD COLUMN 컬럼명 자료형;
```
- `ALTER TABLE` : "이미 있는 표를 수정하겠다"
- `ADD COLUMN` : "칸(컬럼)을 하나 추가하겠다"
- 뒤에 그 컬럼의 이름과 자료형을 적어줌

```sql
INSERT INTO 테이블명 (컬럼명, ...) VALUES (값1, 값2, ...);
```
- `INSERT INTO 테이블명 (컬럼명, ...)` : "이 표의, 이 컬럼들에"
- `VALUES (값1, 값2, ...)` : "이 값들을 순서대로 하나씩 채워서 새 행을 넣어라" (컬럼 나열 순서와 값 나열 순서가 서로 짝지어짐)

## | 2장 1강 : 데이터 조회하기

```sql
SELECT product_id, product_name, list_price
FROM products
WHERE list_price BETWEEN 500 AND 1000;
```
- `SELECT product_id, product_name, list_price` : "이 3개 열만 보여줘"
- `FROM products` : "products 표에서"
- `WHERE list_price BETWEEN 500 AND 1000;` : "근데 list_price 값이 500 이상 1000 이하인 것만" (BETWEEN은 시작값과 끝값을 **둘 다 포함**한다)

```sql
SELECT order_id, product_id, list_price,
       CASE WHEN list_price < 100 THEN '저가'
            WHEN list_price < 500 THEN '중가'
            ELSE '고가'
       END AS price_grade
FROM order_items;
```
- `CASE WHEN list_price < 100 THEN '저가'` : "만약 list_price가 100보다 작으면 '저가'라고 표시해라"
- `WHEN list_price < 500 THEN '중가'` : "(위 조건이 아니면서) 500보다 작으면 '중가'"
- `ELSE '고가'` : "위 조건 어디에도 안 걸리면 '고가'"
- `END AS price_grade` : "여기까지가 이 조건문의 끝이고, 이렇게 만들어진 새 값에 price_grade라는 이름을 붙여서 하나의 열처럼 보여줘라"

## | 2장 2강 : 데이터 집계와 분석

```sql
SELECT 성별,
       COUNT(*) AS cnt,
       AVG(나이) AS avg_age
FROM basic.theglory
GROUP BY 성별;
```
- `COUNT(*) AS cnt` : 전체 행 개수를 세고, 그 결과에 cnt라는 이름을 붙임
- `AVG(나이) AS avg_age` : 나이 열의 평균을 구하고, avg_age라는 이름을 붙임
- `GROUP BY 성별;` : "성별 값이 같은 행끼리 하나로 묶은 다음에, 위의 COUNT/AVG를 그룹별로 각각 계산해라" (그룹핑을 안 하면 전체를 하나로 뭉쳐서 딱 1개의 결과만 나옴)

```sql
SELECT category_id, AVG(list_price) AS avg_price
FROM products
GROUP BY category_id
HAVING AVG(list_price) >= 500;
```
- `GROUP BY category_id` : 카테고리별로 먼저 묶고
- `HAVING AVG(list_price) >= 500;` : "묶은 다음 계산된 평균 가격이 500 이상인 그룹만 남겨라" (개별 행이 아니라, 이미 계산되어 나온 그룹의 평균값을 기준으로 거르는 것)

## | 2장 3강 : 테이블 결합(JOIN/UNION)

```sql
SELECT o.order_id, c.first_name, c.last_name, o.order_date
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
```
- `FROM orders o` : orders 표를 o라는 별명으로
- `INNER JOIN customers c ON o.customer_id = c.customer_id;`
  - `INNER JOIN customers c` : customers 표(별명 c)도 같이 가져오는데
  - `ON o.customer_id = c.customer_id` : "o의 customer_id와 c의 customer_id가 같은 행끼리만" 옆으로 이어붙여라 (일치하지 않는 행은 아예 결과에서 빠짐 — 그래서 이름이 INNER=안쪽/교집합)

```sql
SELECT store_id FROM staffs
UNION
SELECT store_id FROM orders;
```
- 위아래로 각각의 SELECT 결과를 세로로 이어붙이는 것 (JOIN처럼 옆으로 붙이는 게 아니라, 위아래로 쌓는 것)
- `UNION`(중간에 끼워진 단어) : "두 결과를 합치되, 중복된 값은 하나로 합쳐서 보여줘라"

## | 3장 1강·2강 : 서브쿼리

```sql
SELECT order_id, customer_id, amount
FROM orders
WHERE amount > (
    SELECT AVG(amount)
    FROM orders
);
```
- 괄호 안 `(SELECT AVG(amount) FROM orders)` : 이것도 하나의 완전한 SELECT문이다. 이게 먼저 실행되어 "평균 금액"이라는 숫자 하나를 계산해낸다
- `WHERE amount > (그 숫자)` : "그렇게 미리 계산된 평균값보다 amount가 큰 행만 보여줘라"
- 이렇게 SELECT문 안에 또 다른 SELECT문이 들어있는 걸 서브쿼리라고 부른다

```sql
SELECT customer_id, total_amount
FROM (
    SELECT customer_id, SUM(amount) AS total_amount
    FROM orders
    GROUP BY customer_id
) AS customer_totals
WHERE total_amount >= 1000000;
```
- `FROM ( SELECT ... ) AS customer_totals`
  - 괄호 안에서 먼저 "고객별 총 주문금액"을 계산해서 임시로 만든 표를 준비
  - `AS customer_totals` : 그 임시 표에 `customer_totals`라는 이름표를 붙여야만, 바깥의 SELECT/WHERE에서 그 표를 마치 진짜 테이블처럼 쓸 수 있다
- `WHERE total_amount >= 1000000;` : 그렇게 미리 집계해둔 결과 표 안에서, total_amount가 100만 이상인 것만 최종적으로 골라냄

# PART 3. "SQL & DB 실습자료" 새 예제 코드 뜯어보기 (다른 데이터셋 기반)

- 이 실습자료는 지금까지 쓰던 `products`, `staffs` 같은 자전거 판매점 데이터 대신, **온라인 쇼핑몰 주문 데이터셋**(customers, orders, order_items, order_payments)을 가지고 같은 개념을 다시 연습해보는 자료다. 표 이름과 컬럼 이름만 바뀌었을 뿐, 원리는 지금까지 배운 것과 동일하다.

## | 데이터 집계 실습 — 2장2강 대응

```sql
-- WHERE → GROUP BY → HAVING 순서
SELECT c.customer_state,
       COUNT(*) AS delivered_order_count
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_status = 'delivered'
GROUP BY c.customer_state
HAVING COUNT(*) >= 100;
```
- `JOIN customers c ON o.customer_id = c.customer_id` : 주문(orders)과 고객(customers)을 고객번호 기준으로 연결
- `WHERE o.order_status = 'delivered'` : 그 중에서도 배송 상태가 'delivered'(배송완료)인 주문만 먼저 걸러내고
- `GROUP BY c.customer_state` : 남은 주문들을 고객이 사는 주(state)별로 묶어서
- `HAVING COUNT(*) >= 100;` : "그 주에서 배송완료된 주문이 100건 이상인 주만" 최종적으로 보여줘라
- 이 쿼리 하나에 WHERE(행 필터링) → GROUP BY(그룹핑) → HAVING(그룹 필터링) 실행 순서가 그대로 다 들어있다.

## | 테이블 결합 실습 — 2장3강 대응

```sql
-- UNION: 중복 주문 ID 제거
SELECT order_id
FROM orders
```
(뒤에 다른 SELECT와 UNION으로 이어지는 구조 — "여러 소스에 등장하는 order_id를 하나로 합쳐서 중복없이 보기" 용도. 원리는 앞서 배운 `UNION`과 동일)

```sql
SELECT p.product_id,
       p.product_category_name
FROM products p
FULL OUTER JOIN order_items oi ON p.product_id = oi.product_id;
```
- `FULL OUTER JOIN` : "상품에는 있는데 주문된 적 없는 상품 / 주문에는 있는데 상품정보가 없는 이상한 데이터, 둘 다 놓치지 않고 전부 보여줘라" (양쪽 표 모두를 합집합으로 포함)

## | 서브쿼리 실습 — 3장1강·2강 대응

```sql
-- EXISTS: 배송 완료 주문이 있는 고객
SELECT c.customer_id,
       c.customer_city
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.order_status = 'delivered'
);
```
- `EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.order_status = 'delivered')`
  - `SELECT 1` : 실제로 어떤 값을 가져오려는게 아니라, "조건에 맞는 행이 존재하기만 하면 되니, 그냥 숫자 1이라도 아무거나 반환해라"는 관례적인 표현 (1 대신 아무 숫자나 `*`를 써도 결과는 같음)
  - 전체 뜻 : "이 고객(c) 번호로, 배송완료 상태인 주문이 하나라도 있으면 TRUE"
- `WHERE EXISTS (...)` : 그 조건이 TRUE인 고객만 최종적으로 보여줌

```sql
SELECT customer_id,
       total_amount
FROM (
    SELECT customer_id, SUM(price) AS total_amount
    FROM order_items
    GROUP BY customer_id
) sub
WHERE total_amount >= (SELECT AVG(total_amount) FROM (
    SELECT customer_id, SUM(price) AS total_amount
    FROM order_items
    GROUP BY customer_id
) sub2);
```
- 이 코드는 서브쿼리 안에 서브쿼리가 또 들어있는(인라인 뷰 두 번 겹침) 구조다.
- 안쪽 `(SELECT customer_id, SUM(price) ... GROUP BY customer_id)` : 먼저 "고객별 총 구매액"이라는 임시 표(sub)를 만든다
- `WHERE total_amount >= (SELECT AVG(total_amount) FROM (똑같은 계산) sub2)` : 그렇게 만든 임시 표의 평균값을 다시 한번 계산해서(sub2), 그 평균보다 큰 고객만 최종적으로 골라낸다
- 즉 "평균 이상 구매한 고객 찾기"를 하려면, 먼저 고객별 합계를 구해야 하고 그 다음에 그 합계들의 평균을 또 구해야 하니, 인라인 뷰를 두 겹으로 겹쳐 쓴 것
