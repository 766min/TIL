# TIL | 2026-09-09
## 공부한 내용 | SQL - 트랜잭션(TCL), ACID 원칙과 ROLLBACK

- 신규 사용자를 만들면서 그 사용자의 기본 문서도 함께 만들어야 한다고 해보자. 그런데 사용자만 들어가고 문서 입력에서 오류가 난다면, 반쪽짜리 데이터가 남는다.

- 이런 "전부 성공 아니면 전부 취소"를 만들어주는게 트랜잭션이다.

### | TCL이란

- TCL(Transaction Control Language)은 트랜잭션을 제어하는 명령어다. 여러개의 DML 작업을 하나의 단위로 묶고, 그 결과를 확정(COMMIT)하거나 취소(ROLLBACK)한다.

- 트랜잭션(Transaction) : 더이상 쪼개질 수 없는 하나의 작업 단위. 안에 들어있는 여러 SQL이 "모두 성공"하거나 "모두 실패"해야 한다. 중간은 없다.

- 예 : 은행 계좌이체를 생각해보자. A 계좌에서 돈이 빠졌는데 B 계좌에 입금되지 않으면 큰일이다. 이 둘은 반드시 함께 성공하거나 함께 취소돼야 한다.

### | BEGIN, COMMIT, ROLLBACK

- 트랜잭션은 BEGIN으로 시작해서 COMMIT 또는 ROLLBACK으로 끝난다.

| 명령어 | 역할 |
| --- | --- |
| BEGIN | 트랜잭션을 시작한다 |
| COMMIT | 그동안의 변경을 영구적으로 확정한다 |
| ROLLBACK | 변경을 모두 취소하고 BEGIN 이전으로 되돌린다 |

```sql
BEGIN;

INSERT INTO users (email, name)
VALUES ('newuser@example.com', '신규유저');

COMMIT;
```

- COMMIT을 안하고 창을 닫으면 어떻게 될까 ?

  - COMMIT하기 전의 변경은 아직 확정되지 않은 상태다. 연결이 끊기거나 ROLLBACK되면 모두 사라진다.

  - 그래서 변경을 실제로 남기려면 반드시 COMMIT을 해야 한다. 반대로 실수를 되돌리고 싶을 때는 ROLLBACK이 구세주가 된다.

### | 작업 단위와 데이터 정합성

- 사용자 생성과 기본 문서 생성은 서로 연결된 작업이다. 둘 중 하나만 성공하면 데이터가 어긋난다. 하나의 트랜잭션으로 묶으면 정합성을 지킬 수 있다.

```sql
BEGIN;

-- 1) 사용자 생성
INSERT INTO users (email, name)
VALUES ('author@example.com', '김작가');

-- 2) 방금 만든 사용자의 기본 문서 생성
INSERT INTO documents (user_id, title, content)
VALUES (
  (SELECT id FROM users WHERE email = 'author@example.com'),
  '시작 가이드',
  '가입을 환영합니다.'
);

COMMIT;
```

### | SQL 작성할 때 주의할 점 ① : COMMIT 전후 조회의 차이

- 같은 세션 안에서는 COMMIT 전에도 변경이 보이지만, 다른 사용자나 다른 연결은 COMMIT 후에야 그 데이터를 볼 수 있다.

- 즉 "내 화면에 보인다고 해서 다른 사람에게도 보이는건 아니다" — COMMIT을 잊으면 그 변경은 나만 보고 있는 상태일 수 있다.

### | ACID 원칙

- ACID는 트랜잭션이 신뢰할 수 있게 동작하기 위해 지켜야 하는 네가지 성질의 앞글자를 따온 이름이다.

| 원칙 | 이름 | 의미 |
| --- | --- | --- |
| A | 원자성(Atomicity) | 모두 성공하거나 모두 실패한다 |
| C | 일관성(Consistency) | 규칙(제약조건)을 깨뜨리지 않는다 |
| I | 격리성(Isolation) | 동시 트랜잭션이 서로 간섭하지 않는다 |
| D | 지속성(Durability) | COMMIT된 것은 장애가 나도 남는다 |

- 예 : 원자성은 마치 상자 속 전구 같다. 하나만 끊어져도 전체가 꺼져야 하는 것처럼, 작업 하나라도 실패하면 전체를 취소한다.

### | ROLLBACK의 역할

- ROLLBACK은 BEGIN 이후의 모든 변경을 취소한다. 트랜잭션 중간에 오류가 나거나, 검증 결과가 이상하면 ROLLBACK으로 안전하게 이전 상태로 돌아갈 수 있다.

```sql
BEGIN;

INSERT INTO users (email, name)
VALUES ('temp@example.com', '임시유저');

-- 문제가 있음을 발견! 모든 변경을 취소
ROLLBACK;

-- 이 사용자는 저장되지 않았다.
SELECT * FROM users WHERE email = 'temp@example.com';
```

### | SQL 작성할 때 주의할 점 ② : PostgreSQL 트랜잭션 중 오류가 나면 전체가 멈춘다

- PostgreSQL은 트랜잭션 중 하나의 명령어라도 오류가 나면, 그 트랜잭션 전체를 실패 상태로 만든다.

- 이후 명령은 무시되고, 결국 ROLLBACK을 해야만 다음 작업을 할 수 있다. 덕분에 일부만 저장되는 사고를 자연스럽게 막아준다.

### | 트랜잭션 있을 때와 없을 때

- 트랜잭션 없이 실행하면 생기는 일 : 트랜잭션으로 묶지 않고 명령어를 하나씩 실행하면, 앞 명령은 이미 COMMIT된 상태가 된다. 뒤 명령에서 오류가 나도 앞 작업은 남아, 반쪽짜리 데이터가 생긴다.

```sql
-- 트랜잭션 없이 실행 (위험)
INSERT INTO users (email, name)
VALUES ('half@example.com', '반쪽유저');   -- 이건 저장됨

INSERT INTO documents (user_id, title)
VALUES (99999, '없는 사용자 문서');            -- 외래키 오류로 실패
-- 결과: 사용자만 남고 문서는 없는 불완전 상태
```

- 트랜잭션으로 묶으면 : 같은 작업을 `BEGIN ... ROLLBACK`으로 묶으면, 문서 삽입이 실패했을 때 사용자 삽입까지 함께 취소된다. 반쪽짜리 데이터가 생기지 않는다.

### | SQL 작성할 때 주의할 점 ③ : 연결된 여러 INSERT는 무조건 트랜잭션으로 묶기

- 서로 연관된(하나가 실패하면 나머지도 의미없어지는) 여러 DML 작업은 절대 따로따로 실행하지 말고, 반드시 `BEGIN ~ COMMIT/ROLLBACK`으로 하나의 단위로 묶어야 한다.

- 트랜잭션 없이 생긴 불완전 데이터(반쪽짜리 데이터)는 나중에 사람이 직접 찾아서 지워야 하므로 훨씬 번거롭다. 처음부터 트랜잭션으로 묶는게 훨씬 안전하다.

```sql
-- 불완전 데이터 예시 정리 (트랜잭션 없이 생겼을 경우)
DELETE FROM users WHERE email = 'half@example.com';
```

### | 실습 : COMMIT/ROLLBACK 비교

1. BEGIN으로 트랜잭션 시작
```sql
BEGIN;
```

2. 트랜잭션 중간에 의도적 오류 발생시키기
```sql
INSERT INTO users (email, name)
VALUES ('rollback@example.com', '롤백유저');

-- 존재하지 않는 user_id로 외래키 오류 유도
INSERT INTO documents (user_id, title)
VALUES (99999, '오류 유도 문서');
```

3. ROLLBACK 후 이전 INSERT까지 취소됐는지 확인
```sql
ROLLBACK;

-- 롤백유저도 저장되지 않았음을 확인
SELECT * FROM users WHERE email = 'rollback@example.com';
```

4. 트랜잭션 없이 같은 작업을 했을 때와 비교
```sql
-- BEGIN 없이 한 줄씩 실행
INSERT INTO users (email, name) VALUES ('nouser@example.com', '누락유저');
INSERT INTO documents (user_id, title) VALUES (99999, '실패할 문서');
-- 누락유저는 살아남고 문서는 실패 → 불완전 상태
SELECT * FROM users WHERE email = 'nouser@example.com';
```

- 이렇게 두 경우를 비교해보면, ROLLBACK으로 묶은 경우엔 흔적조차 안 남지만, 트랜잭션 없이 실행한 경우엔 '누락유저'라는 반쪽짜리 데이터가 그대로 남는걸 확인할 수 있다.

### | 이번 강의 핵심 정리

1. TCL은 트랜잭션을 제어하는 명령어로, 여러 DML 작업을 하나의 단위로 묶는다.
2. 트랜잭션은 "모두 성공 또는 모두 실패"를 보장해 데이터 정합성을 지킨다.
3. BEGIN으로 시작하고, COMMIT으로 확정, ROLLBACK으로 취소한다. COMMIT 전의 변경은 아직 확정되지 않은 상태이므로, 남기려면 반드시 COMMIT해야 한다.
4. ACID는 원자성·일관성·격리성·지속성으로, 트랜잭션이 지켜야 할 네가지 원칙이다.
5. PostgreSQL은 트랜잭션 중 오류가 나면 전체를 실패로 처리해서 일부만 저장되는걸 막아준다.
6. 서로 연관된 여러 DML 작업은 반드시 트랜잭션으로 묶어야, 반쪽짜리 데이터가 생기는걸 예방할 수 있다.

Q1. 아래 SQL을 실행한 뒤 연결이 끊겼습니다. 신규유저 데이터는 실제로 저장되었을까요 ?

```sql
BEGIN;

INSERT INTO users (email, name)
VALUES ('newuser@example.com', '신규유저');

-- (COMMIT을 실행하지 않고 연결이 끊김)
```

A. 저장되지 않는다.

-> COMMIT하기 전의 변경 사항은 아직 확정되지 않은 상태라서, 연결이 끊기면 그 변경은 사라진다. 데이터를 실제로 남기려면 반드시 COMMIT을 실행해야 한다.

Q2. ACID 원칙 중, "작업 하나라도 실패하면 트랜잭션 전체를 취소해서 모두 성공하거나 모두 실패하게 만든다"는 성질에 해당하는 것은 ?

[ 보기 ]

a. 일관성(Consistency)

b. 원자성(Atomicity)

c. 격리성(Isolation)

d. 지속성(Durability)

A. b. 원자성(Atomicity)

-> 원자성은 트랜잭션 안의 여러 작업이 마치 하나의 더 이상 쪼갤 수 없는 작업처럼, 모두 성공하거나 모두 실패해야 한다는 원칙이다. (상자 속 전구가 하나만 끊겨도 전체가 꺼지는 것과 같은 비유)

Q3. 트랜잭션으로 묶지 않고 사용자(users) INSERT와 문서(documents) INSERT를 각각 따로 실행했는데, 문서 INSERT에서 외래키 오류가 났습니다. 이때 사용자 데이터는 어떻게 되나요 ?

A. 이미 COMMIT된 상태이므로 그대로 저장되어 남는다. (사용자만 남고 문서는 없는 반쪽짜리 데이터가 된다.)

-> 트랜잭션으로 묶지 않으면 각 명령어가 실행되는 즉시 확정되기 때문에, 뒤 명령이 실패해도 앞서 실행된 명령은 취소되지 않고 그대로 남아 데이터 불일치가 발생한다.

Q4. PostgreSQL에서 트랜잭션 도중 하나의 SQL 명령어가 오류를 내면 어떤 일이 일어나나요 ?

[ 보기 ]

a. 오류가 난 명령어만 무시되고 나머지는 정상적으로 계속 실행된다

b. 트랜잭션 전체가 실패 상태가 되어, ROLLBACK 전까지 이후 명령이 무시된다

c. 자동으로 COMMIT되어 오류 이전까지의 작업만 저장된다

d. 데이터베이스 연결이 즉시 강제 종료된다

A. b.

-> PostgreSQL은 트랜잭션 중 하나라도 오류가 발생하면 그 트랜잭션 전체를 실패 상태로 표시하고, ROLLBACK을 해야만 다음 작업을 이어갈 수 있게 만들어 일부만 저장되는 사고를 막아준다.

Q5. 서로 연관된 두 개 이상의 INSERT 작업(예: 사용자 생성 + 그 사용자의 기본 문서 생성)을 안전하게 처리하는 가장 올바른 방법은 무엇인가요 ?

A. BEGIN으로 트랜잭션을 시작해서 관련된 INSERT들을 하나로 묶고, 모두 성공하면 COMMIT, 하나라도 실패하면 ROLLBACK한다.

-> 연관된 작업을 트랜잭션으로 묶어야 "모두 성공 또는 모두 실패"가 보장되어, 사용자만 생성되고 문서는 없는 것과 같은 반쪽짜리 데이터(데이터 불일치)를 예방할 수 있다.
