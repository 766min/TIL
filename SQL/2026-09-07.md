## 공부한 내용 | SQL - 데이터 집계와 분석, 테이블 결합(JOIN/UNION)

- 데이터 분석에서는 단순히 데이터를 조회하는 것을 넘어, 전체 데이터의 통계적 의미를 파악하는게 중요하다.

- 집계함수를 사용하면 수백만건의 데이터를 요약해 평균, 합계, 최댓값 등을 한눈에 볼 수 있다.

### | SQL 집계함수 : COUNT, MAX, MIN, SUM, AVG

- 집계함수(Aggregate Function)는 테이블의 여러 행 또는 열에 대해 계산을 수행하고, 하나의 결과값을 반환한다.

- SELECT절에서 사용하며, 전체 데이터 또는 특정 열을 대상으로 적용할 수 있다.

| 집계함수 | 기능 |
| --- | --- |
| COUNT | 행의 수 반환 |
| SUM | 열의 합계 반환 |
| AVG | 열의 평균 반환 |
| MIN | 열의 최솟값 반환 |
| MAX | 열의 최댓값 반환 |

```sql
-- 1. 전체 데이터 개수
SELECT COUNT(*) AS cnt
FROM basic.theglory;

-- 2. 나이의 평균, 최대, 최소, 합계
SELECT AVG(나이) AS avg_age,
       MAX(나이) AS max_age,
       MIN(나이) AS min_age,
       SUM(나이) AS sum_age
FROM basic.theglory;
```

- `COUNT(*)`와 `COUNT(열명)`는 어떻게 다를까 ?

  - `COUNT(*)`는 NULL 여부에 관계없이 모든 행의 수를 센다.

  - `COUNT(열명)`는 해당 열에서 NULL이 아닌 행의 수만 센다.

  - 예를 들어 날짜 열에 NULL이 2개 있는 theglory 테이블(전체 7행)에서 `COUNT(*)`는 7(전체 행 수), `COUNT(날짜)`는 5(날짜가 있는 행만)가 된다.

  - 데이터의 전체 건수를 셀 때는 COUNT(*), 특정 열의 유효 데이터 수를 셀 때는 COUNT(열명)을 사용한다.

### | SQL 그룹화 : GROUP BY

- 전체 데이터를 통째로 집계하는 것을 넘어, 특정 열을 기준으로 데이터를 묶어서 집계하고 싶을 때 GROUP BY를 사용한다.

- 예를 들어 '성별 기준 평균 나이', '직업 기준 데이터 수'처럼 기준별 비교 분석이 가능하다.

- SQL 작동 순서 : `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> `SELECT` -> `ORDER BY`

```sql
-- GROUP BY 기본 구조
SELECT 기준열, 집계함수(열)
FROM 테이블명
WHERE 조건    -- 생략 가능
GROUP BY 기준열;

-- 예시: 성별 기준 집계
SELECT 성별,
       COUNT(*) AS cnt,
       AVG(나이) AS avg_age
FROM basic.theglory
GROUP BY 성별;
```

### | SQL 작성할 때 주의할 점 ① : GROUP BY 규칙

- SELECT에 기준열과 집계함수를 같이 쓸 때 GROUP BY를 빠뜨리면 에러가 발생한다.

  - 이유 : 집계함수는 여러 행을 하나로 줄이는 반면, 기준열은 N개의 값을 그대로 반환하려 하기 때문에 행 수가 맞지 않아 충돌이 발생한다.

  - GROUP BY를 사용해야 기준열을 그룹화하여 집계함수와 함께 하나의 행으로 반환할 수 있다.

  - **SELECT절에 집계함수가 아닌 열이 있다면, 해당 열은 반드시 GROUP BY에도 명시해야 한다는 규칙을 꼭 기억할 것.**

### | HAVING과 WHERE의 차이

- `HAVING`절은 GROUP BY로 그룹화된 결과에 조건을 적용할 때 사용한다. WHERE와 동일하게 데이터를 필터링하지만, 적용 시점이 다르다.

| 필터링 구문 | 필터링 시점 | 사용 대상 |
| --- | --- | --- |
| WHERE | GROUP BY 전 원본 데이터 필터링 | 개별 행의 조건 |
| HAVING | GROUP BY 후 집계 결과 필터링 | 집계함수 결과의 조건 |

```sql
-- 예시: 나이 31세 이상 + 성별 그룹화 + 평균 나이 41 초과 필터
SELECT 성별, AVG(나이) AS avg_age
FROM basic.theglory
WHERE 나이 >= 31          -- 1단계: 그룹화 전 개별 행 필터링
GROUP BY 성별             -- 2단계: 성별로 그룹화
HAVING AVG(나이) > 41;    -- 3단계: 집계 결과 필터링
```

- 위 쿼리의 실행 순서 : ① `WHERE 나이 >= 31` -> 나이가 31 미만인 행 제외 -> ② `GROUP BY 성별` -> 남녀로 그룹화하여 각각 평균 나이 계산 -> ③ `HAVING AVG(나이) > 41` -> 평균 나이가 41 초과인 그룹만 반환

### | SQL 작성할 때 주의할 점 ② : HAVING 없이 WHERE만으로 집계 결과를 거를 수 없다

- WHERE절은 GROUP BY 전에 실행되기 때문에 집계함수의 결과값을 조건으로 사용할 수 없다.

- 예를 들어 `WHERE AVG(나이) > 41`처럼 작성하면 에러가 발생한다. 집계 결과에 조건을 걸어야 할 때는 반드시 HAVING을 사용해야 한다.

- 반대로 집계 전 개별 행을 필터링할 때는 성능 면에서 WHERE가 더 효율적이다. (먼저 데이터를 줄인 뒤 집계하기 때문)

### | 테이블 결합 : 하나의 테이블만으로는 부족할 때

- 데이터베이스에서는 정보를 효율적으로 관리하기 위해 여러 테이블로 나누어 저장한다. 예를 들어 주문 정보는 orders 테이블에, 고객 정보는 customers 테이블에 따로 저장된다.

- 하지만 실제 분석에서는 "어느 고객이 얼마를 주문했는가?"처럼 여러 테이블의 데이터를 함께 봐야 할 때가 많다. 이때 필요한게 테이블 결합 — UNION과 JOIN이다.

#### - UNION : 행 방향으로 테이블 합치기

- UNION은 두 개 이상의 SELECT 결과를 세로(행) 방향으로 쌓아서 합치는 방법이다. 마치 두 장의 명단표를 아래위로 붙이는 것처럼, 같은 열 구조를 가진 결과들을 하나로 이어붙인다.

- UNION을 사용하려면 두 SELECT문의 열 수와 데이터 타입이 일치해야 한다.

```sql
-- 예시: 2023년과 2024년 주문 데이터를 합치기
SELECT order_id, customer_id, amount FROM orders_2023
UNION
SELECT order_id, customer_id, amount FROM orders_2024;
```

- UNION vs UNION ALL : 핵심 차이는 중복 행 처리 방식이다.

  - `UNION` : 정렬 또는 해시 기반 연산으로 중복을 제거하기 때문에 추가 비용이 발생할 수 있다.

  - `UNION ALL` : 중복 여부와 상관없이 모든 행을 포함한다. 속도가 더 빠르고, 중복을 의도적으로 유지해야 할 때 쓴다.

- UNION을 쓸 때 열 이름이 두 테이블에서 달라도 될까 ?

  - 괜찮다. UNION은 열 이름이 아니라 열의 위치(순서)와 데이터 타입을 기준으로 결합한다. 결과 열 이름은 첫번째 SELECT문의 열 이름을 따른다.

#### - JOIN : 열 방향으로 테이블 합치기

- JOIN은 두 테이블을 가로(열) 방향으로 연결하는 방법이다. 공통 키(예: customer_id)를 기준으로 두 테이블의 행을 연결해서, 마치 하나의 넓은 테이블처럼 조회할 수 있다.

- JOIN을 사용할 때는 ON절로 어떤 열을 기준으로 연결할지 지정한다.

```sql
-- 기본 JOIN 문법
SELECT 테이블1.열, 테이블2.열
FROM 테이블1
JOIN 테이블2 ON 테이블1.공통키 = 테이블2.공통키;
```

- JOIN은 어떤 행을 포함할지에 따라 네가지 종류로 나뉜다.

| JOIN 종류 | 설명 | 포함하는 행 |
| --- | --- | --- |
| INNER JOIN | 두 테이블 모두에 일치하는 행만 | 교집합 |
| LEFT JOIN | 왼쪽 테이블 전체 + 오른쪽에서 일치하는 행 | 왼쪽 기준 |
| RIGHT JOIN | 오른쪽 테이블 전체 + 왼쪽에서 일치하는 행 | 오른쪽 기준 |
| FULL OUTER JOIN | 양쪽 테이블 모두 포함(일치 안해도 포함) | 합집합 |

```sql
-- INNER JOIN : 주문한 고객 정보만 조회 (주문 없는 고객 제외)
SELECT o.order_id, c.customer_name, o.amount
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;

-- LEFT JOIN : 모든 고객 조회 (주문이 없으면 order_id가 NULL)
SELECT c.customer_name, o.order_id, o.amount
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- RIGHT JOIN : 모든 주문 조회 (고객 정보 없으면 customer_name이 NULL)
SELECT c.customer_name, o.order_id, o.amount
FROM customers c
RIGHT JOIN orders o ON c.customer_id = o.customer_id;

-- FULL OUTER JOIN : 고객과 주문 모두 포함 (어느 쪽이든 없으면 NULL)
SELECT c.customer_name, o.order_id, o.amount
FROM customers c
FULL OUTER JOIN orders o ON c.customer_id = o.customer_id;
```

- INNER JOIN, LEFT JOIN, RIGHT JOIN이 헷갈릴 때는 방향으로 기억하면 편하다.

  - INNER : "두 테이블 모두에 있는 것만" -> 교집합

  - LEFT : "왼쪽은 무조건 다 나와" -> 왼쪽 기준

  - RIGHT : "오른쪽은 무조건 다 나와" -> 오른쪽 기준

  - FULL OUTER : "둘 다 무조건 다 나와" -> 합집합

  - 실무에서는 LEFT JOIN이 가장 자주 쓰인다. 기준 테이블을 왼쪽에 두고 필요한 정보를 오른쪽에서 끌어오는 패턴이다.

#### - ON절 활용법

- ON절은 두 테이블을 어떤 열 기준으로 연결할지 지정한다. 일반적으로 한 테이블의 기본키(PK)와 다른 테이블의 외래키(FK)를 연결하는 형태로 사용한다.

```sql
-- 복수 조건도 가능 (AND 사용)
FROM 주문 o
JOIN 배송 d ON o.order_id = d.order_id AND o.store_id = d.store_id
```

- ☑️ 심화 : 테이블 별칭(alias) 활용하기

  - JOIN을 사용할 때 테이블 이름이 길면 쿼리가 복잡해질 수 있다. `FROM orders o`처럼 테이블에 짧은 별칭을 붙여 사용하면 훨씬 간결해진다.

```sql
-- 별칭 없이 작성 (복잡)
SELECT orders.order_id, customers.customer_name
FROM orders
INNER JOIN customers ON orders.customer_id = customers.customer_id;

-- 별칭 사용 (간결)
SELECT o.order_id, c.customer_name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
```
  - 별칭은 테이블 이름 바로 뒤에 공백 후 입력한다. AS 키워드를 써도 되지만 생략하는 경우가 더 많다.

### | SQL 작성할 때 주의할 점 ③ : UNION vs JOIN, 헷갈리지 말기

| 구분 | JOIN | UNION |
| --- | --- | --- |
| 결합 방향 | 가로(열 방향) | 세로(행 방향) |
| 목적 | 다른 테이블의 정보를 연결 | 같은 구조의 결과를 쌓기 |
| 조건 | 공통 키(ON절)가 필요 | 열 수와 타입이 동일해야 함 |
| 활용 예시 | 고객-주문, 제품-카테고리 연결 | 연도별 데이터 통합, 지역별 데이터 합치기 |

- UNION은 행을 추가하는 방식(같은 형태의 데이터를 위아래로 쌓기)이고, JOIN은 열을 추가하는 방식(서로 다른 테이블의 정보를 좌우로 연결)이다.

- 예를 들어 2023년과 2024년 데이터를 하나의 테이블로 통합하려면 UNION을, 주문 데이터에 고객 이름을 붙이고 싶다면 JOIN을 쓴다.

SELECT store_id, COUNT(*) AS order_cnt

SELECT category_id, AVG(list_price) AS avg_price

4. customers를 기준으로 orders를 연결해(주문이 없는 고객도 포함), 고객ID, 이름, order_id를 조회하세요.

SELECT c.customer_id, c.first_name, c.last_name, o.order_id

### | 이번 강의 핵심 정리

1. 집계함수(COUNT, SUM, AVG, MIN, MAX)는 여러 행을 하나의 결과값으로 요약한다.
2. GROUP BY는 특정 열을 기준으로 데이터를 그룹화하여 집계함수를 기준별로 적용할 수 있게 한다. SELECT절에 집계함수가 아닌 열이 있다면 반드시 GROUP BY에도 명시해야 한다.
3. WHERE는 GROUP BY 전 개별 행을 필터링하고, HAVING은 GROUP BY 후 집계 결과를 필터링한다.
4. UNION은 행 방향(세로)으로 결과를 합치고, JOIN은 열 방향(가로)으로 테이블을 연결한다.
5. INNER JOIN은 교집합만, LEFT/RIGHT JOIN은 한쪽 전체, FULL OUTER JOIN은 합집합을 반환한다.

Q1. 다음 쿼리를 실행하면 에러가 발생합니다. 그 이유로 가장 적절한 것은 ?

```sql
SELECT 성별, 나이, AVG(나이)
FROM basic.theglory
GROUP BY 성별;
```

A. SELECT절에 집계함수(AVG)가 아닌 열 '나이'가 있는데, 이 열이 GROUP BY에 명시되어 있지 않아서

-> 집계함수는 여러 행을 하나로 줄이는 반면, GROUP BY에 없는 일반 열(나이)은 여러 값을 그대로 반환하려 해서 행 수가 맞지 않아 충돌한다. SELECT절에 집계함수가 아닌 열이 있다면 반드시 GROUP BY에도 명시해야 한다.

Q2. 평균 나이가 41살을 초과하는 그룹만 조회하려고 할 때, 아래 중 문법적으로 옳은 것은 ?

[ 보기 ]

a. `WHERE AVG(나이) > 41`

b. `HAVING AVG(나이) > 41`

c. `GROUP BY AVG(나이) > 41`

d. `ORDER BY AVG(나이) > 41`

A. b.

-> WHERE절은 GROUP BY보다 먼저 실행되기 때문에 아직 계산되지 않은 집계함수 결과를 조건으로 쓸 수 없다. 집계 결과에 조건을 걸 때는 반드시 HAVING을 사용해야 한다.

Q3. customers 테이블과 orders 테이블을 LEFT JOIN(customers 기준)했을 때, 한 번도 주문하지 않은 고객의 order_id 값은 어떻게 나오나요 ?

A. NULL로 나온다.

-> LEFT JOIN은 왼쪽(customers) 테이블의 모든 행을 결과에 포함하고, 오른쪽(orders) 테이블에 일치하는 행이 없으면 해당 열은 NULL로 채워진다.

Q4. 2023년 주문 테이블과 2024년 주문 테이블을 하나로 합쳐서 조회하고 싶을 때, UNION을 사용하기 위한 전제 조건으로 옳은 것은 ?

[ 보기 ]

a. 두 테이블의 이름이 같아야 한다

b. 두 SELECT문의 열 개수와 데이터 타입이 일치해야 한다

c. 두 테이블에 공통 키(PK-FK)가 있어야 한다

d. 두 테이블의 행 개수가 같아야 한다

A. b.

-> UNION은 열 이름이 아니라 열의 개수와 데이터 타입을 기준으로 결과를 세로로 이어붙이기 때문에, 두 SELECT문의 열 개수와 타입이 일치해야 정상적으로 동작한다.

Q5. UNION과 JOIN의 차이를 잘못 설명한 것은 ?

[ 보기 ]

a. UNION은 행(세로) 방향으로 결과를 합친다

b. JOIN은 열(가로) 방향으로 테이블을 연결한다

c. JOIN은 공통 키(ON절)가 필요하지만, UNION은 필요하지 않다

d. UNION과 JOIN은 항상 서로 완전히 대체 가능한 동일한 기능이다

A. d.

-> UNION은 같은 구조의 결과를 세로로 쌓는 것이고, JOIN은 서로 다른 테이블의 정보를 가로로 연결하는 것이라 목적과 결과 구조 자체가 다르며, 상황에 따라 구분해서 사용해야 한다.
