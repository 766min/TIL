## | 3장 8강 : SDK 기반 미니 과제 — 사용자별 문서 CRUD

### 코드 ① : 로그인한 사용자가 본인 문서만 만들고 조회하기

```python
user = supabase.auth.get_user().user

# 생성: 로그인 사용자의 문서
create_document("오늘의 메모", "본문 내용", user.id)

# 조회: 본인 문서만
docs = supabase.table("documents").select("*").eq("user_id", user.id).execute()
print(docs.data)
```

한 줄씩 뜯어보면 :

- `user = supabase.auth.get_user().user`
  - `supabase.auth` : "supabase의 로그인 담당 부서"에 접근한다는 뜻
  - `.get_user()` : "지금 로그인되어 있는 사람이 누군지 알려줘"라고 물어보는 것
  - `.user` : 그 물어본 결과 중에서 "사용자 정보"만 쏙 뽑아내는 것
  - 전체 뜻 : "지금 로그인한 사람이 누구인지 알아내서 `user`라는 이름의 상자에 담아둬라"

- `# 생성: 로그인 사용자의 문서` : `#`으로 시작하는 줄은 **주석**이다. 컴퓨터는 이 줄을 실행하지 않고 그냥 무시한다. 사람이 "이 밑에 코드가 뭘 하는지" 메모해두는 용도다.

- `create_document("오늘의 메모", "본문 내용", user.id)`
  - `create_document`라는 이름의 함수(미리 만들어둔 기능 뭉치)를 실행한다.
  - 괄호 안의 `"오늘의 메모"`, `"본문 내용"`, `user.id` 세 가지를 그 함수에게 재료로 건네준다.
  - 즉 "제목은 '오늘의 메모', 내용은 '본문 내용', 작성자는 방금 알아낸 user.id로 해서 문서 하나 만들어줘"라는 뜻

- `docs = supabase.table("documents").select("*").eq("user_id", user.id).execute()`
  - `supabase.table("documents")` : "documents라는 이름의 테이블(표)로 가라"
  - `.select("*")` : "그 표의 모든 열(칸)을 다 보여줘"
  - `.eq("user_id", user.id)` : "근데 user_id 열의 값이 지금 로그인한 사람의 id랑 **똑같은(eq = equal)** 행만 골라줘"
  - `.execute()` : "자, 이제 위에서 정한 조건대로 진짜로 실행해!" (여기서 실제로 DB에 요청이 나간다)
  - `docs =` : 그 결과를 `docs`라는 상자에 담아둔다.
  - 전체 뜻 : "documents 표에서, 지금 로그인한 사람이 쓴 문서만 전부 가져와서 docs에 담아라"

- `print(docs.data)`
  - `print(...)` : 괄호 안의 내용을 화면에 출력해라(보여줘라)
  - `docs.data` : 방금 담아둔 `docs` 상자 안에서, 진짜 데이터 부분만 꺼내기 (docs 안에는 데이터 말고도 부가정보가 더 들어있어서, 순수 데이터만 쓰려면 `.data`를 붙여야 함)
  - 전체 뜻 : "방금 가져온 문서 목록을 화면에 찍어서 보여줘"

### 코드 ② : 실행 결과로 나온 데이터 (JSON)

```json
[
   {
      "id":"158fba8f-39e9-4cc6-85fa-be71781916dc",
      "title":"로그인 사용자의 문서",
      "content":"본문",
      "user_id":"1804e97c-5e28-456e-9220-f7e7796c62a0",
      "status":"draft",
      "created_at":"2026-07-31T03:40:50.754048+00:00"
   }
]
```

- 이건 코드가 아니라, 위 코드를 실행했을 때 **돌려받은 결과물**이다.
- `[  ]` 대괄호 : "문서가 여러 개 들어있는 목록(리스트)"이라는 뜻. 지금은 문서가 1개라서 안에 `{ }`가 하나만 있음.
- `{ }` 중괄호 안의 `"id": "158fba8f-..."` 처럼 `이름: 값` 짝으로 이루어진 걸 하나씩 뜯어보면:
  - `"id"` : 이 문서에 자동으로 부여된 고유번호 (아무리 문서가 많아져도 이 번호는 절대 겹치지 않음)
  - `"title"` : 문서 제목
  - `"content"` : 문서 본문
  - `"user_id"` : 이 문서를 누가 썼는지 (작성자의 고유번호)
  - `"status"` : 지금 이 문서의 상태 (초안이면 'draft')
  - `"created_at"` : 언제 만들어졌는지 (연-월-일T시:분:초 형태의 시각)

### 코드 ③ : 전체 흐름을 하나의 함수로 정리하기

```python
def run_app():
    user = supabase.auth.get_user().user
    if user is None:
        print("로그인이 필요합니다.")
        return

    # 생성
    created = create_document("통합 테스트 문서", "본문", user.id)

    # 조회
    docs = supabase.table("documents").select("*").eq("user_id", user.id).execute()
    print("내 문서 수:", len(docs.data))

    # 수정·삭제
    doc_id = created[0]["id"]
    update_document_status(doc_id, "published")
    delete_document(doc_id)
```

- `def run_app():`
  - `def`는 "define(정의하다)"의 줄임말. "지금부터 `run_app`이라는 이름의 새로운 기능(함수)을 하나 만들겠다"는 선언
  - 콜론(`:`) 뒤에 들여쓰기 된 부분이 전부 이 함수 안에 들어있는 "할 일 목록"이다.

- `user = supabase.auth.get_user().user` : 코드①에서 설명한 것과 똑같이, 지금 로그인한 사람을 알아내서 `user`에 담는다.

- `if user is None:`
  - `if`는 "만약 ~라면"이라는 뜻
  - `user is None` : "user 상자 안에 아무것도 안 들어있다면" (즉 로그인이 안 되어 있어서 아무 정보도 못 가져온 상태)
  - 전체 뜻 : "만약 로그인이 안 되어있다면 (아래 두 줄을 실행해라)"

- `print("로그인이 필요합니다.")` : 화면에 "로그인이 필요합니다."라는 안내 문구를 보여준다.

- `return` : "여기서 이 함수를 끝내고 빠져나가라"는 뜻. 로그인이 안 되어 있으니, 그 아래에 있는 문서 생성/조회 코드는 아예 실행하지 않고 함수를 종료시킨다.

- `created = create_document("통합 테스트 문서", "본문", user.id)`
  - 문서를 하나 만들고, 그 결과(방금 만들어진 문서 정보)를 `created`라는 상자에 담아둔다.

- `docs = supabase.table("documents")...`, `print("내 문서 수:", len(docs.data))`
  - 앞부분은 코드①과 동일하게 본인 문서를 조회
  - `len(docs.data)` : `len`은 "length(길이)"의 줄임말. `docs.data`(문서 목록) 안에 문서가 **몇 개** 들어있는지 개수를 세어준다.
  - `print("내 문서 수:", len(docs.data))` : "내 문서 수:"라는 글자와, 방금 센 개수를 나란히 화면에 출력한다.

- `doc_id = created[0]["id"]`
  - `created`는 방금 만든 문서 정보가 담긴 목록(리스트)이다.
  - `created[0]` : 그 목록에서 **0번째(첫번째)** 문서를 꺼낸다. (컴퓨터는 순서를 셀 때 1이 아니라 0부터 센다는 게 포인트!)
  - `["id"]` : 그 문서 정보 중에서 `id`라는 값만 콕 집어서 꺼낸다.
  - 전체 뜻 : "방금 만든 문서의 고유번호를 doc_id라는 상자에 담아둬라"

- `update_document_status(doc_id, "published")` : "doc_id에 해당하는 그 문서의 상태를 'published'(발행됨)로 바꿔라"

- `delete_document(doc_id)` : "doc_id에 해당하는 그 문서를 삭제해라"

## | 4장 2강 : 질문·응답 로그 테이블 구현

### 코드 ① : documents 테이블 만들기 (복습)

```sql
create table documents (
  id bigint generated always as identity primary key,
  user_id uuid references auth.users (id),
  title text not null,
  content text,
  status text default 'draft' check (status in ('draft', 'published', 'archived')),
  created_at timestamptz default now()
);
```

- `create table documents (` : "documents라는 이름의 새 표를 만들겠다. 그 안에 들어갈 열(컬럼)들은 아래와 같다"
- `id bigint generated always as identity primary key,`
  - `id` : 열 이름
  - `bigint` : 이 열엔 아주 큰 정수(숫자)만 들어간다는 뜻
  - `generated always as identity` : "이 값은 사람이 입력하지 말고, 새 행이 추가될 때마다 컴퓨터가 자동으로 1, 2, 3... 번호를 매겨라"
  - `primary key` : "이 열의 값으로 각 행을 구별한다. 절대 중복되면 안되고, 비어있어도 안 된다" (기본키)
- `user_id uuid references auth.users (id),`
  - `uuid` : 아주 길고 복잡한 형태의 고유 식별자 타입 (예: `1804e97c-5e28-...`)
  - `references auth.users (id)` : "이 user_id 값은 반드시 auth.users라는 표(회원 목록)에 있는 id 값이어야 한다" (외래키 - 존재하지 않는 회원 번호는 못 넣게 막아줌)
- `title text not null,` : "title 열은 글자(text)를 담고, 반드시 값이 있어야 한다(not null = 비어있으면 안됨)"
- `content text,` : "content 열은 글자를 담고, 비어있어도 상관없다" (not null이 없으니까)
- `status text default 'draft' check (status in ('draft', 'published', 'archived')),`
  - `default 'draft'` : "값을 안 넣으면 자동으로 'draft'(초안)를 넣어라"
  - `check (status in (...))` : "이 열의 값은 반드시 'draft', 'published', 'archived' 이 셋 중 하나여야 한다. 아니면 저장을 거부해라"
- `created_at timestamptz default now()` : "이 열은 시간대 포함 시각을 담고, 값을 안 넣으면 자동으로 지금 이 순간의 시각을 넣어라"

### 코드 ② : queries 테이블 만들기

```sql
create table queries (
  id bigint generated always as identity primary key,
  user_id uuid references auth.users (id),
  document_id bigint references documents (id),
  question text not null,
  status text default 'pending' check (status in ('pending', 'completed', 'failed')),
  created_at timestamptz default now()
);
```

- 위 documents와 구조는 똑같은 패턴이고, 새로운 부분만 짚으면:
- `document_id bigint references documents (id),` : "이 값은 반드시 documents 표에 실제로 있는 id 값이어야 한다" → 즉 "이 질문이 어느 문서에 대한 질문인지"를 연결해주는 열
- `question text not null,` : 질문 내용, 반드시 있어야 함
- `status text default 'pending' check (...)` : 상태값은 기본이 'pending'(대기중)이고, 'pending'/'completed'/'failed' 중 하나여야 함

### 코드 ③ : query_logs 테이블 만들기

```sql
create table query_logs (
  id bigint generated always as identity primary key,
  query_id bigint references queries (id),
  answer text,
  model_name text,
  status text default 'success' check (status in ('success', 'error')),
  error_message text,
  created_at timestamptz default now()
);
```

- `query_id bigint references queries (id),` : "이 응답이 어떤 질문에 대한 응답인지" queries 표와 연결
- `answer text,` : AI가 만든 답변 텍스트 (없어도 됨)
- `model_name text,` : 어떤 AI 모델이 답했는지 이름 (예: 'gpt-4o-mini')
- `status ... default 'success' check (status in ('success', 'error'))` : 성공/실패 상태
- `error_message text,` : 실패했을 때 왜 실패했는지 적어두는 열

### 코드 ④ : 더미 데이터 넣고 조회해보기

```sql
insert into queries (user_id, document_id, question, status)
values
  ('00000000-0000-0000-0000-000000000001', 1, 'useEffect는 언제 실행되나요?', 'completed'),
  ('00000000-0000-0000-0000-000000000001', 1, 'useState와 useRef의 차이는?', 'completed');
```

- `insert into queries (user_id, document_id, question, status)` : "queries 표에, user_id·document_id·question·status 이 4개 열에 값을 채워서 새 행을 넣겠다"
- `values (...), (...);` : 콤마로 구분해서 여러 개의 행을 한 번에 넣을 수 있다. 여기선 2개 행을 동시에 넣음
- 각 괄호 안 값들은 순서대로 위에 나열한 열 이름에 하나씩 짝지어 들어간다. (`user_id`='00000000...', `document_id`=1, `question`='useEffect는...', `status`='completed')
- `id`와 `created_at`은 안 적었는데, 이유는 앞서 배운 것처럼 자동으로 채워지는 열이기 때문

```sql
insert into query_logs (query_id, answer, model_name, status)
values
  (1, '렌더링이 끝난 뒤에 실행됩니다.', 'gpt-4o-mini', 'success'),
  (2, 'useState는 값이 바뀌면 리렌더링되고, useRef는 리렌더링되지 않습니다.', 'gpt-4o-mini', 'success');
```

- 같은 방식으로, `query_id`가 1인 질문에 대한 답변, `query_id`가 2인 질문에 대한 답변을 각각 넣은 것. (여기서 1, 2는 방금 위에서 자동으로 생성된 질문들의 id다)

```sql
select id, question, status, created_at
from queries
where user_id = '00000000-0000-0000-0000-000000000001'
order by created_at desc;
```

- `select id, question, status, created_at` : "id, question, status, created_at 이 4개 열만 보여줘"
- `from queries` : "queries 표에서"
- `where user_id = '00000000-...'` : "근데 user_id가 이 특정 값과 정확히 일치하는 행만"
- `order by created_at desc` : "그 결과를 created_at(만든 시각) 기준으로, desc(내림차순 = 최신순)로 정렬해서 보여줘"

```sql
select q.question, l.answer, l.model_name
from queries q
join query_logs l on l.query_id = q.id
where q.document_id = 1
order by q.created_at desc;
```

- `from queries q` : "queries 표를 가져오는데, 앞으로는 이걸 q라는 짧은 별명으로 부르겠다"
- `join query_logs l on l.query_id = q.id` : "query_logs 표(별명 l)도 같이 가져오는데, l의 query_id 값과 q의 id 값이 같은 행끼리 옆으로 이어붙여라"
- `q.question, l.answer, l.model_name` : q 표의 question 열, l 표의 answer·model_name 열을 나란히 보여줘라 (별명.열이름 형태로 어느 표의 열인지 명시)
- `where q.document_id = 1` : "그 중에서도 q의 document_id가 1인 것만"
- `order by q.created_at desc` : 최신순 정렬

## | 4장 3강 : SDK 기반 질문·응답 로그 저장

### 코드 ① : Supabase에 접속할 준비하기

```python
import os
from dotenv import load_dotenv
from supabase import create_client, Client

# .env 파일의 값을 환경변수로 불러오기
load_dotenv()

url = os.environ.get("SUPABASE_URL")
key = os.environ.get("SUPABASE_PUBLISHABLE_KEY")

# Client 초기화
supabase: Client = create_client(url, key)
```

- `import os` : "os"라는, 컴퓨터 환경(설정값 등)을 다루는 파이썬 기본 도구 모음을 가져와서 쓰겠다
- `from dotenv import load_dotenv` : "dotenv"라는 외부 도구 상자에서 `load_dotenv`라는 기능 하나만 콕 집어서 가져오겠다
- `from supabase import create_client, Client` : "supabase" 도구 상자에서 `create_client`와 `Client` 두 가지를 가져오겠다
- `load_dotenv()` : `.env`라는 별도 파일(비밀번호·주소 같은 민감한 값들을 코드에 직접 안 적고 따로 보관해두는 파일)의 내용을 지금 이 프로그램이 쓸 수 있게 불러온다
- `url = os.environ.get("SUPABASE_URL")` : 방금 불러온 값들 중에서 "SUPABASE_URL"이라는 이름표가 붙은 값(우리 Supabase 프로젝트 주소)을 꺼내서 `url`에 담는다
- `key = os.environ.get("SUPABASE_PUBLISHABLE_KEY")` : 마찬가지로 접속에 필요한 "열쇠(key)" 값을 꺼내서 `key`에 담는다
- `supabase: Client = create_client(url, key)` : "url과 key를 가지고 진짜로 Supabase에 접속하는 통로(client)를 하나 만들어서, 그걸 `supabase`라는 이름으로 저장해라." (`: Client`는 "이 변수는 Client 종류의 물건이다"라고 표시만 해두는 것, 실제 동작에는 큰 영향 없음)
- 이렇게 한 번 만들어둔 `supabase`를 앞으로 모든 코드에서 계속 재사용하게 된다.

### 코드 ② : 질문을 저장하는 함수

```python
def create_query(user_id: str, document_id: int, question: str):
    response = (
        supabase.table("queries")
        .insert({
            "user_id": user_id,
            "document_id": document_id,
            "question": question,
        })
        .execute()
    )
    return response.data[0]
```

- `def create_query(user_id: str, document_id: int, question: str):`
  - "`create_query`라는 함수를 만드는데, 이 함수를 쓸 때는 반드시 user_id(글자), document_id(숫자), question(글자) 이 3가지 재료를 넣어줘야 한다"
  - `: str`, `: int`는 "이 재료는 글자여야 한다", "이 재료는 숫자여야 한다"는 힌트 표시일 뿐, 강제로 막는 건 아니다.
- `response = ( ... )` : 괄호 안의 긴 코드를 실행한 결과를 `response`에 담겠다는 뜻. 괄호로 묶은 건 여러 줄에 걸쳐 써도 하나의 명령문이라고 표시하기 위함
- `supabase.table("queries")` : queries 표로 간다
- `.insert({ "user_id": user_id, "document_id": document_id, "question": question, })`
  - `insert({ ... })` : 중괄호 안에 적은 `이름: 값` 짝들로 새 행을 하나 추가하겠다
  - `"user_id": user_id` : "user_id라는 열에는, 이 함수가 전달받은 user_id 값을 넣어라" (앞의 "user_id"는 표의 열 이름, 뒤의 user_id는 함수 재료 이름 — 이름이 같아서 헷갈릴 수 있지만 역할이 다름)
- `.execute()` : 지금까지 준비한 명령을 진짜로 실행해라
- `return response.data[0]`
  - `return` : 이 함수를 호출한 쪽에게 값을 돌려준다
  - `response.data` : 방금 저장하고 나서 돌려받은 결과 데이터 (보통 방금 만든 행 정보가 목록 형태로 들어있음)
  - `[0]` : 그 목록의 첫번째(0번째) 항목만 꺼낸다 (방금 만든 행은 하나뿐이니까)
  - 전체 뜻 : "방금 새로 만든 질문 행의 정보를 돌려줘라"

## | 4장 4강 : 트랜잭션이 필요한 AI 데이터 처리 시나리오

### 코드 ① : 정상 처리(COMMIT)와 실패 취소(ROLLBACK) 비교

```sql
-- 정상 처리 흐름 (COMMIT)
begin;

insert into queries (user_id, document_id, question, status)
values ('00000000-0000-0000-0000-000000000001', 1, 'useEffect는?', 'completed');

insert into query_logs (query_id, answer, model_name, status)
values (currval(pg_get_serial_sequence('queries', 'id')), '렌더링 후 실행됩니다.', 'gpt-4o-mini', 'success');

commit;
```

- `begin;` : "지금부터 여러 명령을 하나로 묶는 트랜잭션을 시작한다"
- 첫번째 `insert` : queries 표에 새 질문 행 추가
- `currval(pg_get_serial_sequence('queries', 'id'))` : 방금 막 만들어진 질문 행의 id값을 "지금 막 발급된 번호 그대로" 가져오는 postgreSQL 함수. 즉 "방금 위에서 만든 질문의 id가 몇번인지 다시 물어보는 것" (수동으로 숫자를 알아내지 않아도, DB가 방금 부여한 번호를 그대로 재활용하게 해줌)
- 두번째 `insert` : 그 방금 생성된 질문 id를 `query_id`로 삼아서 응답 로그를 추가
- `commit;` : "지금까지 한 모든 변경사항을 확정(진짜로 저장)해라"

```sql
-- 실패 및 취소 흐름 (ROLLBACK)
begin;

insert into queries (user_id, document_id, question, status)
values ('00000000-0000-0000-0000-000000000001', 1, '취소될 질문', 'completed');

-- 응답 저장이 실패했다고 가정하고 ROLLBACK 실행
rollback;

-- 아래 조회 결과가 0건이면 ROLLBACK으로 질문 저장이 깔끔하게 되돌려진 거예요.
select * from queries where question = '취소될 질문';
```

- `begin;` : 트랜잭션 시작
- `insert into queries ...` : '취소될 질문'이라는 내용으로 질문 하나를 삽입 (아직 COMMIT은 안 했으니 확정된 건 아님)
- `rollback;` : "지금까지 한 모든 변경사항을 전부 취소하고, begin 이전 상태로 되돌려라"
- `select * from queries where question = '취소될 질문';` : "'취소될 질문'이라는 내용의 행이 진짜로 있는지 조회" → ROLLBACK이 제대로 됐다면, 이 조회 결과는 **0건**이 나와야 정상이다 (애초에 저장된 적이 없는 것처럼 사라짐)

### 코드 ② : 여러 저장을 하나의 함수(트랜잭션)로 묶기

```sql
create or replace function ask_and_log(
  p_user_id uuid,
  p_document_id bigint,
  p_question text,
  p_answer text,
  p_model_name text
)
returns bigint -- 생성된 query의 ID를 반환
language plpgsql
as $$
declare
  v_query_id bigint;
begin
  -- queries 테이블에 질문 저장 및 생성된 ID 추출
  insert into queries (user_id, document_id, question, status)
  values (p_user_id, p_document_id, p_question, 'completed')
  returning id into v_query_id;

  -- query_logs 테이블에 응답 로그 저장 (v_query_id 활용)
  insert into query_logs (query_id, answer, model_name, status)
  values (v_query_id, p_answer, p_model_name, 'success');

  -- 성공 시 생성된 query_id 반환
  return v_query_id;

-- PL/pgSQL 함수 실행 도중 오류가 발생하면 전체 과정이 자동으로 ROLLBACK 됩니다.
end;
$$;
```

- `create or replace function ask_and_log(...)` : "`ask_and_log`라는 이름의 함수를 새로 만든다. 이미 같은 이름이 있으면 덮어써라(replace)"
- 괄호 안의 `p_user_id uuid, p_document_id bigint, ...` : 이 함수를 실행할 때 받아야 할 재료 5개와 그 타입 (변수 앞에 `p_`를 붙인 건 "파라미터(parameter, 매개변수)"라는 걸 표시하려는 관례적인 이름짓기)
- `returns bigint` : "이 함수는 실행이 끝나면 정수(bigint) 하나를 결과로 돌려준다"
- `language plpgsql` : "이 함수는 PL/pgSQL이라는, PostgreSQL 전용의 프로그래밍 언어로 작성했다" (일반 SQL문 여러 개를 순서대로/조건부로 실행할 수 있게 해주는 확장 문법)
- `as $$ ... $$;` : `$$`로 감싼 부분이 이 함수의 실제 내용물이다 (마치 문자열을 따옴표로 감싸듯, 긴 코드 덩어리를 감싸는 표시)
- `declare v_query_id bigint;` : "이 함수 안에서 잠깐 쓸 임시 상자를 하나 만든다. 이름은 v_query_id, 정수를 담을 수 있다" (변수 선언)
- `begin ... end;` : 이 사이가 함수가 실제로 실행하는 명령들
- `insert into queries (...) values (...) returning id into v_query_id;`
  - 질문을 하나 저장하고
  - `returning id into v_query_id` : "방금 저장한 행의 id 값을, 아까 만들어둔 v_query_id 상자에 담아둬라" (저장하자마자 자동으로 생성된 번호를 바로 붙잡아두는 것)
- `insert into query_logs (...) values (v_query_id, ...);` : 방금 붙잡아둔 질문 id(v_query_id)를 이용해서 응답 로그도 저장
- `return v_query_id;` : 이 함수를 실행한 쪽에게 "방금 만든 질문의 id"를 돌려준다
- 마지막 주석 : "이 함수 안에서 도중에 뭔가 오류가 나면, 이미 실행됐던 insert까지 전부 자동으로 취소(ROLLBACK)된다"는 뜻. 즉 이 함수 하나를 실행하는 것 자체가 이미 "질문 저장 + 응답 저장"을 하나로 묶은 트랜잭션이 되는 것

### 코드 ③ : 파이썬에서 방금 만든 함수(RPC) 호출하기

  - `"ask_and_log"` : 실행할 함수의 이름

- `response = ` : 그 결과를 담기
- `print("저장 완료:", response.data)` : "저장 완료:"라는 글자와, 함수가 돌려준 결과(방금 만든 질문의 id)를 함께 출력

## | 4장 5강 : 데이터 품질과 접근 권한 점검

### 코드 ① : 빈 값(결측)과 중복 찾기

```sql
-- 제목이 비어 있는 문서 찾기
select id, user_id, title
from documents
where title is null or title = '';
```

- `where title is null or title = '';`
  - `title is null` : "title 열에 아예 값이 없는(NULL인) 경우"
  - `or title = ''` : "**또는** title 값이 있긴 한데 그냥 빈 글자('')인 경우"
  - 이 둘을 `or`로 묶어서, "값이 아예 없거나, 혹은 텅 빈 글자인 것 둘 다" 찾아낸다 (NULL과 빈 문자열은 서로 다른 개념이라, 둘 다 체크해줘야 진짜 "제목이 없는" 케이스를 놓치지 않음)

```sql
-- 같은 사용자가 같은 제목을 중복 등록했는지 찾기
select user_id, title, count(*) as cnt
from documents
group by user_id, title
having count(*) > 1;
```

- `group by user_id, title` : "user_id와 title, 이 두 값이 똑같은 것끼리 하나의 그룹으로 묶어라" (예: 같은 사람이 같은 제목으로 쓴 문서들끼리 뭉쳐짐)
- `count(*) as cnt` : 각 그룹에 몇개의 행이 뭉쳐졌는지 세서, 그 개수에 `cnt`라는 별명을 붙임
- `having count(*) > 1` : "그 그룹 중에서, 뭉쳐진 개수가 1개 초과(즉 2개 이상)인 그룹만 보여줘" → 진짜로 중복 등록된 경우만 걸러내는 것

### 코드 ② : 잘못된 상태값을 CHECK 제약이 막아주는 예시

```sql
-- status 허용값은 'draft' / 'published' / 'archived' 이므로 아래는 오류가 남
insert into documents (user_id, title, status)
values ((select id from auth.users limit 1), '테스트', 'deleted');
-- ERROR: new row violates check constraint
```

- `(select id from auth.users limit 1)` : 이 부분 자체가 하나의 작은 서브쿼리다. "auth.users 표에서 id값 하나만, 그 중 1개(`limit 1`)만 가져와라"는 뜻 → 진짜 존재하는 회원 id를 하나 빌려와서 그대로 쓰는 것
- `'deleted'` : status에 넣으려는 값인데, 이 표는 'draft'/'published'/'archived'만 허용하도록 `CHECK` 제약이 걸려있었다 (4장2강 코드①에서 만들 때 걸어둠). 그래서 'deleted'는 허용되지 않은 값이라 저장이 거부되고 오류가 난다.
- 즉 이 코드는 "일부러 규칙을 어겨서, CHECK 제약이 진짜로 막아주는지 확인해보는" 테스트용 코드다.

### 코드 ③ : RLS(행 단위 보안)로 본인 데이터만 보이게 만들기

```sql
-- documents 테이블에 RLS 켜기
alter table documents enable row level security;

-- 본인 문서만 조회 허용하는 정책
create policy "Users can view own documents"
on documents
for select
using (auth.uid() = user_id);
```

- `alter table documents enable row level security;` : "documents 표에 행 단위 보안(RLS) 기능을 켜라" (이걸 켜야 아래 정책이 실제로 작동함)
- `create policy "Users can view own documents"` : "'Users can view own documents'라는 이름의 규칙(정책)을 하나 만든다"
- `on documents` : "이 규칙은 documents 표에 적용된다"
- `for select` : "이 규칙은 조회(SELECT)할 때 적용된다" (수정이나 삭제에는 적용 안 됨, 따로 정책을 또 만들어야 함)
- `using (auth.uid() = user_id)`
  - `auth.uid()` : "지금 로그인한 사람의 id를 알려주는 함수"
  - `auth.uid() = user_id` : "그 값이, 이 행의 user_id 열과 똑같은 경우에만" 이 행을 보여줘라
  - 전체 뜻 : "documents를 조회할 때는, 자기가 쓴 문서(user_id가 자기 자신인 것)만 보이게 해라"

```sql
-- 로그인한 사용자가 자신의 문서만 보이는지 확인
select id, title, user_id
from documents;
-- RLS가 적용되면 auth.uid()와 user_id가 같은 행만 나옴
```

- 이 SELECT문 자체는 특별한 조건이 없어 보이지만, 방금 켜둔 RLS 정책이 자동으로 "숨은 조건"처럼 뒤에서 적용된다. 그래서 겉으로는 그냥 `select * from documents` 처럼 보여도, 실제로는 로그인한 사람 것만 보이게 된다.

## | 4장 6강 : 통합 프로젝트 1 — DB 스키마와 샘플 데이터 완성

### 코드 ① : 4개 표를 순서대로 만드는 최종 schema.sql

```sql
-- 1) 문서
create table documents (
  id bigint generated always as identity primary key,
  user_id uuid references auth.users (id),
  title text not null,
  content text,
  status text default 'draft' check (status in ('draft', 'published', 'archived')),
  created_at timestamptz default now()
);

-- 2) 사용자 질문
create table queries (
  id bigint generated always as identity primary key,
  user_id uuid references auth.users (id),
  document_id bigint references documents (id) on delete cascade,
  question text not null,
  status text default 'pending' check (status in ('pending', 'completed', 'failed')),
  created_at timestamptz default now()
);

-- 3) 모델 응답 로그
create table query_logs (
  id bigint generated always as identity primary key,
  query_id bigint references queries (id) on delete cascade,
  answer text,
  model_name text,
  status text default 'success' check (status in ('success', 'error')),
  error_message text,
  created_at timestamptz default now()
);

-- 4) 피드백
create table feedbacks (
  id bigint generated always as identity primary key,
  query_log_id bigint references query_logs (id) on delete cascade,
  score int check (score between 1 and 5),
  comment text,
  created_at timestamptz default now()
);
```

- 앞서 만든 documents, queries, query_logs 표에 새로 눈에 띄는 부분만 짚으면:
- `document_id bigint references documents (id) on delete cascade,`
  - 이전엔 없던 `on delete cascade`가 추가됐다.
  - 뜻 : "documents 표에서 부모 문서가 삭제되면, 그걸 참조하고 있던 이 queries 행도 자동으로 같이 삭제해라"
- `query_id bigint references queries (id) on delete cascade,` : 같은 원리로, 질문이 삭제되면 그 응답 로그도 같이 삭제
- 새로 나온 `feedbacks` 표 :
  - `query_log_id bigint references query_logs (id) on delete cascade,` : 어떤 응답에 대한 피드백인지 연결, 그 응답이 삭제되면 피드백도 같이 삭제
  - `score int check (score between 1 and 5),` : "score는 정수이고, 1 이상 5 이하여야 한다" (별점 같은 개념)
  - `comment text,` : 피드백 코멘트, 없어도 됨

### 코드 ② : 순서에 맞게 샘플 데이터(seed) 넣기

```sql
-- 문서
insert into documents (user_id, title, content, status)
values
  ('00000000-0000-0000-0000-000000000001', 'React 공식 문서', 'React Hooks 설명...', 'published'),
  ('00000000-0000-0000-0000-000000000001', 'Supabase 가이드', 'Supabase 시작하기...', 'published');

-- 질문
insert into queries (user_id, document_id, question, status)
values
  ('00000000-0000-0000-0000-000000000001', 1, 'useEffect는 언제 실행되나요?', 'completed'),
  ('00000000-0000-0000-0000-000000000001', 2, 'RLS는 어떻게 켜나요?', 'completed');

-- 응답 로그
insert into query_logs (query_id, answer, model_name, status)
values
  (1, '렌더링이 끝난 뒤 실행됩니다.', 'gpt-4o-mini', 'success'),
  (2, 'alter table ... enable row level security 로 켭니다.', 'gpt-4o-mini', 'success');

-- 피드백
insert into feedbacks (query_log_id, score, comment)
values
  (1, 5, '정확해요'),
  (2, 4, '도움이 됐어요');
```

- 4개의 `insert`가 위에서 아래로 순서대로 실행된다. **이 순서가 중요한 이유** : queries가 documents를 참조하고, query_logs가 queries를 참조하고, feedbacks가 query_logs를 참조하기 때문에, **부모 데이터가 먼저 존재해야만** 자식 데이터를 넣을 수 있다. (부모도 없는데 자식부터 넣으려 하면 외래키 오류가 남)
- 각 문장 안의 숫자(`1`, `2`)는 앞서 넣은 행들의 id를 그대로 손으로 적어넣은 것. (실습이라 직접 숫자를 알고 있으니 이렇게 쓴 것이고, 진짜 서비스에서는 코드④의 `returning id into ...`처럼 자동으로 받아서 씀)

### 코드 ③ : 4개 표를 한번에 이어서 검증하기

```sql
select
  d.title,
  q.question,
  l.answer,
  f.score
from documents d
join queries q on q.document_id = d.id
join query_logs l on l.query_id = q.id
left join feedbacks f on f.query_log_id = l.id
order by d.id;
```

- `from documents d` : documents 표를 `d`라는 별명으로
- `join queries q on q.document_id = d.id` : queries 표(별명 q)를, "q의 document_id가 d의 id와 같은" 행끼리 이어붙인다 (INNER JOIN)
- `join query_logs l on l.query_id = q.id` : query_logs 표(별명 l)를, "l의 query_id가 q의 id와 같은" 행끼리 이어붙인다
- `left join feedbacks f on f.query_log_id = l.id`
  - 여기만 `left join`을 쓴 이유 : 아직 피드백이 안 달린 응답도 있을 수 있으니까, "feedbacks가 없어도 앞의 결과(문서·질문·답변)는 그대로 다 보여주고, 피드백만 있으면 붙이고 없으면 NULL로 비워둬라"는 뜻
- `select d.title, q.question, l.answer, f.score` : 4개 표에서 각각 필요한 열 하나씩만 뽑아서 나란히 보여줌
- `order by d.id;` : 문서 id 순서로 정렬

```sql
-- 999번 문서는 없으므로 오류가 남
insert into queries (user_id, document_id, question)
values ('00000000-0000-0000-0000-000000000001', 999, '없는 문서 질문');
-- ERROR: insert violates foreign key constraint
```

- `document_id`에 `999`를 넣으려 하는데, 실제로 documents 표에는 id가 999인 문서가 없다. `references documents (id)`로 외래키가 걸려있어서, 존재하지 않는 문서를 가리키는 값은 저장이 거부된다 — 이게 바로 참조 무결성이 실제로 지켜지는 순간이다.

### 코드 ② : 문서 CRUD 4종 함수

```python
def create_document(user_id: str, title: str, content: str):
    return (
        supabase.table("documents")
        .insert({"user_id": user_id, "title": title, "content": content})
        .execute()
        .data[0]
    )

def get_documents(user_id: str):
    return (
        supabase.table("documents")
        .select("*")
        .eq("user_id", user_id)
        .order("created_at", desc=True)
        .execute()
        .data
    )

def update_document(document_id: int, new_title: str):
    return (
        supabase.table("documents")
        .update({"title": new_title})
        .eq("id", document_id)
        .execute()
        .data
    )

def delete_document(document_id: int):
    return (
        supabase.table("documents")
        .delete()
        .eq("id", document_id)
        .execute()
        .data
    )
```

- 여기서부턴 앞서 배운 것들과 패턴이 겹치니, **새로 나온 것만** 짚는다.
- `def create_document(...): return (...)` : 이전 코드들은 `response = (...)`로 담아두고 그 다음 줄에서 `return response.data[0]`을 했는데, 여기선 그 두 단계를 `return (...).data[0]`처럼 **한 번에** 이어 쓴 것. 결과는 똑같다.
- `.update({"title": new_title}).eq("id", document_id)`
  - `.update({...})` : "이 표의 행을 수정하겠다. title 열을 new_title 값으로 바꿔라"
  - `.eq("id", document_id)` : "근데 id가 document_id와 같은 행만" (이 조건이 없으면 표 전체가 수정될 뻔한 위험한 코드가 됨 — 이전에 배운 "eq()를 빼먹으면 위험하다"가 바로 이 상황)
- `.delete().eq("id", document_id)` : "id가 document_id와 같은 행만 삭제해라" (마찬가지로 eq()가 필수)

### 코드 ③ : 질문 저장 + 응답까지 한번에 이어붙이기

```python
def ask_question(user_id: str, document_id: int, question: str):
    # 1) 질문 저장
    query = create_query(user_id, document_id, question)

    # 2) 더미 LLM 응답 생성
    dummy_answer = f"'{question}'에 대한 더미 응답입니다."

    # 3) 응답 로그 저장
    log = save_query_log(query["id"], dummy_answer, "gpt-4o-mini")
    return query, log
```

- `query = create_query(user_id, document_id, question)` : 앞서 만들어둔 함수를 그대로 재사용해서 질문 저장, 그 결과를 `query`에 담기
- `dummy_answer = f"'{question}'에 대한 더미 응답입니다."`
  - `f"..."` : 문자열 앞에 `f`를 붙이면, 중괄호 `{ }` 안에 변수를 넣어서 그 변수의 실제 값을 문자열 안에 끼워넣을 수 있다 ("f-string"이라고 부름)
  - 예를 들어 question이 "useEffect는?"이라면, 결과는 `"'useEffect는?'에 대한 더미 응답입니다."`가 된다
- `log = save_query_log(query["id"], dummy_answer, "gpt-4o-mini")` : 방금 만든 질문의 id, 방금 만든 가짜 답변, 모델 이름으로 응답 로그 저장
- `return query, log` : 질문 정보와 로그 정보, **두 개를 한꺼번에** 돌려준다 (파이썬에서는 콤마로 구분해서 여러 값을 동시에 return 할 수 있다)

### | 이번 정리에서 얻어가는 것

- 코드 한 줄 한 줄을 뜯어보면, 결국 SQL이든 파이썬이든 전부 **"사람이 이해하는 말을, 컴퓨터가 알아듣는 정해진 문법으로 그대로 옮겨적은 것"**일 뿐이다.
- 함수(`def`) 안에 있는 코드도, 결국 우리가 SQL Editor에서 직접 실행하던 SQL 문장들을, 파이썬이 대신 실행해주도록 포장해놓은 것에 불과하다.
- 트랜잭션(`begin ~ commit/rollback`)이나 RPC 함수도, 결국 "여러 SQL 문장을 순서대로, 안전하게 묶어서 실행한다"는 지금까지 배운 개념을 코드로 구현한 것뿐이다.
