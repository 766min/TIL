## | ⚠️ 위험 행동 체크리스트 ① : "런(Run)을 반복하면 생기는 문제"

- 실습할 때는 같은 스크립트를 여러 번 실행하는 일이 정말 많다. 근데 SQL은 **"다시 실행해도 안전한 코드"와 "다시 실행하면 사고나는 코드"가 따로 있다.** 이걸 모르면 실습 중에 이상한 에러나 이상한 데이터가 계속 쌓이는 걸 겪게 된다.

### - 문제 1 : CREATE TABLE을 두 번 실행하면 에러가 난다

```sql
CREATE TABLE members (
  id INT PRIMARY KEY,
  name VARCHAR(50)
);
```
- 이 코드를 한 번 실행해서 표가 생긴 상태에서, **똑같은 코드를 또 실행하면** `ERROR: relation "members" already exists` 에러가 난다. (이미 있는 표를 또 만들려고 하니까)

- 해결법 ① : 실행하기 전에 먼저 지우고 새로 만들기
```sql
DROP TABLE IF EXISTS members;   -- 있으면 지우고, 없으면 그냥 넘어감(에러 안남)
CREATE TABLE members (
  id INT PRIMARY KEY,
  name VARCHAR(50)
);
```
- 해결법 ② : 없을 때만 만들게 하기
```sql
CREATE TABLE IF NOT EXISTS members (
  id INT PRIMARY KEY,
  name VARCHAR(50)
);
```
  - 이렇게 하면 표가 이미 있으면 아무 일도 안 하고, 없을 때만 새로 만들어서 몇 번을 실행해도 에러가 안 난다.

### - 문제 2 : INSERT를 실행할 때마다 데이터가 계속 쌓인다

```sql
INSERT INTO members (id, name) VALUES (1, '홍길동');
```
- 이 코드를 실습하다가 **까먹고 두세 번 더 실행**하면, `id=1`이 중복되어 PK 에러가 나거나(PK가 걸려있으면), PK가 없다면 똑같은 데이터가 여러 줄 쌓여버린다.

- 해결법 : 실습을 새로 시작할 때는 항상 **DROP → CREATE → INSERT** 세트를 한 번에 통째로 다시 실행하는 습관을 들인다. 이렇게 스크립트 하나를 몇 번을 실행해도 항상 "깨끗한 처음 상태"로 돌아가게 짜는 걸 **"멱등성(몇 번을 실행해도 결과가 같음)이 있는 스크립트"**라고 부른다. 실무에서도 마이그레이션·시드 스크립트를 이렇게 짜는게 기본이다.

### - 오늘 쓸 실습용 스키마 스크립트 (이 파일 통째로 몇 번이든 다시 실행해도 안전함)

```sql
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS books;
DROP TABLE IF EXISTS members;

CREATE TABLE members (
  id INT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  email VARCHAR(100) UNIQUE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE books (
  id INT PRIMARY KEY,
  title VARCHAR(100) NOT NULL,
  category VARCHAR(30),
  price DECIMAL(10,2),
  stock INT DEFAULT 0
);

CREATE TABLE orders (
  id INT PRIMARY KEY,
  member_id INT REFERENCES members(id),
  book_id INT REFERENCES books(id),
  quantity INT NOT NULL,
  order_date TIMESTAMPTZ DEFAULT NOW()
);

INSERT INTO members (id, name, email) VALUES
  (1, '홍길동', 'hong@test.com'),
  (2, '김철수', 'kim@test.com'),
  (3, '이영희', 'lee@test.com');

INSERT INTO books (id, title, category, price, stock) VALUES
  (1, 'SQL 첫걸음', 'IT', 18000, 50),
  (2, '파이썬 입문', 'IT', 22000, 30),
  (3, '소설 하나', '소설', 13500, 20),
  (4, '에세이 모음', '에세이', 15000, 0);

INSERT INTO orders (id, member_id, book_id, quantity) VALUES
  (1, 1, 1, 2),
  (2, 1, 2, 1),
  (3, 2, 1, 1),
  (4, 3, 3, 3);
```

- 이 스크립트를 SQL Editor에 붙여넣고 실행하면, 매번 표를 깨끗하게 초기화하면서 시작할 수 있다. **연습 도중 꼬였다 싶으면 이 스크립트를 다시 통째로 실행**하면 처음 상태로 복구된다.

## | STEP 1. SELECT 기초부터 탄탄하게

```sql
-- 1. 전체 조회
SELECT * FROM books;

-- 2. 필요한 열만
SELECT title, price FROM books;

-- 3. 조건 걸기
SELECT * FROM books WHERE category = 'IT';

-- 4. 범위 조건
SELECT * FROM books WHERE price BETWEEN 15000 AND 20000;

-- 5. 패턴 검색
SELECT * FROM books WHERE title LIKE '%입문%';

-- 6. 여러 값 중 하나
SELECT * FROM books WHERE category IN ('IT', '소설');

-- 7. 정렬 + 상위 n개
SELECT * FROM books ORDER BY price DESC LIMIT 2;
```

### ⚠️ 오해하기 쉬운 코드 — STEP 1

- **`SELECT *`를 습관적으로 쓰기** : 학습할 땐 편하지만, 실무에서는 필요한 열만 콕 집어서 쓰는게 기본이다. (이유 : 성능, 가독성, 테이블 구조 변경 시 사고 위험 — 09-04 노트 참고)

- **`WHERE stock = NULL`처럼 쓰기** : 이렇게 쓰면 **항상 아무 결과도 안 나온다.** NULL은 `=`로 비교가 안되고 반드시 `IS NULL`을 써야 한다.
```sql
-- 틀림 (결과 항상 0건)
SELECT * FROM books WHERE stock = NULL;
-- 맞음
SELECT * FROM books WHERE stock IS NULL;
-- 지금 스키마에서 "재고가 0인 책"을 찾고 싶다면 IS NULL이 아니라 이렇게 써야 함
SELECT * FROM books WHERE stock = 0;
```
  - 여기서 헷갈리기 쉬운 포인트 : **"값이 없다(NULL)"**과 **"값이 0이다"**는 완전히 다르다. `에세이 모음`은 stock이 0으로 채워져있지 NULL이 아니라서, `IS NULL`로 찾으면 안 걸린다.

- **`BETWEEN`을 "미만"으로 착각하기** : `BETWEEN 15000 AND 20000`은 15000 이상 **20000 이하**(둘 다 포함)다. "20000 미만"이 아니다.

## | STEP 2. 집계함수 & GROUP BY / HAVING 탄탄하게

```sql
-- 1. 기본 집계
SELECT COUNT(*) AS 전체책수, AVG(price) AS 평균가격, SUM(stock) AS 총재고
FROM books;

-- 2. 카테고리별로 묶어서 집계
SELECT category, COUNT(*) AS 책수, ROUND(AVG(price), 0) AS 평균가격
FROM books
GROUP BY category;

-- 3. 그룹 결과를 다시 조건으로 거르기 (HAVING)
SELECT category, COUNT(*) AS 책수
FROM books
GROUP BY category
HAVING COUNT(*) >= 2;

-- 4. 회원별 총 구매 수량
SELECT member_id, SUM(quantity) AS 총구매수량
FROM orders
GROUP BY member_id
ORDER BY 총구매수량 DESC;
```

### ⚠️ 오해하기 쉬운 코드 — STEP 2

- **SELECT에 집계함수 아닌 열을 같이 쓰면서 GROUP BY를 빠뜨리기** : 아래 코드는 에러가 난다.
```sql
-- 에러남 : title은 집계함수가 아닌데 GROUP BY에 없음
SELECT category, title, COUNT(*) FROM books GROUP BY category;
```
- **`COUNT(*)`와 `COUNT(컬럼)`을 같은 걸로 착각하기** : `COUNT(*)`는 NULL 포함 전체 행 수, `COUNT(컬럼)`은 그 컬럼이 NULL이 아닌 행만 센다.
- **WHERE 자리에 집계 조건을 넣으려 하기** : `WHERE COUNT(*) >= 2`는 에러난다. 집계 결과를 거를 땐 무조건 HAVING.

## | STEP 3. 테이블 결합 (JOIN)

```sql
-- 1. 주문 내역에 회원 이름, 책 제목 붙여서 보기
SELECT o.id AS 주문번호, m.name AS 회원, b.title AS 책, o.quantity AS 수량
FROM orders o
JOIN members m ON o.member_id = m.id
JOIN books b ON o.book_id = b.id;

-- 2. 한 번도 주문 안 한 회원까지 포함해서 보기 (LEFT JOIN)
SELECT m.name, o.id AS 주문번호
FROM members m
LEFT JOIN orders o ON m.id = o.member_id;

-- 3. 회원별 총 결제금액 (JOIN + 집계 조합)
SELECT m.name, SUM(b.price * o.quantity) AS 총결제금액
FROM members m
JOIN orders o ON m.id = o.member_id
JOIN books b ON o.book_id = b.id
GROUP BY m.name
ORDER BY 총결제금액 DESC;
```

### ⚠️ 오해하기 쉬운 코드 — STEP 3

- **JOIN 후에 생기는 중복행(fan-out)을 모르고 집계하기** : 위 예시③처럼 세 표를 JOIN한 다음 바로 `COUNT(m.id)`를 하면, 회원 한 명이 주문을 여러 번 했을 경우 그 회원이 여러 번 중복 카운트된다. 순수하게 "회원 수"를 세고 싶으면 `COUNT(DISTINCT m.id)`를 써야 한다.
- **별칭 없이 같은 컬럼명(`id`) 쓰기** : `members`와 `books`, `orders` 모두 `id`라는 컬럼이 있어서, 별칭 없이 그냥 `id`라고만 쓰면 "column reference is ambiguous(모호하다)" 에러가 난다. 항상 `m.id`, `b.id`처럼 어느 표 것인지 명시해야 한다.

## | STEP 4. 서브쿼리

```sql
-- 1. WHERE절 서브쿼리 : 평균가보다 비싼 책
SELECT title, price
FROM books
WHERE price > (SELECT AVG(price) FROM books);

-- 2. IN + 서브쿼리 : 주문된 적 있는 책만
SELECT title FROM books
WHERE id IN (SELECT DISTINCT book_id FROM orders);

-- 3. EXISTS : 한 번도 주문 안 한 회원 (NOT IN보다 안전)
SELECT name FROM members m
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.member_id = m.id
);

-- 4. FROM절 서브쿼리(인라인 뷰) : 카테고리별 매출 집계 후 다시 필터링
SELECT category, 매출
FROM (
  SELECT b.category AS category, SUM(b.price * o.quantity) AS 매출
  FROM books b
  JOIN orders o ON b.id = o.book_id
  GROUP BY b.category
) AS category_sales
WHERE 매출 >= 30000;
```

### ⚠️ 오해하기 쉬운 코드 — STEP 4

- **`NOT IN` + 서브쿼리에 NULL이 섞여있으면 결과가 통째로 0건이 되는 함정** : 지금 스키마엔 NULL이 없어서 안전하지만, `member_id`가 NULL인 주문이 하나라도 있었다면 `WHERE member_id NOT IN (SELECT member_id FROM orders)`는 전부 빈 결과가 나온다. 그래서 위 예시③처럼 `NOT EXISTS`를 쓰는게 더 안전하다.
- **인라인 뷰에 별칭(AS)을 안 붙이기** : FROM절 서브쿼리는 반드시 이름표(별칭)를 붙여야 하고, 안 붙이면 에러난다.

## | STEP 5. 제약조건 & 관계 복습 (PK / FK / 1:1·1:N·N:M)

- 방금 만든 스키마를 놓고 관계를 확인해보자.

  - `members` : `orders`  ->  1:N (한 회원이 여러 주문 가능, FK는 orders.member_id에 있음)
  - `books` : `orders`  ->  1:N (한 책이 여러 주문에 등장 가능, FK는 orders.book_id에 있음)

```sql
-- FK 제약이 실제로 막아주는지 확인 (일부러 없는 회원번호로 주문 시도)
```

## | STEP 6. DML을 안전하게 연습하기 (INSERT / UPDATE / DELETE)

### ⚠️ 위험 행동 체크리스트 ② : UPDATE/DELETE는 항상 이 순서로

1. **먼저 SELECT로 확인** — 내가 지금 하려는 조건이 정확히 어떤 행을 가리키는지 눈으로 본다.
```sql
SELECT * FROM books WHERE id = 4;
```
2. **그 다음에야 UPDATE/DELETE로 바꿔서 실행**
```sql
UPDATE books SET stock = 10 WHERE id = 4;
DELETE FROM books WHERE id = 4;
```
3. **WHERE 없는 UPDATE/DELETE는 절대 실행 금지** — 조건을 빼먹으면 표 전체가 수정/삭제된다. (09-10 노트 "🔴 사고 등급" 참고)

```sql
-- 절대 이렇게 실행하면 안됨! (books 표 전체 재고가 0이 되어버림)
UPDATE books SET stock = 0;
```

## | STEP 7. 트랜잭션 실습 — "주문하면 재고가 줄어드는" 시나리오

- 실제 서비스라면 "주문 저장"과 "재고 차감"은 반드시 함께 성공하거나 함께 취소되어야 한다. 이걸 트랜잭션으로 묶어서 연습해보자.

```sql
BEGIN;

-- 1) 주문 추가
INSERT INTO orders (id, member_id, book_id, quantity) VALUES (5, 2, 2, 1);

-- 2) 그만큼 재고 차감
UPDATE books SET stock = stock - 1 WHERE id = 2;

COMMIT;

-- 확인
SELECT * FROM books WHERE id = 2;
```

- 만약 2번 재고 차감 단계에서 뭔가 잘못됐다고 가정하고 싶다면, `COMMIT` 대신 `ROLLBACK`을 실행해서 주문과 재고차감이 둘 다 취소되는지 확인해보자.

```sql
BEGIN;
INSERT INTO orders (id, member_id, book_id, quantity) VALUES (6, 3, 1, 1);
UPDATE books SET stock = stock - 1 WHERE id = 1;
ROLLBACK;   -- 취소!

-- 6번 주문도, 재고 차감도 둘 다 없었던 일이 되어있어야 정상
SELECT * FROM orders WHERE id = 6;
SELECT * FROM books WHERE id = 1;
```

## | 🤝 협업할 때 주의할 행동 (Supabase를 여러 명이 같이 쓸 때)

- **남의 표를 함부로 DROP/TRUNCATE 하지 않기** : 실습하다가 "일단 다 지우고 새로 하자"는 생각으로 전체 초기화 스크립트를 돌리면, 같은 프로젝트를 쓰는 팀원의 데이터까지 같이 날아간다. 내 연습용 표는 이름 앞에 `practice_`, `test_` 같은 접두어를 붙여서 남의 표와 확실히 구분하는게 안전하다.

- **스키마를 바꾸기 전(ALTER TABLE, DROP COLUMN 등) 팀원에게 미리 알리기** : 다른 사람이 그 컬럼을 이미 쓰고 있는 코드/쿼리가 있을 수 있다. 스키마 변경은 "나만의 작업"이 아니라 "팀 전체에 영향을 주는 작업"이라고 생각해야 한다.

- **더미 데이터를 넣을 때 자기 것임을 표시해두기** : 예를 들어 이름에 `[테스트]` 접두어를 붙이거나, 이메일을 `내이름+test@example.com`처럼 만들어서, 나중에 "이게 누가 넣은 테스트 데이터지?"하고 헷갈리지 않게 한다.

- **스키마(CREATE TABLE 문)는 SQL 파일로 만들어서 git으로 버전관리하기** : 실무에서는 `schema.sql`, `seed.sql` 같은 파일을 만들어서 깃 저장소에 올려두고, 팀원 모두가 "지금 우리 DB 구조가 정확히 어떻게 생겼는지" 코드로 추적할 수 있게 한다. (09-10 노트의 통합 프로젝트 schema.sql이 이 사례)

- **RLS(행 단위 보안)가 켜진 프로젝트에서는 "내 데이터가 안 보이는 게 정상일 수 있다"는 점 기억하기** : 협업 중에 "어? 방금 넣은 데이터가 안 보여요!" 하고 당황하는 경우가 많은데, RLS 정책 때문에 본인 것만 보이도록 막혀있는 정상 동작일 수 있다. 당황하지 말고 먼저 RLS 정책부터 확인하기.

## | 실무에서 바로 도움되는 습관 총정리

1. 스크립트는 항상 **"몇 번 실행해도 안전하게"**(DROP IF EXISTS → CREATE → INSERT) 짜는 습관을 들인다.
2. UPDATE/DELETE 전에는 **반드시 같은 조건으로 SELECT를 먼저** 돌려서 눈으로 확인한다.
3. 여러 테이블에 걸친 저장(재고 차감 + 주문 저장 등)은 **트랜잭션(BEGIN~COMMIT/ROLLBACK)으로 묶는다.**
4. NULL 비교는 `=`가 아니라 `IS NULL` / `IS NOT NULL`로 한다.
5. 서로 다른 표에 같은 컬럼명(`id` 등)이 있으면 **항상 별칭을 붙여서** 어느 표 것인지 명확히 한다.
6. 협업 환경에서는 **내 실습 데이터와 남의 데이터를 구분**하고, 스키마 변경은 팀에 미리 공유한다.
