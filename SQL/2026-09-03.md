## 공부한 내용 | SQL

### | 데이터 사이언티스트란

- 회사 안팎의 여러 데이터를 모으고, 정리하고, 분석해서, 통계나 머신러닝 같은 방법으로 비즈니스 문제를 해결하는 전문가

#### - 주로 하는 일

  - 데이터 수집 : 필요한 데이터를 여기저기서(데이터베이스, 로그, 외부자료) 모아온다. SQL로 직접 꺼내오는 경우가 많다.

  - 데이터 전처리 및 탐색 : 빠진 값, 이상한 값, 중복된 값을 손봐서 분석하기 좋은 형태로 정리한다. 이때 데이터를 미리 훑어보며 패턴을 파악하는 걸 EDA(탐색적 데이터 분석)라고 부른다.

  - 모델링 및 예측 분석 : 통계·머신러닝으로 예측 모델을 만든다. (예 : 이 고객이 곧 탈퇴할지 예측하기)

  - 모델 평가 및 개선 : 만든 모델이 얼마나 정확한지 점수를 매기고 더 좋게 다듬는다. (정확도, RMSE 같은 지표로 평가한다. RMSE는 '모델이 평균적으로 얼마나 틀렸는지'를 숫자로 나타낸 오차지표)

  - 인사이트 도출 및 적용 : 분석 결과를 리포트나 발표자료로 만들어서, 실제 회사 의사결정에 반영되게 한다.

#### - 핵심 역량 4가지

  - SQL : 데이터베이스에서 필요한 데이터를 직접 꺼내고 다듬는 능력

  - 파이썬 : 데이터 전처리·분석·시각화·머신러닝을 수행하는 능력

  - 통계 및 머신러닝 : 데이터 패턴을 이해하고 예측 모델을 만드는 능력

  - 비즈니스 커뮤니케이션 : 분석 결과를 전문가 아닌 사람에게도 쉽게 설명하는 능력

#### - 왜 모델링만 잘하면 안되나 ?

  - 모델을 만들기 전에 '어떤 데이터가 필요한지' 직접 찾아내고 다듬을 줄 알아야 한다.

  - SQL을 할 줄 알면, 매번 개발팀에게 데이터를 부탁하지 않고 스스로 빠르게 확인할 수 있어서, 일하는 속도가 훨씬 빨라진다.

### | 기본 용어 정리

- 데이터(Data) : 사실이나 정보를 나타내는 날것의 값

  - 이름, 나이, 구매금액, 날짜 같은 것들

  - 데이터 자체는 아무 의미가 없다가, 맥락과 함께 분석되면 '정보'가 된다.

- 데이터베이스(DB) : 데이터를 체계적으로 정리해둔 집합

  - 그냥 막 쌓아둔게 아니라, 빠르게 찾을 수 있게 구조화된 저장 공간 (예 : 도서관의 서가 시스템)

- 쿼리(Query) : 데이터베이스에게 보내는 질문이나 명령

- SQL(Structured Query Language) : 이 쿼리를 작성하는데 쓰는 표준 언어

  - '2024년에 가입한 회원 목록을 보여줘' 같은 자연어 질문을, SQL이라는 정해진 문법으로 바꿔서 물어보면, 데이터베이스가 알아듣고 답해준다.

#### | DBMS(Database Management System) : 데이터베이스를 관리해주는 프로그램

- 데이터베이스를 만들고, 관리하고, 운영하는 소프트웨어

- 사용자가 SQL로 뭔가 요청하면, DBMS가 그걸 해석해서 실제로 데이터를 저장하거나 찾아준다.

- RDBMS : 그 DBMS 중에서, "표 형태 + 관계"라는 특정 방식을 쓰는 하위 종류

##### | 주요 DBMS 종류

  - MySQL : 오픈소스, 가볍고 빠르다, 대표적으로 제일 많이 사용됨 -> 주로 쓰는 곳 : 웹서비스, 스타트업

  - PostgreSQL : 오픈소스, 기능이 풍부하고 안정적, 요즘 많이 사랑받음 -> 주로 쓰는 곳 : 데이터 분석, 대기업

    - 작은 따옴표(' ') : 문자열 리터럴을 감쌀 때 사용

      - 문자열 리터럴 : 코드안에 직접 써넣은 텍스트 값, '홍길동', '서울' 과 같은거

    - 큰 따옴표(" ") : 구분 식별자(컬럼, 테이블명)를 감쌀 때 사용 -> 특수문자가 포함되거나, 대소문자를 섞어쓰거나, 예약어를 이름으로 써야할 때 사용한다.

      - "user name"처럼 공백이 들어간 컬럼의 경우

      - 예약어(SELECT, ORDER같은 이미 문법응로 정해진 단어)를 이름으로 쓰고싶은 경우

      - PostgreSQL은 자동으로 전부 소문자로 인식하기때문에 대소문자를 정확하게 구분해서 쓰고싶을 때

  - Oracle : 유료, 대용량 처리에 강하다 -> 주로 쓰는 곳 : 금융, 공공기관

  - SQL Server : 마이크로소프트 제품, 윈도우 환경에 최적화 -> 주로 쓰는 곳 : 기업 환경

  - SQLite : 아주 가벼움, 파일 하나로 작동 -> 주로 쓰는 곳 : 모바일, 임베디드

  - MariaDB : MySQL에서 갈라져 나온 무료 버전 -> 주로 쓰는 곳 : 웹서비스

#### | 데이터 저장 모델 3가지

- 데이터를 저장하는 방식에 따라 크게 세가지로 나뉜다.

  - 계층형(HDBMS) : 부모-자식 관계로 저장 -> 상하 관계는 명확하지만 유연성이 낮다.

  - 관계형(RDBMS) : 표(행·열) 형태로 저장 -> 유연하고, SQL로 조회 가능해서 현재 대부분의 기업이 이걸 쓴다.

  - 망형(NDBMS) : 그물망처럼 복잡하게 연결된 구조 -> 복잡한 관계도 표현 가능하지만 만들기 어렵다.

- 왜 관계형(RDBMS)을 제일 많이 쓰는가 ?

  - 표 형태라서 사람이 직관적으로 이해하기 쉽다.

  - 여러 표를 서로 연결해서 복잡한 관계도 유연하게 표현 가능하다.

  - SQL이라는 공통 언어를 쓰기 때문에, 한 번 배우면 어느 회사, 어느 DBMS에서든 비슷하게 활용 가능하다.

  - 데이터가 안 깨지게 지켜주는 기능(무결성 보장), 안전하게 처리하는 기능(트랜잭션) 등이 잘 갖춰져 있다.

##### | 관계형 DB의 테이블 구조

- 관계형 DB에서 데이터는 테이블(표)이라는 2차원 구조로 저장된다.

  - 테이블 : 표 전체 묶음

  - 행(Row) : 데이터 항목 하나

    - 서로 다른 종류의 값들이 모여, 하나의 개체(entity)를 이루는 것

  - 열(Column) : 데이터의 속성(종류)

    - 같은 종류의 값이 세로로 쭉 모여있는것

    - 열에는 타입이 고정되어있다.

      - '나이'열은 처음부터 INT로 정해져 있어서, 그 열의 모든 값은 반드시 숫자여야 한다.

      - 제약조건도 열 단위로 걸린다.

  - 셀(Cell) : 행과 열이 만나는 한 칸

#### | SQL의 작성 순서와 실행 순서

- SQL은 '내가 쓰는 순서'와 '컴퓨터가 실제로 처리하는 순서'가 서로 다르다.

  - 작성 순서 : `SELECT` -> `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> `ORDER BY`

    - SELECT로 뭘 보여줄지(어떤 열을) 정하고 
    
    - FROM으로 어느 테이블에서 가져올지 정하고 
    
    - WHERE로 그 중에서 어떤 조건에 맞는 행만 볼지를 정하고 
    
    - GROUP BY로 (필요하면) 어떤 기준으로 묶어서 집계할지 정하고 
    
    - HAVING으로 묶은 결과 중에서 또 어떤 조건으로 걸러낼지 정하고 
    
    - ORDER BY로 마지막으로 그 결과를 어떤 기준으로 정렬해서 보여줄지 정한다.

  - 실행 순서 : `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> `SELECT` -> `ORDER BY`

    - FROM으로 먼저 '어느 테이블을 다룰건제'부터 보고 
    
    - WHERE로 그 테이블의 모든 행 중에서, 조건에 안 맞는 행들을 먼저 걸러내고 버린다.(아직 그룹으로 안 묶은 상태, 낱개 행 단위로 거르기) 그리고 
    
    - GROUP BY로 살아남은 행들을 기준열로 묶는다.(성별별로 묶거나 하는 등)
    
    - 그리고 HAVING으로 묶인 그룹중에서, 집계 조건에 안 맞는 그룹을 걸러낸다.(그룹 단위로 거르기) 
    
    - 그후에 SELECT로 진짜로 '화면에 보여줄 열'을 뽑아서 결과표로 만든다. 

      - (SELECT안에 AVG(나이), COUNT(*) 같은 집계함수가 들어있으면, GROUP BY로 그룹이 다 묶인 다음에야 계산이 가능하기 때문에 GROUP BY로 그룹이 다 묶인 다음에야 계산이 가능하므로 SELECT는 거의 마지막에 처리된다.)
    
    - 마지막으로 ORDER BY로 완성된 결과표를 정렬해서 최종적으로 보여준다.

- 즉, 우리는 SELECT를 맨 먼저 쓰지만, 컴퓨터는 FROM(어느 표에서 가져올지)부터 제일 먼저 처리한다.

  - 이 순서를 알아야 SQL 에러의 원인을 빨리 찾을 수 있다.

  - 예를 들어, SELECT에서 만든 별명(별칭)을 WHERE 절에서는 못 쓴다. 왜냐면 WHERE가 SELECT보다 먼저 실행되기 때문에, 아직 그 별명이 만들어지기도 전에 찾으려고 하는거라서 에러가 난다.

### | 데이터베이스 구조

- 데이터베이스는 그냥 '데이터를 담아주는 상자'가 아니다.

- '이상한 데이터가 못 들어오게 막고, 데이터끼리의 관계가 안 깨지게 지키는 규칙들'이 잔뜩 들어있는 시스템이다.

#### - 데이터 타입 : '이 칸엔 이런 것만 넣을 수 있다'

- 테이블의 각 칸(열)에 '여기엔 이런 종류의 데이터만 들어올 수 있다'고 미리 정해두는 것

  - `INT` : 정수(숫자) -> 예) 나이 : 25, 수량 : 100

  - `VARCHAR(n)` : 길이가 최대 n자인 문자열 -> 예) 이름 : "홍길동"

  - `DATE` : 날짜 -> 예) 가입일 : 2024-01-01

  - `DECIMAL(p, s)` : 소수점 있는 숫자 -> 예) 가격 : 29900.50

    - DECIMAL(전체자릿수(정수부 + 소수부를 합쳐서 총 몇자리까지 저장할지), 소수점이하자릿수(그 중에서 소수점 뒤로 몇자리까지 저장할지
    
      -> DECIMAL(10, 2)는 전체 10자리 중 2자리가 소수부니까 정수부는 최대 8자리, 소수부는 최대 2자리

  - `BOOLEAN` : 참/거짓 딱 둘 중 하나 -> 예) 활성여부 : true/false

  - `TEXT` : 길이 제한 없는 긴 글 -> 예) 게시글 본문

- VARCHAR vs TEXT, 뭘 언제 써야하나

  - `VARCHAR(n)` : 이름, 이메일처럼 길이가 대충 짐작이 될 때

  - `TEXT` : 게시글, 댓글처럼 길이가 들쭉날쭉할 때

  - 길이를 예측할 수 있으면 VARCHAR가 더 효율적이다.

#### - 스키마(Schema) : 데이터베이스의 설계도

- '이 데이터베이스 안에 어떤 표들이 있고, 각 표에 어떤 칸이 있고, 그 칸에 뭘 넣을 수 있는지'를 미리 그려둔 설계도

- 스키마만 봐도 '아 이 표엔 아이디·이름·이메일·가입일이 들어가는구나'를 한눈에 알 수 있다.

#### - PK와 FK : 표들을 서로 연결하는 열쇠

- PK(기본키) : 표 안의 한 줄을 다른 줄과 절대 안 겹치게 딱 하나로 구별해주는 값. 주민등록번호와 같다. 중복 안되고, 비어있어도 안된다.

- FK(외래키) : 다른 표의 PK를 가리키는 값

  - 예 : 회원 표의 `user_id`(PK)를, 주문 표의 `user_id`(FK)가 가리켜서, '이 주문이 누구 것인지' 알 수 있다.

##### | PK, FK는 실제로 SQL 코드로 지정한다

- `PRIMARY KEY`, `REFERENCES` 라는 키워드를 컬럼 옆에 붙이기만 하면 된다. (Supabase의 SQL Editor에 이 코드를 타이핑하고 실행하면 됨)

```sql
CREATE TABLE users (
  id INT PRIMARY KEY,          -- 이 한 단어가 PK 지정
  name VARCHAR(50)
);

CREATE TABLE orders (
  id INT PRIMARY KEY,
  user_id INT REFERENCES users(id),   -- 이 부분이 FK 지정
  amount DECIMAL(10,2)
);
```

- `PRIMARY KEY` : "이 컬럼의 값으로 각 행을 구별한다"는 뜻 -> 그 컬럼을 PK로 만들어주는 키워드

- `REFERENCES` : 원래 '참조하다, 가리키다'라는 뜻의 영어단어. `REFERENCES 표(컬럼)`이라고 쓰면 "이 값은 반드시 저 표에 진짜 있는 값이어야 한다"는 규칙이 걸린다 -> 그 컬럼을 FK로 만들어주는 키워드

  - "REFERENCES가 곧 FK"라기보다, **REFERENCES 키워드를 써서 그 컬럼을 FK로 만드는 것**이라고 이해하면 정확하다.

- Supabase에서는 SQL을 직접 안 치고, **Table Editor** 화면에서 컬럼 만들 때 'Primary Key' 체크박스 체크 / 'Foreign Key' 버튼으로 참조할 표·컬럼을 드롭다운으로 골라서 마우스 클릭만으로 지정할 수도 있다. (내부적으로는 결국 위와 같은 SQL이 자동으로 실행되는 것)

##### | 참조 무결성 : '존재하지 않는 사람을 가리키면 안돼'

- FK가 가리키는 값은 반드시 그 대상 표에 실제로 존재해야 한다. 존재하지 않는 회원을 주문 표에서 가리키려 하면 저장이 거부된다.

- 참조당하는 회원은 기본적으로 삭제가 불가하다. (고아 데이터 방지)

  - 예외 : `ON DELETE CASCADE`(같이 삭제), `ON DELETE SET NULL`(FK를 비움)

##### | 정규화(Normalization) : 표를 깔끔하게 나누는 작업

- 중복 데이터를 줄이고 데이터가 안 어긋나게 표를 체계적으로 쪼개는 작업

  - 1NF : 한 칸엔 값 하나만 (여러 값 몰아넣지 않기)

  - 2NF : 복합키 중 '일부'에만 의존하는 열을 따로 분리

  - 3NF : PK가 아닌 컬럼끼리도 서로 의존하면 안됨 (예 : 등급이름은 등급표로 따로 분리)

- 항상 좋은건 아니다 : 너무 잘게 쪼개면 조회할 때 여러 표를 JOIN해야 해서 느려질 수 있다. 상황에 맞게 적당히 나누는게 핵심이다. (반정규화도 허용됨)

##### | 정규화는 어디서, 어떻게 하는가 — Supabase를 켜기 전, 종이 위에서 먼저

- 정규화는 SQL로 실행하는 명령어가 따로 있는게 아니다. **"표를 몇 개로, 어떻게 나눌지" 사람이 먼저 판단하는 설계 단계**이고, 그 판단이 끝난 뒤에야 Supabase에서 CREATE TABLE로 구현한다.

| 단계 | 어디서 하나 | 뭘 하나 |
| --- | --- | --- |
| 1. 정규화 | 종이, 노션, 엑셀, ERD 툴(dbdiagram.io 등) | 표를 몇 개로 나눌지, 컬럼을 어디에 넣을지 사람이 직접 판단 |
| 2. 구현 | Supabase (SQL Editor / Table Editor) | 1단계 설계를 실제 CREATE TABLE 코드(또는 클릭)로 옮겨서 테이블 생성 |

- 예 : 정규화 전 (한 표에 다 몰아넣음)

| 회원id | 이름 | 등급 | 등급혜택 |
| --- | --- | --- | --- |
| 1 | 홍길동 | VIP | 무료배송+10%할인 |
| 2 | 김철수 | VIP | 무료배송+10%할인 |

  - 문제 : VIP 회원이 100명이면 '무료배송+10%할인'이라는 문구가 100번 중복 저장됨. 혜택 내용이 바뀌면 100줄을 다 고쳐야 함.

- 정규화 (사람이 먼저 종이에 판단) -> "등급 정보는 따로 빼자"

```sql
-- 정규화 결과를 Supabase SQL Editor에서 코드로 구현
CREATE TABLE grades (
  id INT PRIMARY KEY,
  grade_name VARCHAR(20),
  benefit TEXT
);

CREATE TABLE users (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  grade_id INT REFERENCES grades(id)   -- 정규화 결과가 FK로 연결됨
);
```

-> 정리하면 : **정규화 = Supabase를 켜기 전 머릿속/종이에서 표를 어떻게 나눌지 미리 결정하는 것**

### | 테이블 간의 관계와 ERD 읽기

- 실제 회사에서 쓰는 데이터베이스는 표(테이블)가 수십~수백개가 된다. 이 표들은 따로따로 노는게 아니라, 서로 연결되어서 하나의 큰 시스템을 이룬다. 이 연결관계를 모르면 데이터를 제대로 찾아내기 어렵다.

#### - 표(테이블)끼리의 관계 3종류

- 두 표가 서로 '몇 개씩' 연결될 수 있는지를 기준으로 관계를 세 종류로 나눈다.

  - 1:1 관계(일대일) : 한쪽 표의 데이터 하나가, 다른 쪽 표의 데이터 딱 하나랑만 연결되는 관계

  - 1:N 관계(일대다) : 한쪽 표의 데이터 하나가, 다른 쪽 표의 여러 데이터와 연결되는 관계

  - N:M 관계(다대다) : 양쪽 표의 데이터가 서로 여러개씩 연결될 수 있는 관계

    - 중요한 규칙 : 다대다 관계는 데이터베이스에서 직접 표현이 안되기 때문에, 중간표를 하나 더 만들어서 1:N 관계 두개로 쪼개서 처리해야 한다.

    - 예 : 학생과 강의를 직접 연결하기 애매하니까, '수강신청명단'이라는 중간 장부를 하나 따로 만들어서 '누가 어떤 강의를 듣는지' 한 줄씩 적어두는 것과 같다. (인스타의 게시물과 태그 관계도 같은 예)

##### | 1:1 예시 — 회원 ↔ 여권

- 한 사람은 여권을 딱 1개만 가지고, 여권 하나는 딱 1명의 소유자만 있다.

users(회원) :

| id | name |
| --- | --- |
| 1 | 홍길동 |
| 2 | 김철수 |

passports(여권) :

| id | user_id | passport_number |
| --- | --- | --- |
| 1 | 1 | M12345678 |
| 2 | 2 | M87654321 |

- `passports.user_id`가 users의 id를 FK로 참조하는데, 한 user_id 값이 딱 한번씩만 등장한다. 이렇게 FK에 UNIQUE까지 걸어서 중복을 막는게 1:1의 특징이다.

```sql
CREATE TABLE passports (
  id INT PRIMARY KEY,
  user_id INT UNIQUE REFERENCES users(id),  -- UNIQUE가 핵심! 중복 불가
  passport_number VARCHAR(20)
);
```

- 실무에서 쓰는 이유 : 자주 안 쓰는 정보(상세 프로필, 민감정보 등)를 본 테이블과 분리해서 관리하고 싶을 때 사용한다.

##### | 1:N 예시 — 고객 ↔ 주문

- 한 고객은 주문을 여러 번 할 수 있지만, 주문 하나는 딱 한 명의 고객 것이다.

customers(고객) :

| id | name |
| --- | --- |
| 1 | 홍길동 |
| 2 | 김철수 |

orders(주문) :

| id | customer_id | amount |
| --- | --- | --- |
| 1 | 1 | 5000 |
| 2 | 1 | 12000 |
| 3 | 2 | 3000 |

- 홍길동(customer_id=1)이 주문을 2번(1번, 2번 주문) 했다 -> "1(고객) : N(주문)"
- FK는 항상 '여러 개 있는 쪽(N, 여기선 orders)'에 붙는다. 여러 주문 각각이 자기가 누구 것인지 하나씩 가리키는 구조라서 그렇다.

```sql
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT REFERENCES customers(id),  -- UNIQUE 없음! 중복 허용
  amount DECIMAL(10,2)
);
```

- 1:1과 비교하면 딱 하나 다른 점 : UNIQUE가 없다. 그래서 같은 customer_id가 여러 번 나와도 괜찮다.

##### | N:M 예시 — 학생 ↔ 강의

- 한 학생은 여러 강의를 듣고, 강의 하나에도 여러 학생이 듣는다. 양쪽 다 여러개씩 연결됨.

students(학생) :

| id | name |
| --- | --- |
| 1 | 홍길동 |
| 2 | 김철수 |

courses(강의) :

| id | course_name |
| --- | --- |
| 1 | SQL 기초 |
| 2 | 파이썬 기초 |

- 문제 : students 표에 course_id를 넣으면, 홍길동이 강의를 2개 들을 때 칸 하나에 값을 2개 넣어야 되서 안된다(1NF 위반). courses 표에 student_id를 넣어도 똑같은 문제가 생긴다.

- 그래서 중간표(연결테이블)를 하나 더 만들어서, 1:N 관계 2개로 쪼개서 해결한다.

enrollments(수강신청 - 중간표) :

| id | student_id | course_id |
| --- | --- | --- |
| 1 | 1 | 1 |
| 2 | 1 | 2 |
| 3 | 2 | 1 |

- 홍길동(id=1)이 SQL기초(1)와 파이썬기초(2)를 둘다 들어서 행이 2줄 생김
- SQL기초(course_id=1)를 홍길동과 김철수 둘다 들어서 행이 2줄 생김
- 즉 "students → enrollments"는 1:N, "courses → enrollments"도 1:N이다. 두 개의 1:N을 겹쳐서 N:M을 흉내내는 것

```sql
CREATE TABLE enrollments (
  id INT PRIMARY KEY,
  student_id INT REFERENCES students(id),
  course_id INT REFERENCES courses(id)
);
```

##### | 세 관계 한눈에 비교

| 관계 | FK 위치 | UNIQUE 필요? | 예시 |
| --- | --- | --- | --- |
| 1:1 | 한쪽 표에 FK + UNIQUE | 필요 | 회원 ↔ 여권 |
| 1:N | '여러 개'인 쪽(N) 표에 FK만 | 불필요 | 고객 ↔ 주문 |
| N:M | 중간표를 새로 만들어서 FK 2개 | 불필요 | 학생 ↔ 강의 (수강신청) |

#### - ERD(Entity Relationship Diagram) 읽는 법

- ERD란 : 표들 사이의 관계를 그림으로 그려서 한눈에 볼 수 있게 만든 설계도. 새로운 프로젝트에 들어가서 '이 데이터베이스가 어떻게 생겼는지' 파악할 때 꼭 필요한 도구

- ERD를 이루는 3가지 요소

  - Entity(엔티티) : 표 하나 -> 사각형으로 표현

  - Attribute(속성) : 표의 열(컬럼) -> 열 이름과 타입으로 표현

  - Relationship(관계) : 표끼리의 연결 -> 선과 기호로 표현

- 기호 읽는 법 = "까마귀발 표기법"

  - 선의 양쪽 끝에 붙는 기호로 '몇 개씩 연결되는지'를 표현한다.

  - `|` 수직선 하나 : 최소 1개, 필수

  - `O` 동그라미 : 0개(있어도 되고 없어도 됨, 선택적)

  - `<` 까마귀발 모양 : 여러 개(N)

  - `||` 수직선 두개 : 정확히 1개, 필수

  - `O<` 동그라미+까마귀발 : 0개 이상

  - `|<` 수직선+까마귀발 : 1개 이상

  - 예 : 회원 테이블 `||—O<` 주문 테이블

    - 왼쪽에서 오른쪽으로 읽으면 : 회원 한 명은 주문을 0개 이상(안해도 되고, 여러번 해도 됨) 가질 수 있음

    - 오른쪽에서 왼쪽으로 읽으면 : 주문 하나는 반드시 딱 한 명의 회원과 연결됨(`||`가 정확히 1개, 필수이니까)

    - 즉, 회원 : 주문 = 1:N 관계

- ERD가 복잡해 보일 때 읽는 순서

  - 가장 많은 표와 연결된 '중심 표'부터 찾기

  - 그 중심 표에서 시작해서, 연결된 표들을 하나씩 따라가며 관계 파악하기

  - 각 선의 양 끝 기호를 보면서 'A는 B를 몇 개 가질 수 있지?'를 스스로 질문하며 읽는다.

### | 테이블 생성, 데이터 입력 문법

#### - DDL(Data Definition Language) : 데이터 정의어

- CREATE : 테이블 생성 담당

```sql
CREATE + 생성대상([TABLE, INDEX, TYPE, ...]);
```

- ALTER : 수정 담당

  - 컬럼 추가 (ADD COLUMN)
```sql
ALTER TABLE 테이블명 ADD COLUMN 컬럼명(필수) 자료형(필수) [제약조건];
```

  - 컬럼 이름 변경 (RENAME COLUMN)
```sql
ALTER TABLE 테이블명 RENAME COLUMN 기존컬럼명 TO 변경할컬럼명;
```

  - 컬럼 삭제 (DROP COLUMN)
```sql
ALTER TABLE 테이블명 DROP COLUMN 컬럼명;
```

  - 데이터 타입 변경 (ALTER COLUMN)
```sql
-- 데이터가 없는 경우 (구조만 변경)
ALTER TABLE 테이블명 ALTER COLUMN 컬럼명 TYPE 자료형;

-- 데이터가 있고 형변환이 필요한 경우
ALTER TABLE 테이블명 ALTER COLUMN 컬럼명 TYPE 자료형 USING(컬럼명::자료형);
```

  ㄴ> 데이터가 이미 들어있는 상태에서 타입만 바꾸면 오류가 날 수 있어서, `USING`으로 어떻게 변환할지 알려줘야 한다. (DB마다 세부 동작은 조금씩 다를 수 있다.)

  - 제약조건 추가/삭제 (SET /  DROP / ADD CONSTRAINT)

```sql
ALTER TABLE 테이블명 ALTER COLUMN 컬럼명 SET [제약조건 or DEFAULT];
ALTER TABLE 테이블명 ALTER COLUMN 컬럼명 DROP [제약조건명 or DEFAULT];
```
##### | SET은 "설정해라, 붙여라"라는 뜻 — 이미 있는 컬럼에 규칙을 나중에 붙일 때

- `SET DEFAULT` : 컬럼에 기본값을 붙이기

```sql
ALTER TABLE users
ALTER COLUMN status SET DEFAULT 'active';
-- "status 컬럼에, 값을 안 넣으면 자동으로 'active'가 들어가게 기본값을 설정해라"

ALTER TABLE users 
ALTER COLUMN status DROP DEFAULT;  -- 반대로 기본값 없애기
```

- `SET NOT NULL` : 컬럼에 필수값 규칙을 붙이기

```sql
ALTER TABLE users
ALTER COLUMN name SET NOT NULL;
-- "name 컬럼에, 이제부터 값이 비어있으면 안된다는 규칙을 붙여라"

ALTER TABLE users ALTER COLUMN name DROP NOT NULL;  -- 반대로 그 규칙 없애기
```

-> `SET`은 "규칙을 붙이는 것", `DROP`은 "그 규칙을 떼어내는 것"으로 항상 짝을 이룬다.

- ⚠️ 헷갈리기 쉬운 포인트 : UPDATE문의 SET이랑 다른 것이다.

  - `ALTER COLUMN ... SET` (DDL) : 컬럼 자체의 **규칙(설계도)**을 바꾸는 것

  - `UPDATE ... SET` (DML) : 이미 있는 특정 행의 **실제 값**을 바꾸는 것

  - 예 : `UPDATE users SET status = 'active' WHERE id = 1;` -> 이건 규칙이 아니라 데이터 값을 직접 바꾸는 것



```sql
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건이름 PRIMARY KEY(컬럼명, ...);
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건이름 UNIQUE(컬럼명, ...);
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건이름 CHECK(조건식);
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건이름 FOREIGN KEY(현재테이블컬럼명)
  REFERENCES 참조테이블명(컬럼명) [ON DELETE CASCADE | SET NULL];

ALTER TABLE 테이블명 DROP CONSTRAINT 제약조건이름;
```


##### | ADD CONSTRAINT — 테이블을 만든 뒤에 제약조건을 나중에 걸 때

- `ADD CONSTRAINT 제약조건이름`은 "이 이름표를 붙인 규칙 하나를 이 표에 새로 추가하겠다"는 뜻이다. 제약조건이름은 나중에 그 규칙을 찾거나 지울 때 식별용으로 쓰는 이름이라, 보통 `pk_테이블명`, `fk_테이블명_참조테이블명`처럼 알아보기 쉽게 짓는다.

```sql
-- 기본키를 나중에 추가하기
ALTER TABLE books ADD CONSTRAINT pk_books PRIMARY KEY(id);

-- 중복 불가 규칙을 나중에 추가하기
ALTER TABLE members ADD CONSTRAINT uq_members_email UNIQUE(email);

-- 조건식 규칙을 나중에 추가하기
ALTER TABLE books ADD CONSTRAINT chk_books_price CHECK(price > 0);

-- 외래키를 나중에 추가하기
ALTER TABLE orders ADD CONSTRAINT fk_orders_member
  FOREIGN KEY(member_id) REFERENCES members(id) ON DELETE CASCADE;

-- 이름으로 찾아서 규칙 삭제하기
ALTER TABLE orders DROP CONSTRAINT fk_orders_member;
```

- `PRIMARY KEY`, `UNIQUE`, `CHECK`, `FOREIGN KEY`는 앞서 CREATE TABLE 안에서 컬럼 옆에 바로 적었던 것과 똑같은 규칙들인데, 여기서는 **표를 이미 다 만든 뒤에 나중에 추가로 걸어주는 것**이라는 차이만 있다.

  - 언제 이렇게 나중에 추가할까 : 표를 처음 설계할 땐 몰랐던 규칙이 나중에 필요해졌을 때, 또는 이미 운영중인 표에 새 규칙을 추가해야 할 때

- DROP : 삭제 담당
```sql
DROP + 삭제대상([TABLE, INDEX, TYPE, ...]);
```
  - DDL은 데이터 삭제시 복구가 불가능하다. (ROLLBACK 불가)

- TRUNCATE TABLE : 테이블 데이터를 비운다(초기화)
```sql
TRUNCATE TABLE 테이블명;
```
  - 테이블 구조는 유지한 채 데이터만 초기화한다.

#### - 제약 조건

  - `PRIMARY KEY` : 기본키

  - `NOT NULL` : 값이 비어있으면 안된다.

  - `UNIQUE` : 같은 값이 두 번 들어오면 안된다.

  - `CHECK` : 조건식을 만족해야만 저장 가능

  - `DEFAULT` : 값을 안넣으면 기본값이 자동으로 채워짐

#### - 외래키(FK)

- 자식쪽 테이블에 존재하고, 부모쪽 테이블에는 외래키가 없다.

- 참조 무결성 제약조건이 적용된다.

  1. 부모쪽 테이블에 없는 참조값을 자식 테이블이 사용할 수 없다.

  2. 부모쪽 레코드에 자식 레코드가 있으면 부모 레코드를 삭제할 수 없다. (자식이 먼저 지워지면 가능)

  3. `ON DELETE` 옵션

     - `CASCADE` : 부모레코드가 삭제되면 자식레코드도 함께 삭제된다.

     - `SET NULL` : 부모레코드가 삭제되면 자식레코드의 참조컬럼 값을 NULL로 바꾼다.

### | DML(Data Manipulation Language) : 데이터 조작어

- INSERT : 추가
```sql
INSERT INTO 테이블명[(컬럼명, ...)] VALUES(값1, 값2, ...), (값1, 값2, ...);
```
  - 대괄호 안 컬럼 목록은 모든 컬럼에 순서대로 값을 넣는 경우 생략 가능하다.

- UPDATE : 수정
```sql
UPDATE 테이블명 SET 컬럼명 = 변경할값, 컬럼명 = 변경할값, ...
[WHERE 조건식(비교, 논리 연산)];
```

- DELETE : 삭제
```sql
DELETE FROM 테이블명
[WHERE 조건식(비교, 논리 연산)];
```

- SELECT : 테이블에서 어떤 컬럼(정보)을 보여줄지 고르는 명령어 (FROM은 어느 테이블에서, SELECT는 그중 무엇을 화면에 보여줄지)
```sql
SELECT DISTINCT 컬럼명 ...;  -- 중복 제거
SELECT ALL 컬럼명 ...;       -- 기본값. 중복 있어도 다 보여줌
SELECT 컬럼명, AMOUNT * 1.1 AS 세금포함금액 FROM orders;  -- 계산식에 별칭(AS) 붙이기
```

### | 데이터 무결성 제약조건 총정리

1. 도메인 무결성 제약조건 : 자료형(데이터 타입)을 지켜야 하는 규칙

2. 개체 무결성 제약조건 : 기본키(PK) 규칙 -> 중복 불가, NULL 불가

3. 참조 무결성 제약조건 : 외래키(FK) 규칙 -> 부모 테이블에 실제로 존재하는 값만 참조 가능

Q1. 다음 중 DDL(Data Definition Language)에 해당하는 명령어는 무엇인가요?

[ 보기 ]

a. CREATE TABLE

b. INSERT INTO

c. SELECT

d. UPDATE

A. CREATE TABLE

-> CREATE TABLE은 테이블 구조를 정의하는 DDL 명령입니다. INSERT, SELECT, UPDATE는 데이터를 조작하는 DML 명령이므로 정답이아니다.

---

Q2. 테이블 내에서 각 행(Row)을 유일하게 식별하며, 중복 값과 NULL 값을 가질 수 없는 열을 무엇이라고 하나요?

A. 기본키(PK)

-> 기본키(PK)는 테이블에서 각 행을 유일하게 식별하는 열로, 중복 불가와 NULL 불가라는 두 가지 핵심 규칙을 가진다.

---

Q3. INSERT INTO 문 실행 시, INT 타입 열에 문자열 '홍길동'을 입력하려고 하면 어떤 일이 발생하나요?

[ 보기 ]

a. 데이터베이스가 오류를 발생시키고 해당 INSERT를 거부한다

b. 문자열이 자동으로 숫자로 변환되어 저장된다

c. 해당 열만 NULL로 저장되고 나머지는 정상 입력된다

d. 경고 메시지만 출력되고 데이터는 정상 저장된다

A. a.데이터베이스가 오류를 발생시키고 해당 INSERT를 거부한다

-> 데이터 타입이 맞지 않으면 데이터베이스는 오류를 발생시키고 해당 INSERT를 거부하여 잘못된 데이터 저장을 방지한다.

---

Q4. FK가 참조하는 값이 반드시 참조 대상 테이블의 PK에 존재해야 한다는 규칙을 무엇이라고 하나요?

A. 참조 무결성

-> 참조 무결성(Referential Integrity)은 외래키(FK)가 참조하는 값이 반드시 참조 대상 테이블의 기본키(PK)에 실제로 존재해야 한다는 규칙으로, 이를 통해 데이터 간 관계의 유효성이 유지된다.

---

Q5. 수강 신청 테이블에서 student_name이 student_id에만 의존하고 course_name이 course_id에만 의존하는 경우, 이를 개선하기 위해 적용하는 정규화 단계는 무엇인가요?

[ 보기 ]
a. 1NF

b. 2NF

c. 3NF

d. 반정규화

A. 2NF

->2NF는 복합키를 사용하는 테이블에서 복합키 전체가 아니라 일부 키에만 의존하는 열을 분리하는 단계이다.. 1NF는 한 칸에 하나의 값만 저장하는 단계이고, 3NF는 PK가 아닌 컬럼 간의 의존 관계를 제거하는 단계이므로 이 사례와는 맞지 않다.
